#+title: RFC 10.15.02.09 - Hook Bootstrap Repair and Server Warm Path
#+property: RFC_ID ASP-RFC-10.15-HOOK-BOOTSTRAP-REPAIR
#+property: LEAN_MODULE ASPProof.HookBootstrapRepair

* Status

Normative extension of the agent hook interception protocol.

* Failure found by formal and runtime audit

The previous recovery order was circular:

1. the plugin invoked =asp hook ...=;
2. the installed binary parsed the complete matcher configuration;
3. only after parsing failed did recovery attempt to materialize the managed
   configuration;
4. an older binary could not parse a newly published enum value, while
   ownership protection correctly refused to overwrite a different file that
   had no matching sidecar.

Consequently the recovery implementation was downstream of the parser whose
failure it was meant to repair. A Stop event could repeat the same failure and
prevent the agent session from reaching another lifecycle transition.

This is a design defect, not an enum-compatibility problem. Mapping a new
reason kind to an old kind would erase policy meaning and leave the publication
race intact.

* Normative architecture

** Configuration-independent bootstrap

Every installed Codex hook command MUST enter through the stable public surface
=asp hook <event> ...=. The =asp= entrypoint delegates to its internal
bootstrap before parsing the hook matcher document. The bootstrap MUST NOT
parse that document before it has established artifact coherence. Its initial
authority is limited to:

- the canonical ASP state home;
- the immutable =asp.toml= development or release artifact mode;
- the digest-addressed bootstrap and protocol entries;
- a bounded input envelope and a stable hook event name.

The bootstrap and =asp= MUST be published as one Runtime Artifact Mutation
Transaction. Protocol carries that transaction guard through coupled receipt
and configuration publication; it does not create a second writer lock. A
development repair may delegate only to
the canonical installer below the configured =[dev].root=. It MUST NOT call
=asp sync=, fetch a repository, or reinterpret an unowned configuration file.

The configured development root is build provenance, never executable
residency. Development and release publication both copy the verified =asp=
bytes into the same content-addressed State Home store. No stable Runtime
slot may resolve into =target/=, a checkout, =~/.local/bin=, or ambient =PATH=.
Deleting a build tree therefore cannot remove the installed Hook evaluator.

Each binary identity owns exactly two retained atomic slots:

- =runtime/profiles/<binary>/active= selects the current generation;
- =runtime/profiles/<binary>/healthy= selects the last health-qualified
  generation.

=runtime/bin/<binary>= is only the stable public alias of =active=. The plugin
launcher resolves =active= and then =healthy=; both point into
=runtime/artifacts/blake3-256/<digest>/<binary>=. Garbage collection retains
only generations reachable from these slots. A missing public alias or active
generation therefore does not deadlock repair while an independently retained
healthy generation exists, and the store consumes at most two binary
generations per identity.

The first verified publication seeds both slots with the same immutable
baseline, so initial installation has no second copy and no missing recovery
edge. Later publication advances only =active=. Only a successful Runtime
health transition whose observed binary content digest equals the current
active digest may then atomically promote =active= to =healthy=. A stale health
receipt from a previous Runtime generation cannot qualify newer bytes.

Publication, health promotion, reachability garbage collection, and coupled
Protocol receipts share one non-blocking cross-process Runtime Artifact
Mutation Transaction owned by the Runtime artifact store. A competing writer fails immediately with
=reasonKind=artifact-publication-conflict=; it does not wait on a timeout and
cannot interleave pointer movement with another writer's garbage collection.

** Warm path and ASP Server

The host necessarily starts one command process for a command hook. The warm
path MUST NOT start a second =asp= process. The bootstrap executes the hook
runtime in-process, while workspace-generation admission and graph-backed
state remain resident in ASP Server. Thus multiple workspaces and sessions
share the server generation without duplicating graph/index construction.

The next resident optimization boundary is a server-owned compiled matcher
generation keyed by matcher contract fingerprint, provider projection
generation, and artifact catalog generation. A cache hit may remove parsing
work, but it MUST NOT weaken configuration identity checks. Cache identity is
not model prefix caching and is not a search-result cache.

** Cold repair, replay, and failure policy

A recognized freshness failure transitions through one stable global repair
key. Concurrent hooks MUST coalesce behind the same writer. After publication,
the original event is replayed at most once with the original bytes.

If repair cannot complete within its deadline:

- =pre-tool= and =permission-request= remain fail-closed because they are
  enforcement events;
- lifecycle and observational events, including =Stop=, degrade open with an
  explicit receipt so version drift cannot deadlock the whole session.

An observational degrade-open result does not authorize a previously denied
source read. It only permits the lifecycle event itself to finish.

* Stateful architecture

    BootstrapReady --> WarmClassify: coherent artifact pair
    WarmClassify --> ServerGeneration: workspace admission
    ServerGeneration --> DecisionPublished: healthy or nonblocking receipt
    BootstrapReady --> DriftObserved: typed freshness failure
    DriftObserved --> RepairReserved: CAS stable repair key
    RepairReserved --> RepairReserved: concurrent request coalesced
    RepairReserved --> PairPublished: binary + bootstrap + config/plugin generation
    PairPublished --> ReplayOnce: original bytes, replayCount = 1
    ReplayOnce --> DecisionPublished: current parser succeeds
    RepairReserved --> EnforcementBlocked: deadline + enforcement event
    RepairReserved --> LifecycleDegradedOpen: deadline + observational event
    EnforcementBlocked --> [*]
    LifecycleDegradedOpen --> [*]
    DecisionPublished --> [*]

The stable repair key is global to one ASP state home and desired artifact
generation. Workspace and session identities are request metadata, not repair
writer identities; otherwise high-frequency multi-workspace hooks could start
duplicate builds for the same artifact.

* Mathematical model

Let =P=(b,c)= be the published binary and configuration generations,
=r= be replay count, and =e= be the event plane. Coherent publication and
bounded replay require =b=c= and =r <= 1=. Failure classification is local to
the event plane.

#+name: hook-bootstrap-repair-model
#+begin_src typst
#let coherent(binary-generation, config-generation) = (
  binary-generation == config-generation
)
#let replay-bounded(replay-count) = replay-count <= 1
#let failure-decision(event-plane) = if event-plane == "enforcement" {
  "deny"
} else {
  "allow"
}
#let warm-cost = (
  host-process-starts: 1,
  asp-child-process-starts: 0,
  server-generation-admissions: 1,
)

#assert(coherent(17, 17))
#assert(not coherent(16, 17))
#assert(replay-bounded(0))
#assert(replay-bounded(1))
#assert(not replay-bounded(2))
#assert(failure-decision("enforcement") == "deny")
#assert(failure-decision("observational") == "allow")
#assert(warm-cost.host-process-starts == 1)
#assert(warm-cost.asp-child-process-starts == 0)
"ok"
#+end_src

For =n= warm events sharing one resident server generation, the process-start
component is =n= rather than =2n=, and graph/index construction remains one
server generation rather than one construction per hook. This inequality is a
performance refinement only; the safety proof remains generation equality,
single-writer publication, and bounded replay.

* Acceptance evidence

- a stale matcher enum is detected before compatibility rewriting;
- the configured development installer publishes an active/healthy slot pair
  without a checkout-resident executable;
- the original hook payload is replayed no more than once;
- concurrent repair requests converge on one writer;
- Stop remains completable after bounded repair failure;
- pre-tool access remains fail-closed after bounded repair failure;
- warm execution starts no second =asp= process;

The complete server-resident evaluator and compiled-generation cache are
specified separately by RFC 10.15.02.10. This module continues to own bootstrap
repair and failure-plane behavior.
- Typst evaluation, Lean build, AXLE audit, plugin schema validation, and a
  live installed-hook replay all pass before hooks are re-enabled.
* Stable public hook interface

The client-visible command is permanently =asp hook <event> --client <client>=.
The bootstrap is an internal module of the sole =asp= executable and MUST NOT
be published as a second binary. The =asp= binary recognizes the =hook=
namespace before the complete matcher is loaded and delegates internally to
that module. Cold repair re-enters the same digest-matched =asp= artifact.

A second executable does not add isolation or correctness: it only creates a
publication pair whose drift can deadlock recovery. The stable =asp hook=
surface keeps client registration invariant while the internal bootstrap and
resident evaluator evolve inside one atomic artifact.
