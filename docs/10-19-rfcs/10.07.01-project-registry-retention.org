#+title: Project Registry Identity and Retention
#+author: ASP
#+status: Draft

* Problem

The State Core project registry must describe durable repositories and their
active checkouts.  It must not grow in proportion to test runs, temporary
directories, or linked worktrees.

The observed global registry contained 2,303 project metadata records:

- 2,233 pointed into temporary-directory roots;
- 2,198 checkout roots no longer existed;
- only 105 checkout roots still existed.

That cardinality is invalid for a machine with only a small set of active
repositories.  It combines two independent defects: incomplete Git identity
normalization and historical temporary-state retention.

* Identity contract

** Repository identity

A durable repository identity represents one logical clone or one canonical
network repository.  Main checkouts and linked worktrees of the same Git
repository MUST resolve to the same repository identity.

Identity evidence is selected in this order:

1. a canonical network remote identity;
2. the canonical common Git directory;
3. the canonical checkout-local Git directory;
4. the canonical checkout path for a non-Git workspace.

Remote transport syntax is not identity.  Equivalent SSH, SCP-like, and HTTPS
forms MUST normalize to the same host/repository value.  Local filesystem
remotes MUST NOT become global durable identities.

** Workspace identity

A workspace identity represents one concrete checkout.  Linked worktrees of
one repository MUST have distinct workspace identities while sharing one
repository identity.

The workspace key is derived from repository identity, canonical checkout root,
and the worktree-private Git directory.

** Git parser ownership

=gix= owns repository discovery and Git topology:

- repository and worktree discovery from an arbitrary descendant path;
- worktree root;
- worktree-private Git directory;
- common Git directory shared by linked worktrees;
- bare-repository handling.

=gix-config= owns Git configuration parsing and canonical remote selection.
ASP MUST NOT make the primary identity path depend on hand-parsing =.git=,
=gitdir:=, =commondir=, or config section syntax.  A filesystem or =git=
subprocess path may remain only as a fail-soft compatibility fallback.

The canonical remote policy remains explicit:

1. =agent-semantic.canonicalRemote=;
2. =remote.pushDefault=;
3. =origin=;
4. the only configured remote when exactly one exists.

* State placement

When =ASP_STATE_HOME= is explicitly set, it remains authoritative.

Without an explicit state home, a temporary checkout or a checkout without a
durable network identity MUST use checkout-local derived state:

#+begin_example
<checkout>/.cache/agent-semantic-protocols/state
#+end_example

Tests MUST set an isolated state home or use checkout-local state.  Test
fixtures MUST NOT create entries below the user's global
=projects/by-id= registry.

* Activity evidence

Each project and workspace records a throttled last-seen timestamp.  Updating
activity MUST NOT rewrite metadata on every command; an implementation-defined
minimum interval limits write amplification.

For legacy entries without activity metadata, directory modification time may
be used only as conservative fallback evidence.

* Retention and garbage collection

Garbage collection is two phase:

1. =asp cache projects gc= reports candidates and is dry-run by default;
2. =asp cache projects gc --apply= removes exactly the reported eligible
   derived-state roots after revalidation.

Every candidate reports:

- repository and workspace ID;
- recorded checkout root;
- identity basis;
- last-seen evidence;
- size;
- reason;
- whether the current repository/workspace protects it.

The current repository and workspace are always protected.  Existing checkout
roots are retained by default.  A missing checkout root becomes eligible only
after a grace period.  More aggressive inactivity cleanup requires an explicit
policy flag.

Cleanup removes only ASP-derived state and artifacts.  It never removes a
source checkout, Git directory, or worktree.

* Migration

Identity migration is deterministic and conflict-aware:

- records that normalize to the same repository ID merge under one project;
- each existing checkout remains a separate workspace;
- client databases and artifacts move to the canonical project/workspace
  layout;
- populated conflicting destinations fail closed and produce a receipt;
- successful migration leaves no writable SQLite compatibility database.

* Regression gates

** Correctness scenarios

1. One repository plus three linked worktrees yields one project and four
   workspaces.
2. SSH, SCP-like, and HTTPS remotes for the same host/path yield one project
   identity.
3. Distinct clones without a durable remote do not collide.
4. A bare repository resolves without inventing a worktree.
5. =include.path=, =includeIf=, and =extensions.worktreeConfig= participate in
   effective remote selection through Git-owned parsing.
6. Ten thousand temporary fixtures create zero new global project entries.
7. GC dry-run is stable and =--apply= removes only the same revalidated set.

** Performance scenarios

Repository/workspace identity resolution is an interactive-path operation.  A
warm single-checkout resolution and a linked-worktree resolution MUST remain
millisecond-scale.  The benchmark receipt records p50, p95, p99, maximum, and
sample count rather than only total wall time.

GC must scan metadata without opening every project database.  Its receipt
separates scan time, candidate evaluation time, and deletion time.
