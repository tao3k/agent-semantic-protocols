#+title: Runtime State Reconciliation and Cleanup
#+property: RFC_ID 10.05.05
#+property: STATUS draft
#+property: PROTOCOL_VERSION 1

* Problem

The Runtime State Home still contains historical serving authorities such as
=runtime/resident/candidates=, per-provider profiles, provider artifact trees,
and endpoint files.  Their continued existence allows a launcher, status
observer, or provider registry to bypass the single content-addressed Runtime
bundle selected by =runtime/artifacts/active= and
=runtime/artifacts/healthy=.

The existing =asp clean --day= operation only retires cache belonging to
disappeared temporary workspaces.  It is not a Runtime-state garbage collector.
There is no public =asp sync= operation.  Treating either fact as implicit
Runtime reconciliation would silently create a second authority.

* Decision

** State Home artifact boundary

=agent-semantic-artifacts= is the only package that derives physical paths
for generated State Home objects.  It owns typed sub-layouts, content-addressed
names, atomic replacement mechanics, reachability inputs, and cleanup plans.
Runtime, Client DB, providers, and CLI code pass typed identities and payloads
to that interface; they do not reconstruct =runtime/*=, =workspaces/*=, or
=receipts/*= paths with string joins.

This physical authority does not move domain state machines into the Artifacts
package.  Runtime owns transition and admission rules, Client DB owns workspace
and index semantics, providers own language projections, and the CLI owns only
command orchestration.  Those owners decide /whether/ a transition is legal;
Artifacts decides /where and how/ its immutable objects, mutable CAS pointers,
and receipts are persisted.

The layout is one tree of typed namespaces rather than unrelated helpers:

#+begin_example
StateHomeLayout
  -> RuntimeStateLayout
       -> RuntimeArtifactStateLayout
       -> RuntimeServingStateLayout
            -> endpoint receipt
            -> content-bound status memory
            -> readiness endpoints
            -> workspace materializations
#+end_example

A downstream package accepting an arbitrary =PathBuf= remains possible at an
explicit test boundary, but production construction begins with
=StateHomeLayout=.  Environment variables may select the State Home only at the
Host edge.  They never replace an individual generated-object path after the
layout has been constructed.

V1 has one Runtime artifact authority:

#+begin_example
runtime/artifacts/
  blake3-256/<content-digest>/...
  bundles/<bundle-digest>/...
  active  -> bundles/<bundle-digest>
  healthy -> bundles/<bundle-digest>
  activation/
  leases/
#+end_example

=active= selects the only serving bundle.  =healthy= selects the only verified
rollback bundle.  A bundle contains the ASP executable, Hook executable,
provider executables, provider catalog, evaluator policy identity, and schema
identity.  No member owns an independent active or healthy selector.

** Provider closure is bundle content

The provider install registry is a declarative build input, not a mutable
post-install selector.  A binary reconciliation first computes the ASP binary
digest, provider registration digest, installed-provider artifact binding,
evaluator policy digest, and schema-bundle digest.  These identities form the
Runtime execution binding embedded in =bundle.json= and participate in the
bundle digest.  Only then may the bundle be staged and atomically selected.

Consequently, changing the registry, any installed provider artifact, policy,
or schema while retaining identical ASP executable bytes produces a distinct
bundle identity.  Repeating the same complete closure produces the same bundle
identity.  The install command does not publish a later
=runtime/provider-catalog.v1.json= side transaction, and daemon startup does
not repair one.  The daemon reads the verified manifest reached by the sole
=active= selector and admits exactly that immutable closure.

The migration order is intentionally strict:

1. construct and validate the complete execution binding without mutating
   State Home;
2. stage all executable and manifest leaves in the immutable CAS;
3. verify every leaf and derive the bundle digest from members plus binding;
4. publish the pending activation event under the artifact mutation guard;
5. atomically switch =active=;
6. let the Runtime validate health before advancing =healthy=;
7. retire root-level provider catalog and installed-provider projections only
   through the reachability-based cleanup transaction.

There is no compatibility read from the root-level catalog after cutover.  A
bundle without the exact execution binding fails admission with a typed
content-binding error; numeric activation generation cannot repair it.

Runtime transport publication is process state, not artifact identity, but it
is still owned by the canonical ASP State Home.  V1 uses exactly one mutable
transport publication root:

#+begin_example
runtime/serving/
  endpoint.v1.json
  status-<content-binding-prefix>.memory
  readiness/
  ... bounded process-owned transport state
#+end_example

The Runtime may use operating-system sockets or loopback ports, but =/tmp=,
=$TMPDIR=, a UID-derived directory, and =runtime/resident/current= are never
publication authorities.  They cannot select a Runtime, repair a missing
handoff, or override the State Home.  Tests may inject an explicit publication
directory; production clients do not discover one from ambient path guesses.
Candidate readiness endpoints are ephemeral children of
=runtime/serving/readiness=.  The parent-held listener and its request token
remain the authority; the pathname is only a transport address.  If the
canonical State Home cannot fit the platform's Unix-domain socket address
budget, readiness fails with
=reasonKind=runtime-readiness-path-unrepresentable=.  It must not shorten the
path by publishing into a global temporary directory.

One resident-transaction observation validates owner, applied artifact,
publication nonce, executable digest, owner epoch, transport endpoints, and
previous-owner drain.  It returns both the immutable handoff receipt and the
exact endpoint value observed at that linearization point.  Status and Query
must consume that value; they may not re-read an endpoint pathname after
handoff validation.  A missing or mismatched publication is one typed terminal
failure and never causes client retry, Runtime launch, or endpoint fallback.

* Sync Transaction

=asp sync= is a reconciliation transaction, not a file-copy command.

1. Read the declarative provider registry and current build inputs.
2. Hash every member and construct one immutable bundle manifest.
3. Validate the exact Runtime execution binding.
4. Publish content into the CAS without changing serving state.
5. Compare the expected previous active bundle digest.
6. Atomically move the single =active= selector.
7. Emit one typed terminal receipt.
8. Produce, but do not implicitly execute, a cleanup plan.

Failure before step 6 leaves =active= unchanged.  Cancellation never commits.
Repeated reconciliation of identical content preserves content identity even
when its internal publication sequence advances.

* Cleanup Transaction

=asp clean= obtains a Runtime cleanup plan from the artifact authority.  It may
delete only paths proven unreachable from all of:

- the active bundle;
- the healthy bundle;
- a live publication or query lease;
- an in-flight handoff transaction;
- an explicitly retained diagnostic artifact inside its retention window.

The default mode is a dry-run receipt.  Execution requires an explicit Runtime
state scope.  Every planned path carries a reason and evidence class.  The
commit compares the plan's expected active and healthy bundle digests before
the first deletion.  A mismatch rejects the entire plan.  Cleanup never starts,
restarts, installs, or selects a Runtime.

* Legacy State

The following names are never serving authorities and must be retired after a
successful reconciliation and reachability proof:

- =runtime/resident= and =runtime/resident/candidates=;
- =runtime/server= as a parallel endpoint, workspace, lifecycle, diagnostic,
  provider-register, or socket publication root;
- =runtime/bin= launchers that resolve through a retired authority;
- =runtime/profiles=;
- root-level =runtime/activation=, =runtime/leases=, and =runtime/locks=;
- per-provider active or healthy selectors;
- root-level installed-provider binding and provider-catalog receipts;
- =runtime/provider-locks= after their declarative inputs are represented by
  the published bundle manifest;
- =runtime/state/*endpoint*=;
- abandoned stage files and expired quarantine directories;
- obsolete provider-artifact trees superseded by the active bundle catalog.

Stable launchers may exist outside the artifact store, but they must resolve
through =runtime/artifacts/active=.  A launcher path is not content identity.

* Rejected Alternatives

** Delete legacy paths during Runtime startup

Rejected because startup would become a hidden mutation authority and a failed
launch could partially delete the last usable bundle.

** Let each provider clean its own profile

Rejected because provider-private retention cannot prove global bundle or
lease reachability.

** Use activation generation as the cleanup key

Rejected because the generation is a monotonic transaction fence, not content
identity.  Equal content may have different generations and different content
must be rejected by digest even if a numeric comparison succeeds.

* Deterministic Gates

- Artifacts derives every generated State Home path; production Runtime,
  Client DB, provider, and CLI code contain no sibling path reconstruction;
- Runtime artifact and serving layouts share exactly one State Home runtime
  root and expose disjoint typed namespaces;
- status memory names are deterministic over the exact execution identity and
  change when any identity member changes;
- constructing a layout performs no I/O and environment mutation after
  construction cannot change any derived path;

- dry-run never mutates the State Home;
- active, healthy, live leases, and handoff transactions are never planned;
- legacy resident candidates become eligible only after bundle reconciliation;
- active or healthy digest drift rejects the complete cleanup commit;
- cancellation before commit deletes nothing;
- repeated identical sync produces the same bundle digest;
- identical binaries with different provider registry, provider artifact,
  evaluator policy, or schema identities produce different bundle digests;
- daemon admission reads no root-level provider catalog or installed-provider
  projection;
- cancellation before the active-slot CAS leaves both root-level legacy state
  and serving selectors unchanged;
- concurrent sync is single-flight per bundle digest;
- cleanup emits exactly one typed terminal;
- status and query never rederive an endpoint path when Host handoff is absent.
- canonical and symlinked State Home paths resolve to the same
  =runtime/serving= publication root;
- no production endpoint path resolves beneath =/tmp= or
  =runtime/resident/current=;
- candidate readiness remains beneath the canonical State Home, and an
  overlong State Home fails closed instead of minting a second temporary-root
  authority;
- a status observation uses the endpoint returned by the same validated
  resident transaction and performs no second endpoint read.
