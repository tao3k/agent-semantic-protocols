* Architecture status and canonical successor

This document is no longer the architectural root of agent search.  The
canonical search architecture is
[[file:10.05-interactive-graph-first-progressive-searchloop.org][Interactive,
graph-first, progressive SearchLoop]].

This RFC retains ownership of CLI adapters, harness behavior, activation,
diagnostics, installation, compatibility input, and human-oriented command
rendering.  Existing search/query sections remain historical locators until
their semantic modules migrate.  Their location MUST NOT be interpreted as
making CLI syntax the agent-facing protocol, and new SearchLoop semantics MUST
NOT be added under this tree.

* One-sentence summary

The =SearchLoop= contract is the agent-facing public protocol.  Search and
exact query are capabilities used by that loop; the CLI is a thin adapter for
human exploration, automation, diagnostics, and recovery.  A local daemon is a
private acceleration cache.  MCP is explicitly excluded from the architecture.

* Synchronization responsibility and trigger contract

Root =asp sync= has no cross-domain responsibility and MUST fail closed with
the explicit domain commands.  Global agent profile projection belongs to
=asp agent config sync=.  It reconciles ASP-owned profiles from the State Home
into supported host agent configuration directories and is not a workspace,
provider, source-index, Org checkout, activation, or resident-service lifecycle
command.

Its trigger contract is:

- =asp install= owns its own post-install projection phase and MUST NOT shell
  out to =asp agent config sync=.  It MAY call the same internal projection owner after
  agent profile artifacts have been installed.
- An operator MAY invoke =asp agent config sync= when =asp healthcheck= reports global agent
  projection drift or when repairing a missing host projection.
- Search, exact query, provider dispatch, PreToolUse, workspace activation,
  resident healthcheck, and checkpoint MUST NOT invoke =asp agent config sync=.
- =asp agent config sync= MUST NOT accept or infer a workspace.  It MUST NOT open a
  workspace database, build a source index, start or stop a resident service,
  write activation state, or clone, fetch, pull, or otherwise synchronize a
  Git repository.

Workspace and provider state use their explicit owners:

| Concern | Owner command or lifecycle | Trigger |
|-
| Install binaries, plugins, hooks, provider manifests, and agent profiles | =asp install= | Explicit install or upgrade |
| Reconcile global host agent projections | =asp agent config sync= | Explicit operator repair after healthcheck drift |
| Detect and activate a canonical Git workspace and ensure its unique resident service | PreToolUse hook | Before a workspace-scoped tool action |
| Stop idle or removed-workspace residents | =asp workspace-db checkpoint= | Checkpoint policy |
| Incrementally acquire provider facts | Provider-owned =search= path | Demand-driven by search |
| Read exact provider source | Provider-owned =query= path | Explicit selector query; never sync-gated |
| Refresh or rebuild full workspace source-index state | =asp cache source-index refresh|rebuild --workspace <path>= | Explicit prewarm, CI, or recovery |
| Materialize missing Org contracts or templates | Org consumer resource owner | Consumer-lazy; no root sync and no workspace Git mutation |

Every synchronization surface MUST carry its domain in the command path so
receipts and side effects have one unambiguous owner.  Root =asp sync= is
intentionally unavailable rather than a compatibility alias.

This file is the stable RFC 005 entry point and compatibility identifier.  It
does not own the detailed search command tree.  The normative body is split
into focused Org modules under
=docs/10-19-rfcs/10.05-cli-first-harness-ux/= so the SearchLoop protocol,
search/query capabilities, provider contracts, hook guidance, and historical
readiness notes can evolve without growing one large always-read document.

The search architecture starts at
[[file:10.05-interactive-graph-first-progressive-searchloop.org][Interactive graph-first progressive SearchLoop]].
The existing search/query modules remain the lower-level capability contracts.
They MUST NOT require an agent to construct a long CLI command sequence in
order to make one bounded search transition.

For resident search routing, =search= is the reasoning plane and =query= is the
exact evidence materialization plane. Resident =search= may close with a
=SearchClosureReceipt= that contains an =EvidenceScope= and =QueryHandoff=, but
it MUST NOT expose =search --choice read:*= or equivalent prompt-visible read
actions. After search closure, the main agent materializes only the exact
=query --selector= commands described by the handoff.

* Explicit search workspace authority

The normative bootstrap contract is defined by
[[file:10.05-cli-first-harness-ux/10.05.11.04-project-semantic-guidance-v1.org][Project Semantic Guidance v1]].
Repository candidates, provider project-entry parsing, package graphs, and
resolved source scopes form ASP Level 0 and run before source-envelope,
Tree-sitter, Search, or Turso initialization.

For =asp <language> search=, an explicit =--workspace <root>= selects both the
semantic project root and the State/cache locator root. The invocation working
directory remains the locator only when =--workspace= is absent. A positional
search path is a query scope, not an implicit workspace selector, and MUST NOT
materialize activation or persistent State for that path.

** Provider workspace-root identity normalization

The provider boundary MUST normalize every explicit search workspace root to
one absolute lexical or canonical identity before downstream discovery,
projection, or cache lookup.  An absolute input remains absolute.  A relative
input that names an existing path resolves from the provider current working
directory.  When the current working directory already ends with the relative
workspace input, the normalized root is the current working directory itself;
the provider MUST NOT concatenate the same workspace identity a second time.
Otherwise the normalized root is exactly one =cwd.join(input)= followed by
lexical normalization and, when the target exists, canonicalization.

Workspace-root normalization is a request-boundary operation.  It MUST NOT
require =asp sync=, generate a second workspace identity, or fall back to a
legacy cache or database root.  Invalid or unresolvable inputs fail with a
focused error naming the input and current working directory.

** Repository and language-project resolution

Repository and language-project resolution is the core authority beneath
source envelopes, incremental parser generations, Tree-sitter inventory,
reasoning search, and workspace database ownership.  It is not an optimization
inside any of those consumers.  This resolution MUST be runnable before a source
envelope exists, MUST NOT open Turso, MUST NOT require =asp sync=, and MUST NOT
depend on an already-materialized search generation.  Its successful output is
one typed =ProjectResolution= receipt; downstream consumers MUST NOT reconstruct
project scope independently.

For a Git checkout, the runtime Git owner MUST use the repository common
directory, worktree, index, ignore, sparse-checkout, submodule, symlink, and
working-tree status semantics to publish a =RepositoryCandidateSnapshot=.  The
snapshot contains the stable repository identity, distinct worktree identity,
candidate generation, tracked index entries, live tracked changes and
deletions, and ignore-aware untracked additions admitted by Git.  ASP MUST NOT
replace Git status/index semantics with an unbounded =read_dir= walk.  A
submodule is a new repository boundary; a sparse checkout cannot admit owners
outside its materialized worktree scope.

Provider project markers are parser dispatch keys, not directory-filter
strings.  A marker such as =Cargo.toml=, =package.json=, =pyproject.toml=, or
=Project.toml= selects the registered provider project resolver and supplies
its exact project-entry path.  The resolver parses that entry plus only
manifest-declared workspace members, package manifests, lockfiles, path
dependencies, target declarations, and source-root declarations.  It emits a
normalized =LanguagePackageGraph= with project, package, target, internal
dependency, external dependency identity, generated-root, and source-root
facts.  Omitted manifest fields MUST be resolved only through the selected
package manager's documented semantics.  A provider MUST NOT invent generic
default roots, extensions, ignored directories, or workspace membership.
Package-manager-derived facts are labeled =package-manager= and retain the
owning parser and project-entry evidence in the receipt.

The shared =ProjectResolution= binds =RepositoryIdentity=,
=WorktreeIdentity=, provider and parser identities, normalized project-entry
path, =LanguagePackageGraph=, =ResolvedSourceScope= records, candidate
generation, manifest and lock digests, and the resolution generation.  A
=ResolvedSourceScope= names its owning package and target, admitted extensions,
source and generated roots, inclusion authority, exact =explicitPaths=, and
exclusion authority.  =explicitPaths= MUST contain only manifest-declared
source roots and target entrypoints for =manifest-explicit= scopes and MUST be
empty for package-manager-conventional scopes.  ASP expands an explicit
directory only over the Git candidate universe and uses those exact admitted
paths when detecting a user-policy conflict with an explicit target.
Flat =packageRoots=, =sourceRoots=, and =sourceExtensions= arrays are derived
receipt projections; they are not provider configuration and are not
independently executable inventory authority.  Provider-owned
=ignoredPathPrefixes= are not part of project resolution.

Scope admission applies ordered authorities:

1. ASP infrastructure exclusions such as Git metadata and State Home runtime
   artifacts are hard exclusions.
2. Package-manager workspace membership, exclusions, and explicit targets are
   authoritative project facts.
3. Package-manager-defined implicit targets and conventional layouts are
   admitted only when produced by that package manager's parser.
4. User policy overlays are explicit final policy facts applied by ASP.

ASP applies repository ignore semantics while Git constructs the repository
candidate universe.  ASP then normalizes its user policy overlay into exact
=policyExclusions= facts carried by the =RepositoryCandidateSnapshot=.  The
candidate universe remains intact for provider parsing so an explicitly
declared package target cannot disappear before authority comparison.  After
provider resolution, ASP applies those exact exclusions once while projecting
the final file scope.  Providers MUST NOT reapply private default ignore lists
or interpret ASP directory-name policy themselves.  A policy exclusion MUST
NOT silently exclude a path explicitly owned by a package target; conflicts
fail closed with a typed =project-scope-conflict= result naming the exact path,
=manifest-explicit= include authority, and =user-policy= exclude authority.

For a non-Git workspace, repository candidate resolution uses an explicitly labeled
=provider-only= repository candidate mode.  The caller supplies a project entry
or the provider probes only its finite registered marker names at the selected
workspace root.  Further traversal follows manifest-declared members,
dependencies, and roots.  Missing project entry is the typed
=project-entry-missing= state; it never authorizes a generic recursive walk.

Repository, worktree, project, and project-instance identities are distinct.
One Git common repository shared by several worktrees has one repository
identity, one stable project identity per provider plus normalized project
entry, and separate worktree/project-instance identities.  This prevents
worktrees, cache directories, and repeated path spellings from manufacturing
new project IDs while preserving their independent live file generations.

  The project-resolution cache key is the Git index/status generation, relevant manifest
and lock digests, provider project-parser digest, and policy-overlay digest.  An
unchanged warm resolution performs no source reads, provider processes,
database opens, or artifact writes.  One manifest or index delta re-resolves
only the affected package-graph closure.  Receipts report candidate counts,
parsed manifest and lock counts, affected package count, =fullWorkspaceReads=,
=fullManifestReparses=, =dbOpens=, and elapsed microseconds.  Ordinary and warm
paths require all three prohibited counters to remain zero.

** Incremental Tree-sitter inventory candidate scope and pruning

For a Git repository, inventory enumeration MUST derive its initial candidate
owner set from the Git worktree and index file scope: tracked files plus current
working-tree additions required to observe live edits.  It MUST then intersect
those candidates with the activated provider project scope, including project
markers, configuration files, package roots, declared source roots, registered
source extensions, and package-manager-owned exclusions.  It then applies the
ASP-owned infrastructure and user-policy exclusions already normalized into the
=RepositoryCandidateSnapshot= exactly once.  Provider-private ignored path
prefixes are not an inventory input.  A Git workspace MUST NOT perform an
unbounded recursive walk from the workspace root.

For a non-Git workspace, ASP MUST use an explicitly labeled =provider-only=
candidate scope derived from finite project-marker probing followed by
package-manager-declared members and source roots.  It MUST NOT silently widen
that scope into a generic workspace-root crawl.

Inventory enumeration consumes the already-normalized ASP candidate snapshot;
it MUST NOT apply a second provider-private ignore pass.  Paths excluded by the
single ASP policy projection MUST never become inventory owners or be published
to the incremental workspace database.  Symlink skipping and registered
source-extension filtering remain mandatory after that projection.  This
enumeration contract is parser/provider owned and MUST NOT require =asp sync=,
use a legacy fallback, or defer excluded-owner removal to
a later database cleanup.

* Exact-selector miss is a typed discovery result
An exact selector already supplies the owner and canonical item identity.  The
workspace-resident DB projection is an optional hot-path cache for this
operation, not a prerequisite.  A missing resident-service endpoint is a typed
cache miss and MUST continue through the parser-owned live-owner projection.
This continuation MUST NOT open Turso directly.  Endpoint decode, workspace
identity, schema, and transport failures remain terminal errors.

An exact selector identifies one deterministic projection request.  Failure to
find that item in a valid live owner is a semantic query result, not a provider
transport failure.

- Provider JSON mode MUST return the existing provider-native exact projection
  v1 contract with a typed =resolutionState= variant for =item-missing=,
  =owner-missing=, =kind-mismatch=, and =ambiguous=.
- A semantic miss MUST NOT be encoded only in stderr and MUST NOT be wrapped by
  the facade as =provider failed: status=... stderr=...=.
- Miss packets MUST include =reasonKind=, the requested owner/item identity,
  structured =candidates= and =actualKinds= arrays, and one
  =recommendedNext= search command.
- Candidate selection MUST prefer the requested canonical item kind.  It MUST
  not fill a bounded candidate list with unrelated modules, reexports, or
  other item kinds merely because they occur first in the owner.
- The language facade MUST render the typed miss compactly and preserve it in
  machine-readable output.  An empty or missing projection is never silently
  treated as source bytes.
- Provider crash, invalid JSON, schema drift, and byte-authority failure remain
  transport/protocol failures and stay distinct from a semantic miss.

This keeps exact =query= deterministic while routing discovery back to
=search owner <path> items=.  Callers consume a typed result and never recover
control flow by parsing provider stderr.

Exact =query --selector= is a direct parser operation because its canonical selector already names both the grammar and one owner path. The exact path MUST validate that the owner is contained by the requested provider workspace, read exactly that one live file, and ask the provider parser to project the selected item from those in-memory bytes. It returns parser-owned byte spans, the requested code projection, and the live file digest without opening Turso, CAS, a source envelope, a workspace Merkle tree, or requiring =asp sync .=. The provider-native v1 response MUST echo the request selector byte-for-byte as =requestedStructuralSelector= and MUST report its parser-resolved identity separately as =structuralSelector=. ASP validates the request echo, owner, source digest, byte span, and projected bytes exactly; it MUST NOT infer provider canonicalization through prefix or substring matching. Source envelopes and incremental generation belong only to reasoning =search=: an unchanged owner reads its published index, while a missing or changed owner updates only that owner and the minimum dependency closure rather than scanning or materializing the full crate. A complete =asp sync .= remains the explicit full-generation and recovery boundary for search. The v1 search envelope requires =providerWorkspaceRoot= and =providerWorkspaceIdentityDigest= so one provider can publish several semantic workspaces without last-writer-wins aliasing; this is a v1 contract completion, not a compatibility v2.

* Incremental reasoning-search source authority

Ordinary =search= MUST NOT require a complete source envelope before it can
route an owner or Tree-sitter request.  Its command context carries only the
target =languageId=, =providerId=, provider-workspace identity, a persisted
generation handle, and an optional explicit owner intent.  It MUST NOT carry a
materialized =CurrentSourceIndexSnapshot= or source-blob collection.

The v1 owner acquisition decision is metadata-first:

1. Canonicalize the explicit owner inside the selected provider workspace.
2. Read the persisted owner fingerprint from the project Turso 0.7 database.
3. Stat the live owner.  The fingerprint binds file identity, byte length,
   modification time, change time, and the last admitted content digest.
4. If file identity, byte length, modification time, and change time are
   unchanged, reuse the indexed parser facts and content digest.  This path
   performs zero source byte reads, zero provider parses, zero CAS writes, zero
   index writes, and zero Merkle writes.  Change time is required so a
   same-length replacement that restores modification time cannot be admitted
   as unchanged.
5. If the owner is changed or new, read and hash exactly that owner, invoke the
   selected provider parser exactly once, and atomically upsert its fingerprint,
   parser facts, structural selectors, byte spans, Merkle leaf, and only the
   affected ancestor path nodes.

The transaction is owner-scoped and fail-closed.  It either publishes the new
owner facts and generation root together or leaves the preceding generation
visible.  It MUST NOT rebuild the full Merkle tree, materialize a provider
source envelope, write CAS source bytes, open another provider, or retain an
SQLite/legacy compatibility path.

=asp <language> search --treesitter-query= is a reasoning-search operation.
It compiles the target language grammar, queries the selected provider's
persisted parser facts, and returns capture signatures plus parser-owned
structural selectors.  A complete unchanged generation is index-only.  Dirty
owners are refreshed through the same bounded owner transaction before their
facts are admitted.  Rust search is not blocked by incomplete TypeScript,
Python, Julia, or other provider generations.

When a workspace-wide request has no complete provider generation, ASP returns
typed =partial= completeness with the indexed owner count, remaining dirty or
unindexed owner count, the bounded work performed in this invocation, and the
next incremental continuation.  It MUST NOT silently walk, parse, envelope, or
Merkle-materialize the full workspace.  =asp sync .= remains an explicit
full-generation recovery operation for callers that require complete
enumeration or negative proof.

Search routing may resolve only the canonical workspace identity and MUST call
that workspace's unique database owner through typed IPC.  It MUST NOT open
=facts.turso=, create or depend on =hooks/state/languages/<language>=, use hook
event state, or introduce another client-specific lifecycle directory.

Workspace Tree-sitter persistence is query-specific.  An arbitrary compiled
Tree-sitter query cannot be answered from the complete-owner item projection
alone.  ASP keys each persisted query-owner result by
=providerWorkspaceIdentityDigest=, =queryDigest=, =ownerPath=, and
=ownerContentDigest=.  The record binds the processed state and the complete
capture projections produced for that query and owner.  Repeating the same
query against the same owner digest is index-only and performs zero source
reads and zero parser invocations.  A new query or dirty owner consumes the
bounded incremental budget, reads only the selected owner, runs the selected
provider grammar once, and atomically publishes the query-owner result.

Each capture projection MUST report its capture name and parser byte span.  ASP
derives the canonical structural selector and signature by finding the
smallest complete-owner item projection whose byte span contains the capture
span.  A missing or stale complete-owner projection triggers at most one
same-owner refresh before the query-owner record is admitted.  ASP MUST NOT
guess item identity from capture text, selector prefixes, or substring
matching.

Provider-scoped owner inventory is a separate persisted authority.  Its
completeness is explicitly =exact= or =known=.  An exact inventory permits an
exact remaining-owner count and may close enumeration after the count reaches
zero.  A known inventory reports only the known pending lower bound and cannot
close enumeration or absence, even when that lower bound reaches zero.  Neither
inventory nor query-specific cache stores source blobs or writes source bytes
to CAS.

* Exact query projection contract

The contract family is v1, while every JSON wire object uses
=schemaVersion: "1"=.  The =v1= token belongs in schema IDs and filenames; it
MUST NOT appear as the =schemaVersion= field value.

Exact query has one explicit projection axis:

#+begin_src shell
asp <language-id> query \
  --selector '<exact-structural-selector>' \
  --projection <source|callable-skeleton> \
  --workspace <workspace-root>
#+end_src

=query= never searches. The selector MUST already be parser-owned and exact.
=projection= selects only the representation of that identity. =source=
materializes the exact selected node bytes. =callable-skeleton= returns
=agent.semantic-protocols.callable-skeleton-projection= =v1= and is valid only
for a provider-owned callable selector.

The projection request is mandatory. The public contract does not infer source
versus skeleton from callable size, output TTY, model context, or provider
defaults. The legacy =--code= and =--names-only= flags are not part of this hard
cut. Clients, provider request packets, provider responses, and tests migrate
together rather than keeping flag aliases that make the requested projection
ambiguous.

The provider-native request carries =projectionKind= byte-for-byte together
with =generationIdentityDigest=, =parserIdentityDigest=, and =queryPackDigest=.
The provider-native response echoes the requested mode as =projectionMode=.
ASP rejects a response whose mode differs from the request. =source= carries =projectionText=.
=callable-skeleton= carries a typed =projectionPayload= conforming to
=callable-skeleton-projection.v1.schema.json=; a skeleton response without that
payload fails closed and MUST NOT substitute the complete callable body.

Every queryable skeleton child carries
=asp.exact-structural-selector.v1=. A later exact query executes that returned
selector with a new explicit projection. It does not use display ranges, byte
offsets, labels, or sibling ordinals to rediscover the child.

The Rust provider is the reference implementation, but the CLI and request
shape are shared across language facades. A provider declares
=callable-skeleton= only after every emitted queryable child round-trips through
exact query and stale generation/parser/query-pack bindings fail closed.

* Health Activation Convergence

`asp healthcheck`, `asp paths`, and `asp hook doctor` MUST resolve the
workspace through the same =ProjectContext::resolve= and derive activation from
=project_state_paths=.  The canonical activation is
=project_state_paths.activation_path=; no command may independently construct
an activation path from a git top-level, =PRJ_CACHE_HOME=, or legacy cache
layout.

Git discovery, cache source selection, and legacy activation locations remain
diagnostic observations.  They MAY be emitted to explain migration state, but
MUST NOT select the activation consumed for health, paths, doctor, provider
profiles, or binary-freshness checks.  A missing canonical activation is an
activation error even when a legacy cache activation exists; a legacy cache
activation is retained only as diagnostic evidence.

Binary freshness is artifact identity, not pathname identity. Health MAY use
canonical-path equality as a fast success, but different executable paths are
fresh when their byte length and streaming SHA-256 digest match. A workspace
build, versioned install path, Homebrew entrypoint, or symlink target MUST NOT
be reported as drift solely because the path strings differ.

* Managed Hook Config Lifecycle

The v1 hook config schema remains stable.  Install owns only a default config
it can prove it previously wrote: the config directory contains
=config.toml.managed.sha256= whose single SHA-256 value is the exact installed
=config.toml= byte sequence.

Install resolves the current default through
=default_client_config_template()=.  An absent config is atomically created
with its sidecar.  A config whose contract fingerprint is current is preserved
(and receives a missing sidecar only when its bytes equal the current managed
template).  A stale or fingerprint-less config is atomically upgraded only
when its sidecar digest matches its present bytes, or when it has one of the
following explicit historical managed signatures:

- current template minus only the top-level =contractFingerprint=;
- pre-rules managed template: current template minus the top-level
  =contractFingerprint= and top-level =rules=.
- the audited pre-rules prompt-era managed template: it has the exact historical
  byte length and SHA-256 signature for =agentSessionGuide.register=,
  =agentSessionGuide.status=, and the three deprecated
  =agentSessionMessages.sourceAccessCompact*= fields; after removing only those
  five proven historical fields, its remaining TOML must equal the current
  pre-rules template with the corresponding current guide fields removed.

These are structural TOML variants, not a permissive rule that accepts an
arbitrary config with missing =rules= or arbitrary prompt text. Any signature,
length, or remaining-structure mismatch remains unproven user-owned
configuration.

Any other valid config is user-owned and install fails with
=user-config-contract-unproven= without changing either config or sidecar.
Invalid TOML retains the existing parse error.  Managed writes use a temporary
file and rename, clean temporary failures, then reload and verify the current
fingerprint before a successful receipt.  Receipts report
=userConfigStatus=current|created|migrated-managed|unproven=.

* Codex Global Plugin Idempotency

Global plugin install MUST remain idempotent in Codex Desktop environments that
do not expose a =codex= CLI executable. When the global Codex config already
enables the exact ASP plugin id and ASP has materialized the current versioned
global plugin cache, install reuses that native state and MUST NOT invoke
=codex plugin marketplace add= or =codex plugin add=. If either proof is
absent, the CLI-owned marketplace/add path remains required and failure is
reported without pretending the plugin is installed.

* Exact-query and discovery rendering contract

Agent-facing exact query has one rendering selector:

#+begin_src text
--projection source|callable-skeleton
#+end_src

Discovery returns the protocol-defined seed frontier by default.  It does not
offer historical boolean rendering switches.  CLI parsers, help generators,
provider manifests, snapshots, tests, and agent guidance MUST expose only the
projection vocabulary defined by the current contract.  An implementation
MUST treat any removed rendering switch as an unknown argument; it MUST NOT
retain a compatibility parser branch or a diagnostic that teaches the removed
syntax.

This is a protocol deletion, not a deprecation window.  Installed provider
artifacts and workspace-resident daemons MUST publish the same help digest and
projection vocabulary before they may report healthy.
