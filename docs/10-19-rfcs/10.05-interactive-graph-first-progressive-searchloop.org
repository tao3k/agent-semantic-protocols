#+title: Interactive Graph-First Progressive SearchLoop
#+subtitle: Canonical agent search, reasoning, and evidence-navigation architecture
#+options: toc:3 num:t

* Status

This document is the canonical architectural root for RFC 10.05.

It replaces the conceptual =CLI-first= framing with three coequal principles:

- interactive-first;
- graph-first; and
- progressive-first.

The historical =10.05-cli-first-harness-ux= paths remain compatibility
locators during reference migration. Their location does not make CLI behavior
architecturally primary.

* Naming decision

The canonical short name is:

#+begin_example
Interactive Graph-First Progressive SearchLoop
#+end_example

The three adjectives describe different protocol dimensions.

** Interactive-first

The primary consumer is an agent participating in a stateful reasoning loop.
Each turn observes current evidence state, chooses a bounded next action,
receives a compact receipt, and updates the session frontier.

Interaction does not mean a terminal prompt or a human menu. It means that
search semantics are organized around state transitions rather than one large
request.

** Graph-first

The searchable substrate is an evidence graph:

- semantic owners are nodes;
- dependencies and proof obligations are edges;
- routers select short valid paths;
- receipts record traversed evidence; and
- cache identity binds reusable graph conclusions.

Commands are transports for graph operations. They are not the ontology.

** Progressive-first

Every turn expands only enough evidence to support the next decision.

Progressive search minimizes:

- graph distance to a justified conclusion;
- evidence tokens returned to the model;
- agent/tool interaction rounds;
- repeated traversal of already proven subgraphs; and
- invalid cache reuse.

Progressive does not mean incomplete or best-effort evidence. Every accepted
conclusion remains fail-closed and receipt-backed.

* Primary protocol loop

The canonical SearchLoop is:

#+begin_example
observe evidence state
  -> classify the unresolved frontier
  -> choose one bounded graph action
  -> execute through the owning provider
  -> validate and merge its receipt
  -> stop, branch, or continue
#+end_example

The loop state, not a command transcript, is the durable protocol object.

** Typed topology before compact rendering

Every SearchLoop entry path, including a user-supplied exact selector, MUST
first construct the same typed graph facts consumed by Graph Turbo: stable
nodes, directed edges, and typed action-frontier entries.  A selector seed is
therefore not a second text protocol.  It contributes an intent node, a
language/provider node, and—only after canonical selector validation—owner and
item nodes with =targets_item=, =serves_owner=, and =owns_item= relations.
Executable actions reference those graph identities; presentation ordinals
such as =A1= are not durable node identities.

Compact Render is a projection over that typed topology.  It MAY preserve
small human-facing lines such as =ownerSeed=, =actionFrontier=, and
=recommendedNext=, but it MUST NOT parse the selector again, invent another
owner/symbol fact, or choose an action independently.  A malformed or
cross-language selector may retain an unresolved input node for explanation,
but it MUST produce no owner/item relation and no executable exact-query
action.  This separation is the prerequisite for a later session cursor to
jump directly to an already materialized node without replaying the complete
SearchLoop.

* Architecture layers

** 10.05.00 Foundations and invariants

Owns terminology, state-machine invariants, safety boundaries, and the
relationship among interaction, graph navigation, progressive disclosure, and
proof receipts.

Language-scoped search, query, check, and cache operations MUST preserve lazy
provider admission.  A language facade resolves through the registered provider
registry to exactly one provider identity; absence of an explicit index-owner
argument MUST NOT widen that operation to complete-generation or global
source-index resolution.  Only an explicitly unscoped operation may request a
complete generation.  Runtime evidence for a language-scoped operation MUST
therefore report no commands or processes for unrelated providers; a missing
runtime for the selected provider is a typed provider-local failure, not a
reason to prepare a shared runtime such as Node.

*** Provider execution gate and memory evidence

Every external provider process started by an ASP language facade MUST run
through the shared Provider Execution Gate.  The gate owns process-group
creation, timeout and cancellation, bounded output capture, memory admission,
termination, and the =provider-process-termination-receipt.v1= evidence.  A
language provider MUST NOT implement a private substitute, and the CLI remains
an adapter over this gate.

The default provider memory ceiling is 2 GiB (=2147483648= bytes).  The ceiling
applies to the combined resident memory of the complete provider process group,
not only the direct child PID.  A configured provider profile MAY choose a
lower ceiling.  Disabling the ceiling is test-only behavior and MUST NOT be
inferred from a missing per-call override.  On platforms where an address-space
rlimit is reliable, ASP SHOULD apply it before exec as an early barrier; ASP
MUST also use parent-owned observation whenever that rlimit cannot establish
the process-group resident-memory guarantee.

When observed process-group resident memory exceeds the ceiling, ASP MUST
terminate the complete process group, classify the result as
=memory-limit-exceeded=, and return a typed provider-local failure.  The
termination receipt MUST report =memoryLimitEnforced=true=,
=memoryLimitExceeded=true=, and the applied =memoryLimitBytes=.  Observability
MUST record the language identity, provider identity, command digest, applied
ceiling, observed process-group resident bytes, observed process count, elapsed
time, and termination action without recording provider stdin or source
content.  A timeout, cancellation, signal, ordinary exit code, and memory-limit
termination remain distinct outcomes.

Provider invocations are not resident services.  Once the process-group leader
for one search, query, check, or cache operation exits, ASP MUST terminate and
reap every remaining descendant in that process group before returning the
facade result.  A descendant that outlives the invocation is an orphan even
when its RSS is below the memory ceiling.  The workspace ASP Server MAY retain
the invocation lease as a crash-recovery backstop, but Server availability MUST
NOT replace transport-owned descendant closure.  The termination receipt MUST
state whether process-group isolation was enforced and whether descendant
cleanup was required, so a successful provider leader cannot hide an orphan
binary that ASP had to terminate.

*** Provider workspace artifact admission

Development-provider installation MUST be driven by the selected provider's
registered =provider-workspace-install= descriptor.  The shared provider
manifest stores only the repository-relative descriptor reference; build
commands, environment, artifact root, entrypoint, and optional launch adapter
remain provider-owned.  ASP MUST NOT duplicate those language-specific facts
in the root CLI or Justfile.

ASP owns execution of the registered workspace build through the Provider
Execution Gate and admission of the resulting artifact.  A directory artifact
MUST be captured as one immutable, digest-addressed tree, preserving the
relative layout required by its entrypoint (for example =bin/= and =lib/=).
Publishing only the entrypoint file from a declared directory artifact is an
identity error.  The provider install receipt MUST bind the tree digest, leaf
count, immutable artifact entrypoint, installed launcher identity, and final
execution-command digest.

The PATH-visible provider entry is an ASP-owned atomic launcher/profile.  It
MAY execute a provider-declared launch program or the immutable artifact
entrypoint directly, but it MUST resolve all artifact-relative programs and
arguments against the admitted tree.  Runtime reconciliation MUST treat a
receipt-covered launcher as current and MUST NOT collapse the tree back into a
single-file installation.  Descriptor identity or path escape failures are
typed provider-local admission failures; they never authorize falling back to
the root development installer.

**** Runtime generation incremental admission

Runtime generation admission MUST be single-flight for the tuple of workspace
identity, provider-registry evidence, schema evidence, and candidate Merkle
identity.  Concurrent callers observe the same tracked build and receipt; a
foreground wall budget never owns or cancels the background generation build.

The active generation scope is the only owner-membership authority.  Provider
fingerprint storage is a byte-bearing cache, not membership authority, because
it may retain relocated or tombstoned owners.  An unchanged owner may be reused
only when an active-generation owner row and a scoped provider snapshot join on
owner path and content digest.  A missing or mismatched join requires rebuilding
that owner from the live workspace.

Mutation evidence MUST be projected by workspace root before reaching a
provider builder.  A nested workspace cannot receive a changed path owned only
by its parent.  The builder overlays rebuilt changed owners and explicit
tombstones onto the admitted active manifest, preserves validated unchanged
owners, derives a complete successor manifest, and publishes that successor in
one writer lane.  A partial changed-owner file set MUST NOT be published as a
complete replacement generation.

Publication is latest-candidate-wins: an older build cannot overwrite a newer
admitted candidate.  Unchanged admission performs no owner-byte rescan, changed
admission reads only changed or unverifiable owners, and shutdown joins or
cancels every tracked builder without leaving a worker or writer task behind.
The Runtime reports single-flight build count, owner bytes read, owner rescan
count, retained owner count, tombstone count, disk-byte delta, RSS delta, and
control-plane latency through the resident telemetry buffer.  The normative
gate is 256 concurrent callers with one build, zero unchanged owner rescans,
changed-owner-only reconstruction, and thirty-run admission p99 below one
millisecond.

** Canonical item identity and atomic projection generations

Exact search identity is a language-neutral typed tuple.  Every registered
language provider MUST project the tuple fields that apply to its grammar:

- =kind= identifies the parser-owned declaration category;
- =symbol= identifies the declaration name;
- =lexicalOwner= identifies the nearest enclosing declaration when the item is
  nested;
- =implementationOwner= identifies the implemented type or receiver;
- =traitOwner= identifies the implemented interface, trait, protocol, or
  equivalent language construct.

Absent dimensions are omitted, never guessed and never encoded as empty text.
Two items with the same =kind= and =symbol= remain distinct when any owner
dimension differs.  A provider MUST NOT collapse an inherent method, a trait
method declaration, and a trait implementation method into one selector.

ASP owns workspace identity, Git/worktree scope, snapshot evidence, generation
publication, and resident lifecycle.  A language provider owns package-manager
scope parsing and syntax projection.  The provider receives an ASP-selected,
bounded batch of changed owner snapshots; it MUST NOT rediscover or rescan the
worktree.  The batch header carries only paths, leaf digests, and byte lengths;
owner bytes follow as bounded length-delimited frames.  Source bytes MUST NOT
be base64-expanded into a generation JSON document.  One batch response
contains owners, canonical item identities, selectors, relations, and the
source leaf digests from which they were parsed.  Projections for unchanged
owners are reused from the previous complete generation by digest identity.

Every relation is attributed to exactly one owner projection.  Its =from=
endpoint MUST be either that owner node or an item identity emitted for that
owner in the same validated batch.  ASP rejects an edge whose source identity
cannot be joined to its emitting owner; it MUST NOT infer attribution from a
language-specific endpoint kind.  The generation store persists owner
attribution with the edge.  An incremental successor clones edges attributed
to unchanged owners, removes all edges attributed to changed or tombstoned
owners, and inserts only the newly validated edges for rebuilt owners.

ASP MUST partition generation projection into ordered, short-lived provider
processes before writing a batch frame.  The default admission bound is at most
32 owners and at most 4 MiB of aggregate owner source bytes per process; an
individual owner that exceeds the byte bound is admitted alone and remains
subject to the Provider Execution Gate.  ASP consumes and validates each batch
response before starting the next batch, so a provider never retains the ASTs
or response graph for a complete large workspace.  Batch partitioning is
language-neutral ASP policy: a Scheme, Python, Rust, or future provider parses
only the bounded owner bytes supplied to that invocation and MUST NOT retain a
resident workspace index after exit.

The per-workspace Tokio writer lane builds a complete next generation off the
read path.  Owner bytes, canonical selectors, relations, moves, tombstones,
root-depth evidence, MemoryBackend state, and the immutable mmap segment are
validated together and published with one epoch transition.  Readers retain a
lease on the previous complete generation until publication succeeds.  A
generation with owner bytes but missing required provider projections is not
admissible.

Search and exact query are immutable consumers.  They MUST NOT invoke a
provider, open or bootstrap Turso, refresh activation, write manifests, or
repair a generation.  Filesystem change observation and stale-generation
reconciliation belong to the resident Tokio supervisor and the affected
workspace writer lane.  Different workspaces reconcile independently; one
workspace has one writer lane and an adaptive resident read pool.

Health and cache status read only the resident status snapshot.  A live process
with a stale admitted generation is =reconciling= or =degraded=, never
=healthy=.  Installed performance gates MUST exercise cold admission, warm
reads, multi-workspace parallelism, multi-session contention, move/tombstone
publication, and provider projection completeness.

** 10.05.50 Adapters and transports

A Host sandbox denial that prevents a local Runtime or workspace-owner Unix socket from being opened before any protocol frame is exchanged is a typed execution-capability boundary, not an endpoint transport failure. ASP MUST classify it as =host-local-ipc-permission-denied= instead of leaking platform error text. A parser-native lexical command MAY continue through the activated provider's registered bounded lexical surface, under the same process timeout, output, descendant, and memory guards as any provider invocation. Its receipt MUST name the degraded route and reason and MUST NOT claim resident generation, Memory Search, or source-index evidence. Endpoint decode, schema, workspace identity, peer identity, post-connect framing, and authority-validation failures remain terminal. Exact projection may use an analogous live-owner route only when the Provider Registry declares the required native-owner projection capability for that language; otherwise it remains fail closed.

The degraded provider-native invocation MUST be materialized from the selected
method descriptor's =provider-method-argument-projection.v1= contract.  The
projection is a closed token AST: each output token is either a literal or one
of the named, typed facade slots =query=, =workspace=, =presentation=, and
=owner=.  It MUST NOT contain shell source, evaluation, arbitrary formatting,
or provider/language-specific dispatch branches.  Lexical projections may map
only =query=, =workspace=, and =presentation=; =owner= is admissible only for
owner-scoped methods.  Token order is registry order and therefore produces
deterministic argv.  A missing projection, an undeclared field, a missing slot
value, an unsupported schema version, or an invalid method/slot combination
MUST fail closed as
=provider-native-argument-projection-unavailable= before provider execution.

* CLI adapter boundary

CLI remains useful for:

- human inspection;
- deterministic debugging;
- CI and shell composition;
- provider conformance tests; and
- environments without a native agent tool transport.

The CLI SHOULD expose a small stable adapter over graph actions. It SHOULD NOT
require an agent to synthesize a large command grammar before it can navigate
evidence.

A complex CLI command is justified only when it represents a stable human or
automation workflow that cannot be expressed as a bounded SearchLoop action.

* Interaction receipt

Every loop step SHOULD emit a compact interaction receipt containing:

- prior evidence-state identity;
- selected graph action;
- semantic owners consulted;
- new evidence nodes or conclusions;
- rejected alternatives and failed predicates;
- updated frontier;
- recommended next action;
- token and interaction-round cost; and
- cache identities consumed or produced.

The receipt is designed for direct agent consumption and machine audit.

* Optimization objective

Search quality is multi-dimensional. The protocol seeks to minimize:

#+begin_example
graph path length
  + returned evidence tokens
  + interaction rounds
  + repeated uncached work
#+end_example

subject to:

#+begin_example
semantic ownership
  + proof-path validity
  + fail-closed admission
  + receipt completeness
#+end_example

No single metric may be reduced by hiding an unresolved proof obligation.

* Cache distinction

Search/evidence caching and model prefix caching are separate:

- evidence caching reuses a conclusion only when semantic owner identity and
  validation policy permit reuse;
- model prefix caching reuses inference computation when prompt prefixes align.

A model cache hit does not validate evidence. An evidence cache miss does not
imply a model cache miss.

* Proof obligation

** Exact-selector active-generation admission

The active-generation proof is parameterized by an operation-scoped provider
closure.  For an ordinary language =search=, language-scoped source-index
lookup, or exact =query=, that closure contains only the selected provider and
its explicitly declared provider dependencies.  Installed receipts, registry
membership, or workspace file extensions MUST NOT widen the closure.

The detailed provider-publication and native-owner transport obligations remain
at the historical compatibility locators below until phase-two physical tree
migration.  Their normative owner is this graph-first RFC:

- [[file:10.05-cli-first-harness-ux/10.05.62-provider-scoped-lazy-activation-and-runtime-publication.org][10.05.62 Provider-scoped lazy activation and runtime publication]]
- [[file:10.05-cli-first-harness-ux/10.05.63-native-incremental-owner-capability-admission-v1.org][10.05.63 Native incremental owner capability admission]]

Admission MUST prove both provider-closure isolation and schema/transport
congruence.  A successful provider process invocation is not sufficient when
the runtime request or response field set differs from the published JSON
schema, and a project-scoped receipt is not sufficient when a read route still
materializes unrelated providers.

An exact structural selector is a stable semantic name, not proof that its
owner still belongs to the active workspace generation.  Before returning a
projection or an owner diagnostic, the Runtime Server MUST bind the read to
one admitted generation and return both its generation digest and source root
digest.

Resolution against that generation has four disjoint outcomes:

- =resolved=: the selector and owner are members of the same active generation;
- =selector-stale= / =selector-not-in-active-generation=: the owner is absent
  from the active generation, including a removed or moved owner;
- =item-missing= / =item-not-in-live-owner=: the owner is active but the named
  item is absent; and
- =kind-mismatch= / =snapshot-item-kind-mismatch=: the symbol exists in the
  active owner under another item kind.

=owner-missing= / =owner-not-in-workspace= is not a valid exact-selector
result because it loses the generation-admission fact and encourages replay of
an owner command for a path already proven absent.  A =selector-stale= receipt
MUST recommend symbol-oriented SearchLoop discovery in the active generation;
it MUST NOT recommend owner-items for the absent path.

The owner-items search surface may still observe =owner-missing= before an
exact selector exists.  That search failure is not an exact-selector result and
MUST be projected as the bounded
=agent.semantic-protocols.search-owner-missing-topology= packet.  The packet
binds the requested language, active generation and root digests, missing owner,
provider-resolved ProjectResolution/source-scope evidence, and one typed search
action.  It MUST NOT paste source, invoke a provider, rescan the workspace, or
repeat the failed owner-items command.  Its project and source-scope nodes come
from the admitted Runtime Server generation; native candidates do not define
workspace membership.

Static hook activation declares provider capabilities only.  Git candidate
identity, package-manager project resolution, source scope, selector inventory,
and exact projection are one Runtime Server generation transaction.  No CLI,
Hook, or Search adapter may independently infer workspace membership or open a
workspace database to repair this result.

The installed Global provider catalog and active artifact receipt are the
immutable executable-identity authority for the query data plane.  A language
runtime projection MUST consume that published identity and MUST NOT hash or
read provider/runtime executable bytes during =search= or =query=.  APIs that
construct a registered-language runtime therefore require an explicit receipt
locator; an absent locator is a lifecycle admission error, not permission to
fall back to byte hashing.

=search owner <path> items= and exact-selector projection are resident data
plane reads.  Both MUST route before activation construction and MUST consume
the already admitted immutable generation without provider context, provider
spawn, database open, or control-socket roundtrip.  A missing generation is a
lifecycle admission failure; the read command MUST NOT repair it.

Workspace admission is a two-phase typed lifecycle.  An
=admit-runtime-generation= receipt in =building= state records accepted work;
it does not authorize the following exact query.  =session-start=,
=user-prompt=, and =pre-tool= MUST follow admission with
=ensure-runtime-generation= and may release the client tool call only after a
validated =ready= receipt.  =building= and =failed= remain fail-closed.  This
ordering is owned by the Hook/Runtime Server contract, not by a retry loop in
the exact-query CLI.

The foreground admission operation and the explicit-query gate are distinct
typed operations.  The former may return =building= immediately after the
resident writer lane accepts work.  The latter MUST ask the Runtime Server to
observe that same single-flight attempt through its terminal transition and
MUST return only a validated published-generation readiness receipt.  An
admission-catalog =ready= entry alone is insufficient after daemon restart:
the gate must also prove that the canonical generation lease and Memory Search
pointer are open in the current Runtime Server process, restoring the committed
immutable generation when the persistent receipt is valid.  Pointer existence,
resident generation identity, or a matching generation digest alone is not a
durability proof.  Reuse requires a successfully decoded current-schema pointer
whose workspace identity and generation digest equal the resident generation.
An incompatible pointer MUST be republished through the per-workspace writer
lane; the old generation remains readable until =DurableReady= commits the new
pointer.  A terminal readiness receipt MUST NOT be exposed as durable before
that commit.  It MUST NOT poll from the CLI,
create another build, infer readiness from a timeout, or translate =building=
into success.  A failed terminal receipt or transport error MUST make the
explicit ASP =pre-tool= decision fail closed; recording a non-blocking
diagnostic while allowing the command violates the generation gate.

Once the Hook releases the command, exact projection remains a read-only data
plane operation: shared Memory Search authority is consulted without socket,
filesystem, Turso, provider, or scheduler work, followed by owner freshness
and selector projection inside the admitted immutable generation.  Search and
query adapters MUST NOT call =ensure-runtime-owner=; filesystem observation,
provider projection, and owner overlay publication are watcher/writer-lane
operations.  A read encountering an unadmitted or incomplete generation fails
closed and MUST never manufacture one.  Thus the only legal cold order is
=Hook ensure-terminal-ready -> writer publication -> exact projection=, while
the legal warm order reuses the already published terminal receipt and mapped
generation.

Explicit admission and observation are different operations.  A later
=admit-runtime-generation= for a =ready= workspace MUST be accepted so the
incremental builder can detect a Git/package-manager generation change and
atomically publish its successor.  =ensure-runtime-generation= and daemon
catalog restore MUST only observe the current attempt to its terminal state;
they MUST NOT schedule a second build when the admitted attempt completed
between the two IPC requests.  =building= remains the only single-flight
exclusion state, and repeated daemon restore remains idempotent.

Provider source envelopes bind two deliberately distinct digests.  The
=addressProviderDigest= is derived from the admitted provider registry and is
used only to locate the canonical envelope.  The nested
=sourceSnapshot.providerDigest= commits the provider-owned project resolution
and source semantics.  Publication and lookup MUST validate both fields; using
either digest in place of the other is an identity error, not a cache miss.

The Lean model under =packages/proofs= must establish at least:

- every =resolved= projection is generation-equal to the active generation;
- an absent owner cannot be classified as a resolved or live-owner item miss;
- an active owner with an absent selector cannot be classified as stale-owner;
- publication changes the visible selector set atomically with its generation;
- a =building= or =failed= admission cannot release an exact query; and
- resident readiness plus pointer existence cannot release a query unless the
  pointer is current-schema and generation-equal to the resident generation;
- recovery from a stale selector never reuses the absent owner as authority.

Future proof work must evaluate not only safety but search efficiency:

- whether a new receipt shortens a justified graph path;
- whether a cache layer avoids recomputation without under-binding identity;
- whether an extra loop turn is logically necessary;
- whether a projection returns the minimum sufficient evidence; and
- whether a CLI addition duplicates an agent-native graph action.

** Provider Register is a bounded reference index

The shared Provider Register MUST NOT inline every language's method inventory,
method descriptors, query pack, and schema inventory.  Its durable root is a
bounded index whose entries contain only =languageId=, =providerId=, and a
descriptor =$ref=.  The referenced registration descriptor is owned by the
language provider and carries that provider's complete registration contract.

Reference resolution is a packaging boundary, not a runtime checkout read.
The build MUST resolve every referenced descriptor, verify that its
=languageId= and =providerId= match the index entry, and bundle the resolved
registry into the ASP artifact.  Runtime dispatch, method lookup, and catalog
identity continue to consume that resolved registry.  Registry and provider
descriptor digests therefore cover resolved descriptor content; hashing only
the reference path is invalid.

Resolution MUST fail closed for a missing reference, an absolute or
parent-traversing path, identity drift, duplicate references, duplicate
languages, or method-inventory drift.  Registering another language adds one
bounded index reference plus its provider-owned descriptor.  It MUST NOT add a
language-specific branch to the CLI or a hard-coded language list to the Rust
loader.
