* Decision

ASP exposes one SearchLoop data plane:

#+begin_example
typed request client
  -> shared agent-semantic-client
  -> ClientFrame gRPC/Tokio stream
  -> Host-admitted transport binding
  -> ASP Runtime Server admission
  -> resident provider/generation/search authority
  -> typed terminal receipt and client presentation
#+end_example

The CLI, Hook, Live Corpus, native integrations, and language clients are equal
clients of this route.  They do not own provider execution, workspace
generation, cache construction, projection truth, lifecycle recovery, or a
semantic fast path.

The Runtime daemon mounts the public =AspClientFrameService= through both the
=AspClientGrpcService= gRPC adapter and the =serve_http_json= HTTP/JSON
adapter.  Both adapters consume the same transport-neutral =ClientFrame=
schema, method catalog, lifecycle admission, and dispatcher; neither adapter
may parse a method into a second route or provide a fallback.  Runtime audits
the existing =data_socket= before endpoint allocation; it does not create a
fourth semantic authority.

Host-native clients use the Runtime-published loopback HTTP/2 endpoint.
Restricted clients receive an already-connected descriptor from the Host and
never discover, bind, or connect a socket themselves.  A filesystem socket,
client-local endpoint derivation, and retrying a denied connect in a broader
permission domain are not admitted transports.  The endpoint record and an
inherited descriptor are two bindings to the same =AspClientFrameService=,
not two semantic dispatchers.  HTTP/JSON remains a debug adapter over that
same service and therefore produces the same typed terminal semantics.

** LSP lessons are negative requirements

SearchLoop does not copy the request-time process composition of LSP.  The
following historically common LSP failure modes are explicit countermodels:

- initialization state scoped to a client process rather than an immutable
  workspace generation;
- capability discovery that advertises a method before its lifecycle and
  terminal route exist;
- request-time server spawning, socket discovery, reconnect, or client retry;
- mutable text/document caches treated as semantic membership authority;
- cancellation that drops a client future but leaves unowned background work;
- dynamic registration or a compatibility command that creates a second
  dispatcher; and
- cross-process chaining of independent features on every interactive read.

ASP improves on LSP by moving all expensive cross-language work to generation
construction and mutation admission.  A Ready Search/Query is a single
generation lease followed by bounded Rust reads over one fused immutable
artifact.  Transports are ablatable, capabilities are generation-bound, and
every request emits exactly one typed terminal without fallback.

A selected-language demand carries only an internal provider work hint.  It
cannot choose collection scope, generation membership, or publication shape.
Generation construction inventories the workspace once, derives the complete
current provider and owner membership, and publishes one complete successor.
The hinted provider may be scheduled first, but publication cannot omit
unhinted admitted owners.  Publishing a selected provider or changed-owner set
as if it were a complete workspace generation is forbidden: a later demand
would erase earlier membership and recreate LSP-style per-language state.  Cold
and mutation admission use the same =CompleteGeneration= linearization point.

Project isolation has one composite key authority.  State Core derives
=ProjectId= from repository identity and =WorkspaceId= from the canonical
checkout binding.  Admission, single-flight lanes, resident generations, and
cache partitions MUST key on the indivisible =(ProjectId, WorkspaceId)= pair.
The absolute project root is validated content used to locate source bytes; it
is not a third partition key.  The same =WorkspaceId= may exist under distinct
projects without aliasing, while a request presenting an existing pair with a
different root is identity drift and fails closed.

This decision deliberately starts from LSP's real trade-offs rather than a
generic client/server analogy.  The official LSP architecture puts each
language analysis tool in a separate process and negotiates client/server
capabilities during =initialize=; the reference implementation also maintains
an incrementally synchronized document mirror through open/change/close
notifications.  Those mechanisms solve editor/tool M-by-N integration, but
they are not admitted as ASP Search authority.  See the upstream
[[https://code.visualstudio.com/api/language-extensions/language-server-extension-guide][Language Server Extension Guide]] and
[[https://microsoft.github.io/language-server-protocol/specifications/specification-current][current LSP specification]].

ASP retains LSP's useful separation of language-specific analysis from the
client, then removes the request-time authority that causes lifecycle and
freshness ambiguity:

| LSP mechanism | ASP hard cut |
|-
| per-client =initialize= capability state | generation-bound server catalog |
| client-maintained document synchronization | content-addressed source snapshot |
| independent language-server process hop | lazy construction worker, absent from Ready reads |
| dynamic registration | immutable admitted capability set |
| request cancellation notification | server-owned attempt with exactly one terminal |
| reconnect/restart recovery | Host-supervised binding plus typed unavailable terminal |

The table is normative.  A Rust type, schema, CLI alias, adapter, or provider
that reintroduces the left-hand authority is legacy and MUST be removed rather
than hidden behind a compatibility feature.

LSP also teaches a less visible lifecycle lesson: a client-visible
=initialize/start accepted= acknowledgement is not service readiness.  ASP
therefore does not admit =SpawnAccepted= or =Starting= as the terminal of a
Search/Query request.  Bootstrap owns the spawned attempt until the Runtime
publishes either the exact Healthy transaction identity or one typed Failed or
Cancelled terminal.  A client never polls a guessed endpoint path, and it
never derives a second endpoint location from State Home.  The endpoint path
and transport identity are values published by the elected Runtime owner.

Schema catalog publication follows the same rule.  Deleting a schema while a
schema family still names that path is a torn publication and MUST fail before
Runtime activation.  Removing a capability deletes its schema, family
membership, method catalog entry, artifact member, and dispatcher route in one
reviewed change.  Runtime startup is not a late garbage collector for stale
schema membership.

Schema Manager executes during the Rust artifact build/publication boundary,
not during daemon bootstrap.  It emits one deterministic catalog that is
embedded in the Runtime binary and therefore covered by the active bundle's
content digest.  Runtime startup only decodes and validates those immutable
bytes.  It MUST NOT locate =CARGO_MANIFEST_DIR=, read a checkout schema tree,
materialize package copies, or repair registry membership.  This moves schema
drift from a post-install availability failure to a pre-publication build
failure.

The build boundary itself is read-only.  It consumes Schema Manager's
=resolve_bundles= value API, which returns canonical closure bytes, document
digests, root-set identities, and the bundle digest without a destination
path.  Calling =materialize= from =build.rs= is forbidden: Cargo would mutate
downstream packages while compiling and then treat those mutable copies as its
own input.  Materialization remains an explicit publication command for
external language packages; embedded Rust consumers receive the same
declarative closure directly from the manager.

Cancellation has two orthogonal dimensions: terminal outcome and diagnostic
payload.  The correlated request emits exactly one =Cancelled= response frame;
that same frame MUST carry a typed =client-request-cancelled= diagnostic and
MUST NOT carry a result or catalog.  The diagnostic is not a second terminal
and does not change the outcome to =Error=.  Conversely, a client MUST reject a
bare =Cancelled= frame, an =Error= frame labelled as cancellation, a mismatched
request identity, or any cancellation response that also carries successful
result data.  This separation avoids the LSP-era ambiguity where cancelling a
local future, receiving a protocol error, and stopping server work could be
mistaken for the same event.

Atomic resident activation is owned by

* Naming

The canonical short name is =SearchLoop=.

=Interactive= means each agent turn observes a typed evidence state, chooses a
bounded action, receives a compact receipt, and advances a session frontier.
It does not mean a terminal prompt or human menu.

=Graph-first= means semantic owners, items, dependencies, capabilities, and
proof obligations are typed nodes and edges.  Commands transport graph
operations; command strings are not the ontology.

=Progressive= means each turn expands only the evidence needed for the next
decision.  It never weakens fail-closed authority or permits best-effort source
claims.

* Primary loop

The canonical state transition is:

#+begin_example
intent
  -> admitted workspace/provider authority
  -> typed seed topology
  -> bounded evidence route
  -> compact inspection
  -> focused expansion or exact materialization
  -> receipt-backed conclusion, reroute, or stop
#+end_example

Loop state, rather than a command transcript, is the durable protocol object.
A user-supplied exact selector enters the same topology as any other seed.  It
does not create a second text protocol.

Interactive transition semantics are owned by
[[file:10.05-interactive-graph-first-progressive-searchloop/10.05.10-interactive-searchloop/00-overview.org][10.05.10 Interactive SearchLoop]].

* Search/query wire and replay contract

Search and exact query are two operations on one public =ClientFrame= data
plane. The language CLI is only a typed adapter: it selects =search= or
=query=, supplies the schema-owned parameters, and renders the returned frame.
It does not create a provider route or interpret a URL/string heuristic.

Every successful or terminal frame carries the same workspace identity,
provider identity, generation identity, source-snapshot identity, request
identity, and schema references. Search results carry the typed =routeGraph=,
=actionFrontier=, and =recommendedNext= fields; query carries the canonical
structural selector and the declared source or projection kind. A query may
consume a selector produced by search only after the Runtime Server validates
that selector against the active immutable generation and source snapshot.

Admission is server-owned and precedes provider work. A cold search/query
request first reaches a single-flight generation admission, observes its
queued/building transition, and waits for one terminal receipt before reading
or dispatching a provider. =Queued= and =Building= are intermediate states,
never query results and never successful no-match evidence. A failed,
cancelled, stale, torn, or cross-generation admission is a typed terminal
error; it cannot fall back to a local provider or cached source.

Replay is identity-bound: replaying the same request against the same
workspace, provider, generation, source snapshot, selector, and schema
references is deterministic; a changed request nonce or any changed identity
must produce a new request and cannot reuse the prior terminal. Search and
query terminals therefore preserve the original request identity and expose
the server-owned error reason and next action without silent retry.

* Global invariants

** One lifecycle authority

ASP Runtime Server owns workspace identity, provider admission, lazy resident
activation, generation publication, bounded concurrency, cancellation, drain,
and lifecycle receipts.  A request client owns none of this mutable state.

Query handling never starts, repairs, restarts, or locally executes a provider.
Runtime absence and provider unavailability are typed terminal evidence, not
permission to construct an alternate route.

Every Search/Query request and terminal binds the same =ProjectId= and
=WorkspaceId=.  The binding is present in both the ClientFrame envelope and
the persisted operation terminal so detached receipts remain attributable.
=workspaceIdentity=, =projectRoot=, an endpoint path, or an activation counter
MUST NOT appear as an alternate partition key.  Stage, publication, resident
lease, search fan-in, and exact-query projection all reject a project or
workspace mismatch before observing or mutating active generation state.
Live Corpus cold/warm/release receipts use the same pair and never expose a
mutable =globalCacheMutationCount=: there is no global cache partition or
global mutation authority.  A cold/release action can only compare-and-mutate
the exact project/workspace resident generation named by the request.

Every public operation that measures or consumes Search/Query semantics enters
the same Runtime activation admission before opening the data plane.  This
includes language facades and formal Live Corpus qualification.  Qualification
MUST NOT construct =AspClient= directly against an endpoint path and thereby
bypass supervisor admission.  It may wait for a newly admitted Runtime to
publish =Healthy= before the measurement phase begins; that bounded startup
wait is recorded separately and is never counted as a Ready-query latency.
Once measurement begins, the benchmark uses the identical resident gRPC
service, catalog, generation lease, cancellation registry, and terminal rules
as =asp <language> search/query=.  A benchmark-only daemon, socket, or recovery
path is a second lifecycle authority and is forbidden.

=Healthy endpoint= and =committed resident transaction= are not synonyms.  A
new owner can publish a reachable endpoint before its applied activation
receipt becomes atomically visible.  Supervisor admission MUST therefore wait
until the reachable endpoint, owner-spawn receipt, applied activation receipt,
publication nonce, artifact path, and content digest all describe the same
transaction.  Endpoint health without that identity closure remains
=Starting=; it is never returned as Ready and is not repaired by client retry.
This rule closes the same initialization race that LSP clients commonly paper
over with reconnect loops, while preserving a single Runtime authority.

Tokio task ownership, generation-attempt terminalization, and telemetry
isolation are owned by
[[file:10.05.11.05-runtime-server-tokio-task-lifecycle.org][10.05.11.05 Runtime Server Tokio Task Lifecycle]].

** Language-scoped lazy admission

A language facade resolves through the registered provider catalog to exactly
one provider identity.  A language-scoped search, query, check, or cache
operation does not widen to a complete-generation or all-provider operation
when an index-owner argument is absent.

Only an explicitly unscoped operation may request global coverage.  Runtime
evidence for a language-scoped operation therefore reports no unrelated
provider process or preparation work.

The same boundary applies before a generation exists.  A targeted demand
constructs =requiredLanguages= from the selected provider identity alone; it
does not enumerate every language detected in the repository.  An absent,
cold, or uninstalled provider for another language cannot turn the selected
request into =query-not-ready=.  Only an explicit =CompleteGeneration=
transaction may fan in the repository-wide provider set.

Provider package, registration, and server authority are owned by
[[file:10.05.61-language-provider-server-authority.org][10.05.61 Language Provider Server Authority]].

** Typed topology before rendering

Every SearchLoop entry constructs stable nodes, directed typed relations, and
typed action-frontier entries before compact rendering.  Canonical selector
validation precedes any =owns_item= or =targets_item= relation.

Presentation ordinals and rendered =recommendedNext= text are not durable node
identities.  A malformed or cross-language selector may remain as unresolved
input evidence, but it produces neither an owner/item relation nor an
executable exact-query action.

Evidence topology and route selection are owned by
[[file:10.05-interactive-graph-first-progressive-searchloop/10.05.20-evidence-graph-routing/00-overview.org][10.05.20 Evidence Graph and Routing]].

** Active-generation authority

A search or exact query reads one admitted immutable generation.  =Ready=
means coverage is proven for the requested workspace owner and provider; an
empty or uncovered generation is not a successful =no-matches= result.

The active generation is the sole membership authority.  Provider fingerprint
storage and retained bytes are caches, not membership truth.  Concurrent
generation demand is single-flight and attempt-bound.

Before a language Search or Query reads =Ready= state, Runtime discovers the
current workspace candidate and submits or coalesces that exact candidate at
the server-owned admission authority.  A previously =Ready= resident whose
candidate or policy identity differs is never read.  =Queued=, =Building=, or
publication lag returns typed =query-not-ready= evidence; the transport does
not wait for construction and does not retry.

Memory ownership and capability-lazy indexes are owned by
[[file:10.05.11.09-runtime-generation-memory-authority.org][10.05.11.09 Runtime Generation Memory Authority]].
Generation publication and readiness are indexed by
[[file:10.05-interactive-graph-first-progressive-searchloop/10.05.20-server-resident-search-generation/00-overview.org][10.05.20 Server-Resident Search Generation]].

** Exact selector and source authority

Exact source materialization accepts one parser-owned structural selector and
returns only the projection declared by the typed operation.  Search-derived
projection and exact source are distinct operations and cannot reinterpret one
another after failure.

Owner discovery is not exact projection.  It may return canonical item
selectors without creating a workspace generation, but it cannot manufacture
source bytes or an exact-query success.

The selector chain is owned by:

- [[file:10.05.11-canonical-item-query-authority.org][10.05.11 Canonical Item Query Authority]];
- [[file:10.05.12-exact-selector-provider-generation-authority.org][10.05.12 Exact Selector Provider Generation Authority]]; and
- [[file:10.05.17-resident-exact-query-authority.org][10.05.17 Resident Exact Query Authority]].

** Request-independent generation work

Public requests submit or coalesce generation demand and observe the current
typed phase.  They do not wait inside the transport future for construction to
finish.  Dropping a request never detaches or silently cancels admitted work.

Every accepted attempt owns exactly one terminal publisher.  =Queued=,
=Building=, =Ready=, =Failed=, and =Cancelled= are Runtime states; client
timeouts, sleeps, polling, and elapsed-time repair cannot create transitions.

Incremental cache and mutation ownership are specified by
[[file:10.05-interactive-graph-first-progressive-searchloop/10.05.70-runtime-owned-incremental-cache-v1.org][10.05.70 Runtime-Owned Incremental Search Cache]].

** Atomic publication

Candidate generation, source root, provider/schema identity, projection
capability, and resident locator advance as one validated publication.  Readers
observe either the previous complete generation or the successor complete
generation.

A request's language/provider target narrows construction work, never the
published authority.  The single-flight builder starts only that provider and
collects its complete current owner, relation, and ProjectResolution
membership.  It then replaces the previous membership for the exact
language/provider authority in the active immutable base and publishes the
result as one =CompleteGeneration=.  Unselected providers, their source blobs,
relations, and ProjectResolution receipts are carried forward byte-for-byte.
The first targeted demand on a cold workspace is the initial complete member
set.  Publishing the target-only candidate directly, or rescanning every
registered provider for one language demand, is forbidden: the former erases
active languages and the latter destroys lazy provider isolation.

Provider coverage ranges only over programming-language registrations.  Org
and Markdown are embedded document surfaces and therefore contribute document
owners to the workspace generation without contributing provider identities,
provider artifacts, or provider processes.  A missing =asp-org= or =asp-md=
artifact can never be a legal =query-not-ready= cause because those artifact
authorities do not exist in the server-first architecture.

For a complete source-index successor, every non-=@scope/= file-hash record
belongs to exactly one admitted owner.  Overlay construction derives that
membership from the successor owner set and removes orphan hashes from the
active base before computing the content Merkle root.  Projection evidence may
remain under =@scope/=, but it is never a workspace source leaf.

No install client, provider, request handler, or cache command may repair or
advance persisted Runtime authority directly.  Publication and serving
activation remain separate transactions with explicit Ready evidence.

** Bounded streams and cancellation

All request fan-out/fan-in uses the workspace Tokio runtime, bounded channels,
deterministic ordering, and one cancellation-aware request scope.  Pure
in-memory graph, rank, Merkle, and route-cost kernels remain synchronous value
functions inside that task tree.

No SearchLoop path creates a private runtime, unmanaged OS thread, nested
=block_on= bridge, unbounded queue, polling loop, or request-time provider
process.

** Receipts are evidence, not lifecycle repair

Every admitted phase emits an attempt-bound start and exactly one completed,
failed, or cancelled terminal.  Receipts bind workspace, provider, generation,
operation, schema, and relevant content identities.

Telemetry may observe lifecycle but cannot authorize it.  A timeout, missing
event, or old receipt never repairs a state transition.  Search-result reuse
and model prefix-cache reuse remain distinct and separately observable.

Receipt, cache identity, replay, and recovery ownership is indexed by
[[file:10.05-interactive-graph-first-progressive-searchloop/10.05.40-receipts-cache-identity/00-overview.org][10.05.40 Receipts, Cache, and Semantic Identity]].

** Hard cut

Replacing a public operation, endpoint, schema projection, or transport deletes
its old parser branch, implementation, fixture, test, dependency, help,
guidance, and document locator in the same architecture change.

There is no compatibility toggle, legacy executor, fallback route, dual serve,
or version-suffixed Rust namespace.  Shared wire identity remains
=schemaVersion: 1= until a genuinely breaking shared schema requires a new
versioned schema artifact.

Typed resident dispatch removal is owned by
[[file:10.05.70-typed-resident-search-dispatch.org][10.05.70 Typed Resident Search Dispatch]].

* Projection boundary

SearchLoop constructs typed evidence and action-frontier state.  The rendering,
ranking projection, token/byte cost, compact packet shape, and other
agent-facing projection semantics are owned exclusively by
[[file:10.06-agent-search-projection.org][RFC 10.06 Agent Search Projection]].

RFC 10.05 does not duplicate projection syntax or cost formulas.  A compact
renderer consumes typed topology and cannot parse selectors again, invent
owner facts, or choose an action independently.

* Resident lexical recall and explicit coverage

Warm lexical recall MUST use the immutable generation's parser-produced query
keys through a resident inverted index.  Native syntax is part of that same
complete generation, not an independently published attachment.  A query MUST NOT walk workspace
directories, reread owner source, rebuild token sets for every document, or
launch a subprocess.  A mutation invalidates the prior generation and submits
its changed paths only as inventory hints to the sole complete-generation
builder.  No overlay or owner-delta path may mint a Search generation.

Generation admission compiles owner paths to dense generation-local
=OwnerId= values and compiles every normalized term to a sorted, duplicate-free
posting list of those IDs.  The string path and full parser-produced owner
vocabulary remain immutable generation data; they MUST NOT be copied into a
request-local score map.  A non-exact query intersects or counts integer
postings, maintains a deterministic bounded Top-K frontier, and materializes
paths/digests only for the final frontier.  Full candidate-set sorting,
per-request =HashMap<&str, score>= construction, and cloning every owner's full
=queryKeys= vocabulary are not admitted Ready-path effects.

The hit's existing =queryKeys= field carries only the bounded normalized terms
that contributed to that hit in this query.  It is not a copy of the owner's
complete lexical vocabulary.  The complete vocabulary remains behind the
generation authority for graph/ripgrep planning.  This is a v1 semantic
clarification with the existing field shape, not a second result schema.
Correctness and the sub-millisecond Ready budget MUST hold on a cache miss;
generation-local query memoization may accelerate exact replay but cannot be a
latency prerequisite or freshness authority.

Cold lexical recall is the bounded rg-equivalent executor over resident bytes,
not a cache or durable index authority.  File discovery executes once while
constructing the immutable inventory; Runtime MUST NOT spawn =fd=, =exa=, or
=rg= from the query path.  Every returned record is proven against a committed
owner blob: workspace membership, owner content digest, and exact line bytes
MUST all agree with the immutable source generation.  A missing owner, stale
blob, or stale line fails the cold request; partial candidates are never
returned.

The content generation consists only of one Runtime-owned =fd=/ignore inventory,
admitted owner bytes, and their content/Merkle identity.  Request admission is
keyed in constant time by the admitted ProjectId, WorkspaceId, provider binding,
and Runtime mutation epoch; it MUST NOT perform a Git/repository walk.  The
builder derives source identity once from the inventory paths and bytes.  Once those facts
validate, Runtime atomically publishes that generation and cold recall becomes
available immediately.  Provider-native syntax is already parser-owned data in
that immutable generation.  Tantivy, the resident graph, and Python Graphs are
independent derived attachments.  They consume the same immutable content
generation asynchronously; none participates in cold admission, and failure of
one cannot roll back the content generation or the other attachments.

The byte-generation linearization point precedes Source Index database
persistence.  Canonical resident publication validates the complete owner set,
ProjectId, WorkspaceId, source root, provider digest, and generation digest,
then publishes the immutable reader and its Ready notification as one ASP
Server transaction.  Turso subsequently persists the same exact identity as a
durability attachment.  A database commit, WAL flush, source-index row rebuild,
or database connection lease is therefore forbidden from the cold Search
foreground path.  Its failure emits one typed durability terminal and retains
the last valid resident generation; it cannot reinterpret a complete byte
generation as =Building= or revoke its query lease.

This is not a second authority or an acknowledgement-before-commit shortcut.
The resident generation is itself the committed Search authority; Turso is a
recoverability projection of that authority.  Publication uses one
=(ProjectId, WorkspaceId, contentGenerationDigest)= compare-and-set.  A late or
failed durability attachment for generation N cannot overwrite N+1, and daemon
recovery may restore only a database record whose complete identity equals the
canonical generation record.  If no such durable record exists, Runtime
reconstructs through the same single-flight byte-generation admission instead
of exposing stale rows.

The ASP Server owns exactly one resident generation-builder service for its
process lifetime.  Opening a generation submits immutable facts to that service;
it MUST NOT create an =IndexWriter=, a builder thread pool, or a detached build
task inside the generation object.  The service may retain reusable Tantivy
writer resources and bounded CPU workers, while published generation objects
contain only immutable cold facts and independently completed attachment
results.  Clients, query handlers, and provider processes cannot own or start
the builder.

The resident builder is a control plane, not another generic thread pool.  Its
Tokio task owns admission, bounded queues, cancellation, drain, and join.  A
Tantivy indexing transaction owns Tantivy's segment workers; a graph transaction
owns a separate CPU permit.  Both acquire typed daemon-wide CPU and memory
permits before entering blocking work, so accepting many content generations
cannot multiply the process worker count.  Queue capacity is not a resource
limit and an in-flight counter is not a permit.

The builder exposes one bounded Tokio event stream plus one immutable latest-state
snapshot of derived attachments.  =broadcast + BroadcastStream= preserves every
transition for live consumers and reports lag explicitly; =watch= retains the
latest state for a late subscriber without replaying stderr or polling files.
For each =(ProjectId, WorkspaceId, contentGenerationDigest, attachment)= key the
stream advances through =queued -> building -> ready|failed= with a strictly
positive process-local sequence.  =graph= and =tantivy= are separate keys and
can become Ready in either order.  Every
transition is emitted by the same Runtime-owned task that owns admission and
join; query handlers cannot manufacture attachment events, and an event for
generation N can never make an attachment visible in generation N+1.

Tokio is the lifecycle scheduler, not the indexing engine.  The bounded channel
and daemon resource supervisor own backpressure, cancellation, and shutdown;
CPU-bound graph and Tantivy transactions cross exactly one =spawn_blocking=
boundary after receiving permits.  Tantivy continues to own its internal
segment workers.  ASP MUST NOT wrap each segment in another Tokio task, start a
per-query Runtime, or use async syntax to hide synchronous cold admission.

Resource selection is feedback-controlled and workload-bound.  Its history key
includes build strategy, logarithmic lexical-byte and owner-count buckets, and
changed-owner ratio; observations from unlike workloads cannot be averaged.
Receipts record queue wait, acquired CPU and memory, build/finalize time, and
measured throughput.  Static products such as a fixed fraction of host memory,
bytes-per-owner, owners-per-worker, or “maximum threads” are not an adaptive
policy.  Search exposes engine capability bounds and executes the explicit
resource envelope; only ASP Server selects that envelope from Host capacity,
current permits, and matching observed history.

An unseen workload bucket MUST NOT trigger disposable sample indexes or
successive-halving before its production attachment.  The resident builder
selects one feasible initial envelope from current daemon CPU and memory
permits, workload size, and Tantivy's validity floor, then materializes the
production attachment exactly once.  That real build is the calibration
observation: its strategy, resources, exact content-generation identity,
build/finalize time, and measured throughput are retained for a later matching
generation.  Calibration therefore adds no build to the cold critical path.

The observation is retained under the exact Tantivy engine digest, effective
machine-capacity identity, and workload key.  Runtime restart may reuse it only
when all three identities match; engine, capacity, or workload drift chooses a
new feasible initial envelope and again learns from the single production
build.  A generation can consume an earlier observation, but it cannot use its
own completion to choose a second build.  This admits non-monotonic machines
without encoding one machine's worker or memory result as a product constant.

Every derived request, receipt, and pointer carries the exact
=contentGenerationDigest=.  An attachment becomes visible only if that digest
equals the currently selected content generation under the attachment's atomic
compare-and-set.  A late completion for generation N cannot attach to N+1, and
opening a cold generation never waits for, reconstructs, or synchronously opens
Tantivy or graph state.  Schema version 1 remains the contract; this is a
hard-cut correction of publication ownership, not a parallel version.

Each derived attachment consumes one shared immutable request and materializes
exactly once.  Digest derivation reads the completed immutable attachment; it
MUST NOT materialize a graph or Tantivy index once for hashing and a second time
for publication.  The build result, digest, Ready event, and retained resident
object are four views of the same transaction.

The request declares byte, record, result, and deadline budgets.  Its receipt
is bound to the same workspace root, provider digest, generation, and index
artifact digest as the resident query and includes the digest of the admitted
coverage input.  Lexical postings and query-cache keys include that Merkle
identity; changing any bound digest creates a different immutable index rather
than mutating or aliasing the prior one.  Timeout, truncation, or executor
failure is a typed coverage-lane terminal and never mutates or supplants
resident search authority.  There is no independently persisted =rg= cache,
implicit whole-workspace invocation, or silent retry from lexical or structural
search.

** Resident recall and byte verification composition

The resident lexical index and cold ripgrep output are composed through one
typed route contract, not through an agent-authored shell pipeline and not by
concatenating two result lists.  Cold rg candidates are immediately verified
against immutable owner bytes and native syntax.  Tantivy-ready requests read
the immutable mapping only and never execute ripgrep.  Qualification fixtures
prove that both routes produce the same admitted candidate set and ordering
for the covered query corpus before an accelerator pointer may become current.

The resident byte index uses fixed-width byte grams to select the smallest
generation-bound owner posting set, intersects remaining postings, and verifies
the literal against mmap owner bytes.  Verification is bounded by an explicit
candidate budget.  If a query is shorter than the gram width or its candidate
set exceeds the budget, the result is typed =query-not-ready= rather than an
unbounded scan.  A complete absence claim is admitted only when at least one
gram has an empty complete posting, or every intersected owner was verified.
Thus posting false positives can cost bounded verification but can never create
a false absence.  Construction sharding remains deterministic and constrained
by owner count, argument bytes, input bytes, record count, result count, and
deadline.

The composition has two distinct modes:

1. =verify-candidates= verifies byte-level matches inside a resident Top-K owner
   set.  It improves precision and context extraction, but an empty result is
   only =no-match-in-candidates= and MUST NOT be rendered as workspace-wide
   absence.
2. =prove-coverage= covers the complete committed owner set for the selected
   language and generation.  Only this mode may emit a complete absence or
   coverage claim, and only when every shard terminates successfully and the
   union receipt proves that every admitted owner was covered exactly once.

The typed plan binds query digest, mode, source root, provider, generation,
index artifact, ordered owner identities, shard boundaries, and budgets.  The
result binds the plan digest plus each shard input/output digest.  Duplicate,
missing, stale, or cross-generation owners fail the whole result.  A timeout or
truncated shard cannot degrade into a successful empty result.

Ripgrep JSON is the preferred executor wire format because file paths and match
text may contain delimiter bytes.  The existing vimgrep-compatible coverage
input remains a versioned contract; changing its record grammar requires a new
schema version rather than an in-place decoder change.

The resident index owns recall ranking and incremental per-owner postings.
Ripgrep owns byte-level verification only.  Parser providers own structural
identity and selector projection.  The Runtime owns generation admission,
plan caching, cancellation, and result coalescing.  No layer may rebuild or
persist a second workspace index under the name of ripgrep coverage.

** Source bytes, native syntax, Tantivy, Rust graph, and optional workers

The production system has four logically ordered construction receipts and one
fused Ready read path.  Source-byte acquisition is itself an explicit streaming
pipeline: one resident =fd=/ignore walk owns filesystem inventory and one
bounded rg-equivalent scan owns lexical byte coverage for admitted owners.
Runtime binds both to normalized owner path and content digest before any
derived index may consume them.  A second Git candidate walk, a second
whole-workspace scan, or request-time process discovery is not admitted.
Owner-byte acquisition uses a bounded set of blocking shards derived from the
Host's available parallelism.  Canonically adjacent paths are distributed
round-robin rather than in contiguous chunks, because directory ordering
otherwise clusters large owners on one worker and turns cold latency into the
slowest-directory latency.  Results retain their original inventory index and
are sorted before hashing, so scheduling never changes generation identity.

Once source admission fixes their common immutable identity, each derived CPU
stage executes as an independently admitted node in the resident builder DAG,
outside Tokio worker threads.  Every node joins before publishing its own
attachment; cold content publication does not join either derived node.  Thus
cold wall time contains no Tantivy or graph build, without turning the stages
into request-time commands, RPCs, or publication authorities:

#+begin_src text
complete content-generation admission
  -> one fd inventory + owner bytes
  -> content/Merkle identity
  -> atomic cold-generation publication

Independent Rust resident-graph transaction
  -> lease exact complete content generation
  -> derive graph from the generation's admitted native-syntax relations
  -> validate exact content-generation identity
  -> atomic graph capability pointer publication

Cold Search/Query while lexical accelerator is building
  -> lease exact complete content generation
  -> rg query over only the admitted fd inventory
  -> content-digest and generation-native-syntax verification
  -> Rust resident graph rank -> exactly one typed terminal

Runtime-owned lexical accelerator transaction
  -> submit exact generation to the ASP Server resident builder
  -> content-addressed lexical shard plan using retained writer resources
  -> attach reused Tantivy shards + build changed shards
  -> validate result equivalence against generation-bound rg fixtures
  -> atomic accelerator pointer publication

Tantivy-ready Search/Query
  -> lease exact complete content generation + accelerator
  -> mmap/open Tantivy + Rust graph + byte-evidence plan
  -> deterministic merge -> exactly one typed terminal
#+end_src

The native-syntax playbook consumes the complete provider parser projection:
owner identity, canonical structural selectors, byte ranges, query keys,
derived projections, module facts, and relations.  It is the semantic core of
the playbook, not an owner-only lookup and not a public =search owner= alias.
Every selector has a proper non-empty byte range and at least one normalized
query key; every relation is bound to an owner in the same content-proven
projection.  Duplicate owners, selectors, or relations make the candidate
incomplete and therefore unpublishable.
The agent-facing receipt projects those facts as bounded
=nativeSyntax.projections[]= records.  It MUST NOT collapse them back into an
owner list or selector count: owner is identity, while the selector/range/key/
derived-projection/relation tuple is the semantic capability.

The indexed lexical stage owns broad candidate recall for identifiers,
qualified names, documentation, package paths, dependency names, and error
text.  Tantivy is the production lexical authority.  Direct product code MUST
NOT create a hand-written postings map, CLI-local scorer, or parallel durable
database lexical authority.

Tantivy does not own file discovery, source scanning, or content-generation
admission.  It consumes compact, deduplicated lexical facts from already
content-proven provider/native-parser owners.  Those facts are partitioned by
a stable owner content key into content-addressed shards.  An unchanged shard
is attached to the accelerator candidate by digest; it is not tokenized,
serialized, or merged again.  Only added, changed, or retired owners rebuild
their affected shards.  Shard attachment and changed-shard construction join
before one accelerator commit, so reuse cannot expose a partially current
index and cannot delay publication of the complete content generation.

=rg= is the cold lexical executor, not a second persistent index and not an
ingestion-time whole-repository tokenizer.  Until the exact generation's
Tantivy accelerator is current, Runtime may execute one bounded =rg= query
against the admitted =fd= inventory.  Every candidate is re-bound to the
generation's owner content digest and provider-native projection before it is
returned.  Once Tantivy is current, the same query route performs zero =fd=
and zero =rg= processes.  A later accelerator may replace only the accelerator
pointer for the same complete content identity; it never mutates source,
syntax, graph, or generation admission authority.

Cold performance evidence distinguishes =coldRgQuery= (complete content
generation, accelerator absent), =bootstrapAccelerator= (no prior shard
artifact), =deltaAccelerator= (prior accelerator plus a declared owner change
set), and =firstTantivyOpen=.  The first reports =fd= inventory reuse, bounded
=rg= execution, content verification and native-syntax verification.  The
accelerator phases report reused/rebuilt/retired shard counts, Tantivy
attach/commit, equivalence validation and pointer publication.  Reporting one
monolithic =cold= or =tantivyCommit= duration is insufficient to diagnose or
qualify the cold path.

The Rust resident graph is the base relation authority, but it is not part of
the content-generation publication quorum.  It is independently derived from
the same admitted provider facts and attaches only through the exact content
generation identity.  Cold byte/native-syntax search remains available while
that graph transaction is absent or building.  =asp-python-graphs= is an optional, intent-selected graph
capability: relationship or an explicit Python-graph request requires an exact
Project/Workspace/Generation/root-bound graph session, while lexical and exact
literal requests may remain entirely on the Rust resident generation.  A
missing or stale optional session is a typed capability failure for a request
that requires it; it never blocks publication or falsifies a complete result.

The v1 Python session admits one bounded graph view per exact
Project/Workspace/Generation/root identity.  The Runtime opens that view only
after the Rust generation is admitted, sends bounded entry-node/ranking work,
and releases it when the corresponding Rust generation retires.  Python never
publishes a source generation or owns the active pointer.  Replaying an exact
identity is idempotent; cross-generation seeds, stale roots, cancellation,
capacity exhaustion, and unknown identities fail closed.  A skipped Python
capability starts no worker and preserves the base generation identity.

Python graph and schema tooling runs from an exact lock-derived environment.
Frozen resolution alone is insufficient because it may leave an extraneous
editable distribution and its pytest/plugin entry points installed.  Every
repository-owned Python command MUST exact-sync the declared project before
execution.  A removed harness distribution or old module namespace is a
Legacy authority conflict and is removed from the environment; no forwarding
module, duplicate entry point, or compatibility import is admitted.  Python
remains a bounded graph algorithm worker, while schema, generation, admission,
and terminal authority stay in the Rust Runtime.

Ripgrep is an optional bounded coverage executor, not the name of source-byte
acquisition and not a Ready-query subprocess.  It receives only an ordered
owner set whose membership and content digests are already committed.  A
receipt may claim ripgrep execution only when it carries the actual v1
=RgCoverageReceipt= input digest and the exact generation/root/provider/index
binding.  Resident byte evidence is reported separately.  Copying Tantivy
owners into =verifiedOwnerIds= or using elapsed =0= as an execution receipt is
forbidden.

The production indexed lexical stage is Tantivy and is owned by
=agent-semantic-search=.  It consumes only the owner identities admitted by
the ripgrep-compatible acquisition/coverage stage and emits a deterministic
ranked owner frontier.  A hand-written postings map, CLI-local lexical scorer,
Turso query facade, or Runtime-local ranking loop is not an alternative
production backend.  Turso may persist generation/catalog material, but it
does not own lexical ranking semantics.  Mutation successors use the same
Tantivy field/token/scoring contract after complete-generation publication;
there is no overlay lexical authority.

The content receipts form one ordered refinement. Native syntax is committed
with source bytes at that refinement boundary; accelerator and graph receipts
are independent transactions over the same admitted identity:

#+begin_example
content-proven source-byte acquisition and complete byte membership
  -> provider-native syntax playbook and canonical parser facts
  -> Rust validation, canonicalization, and atomic content publication

exact content-generation identity
  -> independent Tantivy accelerator publication
  -> independent Rust resident-graph publication
  -> optional independent Python Graph session
#+end_example

The output owner set of each stage is a subset of the preceding admitted
candidate set.  A later stage may reorder, annotate, or expand relations among
admitted identities, but it cannot mint an owner, selector, source byte, or
generation identity.  Content publication requires only acquisition and native
syntax to have joined with one exact identity.  Derived workers may finish
later, but attach only after their complete receipt validates against that
published identity.  Reversing the content stages, replaying from a different
generation, exposing a partial derived artifact, or attaching stale work is
fail-closed.

The resident attachment snapshot has exactly one slot per
=(ProjectId, WorkspaceId, attachmentKind)=.  Content digest proves what was
built; a nonzero Runtime generation token proves ordering.  Publishing a newer
=queued= event replaces that slot, while every later event with an older token
is discarded before both the =watch= snapshot and =broadcast= stream.  Thus a
slow Graph or Tantivy build for generation N cannot roll back generation N+1,
and snapshot memory is bounded by active workspaces rather than generation
history.

Every construction lane uses the same workspace, source root, provider set,
schema catalog, algorithm catalog, generation candidate, and owner content
identities.  Publication is rejected unless all required lane receipts have
that exact identity.  The composition receipt records:

- the acquisition, native-syntax, lexical, and graph artifacts and their shared identity;
- indexed-owner coverage, graph frontier/closure state, and ripgrep shard
  coverage;
- the marginal verified-owner gain contributed by each additional lane;
- elapsed time and budgets per lane;
- the chosen ordered route and alternatives that were rejected; and
- residual uncertainty, including unindexed owners, unresolved graph edges,
  unverified candidates, truncation, and stale evidence.

Runtime receipts MUST NOT label these online observations as true recall.
True =recall@k=, MRR, nDCG, and precision require a golden answer set and belong
to qualification/replay.  Online routing consumes calibrated evidence such as
owner coverage, set overlap, graph closure, marginal verified gain, and prior
benchmark calibration bound to the planner digest.  A missing calibration is
typed =uncalibrated=; it does not prevent deterministic routing, but the agent
must see the remaining uncertainty.

The public workspace orchestrator is exactly =asp search playbook=.  It is a
server-owned planner, never an alias for any provider's =search= method.  Given
ProjectId, WorkspaceId, the active content generation, intent, and query, it
emits =workspace-search-playbook-plan.v1= with one deterministic route per
admitted language.  Each route binds language/provider/generation, declared
extensions, =search= or =query=, normalized terms/selectors, budget,
dependencies, and the exact public =asp <language> ...= command.  Unsupported
or unavailable languages are explicit skipped records with typed reasons.

The Server may execute that plan with bounded fan-out/fan-in.  File discovery
occurs once while building the content generation.  Ripgrep may run only on a
cold lexical request before Tantivy readiness and never on a warm plan request.
Lexical and parser indexes remain language-scoped resident inputs.  Python Graph may fuse relationships only
after every route terminal is bound to the same content generation.  There is
no fallback from a missing language route to a workspace-wide provider call.

Conversely, =asp <language> search|query= is strictly the execution data plane
for one registered provider, its declared extensions, and parser-owned facts.
It cannot observe another language's owners and cannot mint a workspace plan.

The fused Ready route policy is intent-sensitive:

| Intent/evidence | Ordered route | Stop condition |
|-
| exact selector with current identity | parser/source direct | selector resolves uniquely; no lexical or ripgrep work |
| conceptual or API query before accelerator readiness | bounded rg frontier -> content/native-syntax verification -> Rust resident graph | verified owner/selector evidence satisfies requested axes |
| conceptual or API query with current accelerator | resident Tantivy frontier -> Rust resident graph -> optional byte evidence | verified owner/selector evidence satisfies requested axes |
| relation, impact, dependency, or ownership query | current lexical frontier (rg cold or Tantivy ready) -> exact Python graph session -> resident byte evidence | required relation witnesses and cited bytes are verified |
| exact literal or diagnostic text | indexed path/profile restriction -> resident byte evidence -> optional Rust graph context | byte match is verified and graph context is sufficient |
| complete absence claim | complete published byte-coverage block | every admitted owner was covered exactly once during publication |

The planner may skip a resident lane only with a typed capability or intent
reason.  Lexical, graph, and byte-evidence reads may fan out as bounded tasks on
the workspace Tokio runtime because they share one immutable mapping; they
join deterministically before encoding.  Candidate union preserves recall;
intersection and graph distance are ranking evidence, not filters that may
discard the only supported owner.  No Ready path starts Python, invokes
ripgrep, performs provider RPC, scans the workspace, reads durable storage, or
discovers an endpoint.

The fused Ready cache is owned by the immutable resident generation.  Its key
binds ProjectId, WorkspaceId, exact source/content generation, normalized query
terms, language/profile/algorithm, lexical frontier, and explicit budgets.  Its
value is an immutable =Arc= projection of the admitted lexical-plus-graph
result; it never retains a writer and never becomes a publication authority.
The atomic generation pointer is the only invalidation boundary.  Receipts
report cache hit/miss, entry count, retained bytes, capacity, shard count, and
zero request-time external work.  Cross-generation or content drift cannot hit
the cache.

The dispatcher MUST NOT hard-code, probe, or infer these lane capabilities.
Generation admission validates the fused receipt once and stores the resulting
capability value beside the immutable resident lease.  Every Ready request reads
that value.  This removes the LSP-style split where initialization advertises a
capability independently from the data snapshot that is expected to implement
it; receipt drift therefore fails admission instead of appearing later as an
empty result or an unreachable method.

*** Generation-bound optional graph stream

=asp_python_graphs= uses its bidirectional gRPC =Session= to admit one bounded
graph projection and perform bounded rank operations for the exact active Rust
generation.  The stream binds project, workspace, source root, generation,
schema/algorithm digests, ordered mutation id, stable frame id, and
cancellation attempt.  Duplicate frame ids are idempotent.  Drift, unknown
fields, invalid owner identities, release, cancellation, stream closure, and
capacity exhaustion fail that optional capability without mutating the active
Rust generation.

The Python process retains only bounded graph views owned by Runtime generation
leases; it retains no publication token or active pointer.  Warm ranking sends
only bounded entry-node/ranking input and never retransmits the full graph.
Release follows Runtime generation retirement.  This preserves Python as a
replaceable graph-algorithm worker without creating a second publication
authority.

*** Search Playbook public surface

The agent-facing discovery command converges on one public surface:

#+begin_src shell
asp <language> search playbook '<query>' \
  [--intent conceptual|relationship|exact-literal|absence-proof] \
  [--scope workspace|owner:<path>] \
  [--coverage candidates|complete] \
  [--max-owners <N>] [--deadline-ms <N>] \
  [--explain compact|full]
#+end_src

Defaults are =--intent conceptual=, =--scope workspace=, =--coverage
candidates=, and =--explain compact=.  =--coverage complete= is admitted only
for an absence-proof request or another policy-authorized complete scan.
=--selector <exact-selector>= is a direct identity route and bypasses lexical,
graph, and ripgrep planning when current.

=seeds= is removed rather than hidden.  =--view seeds=, =--seeds=,
=searchSynthesis.seeds=, and seed-frontier output are not part of the new
contract.  Indexed lexical search emits =candidateOwnerIds=; Python graph
traversal receives =entryOwnerIds= and =entryNodeIds=; the planner emits route
stages and verified evidence.  These names describe identities at a boundary
instead of preserving the old seed product.

=prime=, =pipe=, =lexical=, standalone =rg=, query packs, and provider
frontiers cease to be public agent workflow.  Where an implementation still
needs one of those algorithms during migration, it is invoked through the
playbook planner and cannot appear as a public =recommendedNext= command.  The
playbook receipt contains one chosen stage sequence, compact evidence
correlation, residual uncertainty, and at most one executable next command.
Flags select semantic constraints; they never select a storage backend or
graph algorithm implementation.

Route stages use the stable families =direct=, =acquire=, =reason=, and
=verify= plus a catalog-bound =capabilityId=.  The initial reason capability is
=search.rust-resident-graph=. The base logical lane is owned by the Rust Runtime
and is materialized from the same immutable generation. Optional numerical
analysis is owned externally by the
=meta-relational-reasoning= facade: GQL/PGL are language adapters and bounded
Ascent evaluation is a backend, not an ASP-owned duplicate relation engine.
Those adapters register additional =reason= capabilities; they do not add
another public search command or change the Playbook receipt shape.  A planner
may select Python graph, logical reasoning, or a hybrid from declared intent,
admitted facts, calibrated quality, and budget.  Capability-specific
input/output remains behind its typed adapter while =candidateOwnerIds=,
=entryNodeIds=, verified identities, relation witnesses, closure status, and
residual uncertainty remain the common boundary.  This is the migration seam
from graph ranking to relational logical reasoning without another CLI or
another source-of-truth graph.

* Qualification gates

The architecture is qualified only when all applicable owner gates pass
together:

1. the current endpoint record resolves one bounded Runtime UDS and one public
   ClientFrame gRPC service;
2. production and public-route tests contain no HTTP/JSON or TCP fallback and
   no fourth client socket;
3. language clients, CLI, Hook, and Live Corpus use the shared typed client;
4. concurrent requests coalesce one admitted generation attempt and every
   attempt reaches exactly one terminal;
5. exact source, callable-skeleton, resident search, zero-match, cancellation,
   backpressure, and payload failure cases retain typed identity evidence;
6. warm resident operations perform zero provider launch, filesystem scan,
   database open, publication lock, retry, polling, or lifecycle mutation;
7. OpenTelemetry and Live Corpus expose phase, service, transport, wall,
   memory, work-counter, and terminal evidence without turning thresholds into
   lifecycle correctness;
8. Lean/AXLE audits refine the same single-route, bounded-stream,
   cancellation, publication, and receipt invariants; and
9. Org links resolve, each normative concern has one canonical owner, and the
   root remains a compact dependency map rather than a second specification.

Performance budgets are defined by the relevant child owner and executable
qualification.  Compilation, installation, daemon startup, provider warmup,
generation construction, transport time, service time, and whole-command wall
time are reported separately.

* Write policy

Change the narrowest canonical child owner first.  Update this root only when a
global decision, invariant, dependency, or owner changes.

Do not append implementation diaries, superseded alternatives, compatibility
notes, test transcripts, or historical snapshots here.  Git provides that
history.  New detail belongs in an existing canonical child owner; a new child
module is justified only when no current owner can express the concern without
mixing responsibilities.
