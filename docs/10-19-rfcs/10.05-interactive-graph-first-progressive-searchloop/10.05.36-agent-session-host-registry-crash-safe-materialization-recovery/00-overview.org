#+title: RFC 10.05.36 — Agent Session Host Registry Crash-Safe Materialization Recovery
#+language: en

* Status

Focused formal verification is complete. This RFC refines [[file:../10.05.35-agent-session-host-registry-executable-receipt-materialization/00-overview.org][RFC 10.05.35 — Agent Session Host Registry Executable Receipt Materialization]]. The Lean source and direct audit compile, all 19 theorem declarations are axiom-free, and the module is imported by the proof-package root.

This RFC verifies recovery and single-winner sealing semantics. It does not claim that a concrete verifier runtime or durable capture store implements them. No Rust implementation is authorized in this session.

* Problem

RFC35 proves that a materialized receipt must pass through adjacent lifecycle stages and bind the complete payload. It does not yet linearize concurrent recovery.

Without an explicit recovery model, five defects remain possible:

- an executor starts before the materialization intent is durable;
- a retry changes invocation identity or reuses an old generation;
- partial stdout or stderr capture is overwritten rather than appended;
- two recovery workers publish different terminal receipts for one invocation;
- a conflicting terminal capture is treated as another successful seal instead of quarantine.

The terminal publication point must therefore be a generation-scoped CAS over one stable invocation key.

* Evidence alignment

=AgentSessionDispatchTransaction= owns durable reservation, stable dispatch keys, idempotent host acceptance, and conflict detection. =AgentSessionHostRegistryCompaction= owns canonical CAS publication and stale-generation quarantine. RFC36 composes those ideas with RFC35 capture and sealing evidence.

The new model deliberately separates capture from publication. Append-only fragments are evidence under construction; only a successful seal CAS publishes a terminal capture.

Invocation before durable intent is prohibited. A process-local object or an in-memory reservation is not durable authorization.

* Append-only capture law

:END:

#let Concat(a, s) = $upright("concat")(#a, #s)$

$
  forall a, b,
  AppendOnly(a, b) <=> exists s, b = Concat(a, s).
$
#+end_src

Recovery may append missing fragments. It may not rewrite, reorder, or delete the captured prefix.

* Single-winner seal law
:PROPERTIES:
:ID: ASP-RFC-10.05-ASRR-SEAL
:END:

#+name: registry-crash-recovery-seal-law
#+begin_src typst
#let Seal(k, t) = $upright("Sealed")(#k, #t)$
#let Quarantine(k, a, c) = $upright("Quarantined")(#k, #a, #c)$
#let Cas(b, r, a) = $upright("SealCas")(#b, #r, #a)$

$
  forall k, a, c,
  a != c =>
  not Cas(Seal(k, a), c, Seal(k, c)) and
  Cas(Seal(k, a), c, Quarantine(k, a, c)).
$
#+end_src

An identical retry is idempotent. A different terminal capture is not a second winner; it advances the slot to quarantine with both competing identities retained.

* Lean contract embedded in Org

#+name: registry-crash-recovery-lean-contract
#+begin_src lean
def IntentAuthorizesInvocation
    (intent : DurableMaterializationIntent)
    (invocation : MaterializationInvocation) : Prop :=
  intent.persisted = true ∧
  invocation.started = true ∧
  invocation.key = intent.key ∧
  invocation.payloadDigest = intent.payloadDigest

def AppendOnlyCapture (before after : CaptureLog) : Prop :=
  ∃ suffix, after = before ++ suffix

inductive SealCas : SealRequest → SealHead → SealHead → Prop where
  | first : SealCas request emptyHead sealedHead
  | replay : SealCas sameRequest sealedHead sealedHead
  | conflict : conflicting ≠ accepted →
      SealCas conflictingRequest sealedHead quarantinedHead

def RetryPreservesExperiment
    (before after : RecoverySnapshot) : Prop :=
  after.intent = before.intent ∧
  AppendOnlyCapture before.capture after.capture
#+end_src

* Lean-discovered obligations

Lean proves that unpersisted intent, a wrong invocation key, or a wrong payload cannot authorize execution. Capture extension is represented as an existing prefix plus a suffix, so recovery cannot claim overwrite semantics.

The seal relation has exactly three constructors:

- =first= publishes from an empty current revision;
- =replay= preserves an identical sealed terminal;
- =conflict= moves a different terminal to quarantine.

There is no constructor that moves a sealed terminal directly to a different sealed terminal, and no constructor that publishes from quarantine. Stale revisions cannot perform the first seal. Generation changes produce distinct invocation keys, closing the ABA reuse hole.

During proof construction, direct simplification of existential append relations and concrete dependent CAS states introduced =propext=. The final model removes those simplifier-dependent proofs: the audited theorem family uses explicit constructors, equality elimination, and structural witnesses, leaving all 19 declarations axiom-free.
