#+title: RFC 10.05.35 — Agent Session Host Registry Executable Receipt Materialization
#+language: en

* Status

Focused formal verification is complete. This RFC refines [[file:../10.05.34-agent-session-host-registry-cross-runtime-replay/00-overview.org][RFC 10.05.34 — Agent Session Host Registry Cross-Runtime Replay]]. The Lean source and direct audit compile, all 25 theorem declarations are axiom-free, and the module is imported by the proof-package root.

No concrete registry verifier command or immutable vector generator was confirmed by parser-owned repository discovery. Therefore this RFC defines and verifies executable receipt materialization, but it does not claim that a runtime receipt has been produced. No Rust implementation is authorized in this session.

* Problem

RFC 10.05.34 defines when cross-runtime outcomes may be accepted. An acceptance relation alone does not prevent software or documentation from labelling incomplete evidence as “executed”. In particular, the following partial states are not executable closure:

- an artifact name without resolution to an exact command and artifact digest;
- generated vectors without immutable suite and byte identities;
- an invocation start without complete stdout, stderr, exit, and duration capture;
- a complete capture without warm-path effect observation;
- a sealed flag without a seal over the complete payload;
- a retry that silently changes artifact, vectors, or invocation identity.

Materialization is a lifecycle, not one Boolean field.

* Evidence alignment

The command boundary reuses =executionCommandDigest=, which binds the ordered command prefix and receipt-validated executable artifacts. The artifact boundary reuses canonical =materializedPath= and artifact digest identity. The invocation/replay boundary reuses the independent executor rule from executable verifier conformance. RFC35 adds the missing lifecycle and sealing relation across those owners.

ASP discovery also exposed two tooling defects during this audit: stale activation state briefly contained unsupported =projectScopeGeneration=, and the Org search adapter emitted a =search lexical= recommendation that its wrapper did not accept. Those are search lifecycle defects, not evidence that a registry verifier exists, and cannot be used to weaken the fail-closed materialization rule.

* Lifecycle law
:PROPERTIES:
:ID: ASP-RFC-10.05-ASRM-LIFECYCLE
:END:

#+name: registry-receipt-materialization-lifecycle-law
#+begin_src typst
#let Step(a, b) = $upright("LegalStageTransition")(#a, #b)$
#let P = $upright("Planned")$
#let R = $upright("Resolved")$
#let I = $upright("Invoked")$
#let C = $upright("Captured")$
#let O = $upright("EffectsObserved")$
#let S = $upright("Sealed")$

$
  Step(P, R) and Step(R, I) and Step(I, C) and Step(C, O) and Step(O, S),
  quad not Step(P, I),
  quad not Step(C, S).
$
#+end_src

Only adjacent transitions are legal. A crash preserves the last completed state; recovery resumes from that state rather than inventing later evidence.

  forall r,
  M(r) =>
  Resolved(r) and Immutable(r) and Independent(r) and

Each predicate binds exact identities. “Observed” is not inferred from the absence of an error message.

* Lean contract embedded in Org

#+name: registry-receipt-materialization-lean-contract
#+begin_src lean
inductive MaterializationStage where
  | planned | resolved | invoked | captured | effectsObserved | sealed

inductive LegalStageTransition : MaterializationStage → MaterializationStage → Prop where
  | resolve : LegalStageTransition .planned .resolved
  | invoke : LegalStageTransition .resolved .invoked
  | capture : LegalStageTransition .invoked .captured
  | observe : LegalStageTransition .captured .effectsObserved
  | seal : LegalStageTransition .effectsObserved .sealed

def ExecutableReceiptMaterialized
    (expectedCommandDigest expectedArtifactDigest expectedSuiteDigest : Nat)
    (producerExecutorDigest : Nat)
    (digestPayload : PayloadDigest)
    (receipt : SealedMaterializationReceipt) : Prop :=
  receipt.payload.stage = .sealed ∧
  receipt.payload.artifact.resolved = true ∧
  receipt.payload.artifact.executionCommandDigest = expectedCommandDigest ∧
  receipt.payload.artifact.artifactDigest = expectedArtifactDigest ∧
  receipt.payload.vectors.immutable = true ∧
  receipt.payload.vectors.suiteDigest = expectedSuiteDigest ∧
  receipt.payload.invocation.executorDigest ≠ producerExecutorDigest ∧
  receipt.payload.capture.complete = true ∧
  receipt.payload.observation.complete = true ∧
  EffectFree receipt.payload.observation.effects ∧
  receipt.sealedPayloadDigest = digestPayload receipt.payload
#+end_src

* Lean-discovered obligations

Lean proves that legal transition constructors prohibit direct =Planned -> Invoked=, =Resolved -> Captured=, =Invoked -> EffectsObserved=, and =Captured -> Sealed= jumps. These are structural impossibilities, not runtime conventions.

The acceptance relation additionally rejects:

- unresolved artifact evidence;
- mutable vector evidence;
- incomplete channel capture, even when =exitCode = 0=;
- incomplete effect observation;
- a non-sealed lifecycle state;
- a sealed digest that does not equal the payload digest.

Retry stability preserves artifact evidence, vector evidence, invocation digest, command digest, artifact digest, vector-bytes digest, and executor identity. This prevents crash recovery from quietly certifying a different run.

* Next boundary

This boundary is refined by [[file:../10.05.36-agent-session-host-registry-crash-safe-materialization-recovery/00-overview.org][RFC 10.05.36 — Agent Session Host Registry Crash-Safe Materialization Recovery]].

The next formal boundary is crash-safe materialization recovery: durable intent before invocation, stable invocation keys across retries, append-only partial capture, single-winner receipt sealing, and quarantine of conflicting terminal captures. That model must distinguish retry from a second experiment and prove that two competing sealers cannot both publish different receipts for one invocation identity.
