#+TITLE: Turso Authority, MemoryBackend Query Plane, And Immutable Epoch Publication
#+DATE: 2026-07-30
#+STATUS: Accepted architecture / implementation gate

* Decision

ASP uses one Tokio lifecycle-owned Runtime Server.  A workspace identity selects
an entry inside that daemon; it does not select another process.  Different
workspaces execute concurrently.  Sessions sharing one workspace reuse the same
entry, read plane, database handle, and writer lane.

The runtime data responsibilities are deliberately separate:

- Turso is the durable canonical-generation and MVCC authority.
- MemoryBackend is the primary query plane for the admitted current generation,
  selector graph, owner bytes, and rootDepth live/untracked overlay.
- memmap2 publishes an immutable, content-addressed epoch projection for
  process-independent readers.
- one Tokio writer lane per workspace builds and validates the next generation,
  MemoryBackend state, and mmap segment before atomically publishing the epoch.

No query command may construct a competing authority or repair state inline.

* Canonical workspace admission

Admission is keyed by the canonical repository identity and workspace identity.
It occurs once per daemon lifetime or after an explicit generation invalidation.
The admitted entry owns:

- the canonical activation reference;
- the current Turso generation transaction identity;
- the current MemoryBackend generation;
- a complete-provider-owner resident read cache populated only from committed
  Turso state or a successful workspace writer receipt;
- the immutable mmap epoch and digest;
- a bounded adaptive read pool;
- one asynchronous writer lane; and
- session leases referencing that entry.

There is one workspace activation.  Per-language activation replicas are
Legacy and must not be read, written, migrated, or consulted.  Provider
selection is a typed subset of the Global provider catalog, not a copied
language-local catalog.

* Global provider catalog identity

A provider catalog leaf identity includes all fields capable of changing parser
or projection semantics:

- provider identity;
- provider manifest digest;
- provider registry digest;
- query-pack digest;
- exact-query-pack identity digest;
- provider binary artifact digest;
- artifact metadata digest; and
- execution contract digest.

Warm reuse requires equality of every identity field.  Any drift creates and
atomically publishes a new catalog generation.  Receipt equality limited to
binary paths or binary digests is insufficient.

A workspace activation selects a subset of this Global catalog.  Artifact
verification therefore requires every activated provider leaf to be present
and current in the Global materialized set; it MUST NOT require equality with
that set and MUST NOT delete globally installed provider leaves merely because
one workspace did not activate them.  Lazy language activation changes the
selection, not the installed catalog authority.

* Generation and rootDepth overlay

The durable Turso generation is complete and immutable.  MemoryBackend combines
that canonical generation with a rootDepth live overlay for tracked changes,
untracked owners, moves, and tombstones.  Overlay facts carry their base
generation and content identity, so they cannot be applied to another epoch.

Writer publication is:

#+begin_example
Turso next generation transaction
  -> validate complete owner and selector envelope
  -> build next MemoryBackend
  -> encode and validate immutable mmap segment
  -> atomically publish epoch pointer and receipt
#+end_example

An incremental owner refresh is part of the same writer protocol.  After the
provider-owned complete-owner transaction commits, the refresh submits the
identical owner bytes, content digest, and parser-owned selector byte ranges to
the workspace writer lane.  The refresh is not complete until the resulting
rootDepth overlay epoch is published.  Search output may not advertise a new
provider generation while exact query remains bound to the previous owner
epoch.

Readers holding the previous epoch continue without blocking.  They never
observe a mixture of old owner bytes, new selectors, or a half-written overlay.

The resident overlay store is a writer-private staging area, not a second
readable authority.  Owner, selector, move, and tombstone mutations become
visible only after one complete MemoryBackend generation and its immutable mmap
segments have been validated and activated by the atomic epoch-pointer switch.
IPC and in-process readers MUST NOT read a staged overlay before that switch.

MemoryBackend and mmap pointers are reusable acceleration artifacts, not
durable authority.  After the lifecycle supervisor grants a new daemon the
unique election lease, the daemon preserves the runtime workspace store and
opens its control/data-plane endpoints without recursively visiting workspace
artifacts.  It then restores admitted workspaces from Turso through their
writer lanes.  A pointer published by an earlier daemon must never be accepted
merely because its mmap segment is internally self-consistent; admission binds
it to current durable identity before it becomes readable.  Until restore or
admission publishes the new daemon generation, readers receive the typed
active-generation admission state.

Daemon startup MUST NOT recursively delete, scan, or rewrite the workspace
store.  Store preparation is an idempotent O(1) directory admission.  Obsolete
content-addressed generations are reclaimed later by a generation-aware
maintenance lane after leases prove them unreachable; lifecycle startup is
never the garbage collector.

The Global daemon owns one durable workspace-admission catalog containing only
=workspaceIdentity + canonicalProjectRoot=.  It is a control-plane lookup set,
not source authority.  First admission atomically records a source scope;
repeated admission performs no write.  On restart the daemon publishes
=Starting=, loads this single catalog, restores all registered scopes from their
Turso canonical materializations through the workspace writer lanes, and only
then publishes =Healthy=.  Restore fans out across independent workspaces but
remains single-flight per source scope.  Startup MUST NOT discover projects by
walking =$ASP_STATE_HOME=, and query-time code MUST NOT repair a missing catalog
by rebuilding a provider index.

A missing or invalid canonical materialization degrades only its catalog scope.
It leaves a terminal failed admission receipt for that =workspaceIdentity= and
does not abort, restart, or hold the Global daemon in =Starting=.  Once all
catalog entries reach a terminal state, the daemon publishes its globally
serviceable =Healthy= status before emitting scope-local restore-failure events.
Consequently, receipt observation is also a lifecycle barrier: after a consumer
receives a restore-failure event, other admitted workspaces are already
serviceable.  The failed scope remains unavailable until its writer lane
publishes a complete canonical Turso generation; startup and query paths do not
invoke a provider to fill the gap.

The atomically published admission catalog is also the process-cold workspace
locator projection.  A query process maps it read-only and resolves an already
canonical =projectRoot= directly to =workspaceIdentity=.  Ordinary search and
exact query MUST NOT call Git discovery, =ResolvedState::resolve=, filesystem
canonicalization, or the Runtime Server control plane to rediscover that key.
Only the lifecycle admission hook may derive a previously unknown workspace
identity and append the resulting canonical scope to the catalog.  Conflicting
workspace identities for one canonical project root fail publication.

** Bounded generation control plane

The Runtime Server IPC boundary is a control plane, never a canonical-generation transport. A client may submit only a bounded generation intent containing the workspace identity, operation identity, and optional expected content identity. It MUST NOT submit =WorkspaceCanonicalMaterialization=, owner bytes, selector projections, provider facts, or any other collection whose encoded size grows with workspace source size.

The workspace writer lane resolves the admitted project scope, invokes the selected provider parsers, constructs the next canonical generation inside the daemon, commits it to Turso, builds the MemoryBackend and mmap projections, and then atomically publishes the epoch. Consequently, growing a workspace or generation MUST NOT grow an IPC control request. Protocol fixtures MUST reject source-bearing generation operations and MUST enforce a fixed control-frame budget independent of owner count and source byte count.

** Provider language-projection closure

Every programming-language provider selected for a generation declares the
shared =languageProjection= v1 descriptor in ProviderRegistry.  Activation
preserves that descriptor and its command, transport, request, response, and
canonical-item identity contracts in the registry fingerprint.  The daemon
writer lane invokes the declared framed batch exactly once for the provider's
same-pass owner bytes; ASP, not the provider, binds returned canonical item
identities and byte ranges to the workspace Merkle tree and creates exact
materialization proofs.

The provider response covers every owner in its admitted source envelope,
including owners with zero canonical items.  A generation records that owner
coverage independently from selector count.  Publication rejects a missing
descriptor, missing owner response, duplicate owner response, source-leaf
digest mismatch, out-of-bounds item range, duplicate structural selector, or
an owner/item identity outside the selected provider.  Owner bytes, selectors,
relations, module graph, generation evidence, Turso rows, MemoryBackend, and
mmap projections cross one writer transaction and one publication barrier.
There is no owner-only generation that can become active.

Document providers use their Git candidate scope and document AST projection
contract; they do not masquerade as programming-language project providers.
All registered programming-language harnesses converge on the shared batch
contract.  A Rust-only consumer or a provider-private reconstruction path is
non-conforming.

* Query-path prohibition

After workspace admission, warm search and exact query must not:

- canonicalize the repository or workspace again;
- probe filesystem locks;
- open or bootstrap Turso;
- write activation, manifest, receipt, or generation files;
- invoke a language provider process;
- run configuration synchronization;
- contact a lifecycle control socket; or
- rebuild a source index.

The read path is an identity lookup, epoch lease, MemoryBackend lookup, and
projection render.  A missing or stale epoch returns a typed admission receipt
to the Runtime Server writer lane; it does not perform a synchronous repair.
Lifecycle hooks request admission before query execution and never wait for a
generation build.  Search and exact consumers must not call the admission
operation or poll its progress.

Generation reconciliation is edge-triggered, not query-triggered.  Session
start and the first user-prompt event may establish a missing workspace entry.
After that, a successful workspace mutation submits exactly one asynchronous
reconciliation request from the post-tool lifecycle edge.  Pre-tool search or
query events MUST NOT restart an admission attempt: doing so races the command
against the generation it just requested and makes
=selector-not-in-active-generation= nondeterministic.  Read-only post-tool
events do not submit reconciliation.  The hook returns the accepted receipt

Mutation classification is owned by the hook match engine and its typed
configuration.  Session activity rendering is an orthogonal output concern:
an =agentSessionAction= decision MUST NOT replace or hide the classifier's
=operationIntent= before generation admission is selected.  The post-tool edge
classifies once, records session activity when applicable, and submits the
generation request from the preserved classified mutation evidence.
without waiting; the workspace writer lane coalesces concurrent submissions
and publishes the complete next epoch atomically.

=search owner <path> items= is a projection over the owner and canonical
selectors already stored in that immutable generation.  It must not stat the
owner, read source bytes, probe an incremental DB record, invoke a language
provider, or publish a runtime overlay.  An absent owner is a generation
diagnostic; changed bytes are admitted asynchronously by the workspace writer
lane as the next complete epoch.

=search lexical= and unscoped =search pipe= consume the same resident
generation lease.  Their source-index candidate lookup MUST execute against
the generation's load-once MemoryBackend and MUST NOT create a workspace-owner
IPC session, connect a control/data socket, open Turso, bootstrap a schema, or
spawn a provider.  Snapshot evidence, lexical candidates, selectors, and owner
bytes therefore come from one epoch lease.  The provider-dispatch layer opens
that lease once and passes it through the SearchLoop context; individual search
stages MUST NOT reopen the mmap generation or recover through the legacy DB
client facade.

Provider owner fingerprint probes and complete-owner snapshot reads follow the
same rule.  A successful durable owner write atomically replaces the
workspace-entry cache after commit.  After daemon restart, startup admission
loads each registered complete snapshot from Turso once before =Healthy=;
concurrent and subsequent readers reuse that immutable value.  A query-time
cache miss never opens Turso.  Provider owner reads must not fall through to two
independent Turso queries on every search command.  Metadata classification and
the matching complete snapshot cross the Runtime Server transport as one typed
request/response, not two connection and framing cycles.

The singleton Runtime Server endpoint owns both its lifecycle control plane and
the workspace database data plane.  Its =transportContractDigest= therefore
MUST bind both =runtime-server-control.v1= and
=workspace-db-owner-ipc.v1=.  The V1 digest is a domain-separated,
length-prefixed composition of the two exact schema byte streams.  Hashing only
the control schema is invalid because a data-plane operation or result change
would allow an old daemon to pass endpoint validation.  Drift in either V1
contract invalidates the endpoint and is recovered by the existing supervised
reconciliation path before a request is admitted.

An exact-repair selector is part of the immutable workspace generation.  The
writer lane merges it into the owning item, advances the epoch, and publishes a
new mmap segment.  A daemon-local selector map is not an accepted authority
because process-cold readers and restarted daemons cannot observe it.

The generation publication includes a fixed-entry exact projection mmap index.
It is keyed by =projectionKind NUL structuralSelector= and points directly to
owner source ranges or immutable derived projection bytes.  A process-cold
exact read maps the pointer and this index, performs a hash binary search, and
copies only the selected bytes.  It must not deserialize the complete
generation JSON into a per-command heap.

Exact search and exact projection consume the same atomic pointer authority.
The projection hot path MUST NOT create a =WorkspaceDbIpcSession=, connect a
workspace-owner socket, or perform a Runtime Server control roundtrip.  It
opens the published exact-projection mmap, validates the pointer-bound epoch
and generation digest, and reads the selector from that immutable generation.
Consequently a selector returned by owner search is executable against the
same published generation; =selector-not-in-active-generation= is a failed
publication invariant, not a normal retry state or a reason to consult an old
session endpoint.

Miss recovery is control-plane work.  The single workspace writer lane may
materialize an owner and atomically publish a replacement generation, after
which a new mmap reader follows the new pointer.  A read command never keeps a
session-local generation alive as its current authority and never repairs an
exact miss by falling back to a provider process on the hot path.

Owner-local search follows the same rule.  When the requested owner already
exists in the active mmap generation it ranks that generation directly with
zero control socket roundtrips and zero provider invocations.  Only an owner
absent from the published generation may request writer-lane recovery; search
must not contact the workspace endpoint merely to prove that a resident owner
is resident.

The same index stores one canonical complete-projection digest per owner.  A
warm owner admission compares content identity plus that digest and never
reconstructs the owner's selectors from the global index.  This prevents
workspace-size-dependent page faults and makes an unchanged owner a zero-write
operation even when the generation contains tens of thousands of unrelated
selectors.

The process-cold mmap attach boundary opens the immutable pointer and projection
segment descriptors synchronously and maps them immediately.  This is not a
blocking file-content read or a lifecycle loop: macOS has no Tokio-native mmap
attach, while =tokio::fs::File::open= delegates both descriptor opens to the
blocking pool and violates the one-millisecond gate.  All daemon supervision,
writer lanes, publication, recovery, transport, and shutdown remain Tokio
tasks.

* Tokio lifecycle

The daemon, endpoint ownership, workspace registry, session leases, adaptive
read pools, writer lanes, health supervision, restart, and shutdown are Tokio
tasks.  Blocking Turso or mmap preparation is isolated behind bounded
=spawn_blocking= work owned by the writer lane; it is never performed by a query
task.  Process lifecycle and transport code must not create independent
=std::thread= or blocking polling loops.

The read-pool size is adaptive.  A fixed global worker count is not an accepted
contract: the daemon uses observed contention, available parallelism, and
workspace pressure while preserving per-workspace isolation.

Runtime Server lifecycle reconciliation prewarms its persistent control lanes
to the current adaptive concurrency plan.  Lane allocation and Unix socket
connection establishment are lifecycle work, not demand work charged to the
next concurrent request wave.  Once reconciled, callers choose an existing lane
with atomic load accounting; they MUST NOT take a pool-wide asynchronous lock
or grow the connection pool on the request path.

The public =server reconcile= operation returns the typed receipt read from the
reconciled daemon.  Merely asking launchd or systemd to start a process is not a
successful reconciliation receipt and MUST NOT be rendered as a synthetic
=starting= state.  Contract or artifact drift is closed only when the latest
endpoint validates and the daemon reports =healthy=.

The macOS service definition overrides launchd's ten-second default spawn
throttle with the smallest supported positive interval.  The default is
incompatible with an atomic developer artifact switch because it converts a
healthy supervised replacement into a deterministic ten-second outage.
Throttle reduction is not the readiness protocol: reconciliation still closes
only on the daemon's typed healthy receipt, and repeated crashes remain an
explicit lifecycle failure.

* Strong performance fixtures

The performance suite is a correctness gate, not a timeout increase.  Every
receipt records elapsed time and the counters that prove which architecture ran.

Required fixtures:

1. one workspace, many sessions, concurrent exact selector reads;
2. one workspace, concurrent search and writer publication;
3. several workspaces, concurrent readers and independent writers;
4. process-cold reader attach to an already published mmap epoch;
5. moved owner, tombstone, tracked edit, and untracked owner in rootDepth;
6. catalog manifest/query-pack drift with unchanged provider binary;
7. daemon binary digest drift followed by supervised atomic restart; and
8. abrupt writer cancellation before and after epoch publication.

Warm and process-cold admitted reads have a data-plane p99 below 1,000
microseconds.  The installed CLI receipt separately reports process startup and
render cost so those costs cannot be misattributed to the query plane.

For admitted warm reads, all of the following counters are exactly zero:

#+begin_example
canonicalizeCalls
lockProbes
dbOpens
schemaBootstraps
providerProcesses
activationLoads
manifestWrites
generationWrites
controlSocketCalls
#+end_example

The concurrency gate must additionally prove:

- no =database is locked= or bounded lock retry receipt;
- no cross-workspace global mutex;
- readers retain a valid old epoch while the writer publishes the next one;
- exactly one published epoch wins each generation transition; and
- query results identify the generation, overlay digest, and epoch used.

* Completion rule

Source edits, isolated unit tests, a healthy daemon, or one fast warm sample do
not close this RFC.  Closure requires installed cold-to-warm evidence for every
registered provider family, the multi-workspace stress fixtures above, exact
zero-I/O counters, and successful moved/untracked/tombstone projection against
the same published epoch.
* Canonical Runtime Artifact Identity

Runtime Server control, health, reconcile, and restart MUST use the immutable
digest-addressed artifact path published by the install transaction as the
single binary identity authority.  A warm control request MUST NOT reopen or
hash executable bytes.  The canonical path has the form
=runtime/artifacts/blake3-256/<digest>/asp=; any daemon or client artifact
outside a validated digest-addressed path fails closed.

This removes the former split identity in which installation published a
BLAKE3 artifact digest while Runtime Server recomputed SHA-256 over the entire
binary on every control request.  The warm-path receipt is
=binaryByteReads=0=; content bytes are admitted only by the install
transaction.

* Exact Query Admission Boundary

Exact query is a resident read transaction.  It MUST NOT call source-index
admission, rebuild a generation, poll an admission state, sleep, or impose a
query-local deadline.  The workspace registry entry owns load-once mmap
checkpoint restoration; owner freshness opens that entry and the selector read
uses the same generation lease and resident overlay.

When no canonical checkpoint exists, exact query fails closed with typed
generation evidence.  Hook or Runtime Server lifecycle admission is the only
authority allowed to build and publish a new generation.

** ASP-RFC-10.05-ESGA-LIFECYCLE-ADMISSION-OWNER

=session-start=, =user-prompt=, and =pre-tool= are lifecycle admission
entrypoints.  They may submit one non-blocking generation build to the Runtime
Server owner.  Exact query and search query are resident consumers: they MUST
NOT submit, poll, or wait for generation admission.  A consumer that observes
no published canonical generation fails closed with typed evidence.

The hook-side admission request calls only the submit operation.  It MUST NOT
call =ensure=, =wait-terminal=, poll =Ready=, or hold the hook open for provider
work.  The immediate typed receipt may be =Building=; completion is published
by the daemon-owned Tokio task and observed through the next immutable epoch.

Admission coordination is partitioned by
=(workspaceIdentity, canonicalProjectRoot)=.  The registry uses a sharded
concurrent key map, an atomic single-flight state and attempt counter per entry,
and a per-entry watch receipt/task handle.  A global async mutex over all
admission states or all generation tasks is non-conforming because it couples
unrelated workspaces and makes hook latency scale with concurrent sessions.
The submit-only admission p99 gate is below 1,000 microseconds under at least
256 concurrent requests to one source scope while accepting exactly one build.

** ASP-RFC-10.05-ESGA-PROJECT-ROOT-ISOLATION

Generation admission single-flight identity is
=(workspaceIdentity, canonicalProjectRoot)=.  Concurrent sessions for the same
pair share one build.  Different canonical project roots under the same
workspace identity MUST have independent admission state and MUST NOT reuse
each other's =Building=, =Ready=, or =Failed= receipt.

** ASP-RFC-10.05-ESGA-COMMIT-PUBLICATION-BINDING

The writer transaction commits the canonical materialization and source-index
scope as one operation.  Its successful typed receipt is the publication
barrier.  MemoryBackend publication MUST use the same validated
materialization identity submitted to that commit and MUST reject receipt or
source-snapshot identity drift.  It MUST NOT require a second pooled
connection read-after-write as commit authority; MVCC visibility timing on a
different connection cannot invalidate an already committed transaction.

* Workspace Handle and Source-Scope Identity

=workspaceIdentity= owns exactly one resident Turso handle, adaptive read pool,
and serial writer lane.  It does not identify a source generation.  A monorepo
may expose several independently parsed package roots through the same
workspace handle, and each package may contain the same relative owner path
such as =src/lib.rs=.

Every durable materialization, MemoryBackend generation, mmap pointer, owner
overlay, and selector overlay is therefore keyed by the pair:

#+begin_example
(workspaceIdentity, canonicalProjectRoot)
#+end_example

=canonicalProjectRoot= is the canonical project root already carried by
=asp_source_index_scope_v1.project_root=.  Provider-owned incremental facts
remain further partitioned by =providerWorkspaceIdentityDigest=, =languageId=,
and =providerId=.  The Runtime Server must never choose the most recently
updated materialization for a workspace without filtering the requested
canonical project root.

The durable canonical materialization primary key and immutable reuse lookup
MUST both contain =workspaceIdentity= and =canonicalProjectRoot=.  A generation
identifier is unique only inside that source scope; it cannot authorize reuse
from another package root in the same workspace.  The single workspace writer
lane multiplexes scoped commands and carries the target scope explicitly.  It
MUST NOT be duplicated per project root.

The client canonicalizes the project root once while binding a Runtime Server
session.  Every request on that session carries the bound source scope; warm
selector reads do not canonicalize again.  The daemon validates that the scope
belongs to the requested workspace before opening or restoring it.

This separation preserves one database handle per workspace while preventing
package-root promotion, cross-package owner collisions, and “latest package
wins” generation replacement.  A map of project roots attached to one
unscoped generation is not conforming.

** ASP-RFC-10.05-ESGA-REPOSITORY-CANDIDATE-SCOPE

A repository candidate snapshot is discovered and scoped only by ASP Runtime.
Its =candidates= and =policyExclusions= are relative to the explicit
=candidateScope.projectRoot=.  No Git worktree prefix is exposed through the
provider contract.

The complete =repository-candidate-snapshot.v1= is an ASP-internal authority.
It may contain repository and worktree identity because ASP uses those fields
to distinguish checkouts and construct workspace identity, but that object
MUST NOT cross the provider ABI.  Provider requests contain only the rebased
candidate generation, candidate paths, policy exclusions, and canonical
project root needed to parse package-manager anchors.  They contain no
repository id, remote URL, Git common directory, worktree id, worktree root,
Git directory, or HEAD identity.

The runtime MUST filter the Git index/worktree candidate set to the requested
canonical project root, strip the repository prefix exactly once, and include
the candidate-base identity in =candidateGeneration.digest=.  When an already
discovered snapshot is reused for a nested request, the ASP consumer MUST
derive a new scoped snapshot before provider invocation.

Language harnesses MUST NOT interpret Git repository or worktree topology.
They consume the already-scoped candidate paths, parse their package-manager
anchors, and return zero or more semantic =ProjectResolution= receipts.  A returned
package root may be nested below =candidateScope.projectRoot=; equality between
the returned package root and candidate base is neither required nor valid as
a provider invariant.  ASP alone composes those =ProjectResolution= receipts into
the workspace graph.

Provider output MUST NOT echo the repository snapshot.  It binds returned
=ProjectResolution= receipts to the request candidate-generation digest.  ASP
validates that digest and every returned workspace-relative path against its
private repository snapshot before graph admission.

The provider ABI is named =ProjectResolution= throughout.  Its v1 command and
schemas are:

#+begin_example
project-resolution-stdin
provider-project-resolution-descriptor.v1.schema.json
provider-project-resolution-request.v1.schema.json
provider-project-resolution-response.v1.schema.json
project-resolution.v1.schema.json
#+end_example

The request carries =candidateBase=, =candidateGeneration=, rebased
=candidatePaths=, and =policyExclusions=.  Paths are relative logical paths;
the provider process working directory supplies the already-admitted project
root.  The request MUST NOT carry an absolute checkout root or any repository,
worktree, Git directory, remote, or HEAD identity.  The response carries only
parser-owned package graph and source-scope facts plus the consumed candidate
generation digest.  ASP creates project/workspace identities and binds the
receipt to the canonical generation envelope.

ASP MUST retain each complete =ProjectResolution= receipt inside that envelope.  It
MUST NOT reduce a receipt to a list of source paths and discard the package
graph.  The canonical generation digest, durable Turso materialization,
immutable mmap epoch, and resident MemoryBackend are all computed from the
same ordered set of admitted =ProjectResolution= receipts plus owner bytes and
selectors.  Package nodes, dependency edges, and resolved source scopes are
therefore generation facts, not activation-only hints.

Each admitted receipt is paired with an ASP-owned workspace-relative
=candidateBase=.  Rebased path identity belongs to this ASP envelope; the
provider receipt remains exactly relative to the candidate base it parsed.
Changing a receipt, its candidate base, or its candidate-generation binding
MUST change the canonical generation digest.  A partial receipt set MUST NOT
be published, and a warm query MUST NOT invoke a provider to reconstruct facts
that activation discarded.

The former =project-resolution-stdin= command and
=provider-project-resolution-*= / =project-resolution.v1= provider schemas are
not aliases.  They are removed from the public provider surface.  A manifest,
provider command, fixture, or client that still exposes them is non-conforming
and MUST fail its contract gate rather than entering a compatibility path.

This is a shared v1 contract for every registered provider.  Rust, Python,
TypeScript, Julia, Gerbil Scheme, document providers, and future lazy-loaded
providers consume the same scoped candidate meaning.  A provider-facing
request whose candidate paths were not rebased to its declared candidate base
is an ASP producer defect and MUST fail before the provider process starts.

* Global daemon health and workspace generation readiness are distinct

The Runtime Server is Global-Healthy as soon as its control and data sockets
are bound.  Catalog restoration and provider generation builds are
workspace-keyed background states and expose their own =Building=, =Ready=, or
=Failed= receipt.  A slow provider, an incompatible old generation, or one
failed workspace MUST NOT leave the Global daemon in =Starting= or block
healthcheck and unrelated workspaces/sessions.
