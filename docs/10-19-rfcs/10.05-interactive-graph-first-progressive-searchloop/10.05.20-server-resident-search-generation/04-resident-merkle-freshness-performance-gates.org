#+title: Resident Merkle Freshness and Performance Gates
#+startup: overview

* Status

Proposed v1 contract for daemon-owned workspace freshness and measurable
foreground/background performance gates.

* Problem

An exact selector may be resolved from an admitted generation whose Merkle root
predates the current workspace contents.  Returning an empty successful query
in that state is incorrect: absence in an obsolete generation is not evidence
of absence in the workspace.

The ASP ServerProcess already owns workspace generations.  File observation,
incremental Merkle computation, selector rebuilding, and publication therefore
belong to its workspace-keyed WorkspaceResident rather than an AgentSession or
foreground CLI process.

* Resident ownership vocabulary

- =ServerProcess= is the physical ASP Server daemon.  One process may host many
  workspaces.
- =WorkspaceResident= is the logically unique service for one workspace
  identity inside the ServerProcess.
- =AgentSession= is a client lifecycle.  It may be long-lived, but it never owns
  workspace durability, Merkle workers, writer lanes, or publication.

Exactly one WorkspaceResident may be active for a workspace identity.  Several
AgentSessions, turns, and subagents may share it.  Agent exit cannot terminate
or replace the WorkspaceResident and cannot discard server-accepted work.

* Load-once Memory Backend data plane

Each canonical workspace-generation pointer owns one process-local client cell.
The cell is keyed by the canonical pointer path and contains the validated mmap
plus its Memory Backend.  Concurrent first opens for the same workspace
coalesce through that workspace's Tokio =OnceCell=.  Cells for different
workspaces initialize independently; there is no cross-workspace open lock.

After initialization, =search= and =query= MUST NOT repeat pointer existence
probes, mmap opens, generation decoding, or full generation validation.  A hot
lease reads the already admitted Memory Backend.  Pointer epoch observation may
replace the backend atomically when publication advances, while extant leases
retain the previous immutable backend until they are dropped.

The required performance evidence distinguishes:

- =coldOpenCount=: at most one per pointer generation under concurrent demand;
- =coalescedOpenCount=: concurrent waiters sharing the same first open;
- =mmapOpenCount= and =generationValidationCount=: zero on unchanged warm hits;
- =databaseOpenCount= and =controlRoundtripCount=: always zero on the data plane;
- warm and concurrent p99 latency, with a sub-millisecond hard gate.

Missing or rejected generations publish a typed terminal state.  They cannot
fall back to per-request activation sync, provider execution, or workspace
materialization.

* Merkle boundary

Merkle identities control content and publication identity only.  They bind:

- workspace identity;
- base and observed workspace roots;
- changed-path set digest;
- selector-set digest;
- provider/parser/query-pack identities;
- published generation identity.

Merkle identities do not render compact output, choose query semantics, or
replace latency accounting.

* WorkspaceResident freshness loop

1. A WorkspaceResident watcher records changed paths for its active workspace.
2. The ASP Server coalesces observations into a bounded changed-path set.
3. A background worker computes the next incremental Merkle root and provider
   selector materialization.
4. Work is single-flight by
   =(workspaceIdentity, baseRoot, changedPathSetDigest)=.
5. Publication is admitted only when the worker still corresponds to the most
   recent observation epoch.  Obsolete results are discarded.
6. The atomic generation pointer changes only after validation succeeds.
7. Warm readers continue using the previous immutable generation until the new
   generation is ready.

A foreground CLI, hook, or AgentSession may return only after the target
WorkspaceResident acknowledges
the mutation admission.  It must not spawn an unacknowledged client-local task
and report =Queued=: process exit would otherwise discard the changed paths
before the daemon observes them.  Acceptance is synchronous and bounded;
materialization and publication remain asynchronous and server-owned.

Removed or inactive workspaces follow the existing checkpoint and retirement
policy.  Watchers are released with the WorkspaceResident entry; retirement of
one entry does not imply shutdown of the ServerProcess.

* Foreground correctness

A foreground exact query may:

- read a generation whose published root covers the latest admitted
  observation; or
- return a typed =generation-stale= / =generation-building= result carrying
  the observed root, active root, and retry guidance.

It must not translate a stale-generation miss into an empty successful result.
Foreground query execution must not perform a full workspace scan, provider
reindex, or Merkle rebuild.

* Read-side owner freshness is mandatory

Mutation admission is an accelerator and durability edge, not the sole
freshness authority.  A client, nested tool surface, editor, filesystem watcher,
or recovered AgentSession may change an owner without producing an observable
post-tool event.  Therefore every exact selector projection MUST prove that the
requested owner's live content digest equals the digest represented by the
generation or resident overlay before returning either a hit or a miss.

The exact-query order is:

1. derive the normalized owner path and language identity from the parser-owned
   structural selector;
2. ask the workspace-keyed WorkspaceResident to ensure that one owner;
3. treat equal content identity as a warm no-op;
4. incrementally publish changed owner bytes and selectors when identity differs;
5. only then open the current immutable generation and resolve the projection.

The incremental publication reply is a durable commit boundary.  The writer
lane MUST publish the exact segment and seqlock generation pointer before it
switches the resident backend or returns terminal =Ready=.  A transient
=ResidentReady= state is not sufficient for an exact-query caller: after a
=Ready= reply, a freshly opened canonical pointer MUST identify the same commit
or a monotonic successor.  Publication failure preserves the previous resident
backend and returns a typed failure; it cannot acknowledge the unpublished
generation and finish durability later.

A monotonic successor is admitted by owner coverage, not by strict generation
digest equality.  The owner-readiness receipt carries the daemon-observed live
owner content digest (or an explicit tombstone).  After reopening, the client
MUST compare that owner identity with the mapped generation.  A background
whole-workspace publication may legitimately replace the owner-local commit
between =Ready= and reopen; it is accepted only when it contains the same ready
owner identity.  Merely observing a different, newer generation digest is
neither failure evidence nor freshness evidence.

A cached hit without this proof is stale evidence.  Read-side freshness MUST
apply to =source=, =callable-skeleton=, and future exact projections uniformly;
it must not be conditional on =OwnerForRepair= or any cache-miss state.  The
foreground path may stat and hash only the requested owner and may use the
resident's fingerprint cache.  It MUST NOT scan the workspace.  Warm owner
freshness plus generation open remains subject to the exact-query performance
gate; a changed owner may use the bounded resident publication lane, but old
bytes must never be returned while that publication is pending.

The Runtime Server owns this read-side check.  An exact-query client may send
only the normalized owner path and the content digest observed in its resident
exact segment.  The daemon compares that admitted digest with the current owner
identity.  A match may return the existing resident readiness receipt without a
workspace scan.  A mismatch, removal, or replacement MUST reconcile the
generation to terminal =Ready= before the client reopens the generation pointer
and reads a projection.  The client MUST NOT hash the owner, discover a Git
candidate, build a Merkle tree, or publish a generation itself.

Mutation admission remains an acceleration path, not a correctness
precondition.  If a post-tool event is lost, delayed, coalesced, or emitted by a
client that exits, the next exact read still detects the changed owner.  The
daemon operation and its tests therefore MUST cover a cached selector hit after
an owner rewrite with no explicit mutation admission.

Owner-local discovery is subject to the same proof.  =search owner ... items=
must ensure the requested owner through the WorkspaceResident writer lane
before opening its immutable mmap generation; otherwise it can recommend a
selector that is stale at the moment it is minted.  The CLI performs no local
provider execution, scan, or write.  Session lookup, owner ensure, and immutable
generation open are separate phases with separate monotonic budgets and an
explicit control-roundtrip receipt.

* Adaptive resident read lanes

Each =WorkspaceDbIpcSession= owns an adaptively bounded read-lane pool.  Request
dispatch MUST reuse an available connected lane before opening an empty lane.
An empty lane may be opened only when every connected lane observed by that
request is busy; once the configured capacity is occupied, the request waits
for a lane.  The adaptive capacity is derived from runtime and machine
pressure policy rather than a client-visible fixed number.

Request sequence numbers may provide a fair scan origin, but MUST NOT cause
round-robin cold connection establishment.  A serial session therefore opens
one connection and reuses it.  Concurrent sessions may expand independently
up to their adaptive capacities while sharing one workspace generation.  The
performance qualification MUST separate first-connect latency, concurrent
multi-session latency, and already-connected service latency; the service gate
MUST NOT be diluted by lazy lane initialization.

The search-generation authority response is O(1) in workspace size.  It carries
the active epoch, generation digest, source-snapshot evidence, and workspace-
generation evidence.  It MUST NOT carry =WorkspaceSnapshot= leaves, owner
bytes, selector indexes, or overlay base leaves.  Those remain resident; typed
=ReadSourceIndex= and exact projection operations return only requested data.

Workspace activity bookkeeping is part of the read hot path and therefore MUST
be lock-free.  Request and generation-lease enter/exit update a monotonic Tokio
time offset through atomics; they MUST NOT contend on a blocking mutex or write
an activity file.  Retirement compares the same monotonic origin with the last
published activity offset.

* Core readiness is independent of optional resident providers

Publishing the ServerProcess endpoint commits the core control plane to accept
requests.  The Tokio accept loop MUST therefore start before Graph Turbo or any
language/provider subprocess completes its handshake.  Optional resident
providers initialize in server-owned Tokio tasks and expose an explicit
=starting=, =healthy=, =failed=, or =unavailable= state through the server
receipt.  Their startup MUST NOT delay core health, workspace admission, exact
projection, shutdown, or supervisor artifact reconciliation.

The owner projection builder resolves parser identity, query-pack identity, and
the managed provider argv from the validated Global provider catalog loaded
once by the ServerProcess.  Query-time activation loading, runtime-profile
resolution, provider binary discovery, and catalog disk reads are forbidden.
The WorkspaceResident passes its admitted workspace identity into the builder;
the builder MUST NOT canonicalize or resolve the workspace identity again.
The catalog generation is part of daemon admission; advancing it requires
supervisor reconciliation rather than silently mixing provider identities in
one ServerProcess generation.

A request that reaches an optional provider while it is =starting= returns a
typed provider-readiness result; it must not wait on provider construction or
fall through to an unmanaged executable.  Shutdown first closes new provider
work, joins the initialization task, and then drains any process that became
live.  This ordering prevents both orphan provider processes and a published
endpoint with no active accept loop.

When the canonical runtime artifact advances while the platform supervisor
definition is unchanged, the Hook MUST reconcile through the authenticated
Runtime Server control plane.  The old daemon publishes =draining= and exits;
launchd/systemd restarts =$ASP_STATE_HOME/runtime/bin/asp=.  The platform
definition pins this stable entry and MUST NOT canonicalize it to the current
digest-addressed target; artifact identity remains receipt-validated.  A sandboxed client MUST
NOT invoke =launchctl kickstart=, =systemctl restart=, or manipulate a PID for
this ordinary artifact transition.  Platform supervisor mutation is reserved
for an absent service or a changed service definition.

* Independent performance gates

Each phase owns a fresh monotonic clock.  One absolute deadline must not be
shared across setup, enqueue, acceptance, and completion.

| Gate | Default v1 budget | Failure meaning |
|------+-------------------+-----------------|
| watcher coalescing | 50 ms | observation backlog |
| writer enqueue | 100 ms | resident writer saturation |
| writer acceptance | 100 ms | foreground admission unavailable |
| session-cold search authority read p99 | < 1 ms | Ready catalog admission regression |
| warm search authority read p99 | < 1 ms | shared-pointer data-plane regression |
| background materialization | measured, no foreground blocking | worker receipt required |
| atomic publication | 250 ms | publication regression |
| core server readiness after endpoint publication | 100 ms | optional provider startup blocked the accept loop |

Background materialization may exceed foreground budgets, but it must emit a
terminal receipt and remain cancellable or supersedable by a newer observation.
A failed attempt remains evidence and increments the next attempt number; it
must not permanently poison the WorkspaceResident.  A later =ensure= starts a
new server-owned attempt while preserving the previous failure receipt.

* Performance receipt

The shared receipt schema records:

- workspace and observation identity;
- active, observed, and published Merkle roots;
- changed-path set digest and count;
- enqueue, acceptance, materialization, publication, and warm-read durations;
- scanned, reused, rebuilt, and published owner counts;
- whether work was coalesced, superseded, or published;
- budget verdicts per phase.

Receipts are evidence for performance gates.  A digest alone is never evidence
that latency or runtime conformance passed.

* OpenTelemetry performance evidence

Performance receipts are also OpenTelemetry observations.  A budget failure
MUST NOT exist only as CLI stdout or stderr: the Runtime Server persists the
corresponding span through its Turso telemetry writer lane so that regressions
remain queryable after the invoking process exits.

The Runtime Server owns one bounded Tokio telemetry ingress and one batched
exporter.  Foreground =search= and =query= paths enqueue an immutable event and
never open Turso, bootstrap telemetry schema, begin a transaction, wait for an
export, or retry a database lock.  Queue saturation increments a resident
dropped-observation counter and remains visible in health/status evidence; it
does not extend the foreground latency budget.

Every performance span records at least:

- OpenTelemetry =trace_id=, =span_id=, span name, start time, end time, and
  status;
- runtime artifact, transport contract, workspace, generation, language, and
  command identities when available;
- =surface=, =stage=, =phase=, =elapsed_micros=, =budget_micros=, and
  =budget_status=;
- the typed failure reason and retry guidance when the span exceeds a gate.

The Turso exporter stores normalized indexed columns for the stable query axes
and the canonical OpenTelemetry attribute map for lossless export.  It uses the
Runtime Server's single telemetry writer lane and MVCC transaction policy.
Different workspaces may emit concurrently; no workspace query owns or waits
on the telemetry transaction.

The CLI failure JSON and the persisted span are two projections of one typed
event.  Budget constants MUST come from the same contract value; a renderer may
not independently hard-code =budgetMicros=.  The v1 query surface MUST support
Turso aggregation by workspace, surface, stage, budget verdict, runtime digest,
and time interval, including count and p50/p95/p99 latency.

* Query-time artifact and generation admission

Provider and ranker executable content identity is established exactly once by
install/publication and carried by the immutable Active ASP Artifact Receipt.
A =search= or =query= consumer may validate the typed receipt binding and the
canonical executable identity, but MUST NOT hash executable bytes or recompute
artifact metadata.  Content or metadata reads of the ASP/provider executable
on an agent-facing path are a performance-contract violation.

The canonical PATH-visible ASP entry is a stable symlink to an immutable
=runtime/artifacts/blake3-256/<digest>/asp= object. The Runtime compatibility
entry points to that PATH-visible entry. Install verifies bytes before
publishing the immutable object, atomically switches the public symlink, and
then switches the Runtime compatibility alias in the same transaction. Supervisor
=status|start|restart= derives the expected digest from the canonical
artifact path identity; it MUST NOT read executable bytes.  In particular, a
restart control frame is sent before the supervisor boundary and binary
freshness cannot consume that boundary.  A regular mutable file at the
canonical runtime entry is not a second supported architecture.

Registered provider runtime entries follow the same single architecture: each
entry is a symlink to its own immutable
=runtime/artifacts/blake3-256/<digest>/<binary>= object.  Reconcile accepts a
canonical digest-lattice symlink without reading or rewriting binary bytes.  A
regular file, an external symlink, or any other unmanaged entry is a typed
configuration error.  There is no migration or compatibility branch in the
runtime reconciler.

Memory mapping a generation file is not by itself Memory Search.  The Runtime
Server MUST load and validate one immutable generation per admitted workspace,
construct its selector, term, and relation indexes once, and retain that
backend behind the workspace resident entry.  A CLI process MUST NOT decode the
complete generation or rebuild those indexes for each request.  The durable
generation segment therefore contains either a zero-copy index directory with
validated offsets or a representation the Runtime Server materializes once;
agent-facing consumers receive only compact query/projection results.  Exact
projection remains a separate immutable segment and does not require the full
search generation.

The generation-open performance receipt distinguishes =pointer-read=,
=segment-map=, =segment-decode=, =index-materialize=, and =resident-lease=.
Only =resident-lease= belongs on a warm foreground request.  The other phases
are admission/publication work and cannot consume the agent-facing deadline.

The resident data plane returns
=agent.semantic-protocols.runtime-server-search-generation-authority= v1 to
search composition.  It binds workspace identity and canonical project root to
the source snapshot and validated workspace-generation evidence already held
by the resident lease.  It MUST NOT contain the complete workspace snapshot,
owner bytes, or serialized selector, term, or relation indexes.  Candidate
lookup uses the resident =ReadSourceIndex= operation; Graph Turbo evaluation
uses the resident =graphs/evaluate= ClientFrame method.  A CLI that opens or decodes
the complete generation mmap after receiving this authority violates the
contract.

The Runtime Server endpoint publishes the canonical =workspaceStorePath=.
Together with workspace identity and canonical project root, this deterministically
locates the stable generation pointer without a control or data-plane socket
round trip.  A process-local Runtime pointer catalog owns one load-once reader
per =(pointerPath, workspaceIdentity, projectRoot)= and shares it across all
sessions.  Generation publication MUST complete this load-once mapping before
the generation becomes Ready.  Query sessions therefore only join an already
initialized catalog entry; they never own first mapping or its waiter wakeup.
Concurrent sessions MUST NOT independently open or mmap the same pointer.  A
missing pointer is not cached, so later server admission can publish it.  When
the pointer does not yet exist, the client performs exactly one typed cold
workspace admission over IPC and then reopens the pointer exactly once.  The
admission call acknowledges resident ownership without waiting for the full
generation build.  A second =Missing= result returns typed
=generation-building= with a retry delay, and =RecoveryRequired= remains a
typed fail-closed supervisor error; neither state authorizes an in-call retry
loop or couples the daemon build lifetime to the client deadline.
The server and client MUST consume the same endpoint-owned store locator; they
MUST NOT independently derive it from ambient state-home configuration.

The typed cold authority admission returns a distinct
=agent.semantic-protocols.runtime-server-search-generation-authority-open-receipt=
v1.  It binds the compact authority to the resident scope's stable
=active-generation.pointer=.  A session maps that fixed-size seqlock pointer
once and caches its typed reader.  Every warm authority read consults that
shared pointer directly; it performs no Unix socket round trip, provider spawn,
Turso open, filesystem read, canonicalization, activation load, or schema
bootstrap.  Publication writes only constant-size source kind, leaf count,
owner count, digests, epoch, and root-depth evidence into the pointer.  A
generation change is observed through the pointer's monotonic publication
sequence without remapping the complete generation.

Unix IPC remains authoritative for missing-generation admission, mutation, complex
lookup, and graph evaluation.  It is not a warm identity transport.  This
separation is required because scheduler and socket tail latency cannot satisfy
the sub-millisecond p99 gate under multi-session pressure even when framing and
connection reuse are optimized.

* Required tests

- delayed workspace-entry initialization cannot consume writer acceptance
  budget;
- enqueue and acceptance clocks are independent;
- a newer observation supersedes an older background worker;
- stale-generation misses are typed and never emitted as empty success;
- unchanged owners are reused under incremental Merkle materialization;
- cold repair terminates and a repeated warm query stays within its budget;
- a missing generation performs one daemon admission and one reopen; a second
  miss returns typed =generation-building= and =RecoveryRequired= terminates
  fail-closed without an in-call retry;
- canonical provider symlinks reconcile with zero binary-byte reads and
  unmanaged runtime entries are rejected without migration;
- watcher retirement releases all workspace-owned tasks and paths.
- an exceeded search/query gate is retrievable from Turso by trace and stage;
- 1,000 concurrent observations do not block foreground query completion and
  are either persisted or accounted for by the dropped-observation counter;
- telemetry schema/bootstrap and database opens are zero on the foreground
  query path;
- the CLI receipt and persisted OpenTelemetry span use the same budget value;
- exporter shutdown drains accepted events without deadlocking the Tokio
  Runtime Server lifecycle.
- agent-facing ranker admission performs zero executable byte reads and zero
  artifact metadata recomputations;
- 1,000 warm searches over one workspace reuse one resident generation and one
  set of search indexes; generation decode and index materialization counts
  remain exactly one;
- concurrent warm searches across multiple sessions share the workspace
  resident lease without a global lock, while different workspaces progress
  independently.
- 64 concurrent session lanes produce at least 1,000 fresh-session catalog-hit
  samples and at least 2,000 warm authority reads; both p99 values remain below
  1 ms.  A separate 1,000-read sequential run also keeps p99 below 1 ms.  A
  sample set smaller than 100 is insufficient for a p99 gate because it aliases
  p99 to max latency.
- warm authority reads have a zero delta for every runtime data-plane I/O
  counter, including control socket round trips.
- pointer wire size remains constant when owner count grows, and the pointer
  contains no owner path or source bytes.
