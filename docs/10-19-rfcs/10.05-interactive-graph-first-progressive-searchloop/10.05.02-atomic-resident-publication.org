#+TITLE: 10.05.02 Atomic Resident Runtime Publication
#+OPTIONS: toc:2 num:nil

Parent architecture: [[file:../10.05-interactive-graph-first-progressive-searchloop.org][RFC 10.05 SearchLoop]].

* Status

Normative. This module owns the zero-downtime publication contract for the ASP
Server used by every public search and query request.

* Single authority

Artifacts owns the sole binary-bundle publication state. The ASP Server owns
Runtime process, endpoint, provider, workspace generation, cache, readiness,
and drain, but it never selects executable bytes. Protocol and command packages
may compose arguments and coordinate installation, but must not implement or
poll either state machine.

One immutable bundle contains every executable that must switch together:

#+begin_example
runtime/resident/candidates/asp/<bundleDigest>/
  asp
  asp-hook
  bundle.json
  activation.json
runtime/resident/active  -> candidates/asp/<activeBundleDigest>
runtime/resident/healthy -> candidates/asp/<healthyBundleDigest>
runtime/bin/asp          -> ../resident/active/asp
runtime/bin/asp-hook     -> ../resident/active/asp-hook
#+end_example

The stable launchers never select an immutable candidate directly and are not
rewritten after their first canonical installation. An install changes only the
=active= bundle selector; Runtime readiness changes only =healthy=. A numeric
content-bound publication nonce, active/healthy selectors, and serving alias
are forbidden serving authorities.

* Candidate handover

Installation MUST follow this ordered transition:

1. Materialize and content-validate every declared bundle member outside the
   mutation lock.
2. Under the one Artifacts mutation transaction, consume the publication lease,
   write the content-bound pending event, ensure the fixed launchers, and switch
   only =active= to the complete bundle. Preserve =healthy= unchanged.
3. Return from installation without waiting for Runtime or a datagram wakeup.
   The durable event is authority; notification is only a best-effort hint.
4. The Runtime activation actor launches the event-bound =active= candidate and
   receives one typed Ready or Failed terminal without polling or sleeps.
5. A matching Ready terminal switches only =healthy= to =active=, publishes the
   applied acknowledgement, then drains the previous healthy process.
6. A matching Failed terminal restores only =active= from =healthy=. A stale
   candidate whose bundle digest or publication nonce differs changes neither
   slot.

A failed candidate materialization or install transaction preserves both prior
slots. A Runtime failure after publication preserves =healthy= and restores the
fixed launchers automatically because they always traverse =active=.

* Client handshake

Every ASP Client transport handshake carries the generation identity expected
by its installed binary. The server endpoint must match all three identity
fields exactly. Any mismatch terminates immediately with typed reason
=runtime-server-generation-mismatch=. It must never enter readiness waiting,
provider spawning, generation restore, polling, or a compatibility route.

* Package ownership

- =agent-semantic-client-protocol=: wire generation identity and mismatch type.
- =agent-semantic-runtime-server=: activation consumption, Ready validation,
  serving-generation admission isolation, Tokio lifecycle, and drain.
- =agent-semantic-client=: expected generation handshake and typed rendering.
- =agent-semantic-client=: thin CLI composition and typed receipt rendering only.
- =agent-semantic-artifacts=: immutable content-addressed storage, the sole
  =active=/=healthy= two-slot publication transaction, Release Activity,
  provenance, and retention.
- =agent-semantic-runtime=: reusable Tokio actor/process primitives only; it
  owns neither artifact publication nor the active server lifecycle.

* Activation event and resident actor

Installation MUST materialize the immutable content-addressed bundle outside
the publication lock. The one short publication transaction then writes exactly
one pending activation event and moves only =active=. The event contains the
bundle digest, primary artifact digest, immutable candidate path, publication
nonce, and candidate identity receipt. The manifest, event, member bytes, and
receipt MUST bind to the same identities. Stable launchers remain fixed and
=healthy= remains unchanged.

Exactly one Tokio activation actor is mounted in the production ASP Server.
At startup it recovers the durable pending event; while online it consumes
datagram/watch wakeups for the same event stream. It launches only the
event-bound candidate path and receipt, never a stale global receipt or the
stable alias. Readiness and child exit are terminalized through Tokio
cancellation-aware selection; polling, sleeping, and outer timeouts are
forbidden. Every launch/readiness failure writes a typed Failed terminal and
leaves the actor supervised and alive.

Installation materializes one immutable bundle, writes its content-bound event,
and atomically switches =active= to that bundle. Stable launchers resolve members
through =active=; =healthy= remains the previous serving bundle. Only a typed
Ready receipt whose digest, publication nonce, schema identity, artifact bytes,
and endpoint bindings all match MAY enter the Artifacts commit. That short
commit changes only =healthy= to the exact =active= bundle and writes the applied
acknowledgement. Activation failure changes only =active= back to =healthy=.
The previous healthy process is drained only after the Ready commit.

The canonical two-slot vocabulary is =active=/=healthy=. On an initial
installation with no serving bundle, a Ready candidate sets both slots to
the same immutable artifact. After every successful commit, retention removes
all artifacts unreachable from =active=, =healthy=, or one live pending event;
pending candidates are bounded and recoverable. No third runtime pointer or
second activation actor exists.

* Resident replacement observation

The resident replacement identity is exactly the canonical applied activation
and serving transaction tuple =(artifactDigest, publicationNonce, ownerEpoch)=.
The Runtime monitor may observe only that tuple.  A pending
activation is input to the resident activation actor and is not an applied or
serving identity until the actor commits it.

A developer source-generation receipt, build output, stable-link target, or
artifact-identity side receipt cannot request handoff and cannot retire a
healthy owner. Missing, malformed, or unknown applied authority is a typed
observation failure: it never fabricates a replacement and never drains the
last healthy resident. A distinct content-bound publication nonce is observable
even when immutable content is reused, and it emits one replacement observation.

* Deterministic acceptance

Source gates must prove: new client rejects an old server; non-Ready candidate
does not switch; Ready candidate switches atomically; in-flight old requests
finish before drain; fallback restores the previous healthy generation; and a
query after switch uses the resident memory path below one millisecond. Build,
process launch, and candidate warm-up are reported separately from query service
latency.
