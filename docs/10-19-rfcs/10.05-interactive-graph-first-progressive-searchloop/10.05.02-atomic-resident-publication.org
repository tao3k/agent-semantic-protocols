#+TITLE: 10.05.02 Atomic Resident Runtime Publication
#+OPTIONS: toc:2 num:nil

Parent architecture: [[file:../10.05-interactive-graph-first-progressive-searchloop.org][RFC 10.05 SearchLoop]].

* Status

Normative. This module owns the zero-downtime publication contract for the ASP
Server used by every public search and query request.

* Single authority

The ASP Server owns Runtime process, endpoint, provider, workspace generation,
cache, readiness, drain, and fallback lifecycle. Protocol and command packages
may compose arguments and coordinate installation, but must not implement or
poll this state machine.

One generation directory contains all authority coupled to a running server:

#+begin_example
runtime/server/publications/<runtimeGenerationDigest>/
  asp
  endpoint.json
  authority.json
runtime/server/current  -> publications/<runtimeGenerationDigest>
runtime/server/fallback -> publications/<previousHealthyGenerationDigest>
#+end_example

The stable client binary alias and endpoint resolver both traverse =current=.
An atomic replacement of that one pointer therefore switches the client binary,
server endpoint, schema, and Runtime generation together. Independent active
binary and endpoint pointers are forbidden.

* Candidate handover

Installation MUST follow this ordered transition:

1. Snapshot the binary into the content-addressed artifact store.
2. Create an immutable candidate generation directory and generation-scoped
   sockets/lifecycle state.
3. Launch the candidate without changing =current=.
4. Receive a typed Ready or Failed receipt. Polling, sleeps, and outer timeouts
   are not readiness mechanisms.
5. Validate =binaryContentDigest=, =runtimeGenerationDigest=, and =schemaDigest=
   across artifact, endpoint, and Ready receipt.
6. Atomically move the previous =current= generation to =fallback= and publish
   the ready candidate as =current=.
7. Stop admitting requests to the old generation, allow its in-flight requests
   to complete, then request its graceful drain.

A candidate that is not Ready cannot change =current= or the client binary
authority. A failed installation leaves the previous active generation intact.

* Client handshake

Every ASP Client transport handshake carries the generation identity expected
by its installed binary. The server endpoint must match all three identity
fields exactly. Any mismatch terminates immediately with typed reason
=runtime-server-generation-mismatch=. It must never enter readiness waiting,
provider spawning, generation restore, polling, or a compatibility route.

* Package ownership

- =agent-semantic-client-protocol=: wire generation identity and mismatch type.
- =agent-semantic-runtime-server=: activation consumption, Ready validation,
  serving-generation admission isolation, Tokio lifecycle, and drain.
- =agent-semantic-client=: expected generation handshake and typed rendering.
- =agent-semantic-protocol=: thin CLI composition and typed receipt rendering only.
- =agent-semantic-artifacts=: immutable content-addressed storage, the sole
  =active=/=healthy= two-slot publication transaction, Release Activity,
  provenance, and retention.
- =agent-semantic-runtime=: reusable Tokio actor/process primitives only; it
  owns neither artifact publication nor the active server lifecycle.

* Activation event and resident actor

Installation MUST materialize the immutable content-addressed candidate outside
the publication lock. It then publishes exactly one pending activation event
containing the typed candidate digest, immutable artifact path, runtime and
schema identities, nonce, and the candidate RuntimeArtifactIdentityReceipt.
The event and receipt MUST bind to the same digest and nonce. This step MUST
NOT mutate =active=, =healthy=, or the stable client alias.

Exactly one Tokio activation actor is mounted in the production ASP Server.
At startup it recovers the durable pending event; while online it consumes
datagram/watch wakeups for the same event stream. It launches only the
event-bound candidate path and receipt, never a stale global receipt or the
stable alias. Readiness and child exit are terminalized through Tokio
cancellation-aware selection; polling, sleeping, and outer timeouts are
forbidden. Every launch/readiness failure writes a typed Failed terminal and
leaves the actor supervised and alive.

Only a typed Ready receipt whose digest, runtime generation, schema identity,
artifact bytes, and event nonce all match MAY enter the Artifacts commit. That
short atomic commit sets =healthy= to the exact currently serving artifact
identity, =active= to the candidate, updates the stable alias to =active=, and
writes the applied acknowledgement. The old generation is drained only after
this commit. Before commit, any failure leaves =active=, =healthy=, and the
stable alias unchanged.

The canonical two-slot vocabulary is =active=/=healthy=. On an initial
installation with no serving generation, a Ready candidate sets both slots to
the same immutable artifact. After every successful commit, retention removes
all artifacts unreachable from =active=, =healthy=, or one live pending event;
pending candidates are bounded and recoverable. No third runtime pointer or
second activation actor exists.

* Resident replacement observation

The resident replacement identity is exactly the canonical applied activation
and serving transaction tuple =(activationGeneration, artifactDigest,
ownerEpoch)=.  The Runtime monitor may observe only that tuple.  A pending
activation is input to the resident activation actor and is not an applied or
serving identity until the actor commits it.

A developer source-generation receipt, build output, stable-link target, or
artifact-identity side receipt cannot request handoff and cannot retire a
healthy owner.  Missing, malformed, or unknown applied authority is a typed
observation failure: it never fabricates a replacement and never drains the
last healthy resident.  A new applied generation is distinct even when its
content digest is unchanged, and it emits one generation-bound replacement
observation.

* Deterministic acceptance

Source gates must prove: new client rejects an old server; non-Ready candidate
does not switch; Ready candidate switches atomically; in-flight old requests
finish before drain; fallback restores the previous healthy generation; and a
query after switch uses the resident memory path below one millisecond. Build,
process launch, and candidate warm-up are reported separately from query service
latency.
