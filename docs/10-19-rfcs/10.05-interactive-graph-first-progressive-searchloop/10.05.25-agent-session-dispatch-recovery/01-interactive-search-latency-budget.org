#+title: Interactive Search Latency Budget and Non-Blocking Recovery

* Status

This module extends the canonical SearchLoop dispatch-recovery contract.  It
defines the agent-visible latency boundary for resident dispatch and workspace
generation recovery.  It precedes Rust implementation and benchmark closure.

* Formalization-discovered defect

A resident bootstrap used to route a parser-owned search remained running for
approximately forty seconds without returning evidence, progress, rejection,
or a timeout receipt.  This is not an acceptable interactive timeout.

The defect is architectural: foreground search is waiting for control-plane
repair.  Increasing the timeout would preserve the defect while making Agent
experience, token use, and SearchLoop round cost worse.

Interactive search and background repair therefore have different clocks and
different receipts.  A background publication may take seconds, but the
foreground request must quickly return one of:

- useful evidence from an exact current generation;
- a generation-progress receipt with a bounded retry token; or
- a terminal unavailable receipt with a precise recovery condition.

Silence is never a protocol result.

* Latency classes

The initial versioned hard ceilings are:

| Class | Hard ceiling | Meaning |
|-
| warm exact result | 1 ms | Existing target remains p99 below 100 microseconds |
| warm search/owner result | 10 ms | Current generation and graph projection are ready |
| first progress or unavailable receipt | 100 ms | Generation is missing, building, stale, or failed |
| progressive wait quantum | 250 ms | Maximum single server-side await before another receipt |
| background repair | independently bounded | Never charged as one foreground wait |

The hard ceilings are admission limits, not performance claims.  Runtime
benchmarks MUST also report p50, p95, and p99.  A platform profile may adopt a
tighter versioned budget, but may not silently relax these ceilings.

* Universal one-second wall gate

Every agent-facing =asp <language> query= and =asp <language> search= invocation
MUST terminate with evidence, progress, or a typed failure in strictly less than
1,000 ms of end-to-end wall time. The clock starts before facade routing,
workspace admission, resident dispatch, provider acquisition, or repair enqueue,
and stops only after the complete protocol reply is observable by the caller.

This is a blocking acceptance gate, not a percentile target. Cold start,
provider startup, owner-freshness reconciliation, project resolution, database
open, background publication, and resident-child bootstrap are not exemptions.
If useful evidence cannot be returned inside the budget, ASP MUST return a
bounded progress or unavailable receipt before the deadline and continue repair
outside the foreground clock.

Any measured wall time greater than or equal to 1,000 ms is classified as
=agent-facing-search-wall-budget-exceeded=. The command is a failed gate even if
it eventually returns correct evidence. A test that omits process startup,
facade routing, or reply serialization is not evidence for this gate.

The observed exact callable-skeleton request for
=latest_turso_source_index_scope_files= took approximately 10.3 seconds in the
tool receipt, while an interactive observation reported 2--3 seconds. Both are
hard failures. The discrepancy is itself evidence that internal provider timing
cannot substitute for caller-observed wall time.

The machine-readable owner is
=schemas/agent-facing-search-wall-receipt.v1.schema.json=. It records only a
command digest, never raw command text. Its conditional schema makes
=within-budget= invalid at or above 1,000,000 microseconds and makes
=budget-exceeded= invalid below that boundary.

The executable gate owner is
=packages/python/tools/src/tools/search_wall_gate.py=. It accepts only an ASP
facade whose language and surface match the receipt identity; it cannot be used
to bless direct provider-binary execution.

#+begin_src sh :eval never
uv run --project packages/python python -m tools.search_wall_gate \
  --language rust --surface query -- \
  asp rust query --selector '<exact-selector>' --workspace . \
  --projection callable-skeleton
#+end_src

The first executable-gate receipt is checked at
=packages/proofs/receipts/agent-facing-search-wall-budget-observed-v1.json=.
It stopped a Rust exact callable-skeleton request after 1,035,628 microseconds
with =budget-exceeded=, =no-reply=, and exit code 124. This is a successful gate
execution recording a failed ASP performance admission.

* Foreground/background state machine

#+begin_src mermaid
stateDiagram-v2
  [*] --> InspectGeneration
  InspectGeneration --> EvidenceReady: current digest + projection ready
  InspectGeneration --> ProgressReady: missing or building generation
  InspectGeneration --> UnavailableReady: terminal publication failure

  EvidenceReady --> Returned: exact <= 1 ms, search <= 10 ms
  ProgressReady --> Returned: progress receipt <= 100 ms
  UnavailableReady --> Returned: unavailable receipt <= 100 ms

  ProgressReady --> BackgroundPublishing: durable publication intent
  BackgroundPublishing --> ProgressReady: wait quantum <= 250 ms
  BackgroundPublishing --> EvidenceReady: generation receipt delivered
  BackgroundPublishing --> UnavailableReady: indexed terminal failure

  note right of Returned
    No foreground transition waits for
    the full background repair deadline.
  end note
#+end_src

* Mathematical contract

#+begin_src typst :lint typst-eval
#let first = math.op("first-receipt")
#let warm = math.op("warm-result")
#let quantum = math.op("wait-quantum")
#let background = math.op("background-repair")
#let evidence = math.op("evidence")
#let progress = math.op("progress")
#let unavailable = math.op("unavailable")
#let reply = math.op("reply")

$ warm <= 1000 "microseconds" $
$ first <= 100000 "microseconds" $
$ quantum <= 250000 "microseconds" $

$ reply(s) in { evidence, progress, unavailable } $

$ background not in { warm, first, quantum } $
#+end_src

The final equation states accounting separation: background repair duration is
not an interactive wait duration.

* Current-generation rule

Search may return evidence only when the admitted generation carries the exact
current workspace root digest and requested projection.  A stale generation is
not a latency fallback.  When the digest or projection does not match, the
foreground request returns a progress receipt and the Runtime Server continues
publication in the background.

This preserves fail-closed evidence semantics without imposing a forty-second
foreground stall.

* Lean correspondence

The executable policy model is maintained in:

- =packages/proofs/ASPProof/ASPAgentFacingSearchWallBudget.lean=

It proves:

- a 40,000 ms foreground wait is rejected;
- every generation state produces a non-silent reply;
- only current ready generations produce evidence;
- missing, building, or stale generations produce progress;
- terminal publication failure produces unavailable;
- retry-after never exceeds the 250 ms wait quantum; and
- the background deadline cannot be substituted for the first-receipt budget.
- 999 ms is admitted while 1,000 ms, 3,000 ms, and the observed 10,300 ms are
  rejected by the agent-facing wall gate; and
- correct eventual evidence cannot override a failed wall-time admission.

* Runtime acceptance gates

The first-progress deadline starts before the foreground adapter attempts to
enqueue repair work.  One absolute deadline covers both bounded-channel enqueue
and writer acceptance.  Timing only the receipt receiver is insufficient
because a saturated writer queue could otherwise consume an unbounded interval
before the timer starts.

The writer, not the caller, issues the accepted receipt after reserving the
actual target generation.  A caller must not synthesize =active_epoch + 1=
after a timeout: concurrent commands can invalidate that guess and the guessed
epoch has no durable intent identity.  If enqueue misses the deadline, the
command was not accepted and may be cancelled.  Once enqueue succeeds, a
foreground acceptance timeout may drop its receiver but must not cancel the
writer's durable publication work.

This timing refinement is proved in
=packages/proofs/ASPProof/ASPForegroundAcceptanceDeadline.lean=.  The model
contains a concrete saturated-queue counterexample: bounding only receipt wait
to 100 ms still permits enqueue to exceed 100 ms.  It also proves that accepted
work carries a background-continuation obligation after foreground timeout.

#+begin_src typst
#let limit = 100000
#let agent-facing-wall-limit = 1000000
#let elapsed(enqueue, acceptance) = enqueue + acceptance
#let receiver_only_bounded(acceptance) = acceptance <= limit
#let absolute_bounded(enqueue, acceptance) = elapsed(enqueue, acceptance) <= limit
#let agent-facing-wall-admitted(elapsed) = elapsed < agent-facing-wall-limit

assert(receiver_only_bounded(0))
assert(not absolute_bounded(100001, 0))
assert(absolute_bounded(40000, 60000))
assert(agent-facing-wall-admitted(999999))
assert(not agent-facing-wall-admitted(1000000))
assert(not agent-facing-wall-admitted(3000000))
assert(not agent-facing-wall-admitted(10300000))
#+end_src

The later implementation must provide benchmark receipts for warm exact,
warm owner, missing generation, building generation, stale digest, projection
missing, terminal failure, and concurrent multi-session search.

Each receipt records:

- time to first protocol reply;
- reply kind;
- workspace identity and generation digest;
- provider process count, database open count, and write count;
- progressive wait count;
- total background repair duration separately; and
- whether useful evidence or strict graph progress was returned.

A latency improvement is rejected if it returns stale evidence, drops required
graph facts, duplicates dispatch, or weakens fail-closed behavior.
