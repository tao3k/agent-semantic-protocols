#+TITLE: On-demand Runtime workspace admission
#+PROPERTY: ASP_SCHEMA_VERSION 1

* Problem

A healthy global Runtime Server may start with an empty workspace-admission
catalog.  The former read path required a catalog entry before it could open a
Runtime session, while the only operation capable of creating that entry was
reachable through a Runtime session.  Agent dispatch then formed this invalid
fixed point:

#+begin_example
read/search needs active generation
  -> typed Agent route needs Runtime registration
  -> Runtime registration needs a workspace namespace
  -> workspace namespace needs an admitted generation
#+end_example

Restarting the server, disabling the Hook, or adding a client-side catalog
writer does not repair this ownership error.

* Contract

The global Runtime endpoint is the bootstrap authority.  For a canonical
absolute project root, a read-side caller MUST:

1. resolve an existing durable catalog entry as identity evidence, or classify
   =WorkspaceNotAdmitted= as a cold bootstrap;
2. bind the global endpoint to the derived workspace identity in either case;
3. call the daemon-owned =EnsureRuntimeGenerationReady= operation; it MUST
   schedule one discovery when absent or join the existing completion watch
   when startup restore or another caller already owns discovery;
4. wait for terminal Ready without issuing the non-blocking
   =EnsureRuntimeGeneration= operation, whose =discovery-in-progress= receipt is
   not a read barrier;
5. open the read-only workspace session using the admitted identity.

Malformed catalogs, permission failures, identity mismatches, failed builds,
and cancelled builds remain typed failures.  They MUST NOT be converted into a
new catalog or hidden by a fallback.

Concurrent first readers MUST converge on the same workspace identity and the
same admission flight.  The CLI and Hook MUST NOT write
=workspace-admissions.v1.json= directly.  Ordinary Hook policy matching remains
Runtime-independent; only parser/search/session operations that require the
resident data plane may invoke on-demand admission.

* Deadlock freedom obligation

Let =G= mean the global endpoint is healthy, =C= mean the workspace catalog is
admitted, =B= mean bounded daemon admission is reachable, and =R= mean the
read-side generation is ready.  The legacy state =G and not C= had no enabled
transition.  Under this contract, =G and not C and B= enables exactly the
daemon-owned admission transition, producing =C=; readiness then produces
=R=.  No Hook disable/reload state participates in the proof.

* Acceptance

- Start a healthy Runtime Server with zero admitted workspaces.
- Issue concurrent exact/search/session requests for one canonical workspace.
- Observe one workspace identity, one admitted generation, and no duplicate
  resident service.
- Require a nonzero generation before typed Agent call/resume.
- Verify catalog corruption and permission failure stay typed and bounded.
- Verify ordinary Hook black/white matrices have no Runtime dependency and
  stay within the one-millisecond CPU budget.

* Agent control-plane independence

AgentSessionRegistry and ChoicePlane operations are global Runtime control-plane
operations keyed by the derived workspace identity.  They MUST bind through the
global endpoint and MUST NOT pass through the Hook admission locator, source
generation catalog, or generation readiness gate.  A slow or failed source
generation therefore cannot prevent typed Agent create/register/call/resume.

* Protocol-interface authority and artifact scope

Workspace admission MUST bind to a versioned protocol-interface catalog, not to
the byte identity, size, filesystem path, or publication receipt of the ASP
Runtime binary.  The catalog is the language-neutral authority for capability
identities and their request and response schema digests.  A provider
registration binds one implementation identity to those interfaces; its binary
digest remains supply-chain evidence owned by the global provider registry and
is not a workspace active-artifact prerequisite.

The Runtime release catalog, provider implementation registry, and workspace
generation catalog are three distinct authorities:

- a Runtime release is global and may be atomically replaced without changing
  project identity, workspace identity, or an admitted workspace generation;
- a provider registration is global and may become unavailable or stale
  without making AgentSessionRegistry or ChoicePlane unavailable;
- a workspace generation contains only the project/workspace identity, source
  snapshot identity, protocol-interface catalog generation, and references to
  selected provider registrations.

Legacy workspace-local =active-asp-artifact-receipt.v1.json= files MAY be read
as migration evidence, but MUST NOT be admission authority.  A stale or missing
legacy receipt can degrade a provider capability to a typed
=provider-unavailable= result; it cannot produce =source-unavailable= for the
global control plane and cannot prevent namespace creation.

* Proof obligations for bootstrap independence

The executable design and its Lean model MUST establish all of the following:

1. From a healthy global Runtime and a valid derived workspace identity, the
   zero-generation state has a transition that creates the first namespace and
   admits a nonzero generation without requiring a pre-existing namespace.
2. Agent create/register/call/resume remains reachable when every language
   provider is unavailable.
3. A stale Runtime or provider artifact receipt affects only the corresponding
   global release or capability selection; it cannot revoke workspace identity
   or global control-plane reachability.
4. Atomic ASP binary replacement preserves project identity, workspace
   identity, admitted generation identity, and protocol-interface identity.
5. The admission dependency relation is well-founded: bootstrap control-plane
   operations have rank zero, workspace generation has rank one, source
   materialization has rank two, and provider query execution has rank three.
   No transition may depend on an operation of equal or greater rank.

The formal owner for these obligations is
=ASPProof.ProtocolInterfaceBootstrapSeparation=.  Its audit surface MUST expose
=zero_generation_bootstrap_progress=,
=first_namespace_creation_requires_no_existing_namespace=,
=provider_unavailable_does_not_block_global_control_plane=,
=stale_runtime_receipt_does_not_block_global_control_plane=,
=stale_provider_receipt_degrades_only_provider_capability=,
=runtime_binary_refresh_preserves_workspace_and_interface_identity=,
=admission_dependency_is_acyclic=, and
=bootstrap_control_plane_has_no_admitted_dependency=.

* Restore-first freshness separation

Runtime startup MUST NOT perform live Git worktree discovery before restoring a
previously validated canonical generation.  =RestoreOnly= validates the durable
materialization, provider catalog identity, checksums, and publication pointer,
then publishes it resident with a schema-valid restore identity.  Live candidate
discovery starts only after Ready and runs in the daemon background.  A changed
candidate enters the existing single admission/mutation lane; it never starts a
second build and never blocks initial durable restore.

The restore identity is not freshness evidence and MUST NOT be exposed as a
current Git candidate.  Read readiness and candidate freshness are separate
facts.  Exact owner reads additionally reconcile their owner atomically, while
broad search transitions to the new generation after background reconciliation.
