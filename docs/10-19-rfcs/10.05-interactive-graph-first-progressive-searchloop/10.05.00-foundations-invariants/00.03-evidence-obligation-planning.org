#+TITLE: Evidence Obligation Planning
#+OPTIONS: toc:2

#+property: rfc_layer 10.05.00-foundations-invariants

* Decision

SearchLoop requires an Evidence Query Planner, not a larger node ranker.  The
planner compiles intent and contract requirements into typed evidence
obligations, constructs bounded acquisition plans, and leaves closure judgment
to an independent validator.

Graph ranking is an optimization input.  It cannot define which evidence is
required, whether alternatives are sufficient, or whether the loop may close.

The planner's online retrieval refinement is defined by
[[file:../10.05.10-interactive-searchloop/00.06-clause-first-retrieval-and-graph-on-demand.org][Clause-first
retrieval and graph-on-demand]].  Its logical query unit is defined by
[[file:00.07-bound-evidence-clause-algebra.org][Bound evidence clause algebra]].

The shared obligation and plan schema MUST be defined before any Python or
provider-specific implementation.  The =asp-python-graphs= Python service
implements or accelerates this contract; it does not own the contract.

* Obligation algebra

The initial shared algebra SHOULD represent:

- owner and project identity;
- symbol, item, or exact selector identity;
- dependency and reachability facts;
- policy findings and their scope;
- test or failure reachability;
- provider capability and route identity;
- source snapshot freshness;
- contradiction resolution;
- exact materialization requirements.

Obligations compose through typed =all=, =any=, and dependency nodes.

For =all(children)=, every child must be discharged.  For =any(children)=, one
child may discharge the parent only through a declared sufficiency rule.
Ranking a branch first does not make it sufficient.

An obligation carries stable identity, provenance requirement, freshness
requirement, acceptable evidence kinds, budget class, and terminal behavior
when it cannot be discharged.

* Compilation boundary

The obligation compiler consumes:

- normalized intent;
- explicit owner, selector, failure, dependency, or changed-file anchors;
- applicable RFC and shared-schema requirements;
- provider capabilities;
- workspace and source generation identity;
- policy overlay;
- user-supplied budget or risk constraints.

It emits an obligation graph plus a trace from every obligation to the intent or
contract clause that introduced it.  It MUST NOT add a hidden closure
requirement or silently drop an expensive obligation.

* Evidence plan

An evidence plan contains:

- obligation identities it intends to discharge;
- ordered, batched, or independent branches;
- action preconditions;
- provider and projection requirements;
- expected evidence kinds;
- bounded cost estimates;
- branch and continuation identities;
- fallback terminal states;
- canonical transcript order.

The plan is a proposal.  Execution may return different evidence, a typed miss,
stale state, provider block, contradiction, or budget exhaustion.

* Planner, scheduler, and validator separation

The planner selects a sound plan from the current frontier.  The scheduler
executes enabled branches serially or concurrently.  The validator checks
freshness, provenance, contradiction, obligation discharge, and closure.

These components MUST NOT share an unchecked mutable =closed= flag.

A learned planner may choose a cheaper branch.  It may not:

- redefine obligation sufficiency;
- suppress a required branch without a proof of discharge;
- treat command success as evidence success;
- convert a provider failure into absence of a fact;
- close from rank score or self-reported confidence.

* Deterministic parallel projection

Parallel execution is allowed when branch independence has been established.
Branch completion order is runtime detail.  The model-facing transcript uses
stable plan and branch identities and a canonical ordering.

Canonical projection improves cache stability but cannot hide timing-dependent
conflicts.  Incompatible generations or contradictory evidence produce a
conflict transition.

* Closure validation

Closure requires:

- every required obligation discharged by compatible, fresh evidence;
- every selected =any= branch carrying its sufficiency witness;
- no unresolved contradiction;
- exact-evidence obligations materialized through parser-owned selectors;
- the terminal receipt bound to the current obligation graph, workspace,
  snapshot, provider contracts, and policy overlay.

An empty scheduler queue or exhausted plan is not closure.

* Typed non-success

Planning and execution may terminate as:

- =needs-input= for unresolved user choice;
- =blocked= for unavailable owner, provider, or external state;
- =budget-exhausted= with the remaining obligation frontier;
- =stale= with required rebase identity;
- =contradictory= with the conflicting evidence set;
- =no-sound-plan= with the unsupported obligations.

These are protocol results, not stderr-only failures.

* Acceptance receipts

Representative-project receipts record:

- obligation count and graph shape;
- plan branches and actual branch execution count;
- provider and model calls;
- evidence bytes and model-facing projected bytes;
- closure or typed non-success reason;
- obligations incorrectly omitted or accepted;
- cold and warm latency;
- deterministic projection digest;
- counterexample and adversarial validation results.

Optimization is accepted only after closure quality is unchanged or improved.

* Change-aware mapped evidence

The planner does not persist high-volatility Coding Search results in a
database.  Within one admitted source generation it maintains a bounded
resident mapping graph over independently produced =EvidenceAtom= values.
Atoms retain producer-axis provenance; typed edges express =same-source=,
=grounds=, =supports=, =contradicts=, and =derives-from=.  Mapping requires a
canonical source identity or parser grounding proof and never turns a
path/lexical match into an exact selector.

This graph accelerates second and later rounds but is disposable.  Rebuilding
it from the same five-axis receipts is semantically equivalent.  Persistence is
reserved for low-volatility Workspace property facts; generation-local mappings
and source-derived relations remain resident artifacts.

* Round comparability and trajectory delta

A progressive round names its query-set predicate, mapping-version, provider
contract, schema, Project/Workspace, and source-generation identities.  Two
rounds are directly comparable only when those validity domains match.  A
generation change requires an explicit relocation proof for every retained
source identity.

The trajectory classifier emits six disjoint identity sets:

- =new=: first admitted appearance;
- =retained=: same valid fact and provenance;
- =strengthened=: additional independent support or stronger grounding;
- =weakened=: support removed without contradiction;
- =contradicted=: a current admitted contradiction exists; and
- =disappeared=: absent from the current bounded result.

=disappeared= is not semantic absence.  Query refinement, truncation, incomplete
coverage, provider failure, or unproved relocation all explain disappearance
without proving the fact false.  Complete absence still requires the
untruncated five-axis owner-universe witness.

Projection sends identity/relation deltas and changed validity fields.  It does
not resend retained evidence bodies.  This makes token cost proportional to
semantic change rather than accumulated rounds.

* Minimal invalidation and reuse

Each atom names the minimal authority and witness dependencies that determine
validity.  A change produces exactly one of:

- =reusable=: complete semantic identity remains valid;
- =revalidation-required=: stable source identity remains but an independently
  checkable authority or relocation condition changed; or
- =invalid=: source identity, parser/provider contract, or required parent is
  no longer admitted.

Invalidation follows =derives-from= edges forward.  One invalid parent
invalidates every dependent derived fact.  Unrelated workspace changes do not
blanket-invalidate atoms whose minimal witness and authorities still validate.

* Budgeted action selection

For a candidate action (a), the planner considers a value vector rather than
a truth score:

[
V(a)=(Delta O,Delta C,Delta S,R,N,T,L,I),
]

where the components are obligation discharge, contradiction gain, selector
progress, future reuse, novelty, token cost, latency, and invalidation risk.
The first five are benefits and the last three are costs.  Feasibility under
the current token, latency, provider, and risk budgets precedes ranking.

The selected action MUST be nondominated among feasible actions under the
declared policy.  Scalarization, learned ranking, or ExTS may break ties and
choose execution order, but cannot establish evidence truth or closure.

* Change-aware acceptance metrics

Evaluation reports at least:

- token-to-closure and time-to-first-valid-selector;
- provider/search/model calls avoided;
- retained-body bytes avoided by delta projection;
- reusable, revalidated, and invalidated atom counts;
- invalidation precision and missed-invalidation findings;
- obligations discharged per executed action;
- unnecessary branch ratio; and
- false closure count, which MUST remain zero.

* Temporal model and TLA+ boundary

Lean proves local construction and implication laws.  TLA+ owns the temporal
countermodels in which mutation, evidence invalidation, revalidation,
generation publication, and concurrent readers interleave.

The executable small model is
[[file:../../../../../../packages/proofs/tla/ChangeAwareEvidenceTrajectory.tla][ChangeAwareEvidenceTrajectory.tla]]
with
[[file:../../../../../../packages/proofs/tla/ChangeAwareEvidenceTrajectory.cfg][its TLC configuration]].
It models old, building, and active generations without overwriting immutable
reader snapshots.

The required invariants are:

- every published derived fact has all parents in the same published evidence
  set;
- a generation cannot publish while revalidation remains pending;
- the active evidence set equals the atomically published generation;
- each reader observes exactly its leased immutable generation; and
- affected evidence not explicitly revalidated cannot silently reappear in the
  next active generation.
- the affected set equals the declared change-impact closure; and
- =new=, =retained=, and =disappeared= exactly partition the previous/current
  round evidence sets rather than reflecting presentation order.

TLC counterexamples are design feedback.  They must update this RFC, the shared
trajectory schema, and Lean obligations before implementation is accepted.

The lifecycle module is the initial reference-model scenario, not a sufficient
implementation of autonomous formal bug finding.  The conformance path is
informed by
[[https://arxiv.org/html/2607.25333v2][Specula: Scaling formal specifications
for autonomous model checking of system code]] and additionally requires:

1. invariants and scenarios grounded in code, tests, documentation, issues, or
   revision evidence;
2. one immutable reference model plus bounded scenario projections;
3. typed model-action/model-variable to code-location mappings;
4. code instrumentation and trace replay that validate model-code conformance;
5. model checking only after the applicable conformance boundary is satisfied;
6. code-level reproduction or independent trace validation of a model
   counterexample; and
7. evidence-backed adjudication among model gap, code bug, invariant gap, and
   unresolved.

The self-evolving loop must add information at every iteration.  Passing trace
validation by weakening guards, adding permissive transitions, hardcoding one
trace, or silently weakening an invariant is an invalid repair.

** Past, current, and future semantics

The three temporal perspectives have different evidence meanings and MUST NOT
be collapsed:

- =past= revisions, fixes, issues, and tests provide scenario and invariant
  evidence, especially when repeated fixes or inconsistent paths identify a
  vulnerable behavior;
- =current= source/parser identities and execution traces establish what the
  active implementation actually admits; and
- =future= in model checking means reachable successor states of the current
  or explicitly proposed candidate model, not a prediction of unspecified
  future code.

A proposed code change may be admitted as a separate candidate snapshot and
compared with the current reference/scenario models before publication.  Its
impact result remains candidate-scoped until code-trace conformance or an exact
implementation witness is available.

Fast fd/rg/Tantivy/parser evidence is useful at this boundary because it
identifies changed actions, variables, branches, fixes, and tests cheaply.
Those hits become grounded scenario/invariant evidence mappings; they do not
become formal invariants merely because the same term appears across revisions.

* Model-facing impact interface

The shared trajectory contract is consumer-neutral.  Any admitted agent-facing
client receives the same bounded relation projection; product names, task
categories, and conversational examples are not protocol enum values.  The
projection supports four relation-oriented questions:

- =WHY=: which admitted mappings and parent facts support this conclusion;
- =WHY-NOT=: which unresolved or contradicted obligations prevent closure;
- =IMPACT=: which evidence, selectors, obligations, and candidate actions are
  reachable from the changed identities; and
- =CHANGED-BY=: which source, manifest, provider, schema, policy, or rule
  identities caused the current invalidation/revalidation state.

These are projections of one admitted impact graph.  They are not four
independent text explanations, and model-generated prose is not impact
authority.

The common contract uses registered =ProducerIdentity= values rather than a
closed list of products or tools.  Search specializes that contract by binding
its five required producer identities and proving five-axis completeness;
other reasoning workflows can reuse evidence/impact relations without becoming
Search protocol variants.
