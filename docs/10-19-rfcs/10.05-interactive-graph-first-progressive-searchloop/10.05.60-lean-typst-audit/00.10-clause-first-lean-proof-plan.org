* Scope
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-SCOPE
:END:

This module defines the RFC-to-AXLE-to-Lean workflow for Clause-first Retrieval
and Graph-on-Demand.  It does not contain Lean implementation and does not
declare the design ready for Rust or Python implementation.

Lean theorem and counterexample sources belong to the independent
=packages/proofs= container.  AXLE extraction remains a separate producer under
=packages/python/tools=.

* Modeling goal
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-GOAL
:END:

The formal model must determine whether Clause-first retrieval is a sound
refinement of the admitted graph-and-query semantics for declared scenario
classes.

It is not sufficient to prove that an implementation follows its own planner.
The model must expose cases where:

- postings cannot reconstruct the logical fact;
- local clauses cannot justify a graph-sensitive conclusion;
- budget or ranking hides a mandatory obligation;
- freshness or identity changes invalidate reuse;
- parallel execution changes meaning;
- improvement policy widens allowed behavior.

* Refinement diagram
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-REFINEMENT
:END:

The proof relation is:

#+begin_example
physical postings
  --reconstruct/admit-->
qualified logical facts
  --bind/classify-->
bound clause frontier
  --escalate when required-->
admitted EvidenceGraph
  --exact selector materialization when required-->
closure validator
#+end_example

Clause-first execution is sound when every accepted clause result has an
equivalent admitted fact/graph interpretation and every closed result satisfies
the same closure proposition as the reference graph-and-query semantics.

Performance superiority is evaluated by receipts, not proved as a universal
theorem.

* Counterexample-first sequence
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-COUNTEREXAMPLES
:END:

Before proving the desired refinements, construct finite witnesses for:

1. n-ary qualifier erasure;
2. Cartesian reconstruction from unrelated postings;
3. stale-snapshot binding reuse;
4. top-k used as enumeration;
5. absence over incomplete scope;
6. clause dependency cycle;
7. global-pool starvation;
8. parallel order-dependent merge;
9. provider-crossed cache key;
10. cost signal suppressing mandatory escalation;
11. provider capability asymmetry;
12. owner alias across worktrees;
13. selector handoff drift;
14. multi-hop binding explosion;
15. incomplete cross-namespace join;
16. learned easy-clause bias;
17. relation/source contradiction;
18. context key overbinding and underbinding.

If the current RFC permits a witness, the RFC is repaired before the theorem is
weakened.

* Liveness qualification
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-LIVENESS
:END:

The RFC does not require a planner to find evidence that does not exist or to
solve every query within a finite positive budget.

The liveness claim is qualified:

For every well-formed non-terminal state, SearchLoop either has an enabled
bounded action, requires graph escalation, needs user input, is blocked by a
typed external condition, exhausts budget with an explicit frontier, or has no
sound plan.

This avoids assuming planner completeness while prohibiting silent deadlock.

* AXLE declaration workflow
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-AXLE-WORKFLOW
:END:

1. extract stable RFC clause, claim, and risk identities;
2. generate a declaration bundle with definitions, assumptions, desired
   invariants, counterexample obligations, and dependencies;
3. classify every imported premise as environmental, parser/provider contract,
   shared-schema contract, or proposition under test;
4. reject theorem-as-axiom cycles;
5. emit logical Lean module boundaries without inventing implementation paths;
6. bind the bundle to RFC and schema digests;
7. record unmapped prose as a formalization gap.

AXLE output is reviewed before Lean proof work begins.

* Lean execution workflow
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-EXECUTION
:END:

1. define identities and validation-domain compatibility;
2. define qualified facts and postings separately;
3. implement finite counterexample models for the risk register;
4. define clauses, bindings, and classification;
5. define transitions without closure assumptions;
6. prove representation and binding safety;
7. prove bounded progress or typed terminal coverage;
8. define graph escalation and closed-scope evidence;
9. prove exact handoff and closure soundness;
10. prove cache and continuation validity;
11. prove concurrency properties;
12. prove improvement-policy refinement;
13. run axiom and unsafe-declaration inventory;
14. emit proof and counterexample receipts.

Proof work is incremental.  Each failed layer can revise the RFC before later
layers accumulate dependencies.

* Failure classification and RFC repair
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-REPAIR
:END:

A failed target is classified as:

- contradictory RFC clauses;
- missing premise;
- lossy representation;
- underspecified state transition;
- invalid escalation boundary;
- unprovable completeness or absence;
- progress/fairness gap;
- cache equivalence gap;
- concurrency conflict;
- unsafe improvement refinement;
- modeling error;
- later implementation obligation.

For RFC defects, preserve the minimal witness, update the claim/risk ledger,
revise the normative clause, regenerate the AXLE bundle, invalidate dependent
proof receipts, and rerun the witness before continuing.

* Proof receipt
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-RECEIPT
:END:

The receipt reports:

- RFC, schema, and AXLE bundle digests;
- theorem, counterexample, claim, risk, and clause identities;
- all axioms and environmental assumptions;
- =sorry=, =admit=, unsafe, and opaque-external inventory;
- proof or witness status;
- dependent receipts invalidated;
- Lean toolchain and package identity;
- unresolved formalization gaps.

Textual alignment, successful compilation, or an empty counterexample search is
not proof closure.

* Implementation readiness
:PROPERTIES:
:ID: ASP-RFC-10.05-CFR-LEAN-READINESS
:END:

Clause-first implementation is not ready merely because the RFC modules exist.
Readiness later requires:

- parser-confirmed AXLE and Lean package owners;
- versioned shared clause, posting, escalation, and receipt schemas;
- resolved critical CFR-R01 through CFR-R20 witnesses;
- proved representation, binding, escalation, and closure safety;
- provider capability-alignment plan;
- shadow equivalence scenarios and receipts;
- explicit implementation refinement mapping.

The current Session stops at RFC and proof-plan design.
