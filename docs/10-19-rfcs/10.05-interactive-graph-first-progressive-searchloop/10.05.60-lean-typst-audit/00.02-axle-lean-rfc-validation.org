* Status and session boundary

This module defines the formal-validation contract for the SearchLoop RFC.
During the current RFC-design session no Rust, Python, AXLE, or Lean
implementation is assumed complete.  AXLE extraction and declaration-bundle
tooling belongs under =packages/python/tools=.  Lean mathematical models,
counterexamples, theorem sources, and proof receipts belong independently under
=packages/proofs=.  The two packages MUST communicate through a versioned
declaration bundle rather than Python importing or owning Lean proof sources.

* Decision

Lean is not a certification wrapper around accepted RFC prose.  AXLE translates
the RFC into an explicit mathematical model so Lean can expose contradictions,
missing preconditions, non-progress states, unsafe transitions, and properties
that cannot be derived from the stated assumptions.

The validation loop is:

#+begin_example
RFC clauses
  -> AXLE declaration and traceability model
  -> Lean definitions, theorems, and adversarial obligations
  -> proof, independence result, or minimal counterexample
  -> RFC defect classification
  -> RFC revision
  -> invalidation and replay of affected proofs
#+end_example

A proof failure MUST be investigated as a possible RFC design failure before it
is classified as a proof-engineering problem.

* Authority boundary

| Artifact | Authority |
|-
| Org RFC | Design intent, terms, ownership, and normative requirements |
| AXLE declaration bundle | Clause-to-model mapping and proof obligations |
| Lean model | Mathematical meaning of state, transition, invariant, and closure |
| Lean theorem | Derivability under explicitly reported assumptions |
| Counterexample witness | Evidence that an invariant or progress claim does not follow |
| Runtime receipt | Evidence that an implementation conforms to a proved model |

Neither AXLE nor Lean may silently strengthen an RFC requirement.  Assumptions
introduced during formalization remain visible and are reported back as missing
RFC premises.

* Traceability contract

Every formal declaration MUST identify:

- a stable RFC clause identity;
- the RFC source digest;
- the mathematical declaration identity;
- whether it is a definition, assumption, invariant, liveness obligation,
  refinement obligation, or implementation obligation;
- the assumptions on which it depends;
- its proof, counterexample, blocked, or unmodeled state;
- the proof artifact digest.

RFC display line numbers are not stable identities.  Heading text alone is also
insufficient when it can be duplicated or renamed.  The declaration bundle
MUST use stable clause identities that survive ordinary document movement.

Changing a clause or dependency invalidates all transitive proof receipts.

* SearchLoop mathematical model

The initial model SHOULD define at least:

- =WorkspaceIdentity= and =ProjectIdentity=;
- =SourceSnapshot= and evidence generation;
- =Intent= and explicit anchors;
- =CandidateIdentity= and parser-owned =Selector=;
- =Evidence= and accepted evidence set;
- =Obligation=, obligation dependency, and declared sufficiency rule;
- =EvidencePlan= with sequential, batch, and independent branch composition;
- =Frontier= and unresolved obligation set;
- =Budget= for items, bytes, latency, and materializations;
- =CacheEntry= with witness set and freshness predicate;
- =LedgerEvent= and derived =ImprovementState=;
- =ContinuationIdentity=;
- =Action= with =orient=, =discover=, =inspect=, =refine=,
  =materialize=, and =close=;
- =TerminalState= with =closed=, =needs-input=, =blocked=, and
  =budget-exhausted=;
- a transition relation =Step(state, action, state')=.

Rendered CLI commands are not part of the semantic state.  CLI parsing is a
separate refinement from adapter input into an allowed transition.

* Safety invariants

The first AXLE declaration bundle MUST express at least these invariants:

** Workspace authority

One loop transition cannot silently change canonical workspace, project, or
source snapshot.  A detected generation change requires an explicit rebase or
typed stale-state result.

** Exact materialization

=materialize= consumes a parser-owned selector.  It does not perform discovery,
guess an owner, or accept a display line range as exact identity.

** Inspect confinement

=inspect= expands identities already present in the frontier.  It cannot search
for a new owner, change workspace scope, or return unbounded source content.

** Evidence provenance

Every accepted fact names its provider, source generation, and derivation.
Evidence from incompatible generations cannot be merged without an explicit
reconciliation transition.

** Budget monotonicity

A non-terminal transition either decreases a finite budget, adds new accepted
evidence, removes a frontier obligation, or records an explicit rebase.  The
loop cannot make an invisible no-progress transition.

** Fail-closed provider routing

A declared native provider capability cannot silently fall back to a legacy
process.  Provider unavailability produces a typed blocked or recovery state.

** Closure soundness

=closed= requires the stated intent to be supported by accepted evidence and
all required obligations to be discharged.  Packet compactness, command
success, or an empty frontier alone is not closure proof.

* Progress and termination obligations

For every well-formed non-terminal state, the model MUST establish one of:

- an enabled bounded transition exists;
- explicit user input is required;
- an external owner or provider is blocked;
- the budget is exhausted;
- the state is stale and must rebase.

A cycle that neither changes evidence nor consumes budget is invalid.  A
=recommendedNext= proposal is valid only when its preconditions hold in the
current state.  The proof model must not assume that executing a recommendation
will produce a hit.

* Concurrency obligations

Independent frontier branches may execute concurrently, but the sequential
contract remains normative.  AXLE MUST identify when two transitions commute
and when they conflict.

Evidence merges require compatible workspace, snapshot, provider contract, and
selector identities.  If branch order changes the accepted result, the model
must require serialization or an explicit conflict transition.

* Adversarial model obligations

The Lean validation plan MUST attempt to construct witnesses for:

- stale source snapshot after candidate discovery;
- ambiguous provider or language ownership;
- selector relocation that resolves to a different semantic item;
- an inspect transition that escapes its candidate set;
- contradictory facts from two providers or generations;
- a no-hit search with an invalid =recommendedNext=;
- exhausted budget with a non-terminal state;
- a loop that repeats without evidence delta;
- concurrent branches whose merge is order-dependent;
- closure based only on command success;
- unavailable native provider followed by silent legacy fallback.

The absence of an automatically generated counterexample is not itself a proof.

* Lean construction order

Lean work follows the dependency order below.  These are logical module names;
their filesystem paths are owned by the independent =packages/proof= Lean
package.

1. =RFCTrace= defines stable clause identities, digests, assumption inventory,
   and declaration traceability.
2. =Identity= defines workspace, project, provider, snapshot, candidate, and
   selector identities plus compatibility relations.
3. =Obligation= defines atomic obligations, AND/OR composition, dependency, and
   sufficiency witnesses.
4. =State= defines well-formed SearchLoop state, frontier, evidence, budgets,
   continuation, and terminal states.
5. =Transition= defines allowed actions and the =Step= relation without yet
   assuming progress or closure.
6. =Closure= defines discharge, contradiction, freshness, and closure
   soundness.
7. =Cache= defines reuse validity and proves that a valid hit preserves
   discharge and closure judgments.
8. =Concurrency= defines branch independence, canonical receipt ordering,
   commutation, and conflict.
9. =Improvement= defines artifact-ledger projection and proves that advisory
   policy updates refine rather than widen the allowed transition system.
10. =Counterexamples= contains constructive stale-state, invalid-next-action,
    no-progress, cache-poisoning, and order-dependent merge witnesses.

Counterexample attempts begin as soon as each definition layer exists; they do
not wait for a final all-green theorem suite.  A desired theorem is stated only
after its terms and assumptions have independent definitions.

The clause-first retrieval refinement has its own detailed theorem and
counterexample plan in
[[file:00.10-clause-first-lean-proof-plan.org][Clause-first Lean proof plan]].

* Core theorem families

The first proof bundle SHOULD target:

- =materialize_requires_exact_selector=;
- =inspect_preserves_workspace_and_candidate_scope=;
- =step_preserves_state_well_formedness=;
- =nonterminal_has_transition_or_typed_terminal=;
- =no_invisible_progress_cycle=;
- =closed_implies_all_required_obligations_discharged=;
- =or_branch_requires_declared_sufficiency=;
- =fresh_cache_hit_preserves_discharge=;
- =stale_cache_hit_cannot_establish_closure=;
- =independent_steps_commute_up_to_canonical_projection=;
- =conflicting_steps_require_serialization_or_conflict=;
- =improvement_policy_cannot_widen_allowed_terminal_states=;
- =ledger_replay_deterministically_rebuilds_improvement_state=.

The planner need not be complete: failure to find a plan may produce a typed
blocked or budget terminal.  It must be sound: any plan accepted for execution
refines the obligation algebra and cannot erase an unresolved requirement.

* Defect classification

Each failed theorem or counterexample is classified as one of:

- =rfc-contradiction=: two normative clauses cannot both hold;
- =missing-premise=: the desired theorem requires an unstated assumption;
- =underspecified-transition=: several incompatible next states are allowed;
- =unreachable-state-claimed=: the RFC requires behavior from a state the model
  cannot construct;
- =non-progress-cycle=: the loop can continue without evidence or budget change;
- =identity-gap=: workspace, snapshot, provider, or selector identity is
  insufficient;
- =schema-gap=: the required fact cannot be represented in a shared packet;
- =projection-gap=: the model is sound but the agent-facing evidence projection
  omits a required fact;
- =implementation-obligation=: the RFC is coherent and the remaining work is
  runtime conformance;
- =modeling-error=: the formalization does not faithfully represent the RFC.

Only the last two classifications are resolved solely outside the RFC.

* RFC repair loop

When Lean exposes a design defect:

1. preserve the theorem failure or minimal witness;
2. identify the smallest set of RFC clause identities involved;
3. state whether the defect changes safety, progress, identity, or projection;
4. revise the RFC before changing the proof obligation;
5. regenerate the AXLE declaration bundle;
6. invalidate affected proof receipts by dependency digest;
7. rerun the failed obligation and its dependent theorem set;
8. record whether the repair excludes the original witness.

Weakening or deleting an obligation solely to obtain a green proof is not an
RFC repair.

* Proof acceptance

An accepted Lean receipt MUST report:

- the RFC and declaration bundle digests;
- theorem and definition identities;
- all axioms and assumptions used;
- absence or explicit inventory of =sorry=, =admit=, unsafe declarations, and
  opaque external facts;
- proof status and affected RFC clauses;
- generated counterexample status;
- Lean toolchain and dependency identity.

A theorem proved from an RFC requirement restated as an axiom provides no
design validation.  AXLE MUST distinguish environmental assumptions from the
properties being tested.

* Readiness gates

SearchLoop is not ready for Rust implementation merely because this RFC is
written.  A later implementation-readiness decision requires:

- parser-owned confirmation of the AXLE extraction owners under
  =packages/python/tools= and Lean theorem owners under =packages/proof=;
- a versioned clause-to-declaration bundle;
- proved core safety invariants or resolved counterexamples;
- progress analysis for every non-terminal state class;
- explicit assumptions with no accidental theorem-as-axiom cycle;
- a proof receipt tied to the current RFC digest;
- an implementation refinement plan that keeps runtime conformance separate
  from model soundness.

The current session intentionally stops before those implementation gates.

* Relationship to RFC 10.06

RFC 10.06 owns graph-route and model-facing evidence projection.  Its sandtable
proof dossier supplies adversarial scenarios and evidence-shape obligations.
This module owns the mathematical SearchLoop state and transition model.

A projection theorem must show that facts required for a valid SearchLoop
transition are representable and available to the agent.  It does not make the
projection layer the owner of SearchLoop semantics or the AXLE/Lean
implementation.
