#+title: Active and Healthy Runtime Artifact Slots
#+startup: overview

* Status

Normative schemaVersion =1= relationship contract.

* Authority

Every Runtime binary is copied into the State Home content store before it
becomes executable:

#+begin_example
runtime/artifacts/blake3-256/<digest>/<binary>
#+end_example

The configured development root and a locked release are source provenance.
Neither a checkout build path, =~/.local/bin=, ambient =PATH=, nor a caller
selected target is executable authority. Development and release use the same
publication algorithm and the same BLAKE3 content identity.

Each binary owns two stable selection slots:

#+begin_example
runtime/profiles/<binary>/active
runtime/profiles/<binary>/healthy
runtime/bin/<binary> -> runtime/profiles/<binary>/active
#+end_example

=active= selects the current candidate. =healthy= selects the last generation
qualified by Runtime health. The first verified publication seeds both slots
with the same digest, which consumes one physical generation. Later publication
moves only =active=. A health transition may move =healthy= only when its
observed Runtime binary digest equals the current active digest.

The plugin launcher may resolve the public alias, then =active=, then =healthy=.
It does not parse Host payloads, recognize bypass variables, inspect config, or
implement policy. It selects with shell builtins and =exec=s the same =asp hook=
Rust owner in place, so the launcher does not retain a waiting parent process.

* Invariants

For every binary identity:

1. both slots resolve only inside the BLAKE3 content store;
2. the public alias resolves through =active= and never into a checkout;
3. selection prefers =active= and uses =healthy= only when active is absent or
   non-executable;
4. a stale health receipt cannot qualify newer active bytes;
5. garbage collection retains exactly the distinct digests reachable through
   =active= and =healthy= and removes every other generation;
6. at most two physical generations remain reachable per binary;
7. an equal active/healthy digest occupies one physical generation;
8. publication and health promotion are Tokio-owned asynchronous operations;
9. blocking filesystem transactions run only through Tokio's blocking pool;
10. schema identity and schemaVersion own wire compatibility; Rust namespaces
    and schema IDs remain version-neutral.

* Transitions

#+begin_example
Empty
  -- publish verified A --> Active(A), Healthy(A)

Active(A), Healthy(H)
  -- publish verified B --> Active(B), Healthy(H)
  -- health observes B --> Active(B), Healthy(B)

Active unavailable, Healthy(H)
  -- launcher fallback --> execute H
#+end_example

Publication stages bytes, verifies the staged digest, atomically publishes the
content generation, initializes =healthy= only when absent, moves =active=, and
repairs the public alias. Health promotion binds the cached Runtime identity to
the active digest before atomically moving =healthy=. Reachability collection
runs after each transition.

* Interface conformance

The executable interface consists of the shared Runtime artifact reference,
identity, and retention schemas. The retention receipt reports:

- =contentAlgorithm: blake3-256=;
- =retentionPolicy: active-healthy-reachability=;
- =retainedSlotsPerBinary: 2=;
- distinct =protectedDigests= derived from stable slots.

The implementation emits only content identity and active/healthy reachability.
Schema namespaces and receipt filenames remain version-neutral.

* Lean correspondence

=packages/proofs/ASPProof/ASPActiveHealthyArtifactRetention.lean= proves:

- reachability contains at most two distinct digests;
- first publication seeds active and healthy;
- later publication preserves healthy;
- active precedes healthy and missing active selects healthy;
- matching health promotes active;
- stale health cannot promote a newer active generation;
- equal slots consume one physical generation.

=RuntimeArtifactAuthority.lean= separately proves that checkout builds and
local PATH entries are provenance or external inputs, never executable domains.
The Rust scenario and schema suites are the executable refinement of these
theorems; Lean success alone is not a Runtime conformance receipt.

* Acceptance gates

- Delete the checkout build after publication; the public active executable
  remains readable and executable.
- Publish at least three distinct versions; only active and healthy digests
  remain.
- Remove or break the public alias and active slot; the launcher executes the
  healthy generation without a second binary or policy implementation.
- Present stale health for a newer active digest; promotion fails closed.
- Validate the version-neutral reference, identity, and retention schemas.
- Run the Lean authority audit without =sorry= or =admit=.
