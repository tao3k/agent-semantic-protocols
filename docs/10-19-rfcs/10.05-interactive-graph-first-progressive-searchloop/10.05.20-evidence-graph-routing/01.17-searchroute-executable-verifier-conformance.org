* Status and authority

This RFC is canonical for proving that a cryptographic transfer receipt was
verified through an executable verifier path rather than accepted from logical
fields or digests alone.

It refines
[[file:01.16-searchroute-cryptographic-transfer-receipt-binding.org][cryptographic transfer-receipt binding]].
It defines runtime evidence obligations without selecting a provider language
or implementing a verifier.

* Lean-discovered execution gap

The abstract =verify : SignatureEnvelope -> Prop= boundary is intentionally
insufficient to prove that a real executable was invoked.

The following evidence is not executable closure:

- matching payload or statement digest;
- a resolved verifier manifest;
- a resolved binary path;
- a zero exit code;
- a decoded accepted response;
- replay performed by the same executor.

Each item is a useful stage receipt. None can replace the complete chain.

Lean constructs an explicit receipt whose digest matches while the verifier is
unresolved. It also constructs an invocation and accepted decode whose replay
uses the same executor. Both prefixes are rejected by the complete predicate.

* Six-stage conformance chain

Executable verification requires all six stages:

1. canonical statement serialization;
2. exact key-registry resolution;
3. exact verifier binary resolution;
4. bound verifier invocation;
5. response decoding and accepted decision;
6. independent replay by a different executor.

Every stage binds the output identity of its predecessor. A later green stage
does not repair a missing or mismatched earlier stage.

* Normative clauses

** ASP-RFC-10.05-EVFC-STAGE-CLOSURE

Executable verification MUST contain all six stage receipts. Admission is the
conjunction of the stage predicates, not the last reported status.

** ASP-RFC-10.05-EVFC-CANONICAL-SERIALIZATION

The statement receipt MUST bind every signature-envelope field, the canonical
serializer digest, statement-schema digest, and serialized statement-bytes
digest. =canonical= MUST be true.

A payload digest without canonical statement serialization is insufficient.

** ASP-RFC-10.05-EVFC-KEY-REGISTRY

Key resolution MUST bind the exact key-registry snapshot, authority digest, key
epoch, algorithm digest, and public-key digest. Resolution MUST succeed and the
resolved key MUST NOT be revoked.

Resolution from another registry snapshot rejects verification.

** ASP-RFC-10.05-EVFC-VERIFIER-RESOLUTION

Verifier resolution MUST bind the verifier identity, executable binary digest,
and signature-algorithm digest. The executable artifact MUST be resolved.

A manifest or binary name without an artifact digest is not executable
evidence.

** ASP-RFC-10.05-EVFC-INVOCATION

The invocation receipt MUST bind:

- verifier binary digest;
- canonical statement-bytes digest;
- resolved public-key digest;
- signature digest;
- executor digest;
- exit code;
- raw response-bytes digest.

The exit code MUST be zero. A zero exit code alone does not imply acceptance.

** ASP-RFC-10.05-EVFC-DECODE

The decode receipt MUST bind the raw response-bytes digest and decoder-schema
digest. Decoding MUST succeed and the decoded decision MUST be accepted.

An undecoded response or rejected decision fails closed.

** ASP-RFC-10.05-EVFC-INDEPENDENT-REPLAY

Independent replay MUST bind the same verifier binary, statement bytes, public
key, signature, and accepted decision. The replay executor digest MUST differ
from the original invocation executor digest.

Repeating a claim within the same executor is not independent replay.

** ASP-RFC-10.05-EVFC-PREFIX-INSUFFICIENT

Digest equality, resolution, invocation, or decoding prefixes MUST NOT be
reported as executable verification closure.

Reports MUST name the highest completed stage and the first missing or
mismatched stage.

** ASP-RFC-10.05-EVFC-CHAIN-PROJECTION

Every executable verification edge MUST project to a valid cryptographic
rotation edge. An executable verification chain MUST project to the
cryptographic chain and retain the exact registry epoch span.

Runtime execution cannot repair invalid semantic identity, authority transfer,
or registry continuity.

** ASP-RFC-10.05-EVFC-GLOBAL-LIFT

Only executable-chain-admitted vector coverage may lift frontier-local Pareto
minimality to global Pareto minimality when the decision depends on an
authority-rotation signature.

* Failure behavior

The executable receipt fails closed when:

- serialization is noncanonical;
- the key is unresolved, revoked, or from another snapshot;
- verifier identity, binary, or algorithm differs;
- invocation inputs do not match resolved artifacts;
- invocation fails;
- the response cannot be decoded;
- the decoded decision is not accepted;
- replay is absent, mismatched, or uses the original executor.

The receipt MUST preserve the stage-specific failure rather than collapse all
failures into =verification failed=.

* Explicit implementation boundary

This RFC proves the dataflow and admission logic only. Provider implementation
must still produce receipts from real process execution and independent replay.
Fixture construction, digest equality, source inspection, or Lean compilation
does not constitute an executable conformance receipt.
