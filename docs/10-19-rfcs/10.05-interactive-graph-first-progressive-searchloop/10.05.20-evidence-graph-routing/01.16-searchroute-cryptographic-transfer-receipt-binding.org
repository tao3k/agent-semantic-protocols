* Status and authority

This RFC is canonical for the signed receipt that authorizes reuse of a
vector-coverage proof across an authority-rotation edge.

It refines
[[file:01.15-searchroute-authority-rotation-chain-continuity.org][authority-rotation chain continuity]].
It defines the proof obligations surrounding cryptographic verification; it
does not select or implement a signature algorithm.

* Lean-discovered cryptographic boundary

A Boolean =oldAuthorityApproved= or =newAuthorityAccepted= records a logical
decision but does not bind that decision to a signed statement.

A rotation-safe receipt must bind:

- one canonical transfer payload;
- the complete old and new registry domains;
- semantic coverage identity;
- a unique nonce;
- issuance and expiry times;
- one replay-domain digest;
- each signer role;
- each authority digest;
- each signer key epoch;
- each signature-algorithm digest;
- the payload digest presented to verification.

Lean also demonstrates that digest equality alone does not establish payload
identity. A constant digest maps two distinct payloads to the same value.
Payload uniqueness therefore requires a separately justified injective or
collision-resistant digest assumption.

* Verification abstraction

The proof kernel treats signature verification as an external proposition:

#+begin_example
verify : SignatureEnvelope -> Prop
#+end_example

Lean proves that every accepted envelope has the required role, authority, key
epoch, algorithm, replay domain, and payload digest before =verify= may
authorize it.

The theorem does not claim that a concrete signature scheme is secure. A
provider must supply an independently tested verifier and bind its algorithm
identity into the envelope.

* Signed payload

The canonical payload contains:

- =semanticIdentity=;
- =fromDomain=;
- =toDomain=;
- =replayDomainDigest=;
- =nonce=;
- =issuedAt=;
- =expiresAt=.

Both signatures bind the same payload digest. The old signature uses role
=oldApprover= and the source-domain authority. The new signature uses role
=newAcceptor= and the destination-domain authority.

* Normative clauses

** ASP-RFC-10.05-CTRB-CANONICAL-PAYLOAD

The receipt MUST contain one canonical transfer payload. The payload MUST equal
the logical authority-transfer certificate in semantic identity and both
registry domains.

Field omission, alternate serialization, or an unbound nonce rejects the
receipt.

** ASP-RFC-10.05-CTRB-DIGEST-BOUNDARY

The stored payload digest MUST equal the result of the selected canonical
payload-digest function.

Digest equality MUST NOT be interpreted as payload equality unless the digest
function has a separately admitted collision-resistance or injectivity
obligation.

** ASP-RFC-10.05-CTRB-DUAL-SIGNATURE-CONTEXT

Both signature envelopes MUST bind the same payload digest. The old envelope
MUST bind role =oldApprover= and the source authority. The new envelope MUST
bind role =newAcceptor= and the destination authority.

Successful verification without these context equalities is insufficient.

** ASP-RFC-10.05-CTRB-REPLAY-DOMAIN

The payload and both signatures MUST equal the active replay-domain digest.

Verification of the same signature bytes in a different workspace, project,
protocol, or publication domain MUST fail closed.

** ASP-RFC-10.05-CTRB-KEY-EPOCH

Each signature MUST bind the exact admitted key epoch for its authority.
Revoked key epochs reject new transfer admission even when the signature
verifier still accepts the bytes.

Historical audit may retain the receipt under the archived key registry, but it
does not authorize new coverage reuse.

** ASP-RFC-10.05-CTRB-ALGORITHM

Each signature envelope MUST bind the admitted signature-algorithm digest.
Changing or migrating the algorithm policy rejects an old receipt unless a
separate migration certificate explicitly reauthorizes it.

** ASP-RFC-10.05-CTRB-TEMPORAL-SCOPE

Transfer admission requires:

#+begin_example
issuedAt <= now < expiresAt
#+end_example

An expired payload or a revoked signer key rejects the receipt.

** ASP-RFC-10.05-CTRB-CHAIN-PROJECTION

Every cryptographically valid rotation edge MUST also be a valid logical
authority-rotation edge. A cryptographic rotation chain MUST project to the
authority-rotation chain and retain its exact epoch span.

Cryptographic verification cannot repair a disconnected or forked registry
chain.

** ASP-RFC-10.05-CTRB-GLOBAL-LIFT

Only cryptographic-chain-admitted vector coverage may lift frontier-local
Pareto minimality to global Pareto minimality across authority rotation.

* Failure behavior

The receipt fails closed when:

- payload and logical transfer fields disagree;
- the canonical payload digest does not match;
- signer role or authority differs;
- either signature binds a different payload;
- replay-domain digest differs;
- key epoch differs or is revoked;
- algorithm digest differs;
- the payload is not yet valid or has expired;
- the cryptographic edge does not project to a valid logical rotation edge.

Failure invalidates new proof reuse. Archived receipts remain available for
historical audit under their original verifier, key registry, and replay
domain.

* Remaining boundary

The abstract =verify= proposition still needs a provider-facing conformance
contract proving canonical byte serialization, signature-verifier invocation,
key-registry resolution, and independent replay. Digest and Lean-proof success
alone do not establish executable cryptographic verification.
