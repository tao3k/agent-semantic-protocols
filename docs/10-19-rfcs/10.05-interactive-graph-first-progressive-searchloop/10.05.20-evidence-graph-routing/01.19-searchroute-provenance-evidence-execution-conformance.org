* Status and authority

This document is the canonical executable-evidence extension of
[[file:01.18-searchroute-verifier-artifact-provenance.org][RFC 10.05.20/01.18]].

RFC 01.18 establishes the structural provenance conjunction: immutable source,
hermetic recipe, bound build attestation, transparent publication, and an
independent rebuild.  This RFC establishes how the decision claims inside that
conjunction become executable evidence rather than trusted Boolean fields.

* Lean-discovered Boolean evidence gap

RFC 01.18 contains fields such as:

- =immutable=;
- =hermetic=;
- =attestationSignatureVerified=;
- =included=;
- =checkpointSignatureVerified=;
- =appendOnlyConsistent=;
- =fresh=;
- =rebuildSucceeded=; and
- =outputCompared=.

These fields are useful decoded decisions, but their names do not prove how the
decision was obtained.  Treating =accepted = true= as complete evidence loses:

1. the type of claim that the verifier evaluated;
2. the exact subject of the claim;
3. the policy version used by the verifier;
4. the verifier binary that was resolved;
5. the canonical statement sent to the verifier;
6. the response that was decoded; and
7. whether an independent executor replayed the same decision.

The Lean counterexamples show that an accepted Boolean can coexist with an
unresolved verifier.  They also show that subject-only binding permits a
recipe-verification decision to be replayed as a source-immutability decision.

* Typed provenance claims

The protocol defines eight non-interchangeable claim kinds:

| Claim kind | Bound subject |
|-
| =sourceImmutable= | source snapshot digest |
| =recipeHermetic= | build recipe digest |
| =buildAttestation= | canonical provenance statement digest |
| =transparencyInclusion= | current transparency root digest |
| =checkpointConsistency= | checkpoint-transition statement digest |
| =checkpointFreshness= | current checkpoint digest |
| =independentRebuild= | rebuilt verifier binary digest |
| =outputComparison= | attested verifier binary digest |

A claim for one row MUST NOT satisfy another row merely because its subject
digest happens to be equal.  Claim kind, subject, and policy are independent
binding axes.

* Five-stage executable claim closure

Each typed claim uses the following five stages.

** Canonical claim statement

The claim kind, subject digest, policy digest, serializer, statement schema,
and canonical statement bytes are bound together.

** Claim-aware verifier resolution

Resolution binds the claim kind and policy to the verifier identifier and
verifier binary.  A generic executable that does not advertise the selected
claim kind and policy is not an admissible resolver result.

** Bound invocation

Invocation binds the canonical statement bytes and resolved binary to the
claim kind, subject, policy, executor, response bytes, and successful exit.

** Decoded accepted decision

Decoding binds response bytes to the configured decoder schema.  Both
=decoded= and =accepted= must be true.

** Independent replay

Replay binds the same claim kind, subject, policy, statement, verifier binary,
and accepted decision.  Its executor identity must differ from the invocation
executor identity.

* Temporal transparency checkpoint chain

A single =fresh = true= or =appendOnlyConsistent = true= field cannot establish
time continuity.  This RFC introduces a transition between a prior and current
checkpoint.

The structural transition requires:

- the same configured log identity at both checkpoints;
- nondecreasing tree size;
- strictly increasing issue time;
- a current issue time no later than the evaluation time;
- an evaluation time within the maximum checkpoint age; and
- a current tree size at least the policy minimum.

The current checkpoint must also equal the log, checkpoint, root, and tree size
already carried by the RFC 01.18 provenance receipt.  This prevents a valid
temporal proof for one checkpoint from being attached to another provenance
receipt.

The =checkpointConsistency= executable claim verifies the canonical transition
statement.  The =checkpointFreshness= executable claim verifies the current
checkpoint under the selected freshness policy.

* Complete execution-backed provenance predicate

The =execution-backed-provenance= Typst definition combines five independent
requirements:

1. valid RFC 01.18 structural provenance;
2. exact binding between the temporal checkpoint and that provenance receipt;
3. a monotone and fresh temporal checkpoint transition;
4. all eight claim-kind, subject, and policy targets; and
5. complete executable verification for all eight claims.

The Lean projection theorem proves that execution-backed provenance preserves
the RFC 01.18 structural provenance theorem.  This extension strengthens the
earlier predicate; it does not redefine or weaken it.

* Rejected weak prefixes

** Accepted Boolean with unresolved verifier

The decoded receipt reports acceptance, but verifier resolution reports
=resolved = false=.  Lean proves that this does not satisfy executable claim
verification.

** Subject-only cross-kind replay

A =recipeHermetic= receipt carries the expected source snapshot digest.  A
subject-only check accepts the digest, but the typed verifier rejects the claim
because =recipeHermetic= is not =sourceImmutable=.

** Cross-policy replay

Every stage agrees internally on policy =999=, while the context requires
policy =700=.  Internal consistency does not authorize cross-policy reuse.

** Same-executor replay

The replay reproduces the accepted decision using the invocation executor.
This is reproducibility within one failure domain, not independent replay.

** Stale checkpoint

The checkpoint was once valid, but evaluation occurs outside the configured
maximum age.  A previously accepted checkpoint cannot be replayed forever.

** Checkpoint tree rollback

The current tree size is smaller than the prior tree size and no longer binds
the RFC 01.18 provenance receipt.  Both temporal continuity and receipt binding
reject the transition.

* SearchLoop, graph routing, and cache consequence

The graph router MUST perform execution-backed feasibility before cost ranking.
A route cannot win because it offers fewer graph hops, lower token cost, fewer
interaction rounds, more search-cache reuse, or better model-prefix-cache
affinity while its provenance decisions are only Boolean prefixes.

Search cache and model cache remain separate axes:

- the search cache may reuse a verified claim receipt only when claim kind,
  subject, policy, verifier binary, and checkpoint transition identity match;
- the model cache may reuse prompt prefixes, but a prefix-cache hit supplies no
  executable provenance evidence; and
- neither cache can extend a checkpoint beyond its freshness window.

The stable cache identity for an executable claim SHOULD include:

- claim kind;
- subject digest;
- policy digest;
- canonical statement digest;
- verifier binary digest;
- decoder schema digest; and
- temporal checkpoint digest when the claim is time-sensitive.

* Normative clauses

** ASP-RFC-10.05-PEEC-CLAIM-STAGE-CLOSURE

Executable provenance claims MUST close canonical statement, claim-aware
resolution, bound invocation, decoded acceptance, and independent replay as one
conjunction.

** ASP-RFC-10.05-PEEC-CLAIM-KIND

Each executable claim MUST bind one explicit provenance claim kind.  Claim
kinds are not interchangeable even when subject digests match.

** ASP-RFC-10.05-PEEC-POLICY

Statement, resolution, invocation, decode, and replay MUST bind the same
configured policy digest.

** ASP-RFC-10.05-PEEC-SUBJECT

Every claim MUST bind the exact provenance subject selected by its claim kind.

** ASP-RFC-10.05-PEEC-RESOLUTION

Verifier resolution MUST bind claim kind, policy, verifier identity, and
verifier binary, and MUST report successful resolution.

** ASP-RFC-10.05-PEEC-INVOCATION-DECODE

Invocation MUST bind the canonical statement and resolved binary.  Decode MUST
bind the exact response and configured decoder schema before acceptance.

** ASP-RFC-10.05-PEEC-INDEPENDENT-REPLAY

Replay MUST bind the same typed claim and accepted decision, and MUST use an
executor distinct from the invocation executor.

** ASP-RFC-10.05-PEEC-CHECKPOINT-BINDING

The current temporal checkpoint MUST equal the log, checkpoint, root, and tree
size carried by the structural provenance receipt.

** ASP-RFC-10.05-PEEC-CHECKPOINT-CONTINUITY

Checkpoint transitions MUST preserve log identity, nondecreasing tree size,
increasing issue time, configured freshness, and minimum tree size.

** ASP-RFC-10.05-PEEC-STRUCTURAL-PROJECTION

Execution-backed provenance MUST project to valid RFC 01.18 structural
provenance.

** ASP-RFC-10.05-PEEC-FEASIBILITY-FIRST

Routes without execution-backed provenance MUST be rejected before graph,
token, round, search-cache, or model-cache cost comparison.

** ASP-RFC-10.05-PEEC-PREFIX-INSUFFICIENT

Accepted Booleans, subject-only binding, same-executor replay, cross-policy
agreement, or a single stale checkpoint MUST NOT establish executable
provenance evidence.

* Implementation boundary

This session ends at RFC, Lean, Org-Babel Typst, and AXLE verification.

Future runtime work requires shared versioned schemas for executable evidence
claim contexts, canonical claim statements, verifier resolution, invocation,
decode, replay, checkpoint transition, and cache identity.  Those schemas must
precede any Rust provider implementation.
