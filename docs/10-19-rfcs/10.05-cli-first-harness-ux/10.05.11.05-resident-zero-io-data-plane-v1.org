#+title: 10.05.11.05 Resident Zero-I/O Data Plane V1
#+startup: overview

* Status

Normative implementation target.

This RFC refines the Global resident daemon contract.  It does not introduce a
second resident, workspace daemon, or compatibility path.

* Problem

An async command is not a non-blocking data plane merely because it executes
inside a Tokio runtime.  Query-time activation reads, manifest reads, canonical
path discovery, filesystem lock probes, database opens, provider processes, and
=tokio::fs= calls all place work outside the resident memory boundary.  They
also make search and exact query observe different workspace generations.

The observed invalid state is:

#+begin_example
owner search -> exact structural selector
exact query  -> owner-not-in-workspace
#+end_example

The producer and consumer are resolving the same owner against different
workspace and generation identities.

* Canonical request identity

Every search and exact-query request MUST carry one
=workspace-reference.v1= value.  It is either a checkout-root reference or an
already canonical workspace-id reference.

Admission resolves that input exactly once into a resident identity containing:

- repository identity;
- workspace identity;
- package identity when the language harness reports a package;
- owner path relative to that package;
- the resident generation handle.

A CLI path, workspace id string, Git checkout, package root, and owner path
MUST NOT be reinterpreted independently after admission.  Search packets and
exact-query selectors MUST retain the same typed workspace reference.

* Single Global resident

There is exactly one supervised Global ASP daemon per user runtime.  It owns a
sharded map keyed by canonical workspace identity.  Each workspace entry owns:

- an immutable active base generation;
- a live worktree overlay;
- a load-once Memory Search index;
- resident Turso read connections;
- an adaptive concurrent read-lease pool;
- one Tokio writer lane;
- session bindings and generation leases.

No cross-workspace global database lock is permitted.  Different workspace
entries execute independently.

* Root-depth worktree model

=rootDepth={1,0}= is a two-layer generation, not a fallback:

- depth 1 is the immutable, content-addressed base generation;
- depth 0 is the live worktree overlay.

The overlay MUST admit tracked, modified, untracked, moved, and tombstoned
owners.  A generation publication is atomic only when owner bytes, item
identities, module edges, relocation facts, and tombstones become visible under
one generation handle.

Owner discovery and exact projection MUST lease that same handle.  Exact query
MUST NOT reopen the workspace or reconstruct membership from the filesystem.

* Zero-I/O query data plane

After the Global daemon is healthy, search and exact query MUST execute without:

- activation or manifest file reads;
- filesystem canonicalization or lock probes;
- Turso database opens or schema bootstrap;
- provider process creation;
- configuration synchronization;
- =std::fs= or =tokio::fs= calls.

The installed provider catalog and activation catalog are control-plane inputs.
They are loaded once and atomically exchanged in memory.  A query MUST NOT call
=sync=, installation, or activation materialization.

The following receipt fields are mandatory for performance gates:

#+begin_example
fsReads=0
dbOpens=0
manifestReads=0
processSpawns=0
lockProbes=0
schemaBootstraps=0
workspaceCanonicalizations=0
#+end_example

* Tokio boundary

The daemon lifecycle, IPC, supervisor reconciliation, read leases, writer
lanes, and shutdown/drain protocol are Tokio-owned.

=std::fs=, =std::process::Command=, =std::thread::sleep=, and blocking file
locks are forbidden in daemon runtime modules.  =tokio::fs= and
=tokio::process::Command= are control-plane facilities and are forbidden in the
query data plane.

=std::time::Duration= and =std::time::Instant= are value and monotonic clock
types; their presence is not blocking.  Sleeping and timeout behavior MUST use
=tokio::time=.

* Admission and lazy loading

Language providers remain registry/schema/harness owned.  Provider code and
query packs are lazily loaded into the Global catalog before a request is
admitted to the data plane.

Org and Markdown are document surfaces, not language providers.  Their owner
set is Git scope minus ignored paths, followed by document-format matching and
parser-owned structural projection.

Lazy loading MUST be coalesced per catalog key.  Concurrent requests for the
same missing catalog entry share one asynchronous load and never create
parallel provider processes or database opens.

* Performance gates

The normative gates exercise a healthy daemon with:

- multiple repositories and workspaces;
- multiple simultaneous client sessions;
- same-workspace read concurrency;
- concurrent reads during a writer transaction;
- untracked, moved, and tombstoned owners;
- a cold selector-cache miss over an already resident generation;
- a warm exact-selector query.

The cold selector-cache miss and warm query are both millisecond-or-better
operations and MUST satisfy every zero-I/O counter.  Process startup,
installation, and catalog publication are measured separately as control-plane
operations and MUST never be charged to a query.

* Removal rule

Per-workspace resident processes, query-time activation loaders, query-time
workspace canonicalization, direct provider-process exact projection, and
filesystem fallback membership are Legacy.  They MUST be physically removed;
they MUST NOT remain behind warnings, feature flags, or compatibility aliases.
