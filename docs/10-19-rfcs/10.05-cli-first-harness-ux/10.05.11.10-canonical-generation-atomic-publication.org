#+title: Canonical Generation Atomic Publication and Cold Restore

* Status

Accepted.

* Authority

Turso is the durable MVCC authority for a workspace canonical generation.
The Runtime Server is the only lifecycle owner that may turn that durable
generation into an active MemoryBackend generation and memmap2 pointer.

The canonical materialization contains the complete owner bytes, selector
ranges, source-snapshot root, import digest, workspace identity, and rootDepth.
It is immutable for one source-index generation.

* Atomic write order

The workspace writer lane performs one Turso Immediate transaction:

#+begin_example
owner and selector rows
  -> posting and selector projections
  -> immutable canonical materialization
  -> active source-index scope pointer
  -> COMMIT
#+end_example

The active scope pointer is published last. A transaction must never expose a
scope generation for which the canonical materialization is absent or differs.
A reusable generation is reusable only when its persisted materialization is
byte-for-byte equal to the requested typed materialization.

* Cold restore

A warm exact query opens the immutable memmap pointer directly and performs no
database open, provider spawn, workspace canonicalization, or control-socket
round trip.

When the pointer is absent, the client asks the single Runtime Server to ensure
the workspace generation. The Runtime Server:

1. resolves the already-admitted workspace session entry;
2. reads the active materialization through that entry's resident Turso handle;
3. verifies workspace identity, rootDepth, owner bytes, selector ranges, and
   durable source-snapshot root;
4. builds the next MemoryBackend generation;
5. publishes the memmap segment and atomically switches the pointer.

The cold path may perform this one restore. It must not run a language provider,
invoke =asp sync=, open a second Turso database, or manufacture a generation
from a single owner overlay.

Concurrent cold restores for one workspace are single-flight inside that
workspace's writer lane. Materialization-to-generation conversion happens
after the command reaches the lane, so concurrent callers cannot calculate the
same stale target epoch. Once the mmap pointer exists, later callers reuse the
published receipt and generation instead of publishing duplicate epochs.

The resident Turso entry prebuilds one adaptive, machine-derived read pool at
workspace admission. A warm query must not canonicalize the project path,
create another Turso connection, resize the read pool, probe a lock, or reopen
the database. Different workspaces own independent pools and writer lanes.

* Exact-query diagnostic boundary

Exact-query diagnostics are a domain subsystem, not a branch of the direct
provider transport. The subsystem owns the typed resolution model, semantic
validation, recovery recommendation, and deterministic JSON or human
rendering. It must not perform stdout writes, provider process management,
workspace canonicalization, source reads, Turso access, or Runtime Server
control I/O.

The direct provider command is only a transport adapter. It may submit a typed
provider request, decode a typed response, ask the diagnostic subsystem to
classify or render that response, and write the returned bytes. It must not
construct =owner-missing=, =item-missing=, or =kind-mismatch= strings itself.
Runtime MemoryBackend and provider-process paths must consume the same
diagnostic API so one resolution state cannot acquire transport-specific
semantics.

The architecture gate rejects diagnostic model, validation, recovery-command,
or human-rendering logic in =provider_direct_exact.rs=. This boundary is
compile-time and source-policy enforced; it is not a compatibility wrapper.

* Overlay admission

Live and untracked owner projections are rootDepth =[1,0]= overlays over an
already active canonical generation. An overlay cannot create epoch 1. Readers
holding the previous epoch remain valid until their leases are released.

* Required gates

- materialization and active scope roll back together;
- a scope without materialization is never reusable;
- a persisted materialization cannot be overwritten with different bytes;
- pointer-missing cold restore uses the resident DB handle and publishes once;
- warm exact projection has zero DB opens, provider spawns, filesystem reads,
  and control-socket calls;
- multi-workspace and multi-session readers remain parallel while each
  workspace retains exactly one writer lane;
- old readers retain the old epoch during atomic pointer publication.
