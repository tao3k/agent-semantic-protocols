#+title: 10.05.11.13 Dev Artifact Authority
#+startup: overview

* Status

Normative.

* Problem

A development checkout can publish a provider manifest whose command bindings
are newer than the binary named by a release lock.  A shared candidate list can
therefore combine the new manifest with an older release binary.  The ABI drift
then appears only after provider spawn and can deadlock source-authority
recovery.

* Dev model

The state-home configuration selects the development runtime model explicitly:

#+begin_src toml
[dev]
enabled = true
root = "/absolute/path/to/agent-semantic-protocols"
#+end_src

The =dev= table is the model boundary.  =enabled = true= selects
=RuntimeMode::Dev { root }= and =root= is the sole source authority for every
development artifact.  A missing =dev= table or =enabled = false= selects the
release runtime model.  There is no =DevScope=, no =scope= field, and no
independent top-level artifact-authority or developer-mode field that can
contradict this model.  Unknown fields fail schema and typed parsing rather
than being accepted as compatibility aliases.

The resident runtime loads this configuration once during supervisor
reconciliation and stores the validated model in its immutable runtime catalog.
Search and query requests MUST NOT reopen =asp.toml=.

The same model also owns the cold installation entry.  In dev mode, a plain
=asp install language <language>= MUST delegate to the root development
installer under the configured checkout.  The caller MUST NOT select a
release, discover a build output, or pass an artifact path.  The development
installer builds the registered provider from =root/languages/*= and returns
the resulting artifact to the ASP publication boundary.  Receipt recording is
internal installer plumbing, not an agent-facing compatibility surface.

Delegation is mode-fenced.  A delegated child may only publish the artifact
receipt; it may not recursively start another development build.  The checkout
root is canonicalized before invocation and the published artifact must remain
under that root, or under the canonical State Home staging directory for a
provider-owned launcher.

The =[dev]= table is validated by
=agent.semantic-protocols.runtime-dev-config= schema version 1 before the typed
Rust model is constructed.

Each registered provider MUST publish one
=agent.semantic-protocols.provider-development-descriptor= schema version 1 in
its provider manifest.  The descriptor supplies =sourceRoot=,
=buildBinding=, and =artifactDomain=.  =sourceRoot= is repository-relative and
MUST NOT contain a parent traversal.  It names the provider's own Git worktree,
not merely the outer ASP checkout.  ASP derives source Merkle evidence from
that exact worktree so nested provider repositories cannot be represented by an
outer gitlink digest.

=artifactDomain= is either =checkout= or
=state-home-provider-staging=.  Checkout artifacts must remain below the
registered =sourceRoot=.  Staged launchers must remain below
=$ASP_STATE_HOME/runtime/provider-artifacts/<registered-binary>/develop=.
Neither domain authorizes arbitrary State Home files, =runtime/bin= entries, a
different provider's staging root, or =PATH=.

The current v1 =buildBinding= is =root-development-installer-v1=.  This is a
typed transition boundary, not a language switch in ASP Rust code.  Provider
selection, source scope, artifact domain, and receipt provenance are read from
the ProviderRegistry manifest.  A later provider-owned executor may replace
the root binding only through a new schema-declared binding and matching
receipt gate.

* Mutually exclusive artifact domains

In the dev model, the resolver candidate domain contains only artifacts
published from the configured root by the root development installer.  An
admitted receipt MUST identify:

- =installMode= as =develop-workspace=
- =sourceKind= as =develop-workspace=
- the canonical checkout identity and source generation digest
- the content-addressed binary artifact digest
- the provider manifest digest and command-binding contract digest

The dev resolver MUST NOT construct a locked-release candidate, consult a
release lock to choose a binary, or fall back to =PATH=.  A missing, stale, or
incompatible checkout artifact fails closed as
=checkout-artifact-unavailable=.  It never falls back to a release binary.

In the release model, only the locked-release domain is admitted; checkout
receipts are not candidates.  Switching runtime models requires one Global
supervisor reconciliation and atomic catalog replacement.

* Health and lifecycle

Health is green only when every activated provider reports an artifact origin
matching the active runtime model and its manifest/command-binding digest
matches the resolved binary receipt.  Model or digest drift schedules a
single-flight Global reconciliation.  Hook callers receive a bounded receipt
and never build, install, or wait for provider replacement.

* Required gates

- the dev model cannot select, open, or execute a locked-release binary
- the dev model cannot use a =PATH= provider fallback
- plain development installation is rooted at =[dev].root= and never downloads
  a release archive
- a delegated development installer cannot recursively delegate another build
- every registered language has exactly one provider development descriptor
- source Merkle evidence is rooted at the provider-owned =sourceRoot=, including
  when the provider is a nested Git worktree
- checkout and State Home staging artifact domains are mutually exclusive and
  provider-identity scoped
- the dev model cannot be constructed without =enabled = true= and an
  absolute, non-filesystem-root =root=
- legacy =scope= and developer-mode aliases are rejected
- missing checkout artifacts fail closed without mutating activation
- the release model cannot admit checkout receipts
- concurrent workspaces observe one immutable runtime-model/catalog generation
- warm search/query performs zero config reads, release-lock reads, provider
  installs, database opens, and process spawns
