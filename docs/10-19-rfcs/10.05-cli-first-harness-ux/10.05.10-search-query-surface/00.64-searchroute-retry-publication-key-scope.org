#+title: RFC 10.05.64 — SearchRoute Retry Publication Key Scope
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented refinement of RFC 10.05.63.  It specifies the
semantic identity dimensions of the retry-publication key.  It does not define
a wire encoding or implement Rust or Python behavior.

* Abstract

RFC 10.05.63 guarantees one sticky winner for one authoritative publication
key.  Per-key atomicity is still unsafe when unrelated semantic domains project
onto the same key.

This RFC defines the full publication key as:

#+begin_example
(workspace identity,
 ledger generation,
 contract version,
 tenant scope,
 retry identity)
#+end_example

Lean countermodels show that omitting any one dimension aliases two distinct
publication domains.  An atomic cell then consistently returns the wrong
domain's winner: serialization succeeds, but semantic identity fails.

* Logic defect exposed by the proof

The statement “same idempotency key” is circular unless the protocol defines
which semantic differences make keys distinct.  A convenient request ID is
not enough:

- the same request ID may occur in two workspaces;
- a restarted ledger generation may reuse an earlier retry ID;
- two contract versions may assign different meaning to one certificate;
- two tenants may generate the same client-visible ID;
- two retries in one domain may otherwise collapse into one cell.

Hashing an incomplete tuple does not repair the omission.  Collision
resistance protects the encoded tuple; it cannot restore fields absent from
that tuple.

* Normative vocabulary

** Workspace identity

The content or authority identity of the evidence workspace in which routing
and admission occur.  A filesystem display path alone is insufficient when it
can be rebound to different content.

** Ledger generation

The authoritative incarnation of the admission/publication ledger.  It is the
same generation boundary used by RFC 10.05.35.

** Contract version

The semantic version of the retry certificate, graph evidence, and publication
rules.  It MUST change when two certificates with the same payload bytes may
have different protocol meaning.

** Tenant scope

The authorization domain permitted to publish and recover the winner.  It MUST
prevent cross-tenant key aliasing and winner disclosure.

** Retry identity

The idempotency identity of the logical retry within the other four dimensions.
It is not globally meaningful without those dimensions.

* Normative requirements

** ASP-RFC-10.05-RPKS-FULL-KEY

The authoritative retry-publication key MUST bind:

1. workspace identity;
2. ledger generation;
3. contract version;
4. tenant scope;
5. retry identity.

Equality of full keys MUST imply equality of all five dimensions.

** ASP-RFC-10.05-RPKS-CANONICALIZATION

The tuple MUST have one canonical encoding before hashing, comparison, or
persistence.  Field order, numeric encoding, text normalization, and absent
values MUST be unambiguous.

A digest MAY serve as the stored key only when the receipt retains the schema
identity and canonicalization contract used to derive it.

** ASP-RFC-10.05-RPKS-WORKSPACE

Omitting workspace identity is forbidden.  Equal retry identities in distinct
workspaces MUST address distinct publication cells.

** ASP-RFC-10.05-RPKS-GENERATION

Omitting ledger generation is forbidden.  A retry from an earlier generation
MUST NOT recover or block the winner of a later generation.

** ASP-RFC-10.05-RPKS-CONTRACT

Omitting contract version is forbidden.  Certificates interpreted under
incompatible semantic contracts MUST NOT share a winner cell.

** ASP-RFC-10.05-RPKS-TENANT

Omitting tenant scope is forbidden.  Publication lookup MUST NOT disclose or
reuse another authorization domain's winner.

** ASP-RFC-10.05-RPKS-RETRY

Omitting retry identity is forbidden.  Distinct logical retries within one
scope MUST retain independent winner cells.

** ASP-RFC-10.05-RPKS-NONIMPLICATION

The protocol MUST preserve these explicit non-implications:

- atomic publication does not imply correct key scoping;
- cryptographic hashing does not imply that the preimage tuple is complete;
- equal display paths do not imply equal workspace identity;
- equal retry IDs do not imply equal publication domains;
- full key separation does not by itself prove authorization-safe lookup;
- key correctness does not prove shortest graph-route optimality.

* Mathematical model

The mathematical source remains embedded in Org and is evaluated by
=typst eval= through stdin.

#+name: searchroute-retry-publication-key-scope-model
#+begin_src typst
#let full(workspace, generation, contract, tenant, retry) = $(#workspace, #generation, #contract, #tenant, #retry)$
#let omitWorkspace(key) = $upright("omit-workspace")(#key)$
#let omitGeneration(key) = $upright("omit-generation")(#key)$
#let omitContract(key) = $upright("omit-contract")(#key)$
#let omitTenant(key) = $upright("omit-tenant")(#key)$
#let omitRetry(key) = $upright("omit-retry")(#key)$

#[
  The full publication key is
  $
    K = #full($W$, $G$, $V$, $T$, $R$).
  $

  Full-key equality preserves all dimensions:
  $
    K_1 = K_2
    arrow.r.double
    (
      W_1 = W_2
      and G_1 = G_2
      and V_1 = V_2
      and T_1 = T_2
      and R_1 = R_2
    ).
  $

  For each dimension there are distinct full keys whose incomplete
  projections are equal:
  $
    K != K_W
    and #omitWorkspace($K$) = #omitWorkspace($K_W$),
  $
  $
    K != K_G
    and #omitGeneration($K$) = #omitGeneration($K_G$),
  $
  $
    K != K_V
    and #omitContract($K$) = #omitContract($K_V$),
  $
  $
    K != K_T
    and #omitTenant($K$) = #omitTenant($K_T$),
  $
  and
  $
    K != K_R
    and #omitRetry($K$) = #omitRetry($K_R$).
  $

  Therefore per-cell winner uniqueness over any incomplete projection does not
  imply semantic-domain separation.
]
#+end_src

* SearchLoop cost relevance

Cross-domain aliasing can return a structurally valid but semantically unrelated
winner.  The graph router may then follow an evidence path from another
workspace, generation, contract, or tenant.  At best the agent detects the
mismatch and repeats searches; at worst it accepts a short invalid path.

Correct key scope is therefore a prerequisite for stable route reuse, low token
cost, fewer interaction rounds, and safe model-prefix cache reuse.  It does not
itself prove path optimality or a cache hit.

* Non-goals and next proof boundary

This RFC does not yet prove:

- canonical byte encoding of the five-field tuple;
- digest collision resistance;
- authorization-safe winner retrieval;
- leader fencing or replicated linearizability;
- bounded winner retention;
- graph-route optimality.

The next proof layer should model canonical key encoding and prove injectivity:
equal encoded keys must imply equal semantic tuples.  It should also construct
delimiter, field-order, and omitted-schema-identity counterexamples.
