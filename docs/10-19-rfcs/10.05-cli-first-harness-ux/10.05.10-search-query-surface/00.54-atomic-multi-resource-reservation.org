#+title: RFC 10.05.10.00.54 — Atomic Multi-Resource Reservation
#+startup: overview

* Status

Draft research specification.

This RFC extends route admission from one additive resource to an atomic vector
of independently conserved resources. It does not add CLI commands or authorize
implementation.

* Problem

A SearchLoop route can require several hard resources:

- model/evidence tokens;
- monetary provider budget;
- provider request quota; and
- future schema-defined additive resources.

Reserving each dimension sequentially is unsafe:

1. token reservation succeeds;
2. money reservation fails;
3. process crashes before token rollback.

The route is not admitted, but token capacity remains held.

Even without a crash, independently visible reservations allow another worker
to observe and act on a partial admission.

* Decision

Admission operates on one =ResourceDemand= and one =MultiResourceLedger=.

The v1 demand contains:

- token units;
- money units; and
- provider-quota units.

=CanReserveAll= requires every demand component to fit its corresponding
available partition.

=reserveAtomically= has exactly two outcomes:

- =admitted=: all three ledgers move available capacity to held;
- =rejected=: the returned ledger is exactly the input ledger.

No partial intermediate ledger is protocol-visible.

* Executable mathematical surface

#+name: atomic-multi-resource-reservation-math
#+begin_src typst
#let can-reserve(ledger, demand) = (
  demand.tokens <= ledger.tokens.available
  and demand.money <= ledger.money.available
  and demand.provider-quota <= ledger.provider-quota.available
)

#let reserve-one(resource, amount) = (
  available: resource.available - amount,
  held: resource.held + amount,
  consumed: resource.consumed,
  quarantined: resource.quarantined,
)

#let reserve-atomically(ledger, demand) = {
  if can-reserve(ledger, demand) {
    (
      outcome: "admitted",
      ledger: (
        tokens: reserve-one(ledger.tokens, demand.tokens),
        money: reserve-one(ledger.money, demand.money),
        provider-quota:
          reserve-one(
            ledger.provider-quota,
            demand.provider-quota,
          ),
      ),
    )
  } else {
    (outcome: "rejected", ledger: ledger)
  }
}

#let ledger = (
  tokens: (available: 100, held: 0, consumed: 0, quarantined: 0),
  money: (available: 5, held: 0, consumed: 0, quarantined: 0),
  provider-quota:
    (available: 2, held: 0, consumed: 0, quarantined: 0),
)
#let demand = (tokens: 20, money: 10, provider-quota: 1)
#let result = reserve-atomically(ledger, demand)

(
  tokens-fit: demand.tokens <= ledger.tokens.available,
  money-fits: demand.money <= ledger.money.available,
  provider-quota-fits:
    demand.provider-quota <= ledger.provider-quota.available,
  outcome: result.outcome,
  ledger-unchanged: result.ledger == ledger,
)
#+end_src

* Resource dimensions

Each dimension has its own:

- unit identity and version;
- available/held/consumed/quarantined ledger;
- conserved total;
- revision; and
- external authority.

Token units cannot be substituted for money or provider quota. The shared
admission schema uses named fields rather than an untyped array.

Adding a dimension requires a new schema version unless the existing contract
explicitly supports a typed extension map.

* All-or-nothing feasibility

A route is multi-resource feasible only when:

#+begin_quote
=tokens fit AND money fits AND provider quota fits=.
#+end_quote

An improvement in one dimension cannot compensate for violating another hard
resource.

This is feasibility-first admission from RFC 00.35 lifted to a resource vector.

* Atomic result

The mathematical operation does not expose sequential sub-reservations.

On success:

- every dimension moves its requested amount from available to held;
- every dimension preserves its conserved total; and
- the result carries one shared reservation digest/revision.

On rejection:

- outcome is =rejected=;
- output ledger equals input ledger;
- no reservation record is created; and
- no compensating rollback is required.

* Partial-feasibility counterexample

Example ledger:

- 100 token units;
- 5 money units;
- 2 provider-quota units.

Example demand:

- 20 token units;
- 10 money units;
- 1 provider-quota unit.

Tokens and quota fit, money does not. The complete admission is rejected and all
three ledgers remain unchanged.

This proves:

#+begin_quote
some resource dimensions feasible does not imply route admission.
#+end_quote

* Transaction boundary

Implementation uses one serializable/CAS transaction that covers:

- all dimension ledger revisions;
- shared reservation record;
- route admission bundle;
- receipt-chain head; and
- resulting context/ledger digest.

If the storage layer cannot atomically update all owners, the protocol requires
a prepared transaction with crash recovery. It MUST NOT publish a successful
admission before every dimension commits.

* Contention

The CAS precondition binds the revision of every dimension. If any revision
changes, the entire proposal becomes stale.

The worker re-evaluates all dimensions against the new snapshot. It does not
retain successful sub-reservations from the failed proposal.

* SearchLoop consequence

The compact admission packet exposes:

#+begin_src json
{
  "admitted": false,
  "demand": {
    "tokens": 20,
    "money": 10,
    "providerQuota": 1
  },
  "available": {
    "tokens": 100,
    "money": 5,
    "providerQuota": 2
  },
  "blockingDimensions": ["money"],
  "ledgerUnchanged": true
}
#+end_src

The next action targets only blocking resource dimensions.

* Cache consequence

Model prefix-cache hits may lower token demand. They do not lower money or
provider quota unless separately certified by those resource owners.

Semantic-cache reuse may lower evidence acquisition tokens. It does not create
provider quota or money capacity.

Every recalculated demand is bound to the same cache/cost context used by the
atomic proposal.

* Python Turbo Graph consequence

The future Python runtime SHOULD:

- represent demands and ledgers with typed named dimensions;
- evaluate all dimensions before proposing admission;
- commit all dimensions and the reservation record atomically;
- return unchanged state on rejection;
- identify blocking dimensions compactly; and
- reject stale multi-revision proposals as one unit.

* Required Lean obligations

The companion Lean model MUST prove:

- admitted outcome is equivalent to all dimensions fitting;
- rejection returns the input ledger unchanged;
- successful reservation preserves each dimension's total;
- the example token and quota dimensions fit;
- the example money dimension does not fit;
- the example atomic result is rejected and unchanged; and
- partial component feasibility does not imply multi-resource feasibility.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

Single-resource conservation does not imply atomic multi-resource admission.
Lean's result type makes partial success unrepresentable: the success branch
contains all updated ledgers, while the rejection branch definitionally returns
the original snapshot.
