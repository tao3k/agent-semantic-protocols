#+title: Package-manager-owned project scope
#+property: header-args :eval never-export

* Status

This clause defines the project-resolution authority used by search, exact query,
source envelopes, and incremental indexing.

* Authority boundary

Git owns repository and worktree identity plus the bounded candidate snapshot.
A programming-language provider owns package-manager parsing and emits a typed
=projectResolution= receipt.  ASP derives source scope only from the
intersection of those two authorities.

Provider manifests MUST NOT publish default extensions, configuration files,
project markers, dependency markers, or any capability that guesses a source
scope without parsing the package manager.  Such fields are absent from the
shared manifest contract.

A programming-language provider MUST declare =projectResolution=.  Its
project-resolution command MUST:

- read only paths admitted by the repository candidate snapshot;
- parse registered package-manager entry files and their declared package
  graph;
- derive source scopes from package targets, members, and explicit provider
  semantics;
- report manifest, lockfile, candidate-generation, and parser digests;
- report =fullWorkspaceReads=0= and =databaseOpens=0=;
- fail closed when no authoritative project entry or source scope exists.

Document providers may use a Git-only bounded scope when package-manager
semantics do not apply.  They MUST declare that distinct provider contract;
they MUST NOT impersonate a programming-language project resolution.

* Ignore and exclusion semantics

There is no provider-local default-ignore list.  Candidate exclusion comes
from Git identity/status/ignore semantics and ASP infrastructure boundaries.
Package membership, target inclusion, generated sources, vendor boundaries,
and package-manager exclusions come from the provider-owned package graph.
User policy may further restrict a resolved scope but cannot silently expand it.

ASP MUST NOT recursively enumerate a workspace root to compensate for missing
Git candidates, project entries, or package graph facts.

* Incremental lifecycle

The workspace daemon stores project-resolution artifacts by repository
candidate generation, project-entry digest, lockfile digest, and provider
parser digest.  A package-manager change invalidates only the affected package
subgraph and its derived source scopes.  Search and exact query consume the
published receipt; they do not reopen or reinterpret package-manager files.

* Fallback reflection

Fallback is not an implicit control-flow branch.  Before a caller may request a
fallback it MUST produce a =fallback-reflection-receipt.v1= that records:

- the failed typed authority and exact failure reason;
- why retry, refresh, or repair cannot preserve the requested semantics;
- the semantic loss introduced by the proposed fallback;
- explicit caller opt-in and a positive, bounded fallback budget;
- the observation that will terminate or invalidate the fallback.

Any unpreserved semantic property forces =reflection-denied=.  Missing opt-in,
missing budget, or an untyped/raw-root-recursion proposal also forces
=reflection-denied=.  A denied reflection returns the original typed failure;
it never silently enters a legacy path.
