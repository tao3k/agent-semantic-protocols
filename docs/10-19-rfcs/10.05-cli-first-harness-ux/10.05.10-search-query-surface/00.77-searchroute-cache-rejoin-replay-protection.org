#+title: RFC 10.05.77 — SearchRoute Cache Rejoin Replay Protection
#+startup: overview

* Status

Draft proof-bearing extension of RFC 10.05.76.

* Abstract

RFC 10.05.76 prevents receipt substitution and cross-scope chain composition,
but an old chain can remain internally valid after a newer rejoin attempt
begins.  Content integrity therefore does not imply freshness.

This RFC introduces an authority-current attempt epoch and one active
reads-enabled claim per replica.  Activation is a state mutation permitted only
for the current epoch while no claim is active.  Repeating the exact accepted
claim is an idempotent observation, not another activation.  A different
terminal digest at the same epoch is a conflict.

* Scope

The model assumes one serialized admission state per replica.  It specifies
which transition is valid once an authority order exists; it does not yet prove
that multiple authority replicas agree on one linearization point.

* Normative clauses

** ASP-RFC-10.05-CRRP-EPOCH — Attempt identity is authority-issued order

The receipt-chain =attemptId= admitted by RFC 10.05.76 MUST be interpreted as,
or bound to, an authority-issued attempt epoch.  Arbitrary client identifiers
and wall-clock timestamps MUST NOT establish freshness.

** ASP-RFC-10.05-CRRP-CURRENT — Only the authority-current epoch may activate

A reads-enabled claim MAY activate only when its replica matches the admission
state, its attempt epoch equals the authority-current epoch, and the active slot
is empty.  Future, unissued epochs and claims for another replica MUST fail
closed.

** ASP-RFC-10.05-CRRP-SUPERSESSION — Beginning a newer attempt supersedes old chains

Beginning a strictly newer attempt MUST clear the previous active claim and
advance the current epoch.  A claim from the prior epoch MUST then be rejected
for both activation and observation, even when its receipt chain remains
content-valid.

** ASP-RFC-10.05-CRRP-UNIQUE — A replica has at most one active claim

The admission state MUST represent at most one active reads-enabled claim for a
replica.  Once activation records a claim, another activation MUST NOT succeed
until an authority transition begins a newer attempt.

** ASP-RFC-10.05-CRRP-IDEMPOTENCE — Exact replay is observation, not mutation

Re-submitting the exact active claim MAY return an idempotent success receipt.
It MUST NOT repeat activation side effects, increment activation counts, or
publish a second active edge.

** ASP-RFC-10.05-CRRP-CONFLICT — Same epoch with different terminal content conflicts

A claim whose epoch and replica match the active claim but whose terminal
receipt digest differs MUST NOT be treated as an idempotent replay.  It is a
conflicting claim and MUST fail closed.

** ASP-RFC-10.05-CRRP-NONIMPLICATION — Integrity does not imply freshness

A complete, scoped, predecessor-linked, content-bound receipt chain does not by
itself prove that its attempt is still current or that activation has not
already occurred.

* Mathematical model

The executable model separates =can-activate= from =can-observe=.  The active
slot contains the accepted claim itself, so exact observation includes terminal
digest equality.

#+name: searchroute-cache-rejoin-replay-protection-model
#+begin_src typst
#let claim(replica, epoch, terminal) = (
  replica: replica,
  epoch: epoch,
  terminal: terminal,
)
#let state(replica, current, active) = (
  replica: replica,
  current: current,
  active: active,
)
#let can-activate(authority, candidate) = (
  candidate.replica == authority.replica
  and candidate.epoch == authority.current
  and authority.active == none
)
#let activate(authority, candidate) = state(
  authority.replica,
  authority.current,
  candidate,
)
#let can-observe(authority, candidate) = authority.active == candidate
#let can-begin-new-attempt(authority, next) = authority.current < next
#let begin-new-attempt(authority, next) = state(
  authority.replica,
  next,
  none,
)
#let initial = state(3, 7, none)
#let accepted = claim(3, 7, 104)
#let conflicting = claim(3, 7, 999)
#let future = claim(3, 8, 105)
#let cross-replica = claim(4, 7, 104)
#let activated = activate(initial, accepted)
#let next-attempt = begin-new-attempt(activated, 8)
#assert(can-activate(initial, accepted))
#assert(can-begin-new-attempt(activated, 8))
#assert(not can-begin-new-attempt(activated, 7))
#assert(not can-begin-new-attempt(activated, 6))
#assert(not can-activate(initial, future))
#assert(not can-activate(initial, cross-replica))
#assert(not can-activate(activated, accepted))
#assert(can-observe(activated, accepted))
#assert(not can-observe(activated, conflicting))
#assert(not can-activate(next-attempt, accepted))
#assert(not can-observe(next-attempt, accepted))
#assert(can-activate(next-attempt, future))
"ok"
#+end_src

The core activation and supersession propositions are:

#+name: searchroute-cache-rejoin-replay-protection-proposition
#+begin_src typst
#let activation = $upright("CanActivate")(S, C) arrow.r.double
  upright("replica")(C) = upright("replica")(S)
  and upright("epoch")(C) = upright("current")(S)
  and upright("active")(S) = upright("None")$
#let supersession = $e < e' arrow.r.double
  not upright("CanActivate")(upright("Begin")(S, e'), C_e)$
#assert(type(activation) == content)
#assert(type(supersession) == content)
"ok"
#+end_src

* SearchLoop and graph-router consequence

The router may expose one compact admission edge with an explicit replay state:

#+begin_example
current + inactive  -> activation permitted
current + same active claim -> idempotent observation
current + different active claim -> conflict
stale or future epoch -> rejected
#+end_example

This prevents an agent retry from creating another graph mutation while still
allowing the agent to recover the already-published evidence edge in one
interaction.

* Remaining proof boundary

The model's per-replica state is serialized.  With concurrent admission
authorities, two nodes can observe =active = None= and both attempt activation,
or advance different next epochs.

A follow-up RFC must introduce:

- a compare-and-swap or consensus-owned linearization token;
- a revision carried by every mutation;
- one-winner activation under concurrent proposals;
- retry behavior after losing the revision race;
- audit evidence connecting the winning revision to the published graph edge.
