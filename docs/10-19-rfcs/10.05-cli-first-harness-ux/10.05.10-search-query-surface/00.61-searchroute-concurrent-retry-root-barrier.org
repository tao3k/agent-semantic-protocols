#+title: RFC 10.05.61 — SearchRoute Concurrent Retry Root Barrier
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented bridge between RFC 10.05.33 concurrent GC
barriers and RFC 10.05.60 authoritative issue-log rotation.  It specifies the
live-root and ordering evidence required for a retry admitted after root
snapshotting but before sweep publication.  It does not implement Rust or
Python runtime behavior.

* Abstract

RFC 10.05.33 proves that a concurrent admission record can install both
receipt identities in a GC remembered set.  RFC 10.05.60 proves that safe
issue-log rotation preserves every live token that was already
authoritatively issued.

Those theorems do not compose automatically.  A rotation planner may:

- consume only the mark-time snapshot and ignore the remembered set;
- observe a remembered identity before its authoritative issue record exists;
- retain the GC payload while dropping the token-origin record;
- publish a retry before the barrier and issue-log evidence form one
  certificate.

This RFC defines the missing bridge.  The complete live-root predicate is the
union of snapshot roots, remembered-set roots, and protocol-owned external
roots.  A concurrent retry certificate additionally proves that both receipt
identities were issued before the rotation cut.  Safe issue-log rotation then
preserves both identities.

* Logic defects exposed by composition

Three independent facts must not be conflated:

1. an identity is reachable by the GC;
2. the authoritative ledger issued that identity;
3. issue-log rotation consumed the complete root union.

The following shortcuts are invalid:

#+begin_example
snapshotReferenced(identity)
  is not equivalent to
snapshotReferenced(identity) or remembered(identity)

remembered(identity)
  does not imply
issuedBeforeRotation(identity)

safeRotation(snapshotRoots)
  does not imply
safeRotation(snapshotRoots union rememberedRoots)
#+end_example

The proof therefore makes pre-rotation issuance a field of the concurrent retry
certificate rather than attempting to derive it from root membership.

* Normative vocabulary

** Complete live root

For GC cycle =cycle= and identity =i=:

#+begin_example
completeLiveRoot(cycle, i) :=
  cycle.snapshotReferenced(i)
  or cycle.remembered(i)
  or externalRoot(i)
#+end_example

=externalRoot= includes recovery, audit-horizon, revocation, or other
protocol-owned roots not represented by the GC cycle.

** Record coverage

An admission record is covered only when both its baseline receipt identity
and extended receipt identity belong to the complete live-root predicate.
One-sided coverage is insufficient.

** Rotation cut

The rotation cut is the authoritative boundary separating pre-rotation and
post-rotation issue-log states.  “Before the cut” is ledger-owned ordering, not
wall-clock time.

** Concurrent retry admission certificate

A concurrent retry admission certificate contains:

- the RFC 10.05.33 concurrent commit certificate;
- authoritative pre-rotation issuance of the baseline receipt identity;
- authoritative pre-rotation issuance of the extended receipt identity.

The certificate is a logical atomicity boundary.  A runtime MAY implement it
with one transaction or with proof-carrying records whose ordering composes to
the same result.

* Normative requirements

** ASP-RFC-10.05-CRRB-ROOT-UNION

Every issue-log rotation and receipt-payload sweep MUST consume the same
complete live-root union:

- mark-time snapshot references;
- remembered-set entries installed after the mark boundary;
- external protocol roots.

A component MUST NOT advertise a “safe sweep” or “safe rotation” receipt when
it evaluated a strict subset of this union.

** ASP-RFC-10.05-CRRB-BARRIER-CAPTURE

When a retry admission commits during an active sweep, the write barrier MUST
install both baseline and extended receipt identities before the retry becomes
publishable.

The remembered-set evidence MUST be scoped to the same GC cycle consumed by
rotation.  Carrying an entry from a prior or future cycle does not satisfy this
clause.

** ASP-RFC-10.05-CRRB-ISSUE-BEFORE-CUT

Both receipt identities MUST be authoritatively issued before the issue-log
rotation cut.  GC root membership does not create token origin.

The concurrent retry admission certificate MUST fail closed when either
pre-rotation issue record is absent, even if both identities are present in
the remembered set.

** ASP-RFC-10.05-CRRB-ROTATION-BRIDGE

Given:

1. a concurrent retry admission certificate;
2. a complete live-root union for the same GC cycle;
3. a safe RFC 10.05.60 issue-log rotation over that union;

the post-rotation authoritative issue relation MUST contain both receipt
identities.

This result preserves token-origin resolution.  Payload availability remains
owned by RFC 10.05.32 and RFC 10.05.33.

** ASP-RFC-10.05-CRRB-ATOMIC-PUBLICATION

Retry publication MUST occur after:

- both issue records are authoritative;
- both barrier entries are installed;
- the certificate binds the issue-log rotation cut and GC cycle.

A runtime MUST NOT expose a retry based on a remembered-set write alone.
Crash recovery MUST either recover the complete certificate or treat the retry
as unpublished.

** ASP-RFC-10.05-CRRB-NONIMPLICATION

The protocol MUST preserve these explicit non-implications:

- mark-time snapshot coverage does not imply complete-root coverage;
- remembered-set membership does not imply authoritative issuance;
- a rotation safe for snapshot roots does not imply safety for remembered
  retry roots;
- issue-log preservation does not imply receipt-payload preservation;
- root preservation does not prove graph-route optimality.

  $
    #concurrent($C$, $r$)

  $

    #root($C$, $i$).
  $

  $
    #safe($B$, $A$)
    and #concurrent($C$, $r$)
    and #issued($B$, baseline($r$))

      and #issued($A$, extension($r$))

  $

  $

  $

* SearchLoop cost relevance

A retry whose barrier identity disappears during rotation causes the agent to
repeat graph discovery or request a larger evidence packet.  This increases
tool rounds, token consumption, and disruption of model-prefix cache locality.
More seriously, treating root membership as issuance can make fabricated graph
evidence appear current and route the model toward a short but invalid path.

This RFC stabilizes the evidence universe across concurrent retry and
compaction.  It does not claim minimum graph distance, minimum token cost,
minimum interaction rounds, or a model-cache hit.

* Non-goals and next proof boundary

This RFC does not yet prove:

- atomic implementation of issue-record and remembered-set writes;
- recovery of a partially persisted concurrent retry certificate;
- uniqueness of the issue-log rotation cut under leader transition;
- quorum agreement across replicas;
- graph-router path optimality.

The next proof layer should model the retry publication state machine around
the combined certificate and prove crash outcomes: before certificate,
certificate durable but acknowledgment lost, and publication durable.
