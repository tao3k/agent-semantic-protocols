#+title: Fallback Reflection Contract

* Status

This document defines the fallback admission contract for ASP search, query,
project resolution, provider invocation, and runtime ownership paths.

Fallback is an exceptional protocol transition.  It is not an implementation
convenience, compatibility surface, retry alias, or permission to bypass a
failed parser-owned route.

* Default

The default fallback budget is zero.

When a declared primary path fails, the normal result is a typed terminal
failure.  ASP MUST NOT silently select a legacy command, scan the workspace
root, open a database directly, invoke an unregistered provider artifact, read
source through a raw shell command, or substitute a release artifact for a
developer checkout.

The absence of a usable primary path never authorizes fallback.

* Reflection before admission

A fallback-capable route MUST perform a typed reflection step before executing
the fallback.  The reflection receipt MUST identify:

- the primary capability, provider, artifact, and generation;
- the typed primary failure and its evidence reference;
- the proposed fallback capability and authority;
- why the fallback preserves the requested semantics;
- facts that the fallback cannot preserve;
- the bounded subject and workspace scope;
- the additional I/O, process, database, and latency cost;
- the policy rule that explicitly authorizes the transition;
- the fallback budget consumed;
- an expiry condition or generation after which admission is invalid;
- an observable counter and a stable receipt identity.

If any field is unavailable, reflection fails closed.

* Admission

Fallback admission requires all of the following:

1. The public contract declares the fallback capability.
2. The caller explicitly opts in, or a named policy grants bounded admission.
3. The primary path returned a typed failure covered by that policy.
4. The fallback operates on the same pinned repository candidate generation.
5. The fallback preserves the requested projection and authority.
6. A reflection receipt is emitted before the fallback performs I/O.
7. The fallback usage counter remains within its explicit budget.

Admission MUST be visible in compact CLI output and structured receipts.  A
successful fallback result MUST remain labelled as fallback-derived; it MUST
NOT be rendered as a primary-path success.

* Routes with no fallback

The fallback budget is permanently zero for:

- package-manager project resolution and resolved source scope;
- parser-owned exact selector and exact source projection;
- provider-native capability declarations;
- workspace database ownership and typed IPC;
- resident lifecycle identity and dispatch authority;
- source-access deny recovery.

For these routes, missing providers, stale artifacts, activation drift,
database permission failures, item misses, and generation mismatches are typed
terminal failures.  They must be repaired at their owning boundary.

In particular:

- project resolution MUST NOT fall back to default source roots, default
  extensions, ignored-prefix lists, or workspace-root recursion;
- exact query MUST NOT fall back to raw source reads or lexical approximations;
- CLI, Hook, and Search MUST NOT fall back from typed IPC to direct Turso open;
- developer provider installation MUST NOT fall back to a release download;
- a missing resident route MUST NOT fall back to inline or generic child work.

* State machine

#+begin_example
primary
  -> success
  -> typed-failure
       -> reflection-denied -> terminal-failure
       -> reflection-admitted -> bounded-fallback -> labelled-result
#+end_example

There is no transition from an untyped error directly to fallback.

* Required verification

Every declared fallback requires scenario tests proving:

- the primary path is used when healthy;
- an untyped failure cannot enter reflection;
- an uncovered typed failure is terminal;
- missing explicit admission is terminal;
- a stale generation invalidates admission;
- a zero or exhausted budget blocks execution;
- the reflection receipt precedes fallback I/O;
- the result remains labelled as fallback-derived;
- the usage counter increments exactly once;
- removal of the fallback does not change primary-path semantics.

Performance tests MUST report primary and fallback latency separately.
Aggregating them into one timing hides regressions and is prohibited.

* Project-resolution consequence

Git owns the repository candidate snapshot.  The language provider owns
package-manager parsing and the package graph.  ASP consumes their typed
project-resolution receipt.

If the provider cannot parse its project entry, ASP returns a typed
project-resolution failure.  It MUST NOT invent a default scope.  A manifest,
lockfile, candidate generation, or provider parser digest change invalidates
the prior scope and requires a new provider-owned resolution.
