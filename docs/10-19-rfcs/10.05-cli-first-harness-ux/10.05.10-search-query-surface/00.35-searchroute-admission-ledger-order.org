#+title: RFC 10.05.35 — SearchRoute Ledger Order and Barrier Token Authenticity
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented refinement of RFC 10.05.34.  It defines the
ordering and authenticity obligations that an admission-GC publication
certificate must discharge.  It does not define a Rust or Python
implementation.

* Abstract

RFC 10.05.34 requires a baseline token and an extension token to be valid
before a publication becomes visible.  An epoch-shaped field alone is not an
ordering proof in a distributed or multi-process ledger:

- two writers may observe skewed wall clocks;
- a restarted ledger may reuse a numerically smaller or larger local value;
- a token from an earlier ledger generation may appear to precede a current
  publication;
- an authorized verifier may accept a token that the ledger never issued.

This RFC replaces time-shaped ordering with a ledger-owned stamp:

#+begin_example
(ledger identity, ledger generation, monotonic sequence)
#+end_example

It also requires verifier soundness with respect to the authoritative token
issue log.  A publication certificate is admissible only when both accepted
tokens were authoritatively issued and both ledger stamps happen before the
publication stamp in the same ledger generation.

* Design defect exposed by the proof

The earlier publication model encoded the intended order as token epochs less
than or equal to a publication epoch.  That is insufficient unless the RFC
also names the authority that allocates the values and the identity boundary
within which comparison is meaningful.

The Lean model exposes three invalid implications:

#+begin_example
wallClock(token) < wallClock(publication)
  does not imply
HappensBefore(token.stamp, publication.stamp)

token.sequence < publication.sequence
  does not imply
HappensBefore(token.stamp, publication.stamp)
when their ledger generations differ

authorizedVerifier(token)
  does not imply
issuedByLedger(token)
without verifier soundness
#+end_example

Consequently, wall-clock values are diagnostic metadata only.  They MUST NOT
be used as admission order, replay protection, or publication authority.

* Normative vocabulary

** Ledger stamp

A =LedgerStamp= MUST contain:

- =ledgerIdentity=: the stable identity of the authoritative admission ledger;
- =ledgerGeneration=: the incarnation of that ledger after creation,
  restoration, or sequence reset;
- =sequence=: a strictly monotonic value allocated by that ledger generation.

The identity and generation form the comparison domain.  A sequence number is
meaningful only inside that domain.

** Same ledger generation

Two stamps are in the same ledger generation exactly when both
=ledgerIdentity= and =ledgerGeneration= are equal.

** Happens-before

=HappensBefore(left, right)= holds exactly when:

1. =left= and =right= belong to the same ledger generation; and
2. =left.sequence < right.sequence=.

This relation is strict, transitive, and irreflexive.

** Authoritative issue log

=issuedByLedger(token)= means that the authoritative ledger recorded the token
as issued under the protocol's token format and generation rules.  The issue
log, not the verifier implementation name, is the origin authority.

** Sound verifier

A verifier is sound when every token it accepts is present in the
authoritative issue relation:

#+begin_example
forall token,
  verifyToken(token) implies issuedByLedger(token)
#+end_example

The RFC does not require every issued token to remain acceptable.  Rotation,
expiry, and revocation may make the verifier intentionally incomplete.

* Normative requirements

** ASP-RFC-10.05-ALO-LEDGER-ORDER

The admission ledger MUST allocate every ordering-relevant token issue and
publication event a ledger stamp.  A publisher MUST establish order using the
ledger-owned =HappensBefore= relation.  Wall-clock timestamps MUST NOT be used
as a substitute.

** ASP-RFC-10.05-ALO-GENERATION

The baseline token, extension token, and publication event MUST have the same
ledger identity and ledger generation.  A token from a previous generation
MUST be rejected even when its numeric sequence is less than the publication
sequence.

Changing ledger identity, restoring a snapshot into a new authority, or
resetting the sequence allocator MUST create a new generation or identity
boundary.  Values from distinct boundaries are incomparable.

** ASP-RFC-10.05-ALO-AUTHENTICITY

The token verifier used by publication admission MUST be sound with respect to
the authoritative issue log.  Successful parsing, a valid signature-shaped
payload, or execution by an authorized verifier process does not by itself
prove that the ledger issued the token.

The publication certificate MUST carry or reference evidence sufficient for
the verifier to establish:

- the accepted token belongs to the authoritative issue relation;
- the token's ledger identity and generation match the publication domain;
- the issue record has not been replaced by an unauthoritative replica.

** ASP-RFC-10.05-ALO-PUBLICATION

A sequenced publication certificate MUST establish all of the following:

1. verifier soundness against the authoritative issue relation;
2. acceptance of the baseline token;
3. acceptance of the extension token;
4. baseline-token issue happens before publication;
5. extension-token issue happens before publication.

Publication visibility MUST remain false until the whole certificate is
available.  Proving only one token order is insufficient.

** ASP-RFC-10.05-ALO-NONIMPLICATION

Implementations and future RFCs MUST preserve these explicit
non-implications:

- wall-clock order does not imply ledger order;
- numeric sequence order across generations does not imply happens-before;
- verifier acceptance without soundness does not imply authoritative issue;
- ledger order does not by itself prove payload retention or crash durability.

The final item keeps this RFC modular: RFC 10.05.32 owns payload retention,
RFC 10.05.33 owns concurrent GC marking, and RFC 10.05.34 owns publication
visibility.

* Mathematical model

The following Org-Babel block is the mathematical source embedded in this RFC.
It is evaluated from stdin by =typst eval=; no generated Typst source file is
part of the protocol.

#+name: searchroute-admission-ledger-order-model
#+begin_src typst
#let same(a, b) = $upright("SameGen")(#a, #b)$
#let hb(a, b) = $upright("HB")(#a, #b)$
#let verify(token) = $upright("Verify")(#token)$
#let issued(token) = $upright("Issued")(#token)$
#let sound = $upright("Sound")(upright("Verify"), upright("Issued"))$
#let ledger-id(stamp) = $upright("ledger-id")(#stamp)$
#let generation(stamp) = $upright("generation")(#stamp)$
#let sequence(stamp) = $upright("sequence")(#stamp)$
#let event-stamp(event) = $upright("stamp")(#event)$
#let wall-time(event) = $upright("wall-time")(#event)$

#[
  Let a ledger stamp be
  $s = (#ledger-id($s$), #generation($s$), #sequence($s$))$.

  Two stamps share one comparison domain exactly when
  $
    #same($a$, $b$)
    equiv
    (#ledger-id($a$) = #ledger-id($b$))
    and (#generation($a$) = #generation($b$)).
  $

  The ledger-owned strict order is
  $
    #hb($a$, $b$)
    equiv
    #same($a$, $b$) and #sequence($a$) < #sequence($b$).
  $

  Therefore
  $
    #hb($a$, $b$) and #hb($b$, $c$)
    arrow.r.double #hb($a$, $c$),
  $
  and
  $
    not #hb($a$, $a$).
  $

  Verifier soundness is the origin obligation
  $
    #sound
    equiv
    forall t,
      #verify($t$) arrow.r.double #issued($t$).
  $

  For baseline token $b$, extension token $e$, and publication $p$, a
  sequenced publication certificate proves
  $
    #sound
    and #verify($b$)
    and #verify($e$)
    and #hb(event-stamp($b$), event-stamp($p$))
    and #hb(event-stamp($e$), event-stamp($p$)).
  $

  Hence it entails both authenticity and order:
  $
    #issued($b$) and #issued($e$)
  $
  and
  $
    #hb(event-stamp($b$), event-stamp($p$))
    and #hb(event-stamp($e$), event-stamp($p$)).
  $

  The following implications are deliberately invalid:
  $
    #wall-time($t$) < #wall-time($p$)
    arrow.r.double.not #hb(event-stamp($t$), event-stamp($p$)),
  $
  $
    #sequence($t$) < #sequence($p$)
    arrow.r.double.not #hb($t$, $p$)
    quad "when" quad #generation($t$) != #generation($p$),
  $
  and
  $
    #verify($t$)
    arrow.r.double.not #issued($t$)
    quad "without" quad #sound.
  $
]
#+end_src

* Interaction with RFC 10.05.34

RFC 10.05.34 remains the owner of the publication-visibility protocol.  Its
epoch comparison is now interpreted as an abstract placeholder that MUST be
discharged by this RFC's ledger-owned certificate before implementation.

A future integration theorem may construct the RFC 10.05.34 publication
certificate from a sequenced publication certificate plus the payload,
retention, and cycle-bound obligations.  This RFC does not claim that theorem:
ledger order proves neither retained payload availability nor GC reachability.

* SearchLoop cost relevance

This refinement is on the correctness path of token-efficient search.  A
publication that admits stale or fabricated graph evidence can make the router
choose a short but invalid path, causing repeated queries, larger packets, and
lost model-prefix cache locality.  Ledger order prevents such evidence from
being considered current; verifier soundness prevents unauthoritative evidence
from appearing current.

The proof does not claim that every accepted path is globally token-optimal.
It establishes a prerequisite: route-cost comparison operates over evidence
that is both ordered and authentic.

* Non-goals and next proof boundary

This RFC does not yet prove:

- durability or replicated consistency of the authoritative issue log;
- safe issue-log compaction and token revocation;
- uniqueness of sequence allocation across a leader transition;
- a complete distributed-history linearizability theorem;
- optimality of the graph-router path or model-cache hit rate.

The next proof layer should model durable issue-log rotation and establish
that compaction preserves every token still referenced by an admissible
publication or retry.
