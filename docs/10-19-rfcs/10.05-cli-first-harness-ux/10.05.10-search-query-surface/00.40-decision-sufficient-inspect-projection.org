#+title: RFC 10.05.10.00.40 — Decision-Sufficient Inspect Projection
#+startup: overview

* Status

Draft research specification.

This RFC defines the correctness criterion for a compact, agent-facing
SearchLoop =inspect= projection. It does not add a complex CLI command tree or
authorize provider implementation.

* Problem

Returning fewer bytes is not sufficient to make inspect efficient. A projection
can be extremely small and omit the one fact that changes the next action. The
agent then needs another round, guesses incorrectly, or executes an invalid
route.

For example, two runtime states may share the same compact summary:

- provider ready and selector executable;
- provider ready and selector missing.

The correct next actions differ:

- execute the route;
- resolve or replace the selector.

If inspect maps both states to one projection, no decoder can always choose the
correct action from that projection.

* Decision

An inspect surface is valid for a decision function only when it is
=decision-sufficient=:

#+begin_quote
every world represented by one projection has the same required next action
#+end_quote

Equivalently, the surface provides a decoder such that:

#+begin_quote
=decode(project(world)) = required-action(world)=
#+end_quote

for every world in the declared scope.

Token minimization happens only among decision-sufficient projections.

* Executable mathematical surface

#+name: decision-sufficient-inspect-projection-math
#+begin_src typst
#let correct(worlds, project, decode, required-action) = {
  worlds.all(world =>
    decode(project(world)) == required-action(world)
  )
}

#let worlds = (
  (provider: "ready", selector: "ready"),
  (provider: "ready", selector: "missing"),
)

#let required-action(world) = {
  if world.selector == "ready" {
    "execute"
  } else {
    "resolve-selector"
  }
}

#let tiny-project(_world) = "provider-ready"
#let tiny-decode(_projection) = "execute"

#let status-project(world) = world.selector
#let status-decode(projection) = {
  if projection == "ready" {
    "execute"
  } else {
    "resolve-selector"
  }
}

(
  tiny-is-correct:
    correct(worlds, tiny-project, tiny-decode, required-action),
  status-is-correct:
    correct(worlds, status-project, status-decode, required-action),
  tiny-token-cost: 1,
  status-token-cost: 2,
  full-state-token-cost: 10,
)
#+end_src

=orgize eval plan --json decision-sufficient-inspect-projection-math ...= and
evaluated using =typst eval --in -=. It is not written as a standalone Typst
document.

* Correctness before compactness

A constant one-token projection is cheaper than a two-token selector-status
projection. It is not usable because it merges worlds whose required actions
differ.

The selector-status projection is decision-sufficient and cheaper than a full
runtime-state dump. It is therefore a valid compact inspect surface for this
decision scope.

This establishes the optimization order:

1. define the next-action decision scope;
2. prove projection sufficiency;
3. minimize token cost among sufficient projections.

Minimizing packet size before defining the decision can remove a necessary
distinguishing fact.

* Inspect scope

Decision sufficiency is relative to:

- root obligation;
- evidence and runtime generation;
- route budget and ledger revision;
- cache and objective context;
- allowed next-action vocabulary; and
- completion policy.

Changing any scoped input can invalidate the projection certificate. A
projection sufficient for choosing =execute= versus =resolve-selector= may not
be sufficient for choosing among several selector implementations.

The inspect receipt therefore binds a =decisionScopeDigest=.

* Progressive refinement

SearchLoop begins with the cheapest known decision-sufficient projection for
the current scope. If the required action remains a refinement action, the next
inspect:

- targets only the unresolved obligation family;
- preserves stable envelope fields;
- adds the distinguishing facts required by the refined action vocabulary; and
- returns a new sufficiency receipt.

This produces a monotone interaction:

#+begin_quote
compact decision -> focused refinement -> compact decision
#+end_quote

The agent does not receive the entire Evidence Graph by default. Full graph
inspection remains available as a diagnostic projection.

* Relationship to completion modes

The inspect projection exposes enough information to distinguish:

- executable exact result;
- executable bounded result;
- executable incomplete incumbent;
- refinement required; and
- bounded failure.

Suppressing the completion mode to save tokens is not decision-sufficient when
the agent's policy treats exact, bounded, and incomplete results differently.

* Relationship to cache

Semantic-search caching and model prefix caching remain separate:

- semantic cache identity controls reuse of graph facts and inspect
  projections;
- stable packet envelopes can improve model prefix-cache hits;
- a prefix-cache hit does not validate stale inspect facts; and
- a semantic projection hit does not guarantee prompt-prefix reuse.

Progressive inspect packets SHOULD keep stable, canonical field ordering and
append focused details after the stable envelope. This is a model-cache
optimization, not part of decision-sufficiency soundness.

* SearchLoop surface

The agent-facing inspect result SHOULD contain:

- decision-scope digest;
- current obligation;
- completion mode;
- selected or required next action;
- minimal distinguishing facts;
- omitted-field families;
- projection token count; and
- sufficiency receipt identity.

The command surface stays small. The agent triggers inspect and follows returned
next actions rather than constructing a large collection of search flags.

* Failure semantics

If no available compact projection is proven decision-sufficient, SearchLoop
returns one of:

- a larger certified projection;
- a focused request for the missing fact;
- an incomplete result with open frontier; or
- a bounded failure receipt.

It MUST NOT return an underspecified projection marked complete.

* Python Turbo Graph consequence

The future Python graph layer SHOULD separate:

- full internal graph state;
- candidate projection families;
- decision decoders;
- projection token-cost estimates; and
- sufficiency certificates.

Sparse graph operations can find distinguishing facts between candidate worlds.
The exported projection is chosen by decision sufficiency and token cost, not by
raw neighborhood size.

* Required Lean obligations

The companion Lean model MUST prove:

- no decoder can make the constant tiny projection correct;
- the selector-status projection has a correct decoder;
- the selector-status projection costs fewer tokens than the full-state
  projection;
- the tiny projection costs fewer tokens but remains invalid; and
- compactness alone does not imply decision sufficiency.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

The original inspect motivation focused on saving tokens. Lean shows that packet
size alone has no correctness theorem. The required invariant is the existence
of a correct decoder for the declared decision scope. Token minimization is
meaningful only after that invariant is established.
