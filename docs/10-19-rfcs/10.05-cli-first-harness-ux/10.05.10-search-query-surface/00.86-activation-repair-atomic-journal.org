#+title: RFC 10.05.86 — Activation Repair Atomic Journal
#+subtitle: Crash-safe repair intent, idempotent sink delivery, and acknowledgement-gated readiness
#+language: en
#+options: toc:3 num:t

* Status

Draft for Lean-backed architectural audit.

This RFC refines the commit and outbox milestones introduced by RFC 10.05.85.
It specifies the smallest durable journal needed to recover from every crash
cut between repair linearization and external sink acknowledgement.

* Core finding

A repair head update and its replay intent cannot be separate uncoordinated
writes.

If the authority generation advances and the process crashes before recording
the journal entry, the system has neither the old admissible repair head nor a
durable description of the new publication. No amount of retry fairness can
reconstruct information that was never committed.

Therefore the repair CAS transaction MUST atomically persist:

- canonical activation identity;
- candidate generation;
- resulting authority revision;
- stable journal entry id;
- schema and binary identity references;
- rollback checkpoint reference; and
- initial publication state.

Immediate delivery is not part of this transaction. Durable replay intent is.

* Local journal and external sink

The protocol contains two independently durable systems:

The sink can accept $k$ immediately before the process crashes. At recovery,
$K_s = k$ while the local journal still says =acknowledged=false=. This is a
normal replay state, not corruption.

* Journal invariant

#+name: activation-repair-journal-invariant
#+begin_src typst
$ g_0 < g arrow.r.double "present" $

$ "present"
arrow.r.double
(i_J = i and g_J = g and r_J = r) $

$ "enqueued" arrow.r.double "present" $

$ "acknowledged" arrow.r.double "enqueued" $

$ "fresh-ready"
arrow.r.double
("acknowledged" and r_f = r) $

$ "rollback-closed" arrow.r.double "fresh-ready" $

$ "retired" arrow.r.double "rollback-closed" $

"ok"
#+end_src

These implications are intentionally one-way. A present journal entry need not
already be enqueued, and a sink-acknowledged publication need not already have
fresh readiness evidence.

The first implication is the exception to vacuous absence: once the active
generation advances beyond the observed predecessor, a durable journal entry
is mandatory. Without this clause, “new head with no entry” would incorrectly
satisfy every entry-conditional invariant.

* Crash matrix

| Crash cut | Durable local state | Durable sink state | Recovery action |
|-
| Before atomic commit | old head, no new entry | unchanged | create a fresh proposal |
| After atomic commit, before enqueue | new head plus present entry | unchanged | enqueue from journal |
| After enqueue, before delivery | durable queued entry | unchanged | deliver using entry id |
| After sink acceptance, before local ack | unacknowledged queued entry | accepted key | redeliver same key, then record ack |
| After local ack, before readiness | acknowledged entry | accepted key | reacquire readiness evidence |
| After readiness, before rollback closure | fresh-ready evidence | accepted key | preserve old generation |
| After rollback closure, before retirement | closed rollback window | accepted key | persist retirement |

The unrecoverable state is “new head without present journal entry.” It MUST be
excluded by storage transaction design rather than repaired heuristically.

* Idempotent replay

#+name: activation-repair-journal-idempotency
#+begin_src typst
$ "sink-key"("deliver"("deliver"(S, k), k))
=
"sink-key"("deliver"(S, k)) $

$ "generation"("deliver"(S, k)) = "generation"(S) $

$ "revision"("deliver"(S, k)) = "revision"(S) $

"ok"
#+end_src

Delivery attempts may increase, but repeated delivery of the same key cannot
change sink acceptance identity, activation generation, or authority revision.

* Normative requirements

** ASP-RFC-10.05-ARAJ-ATOMIC

Repair CAS and durable journal-entry creation MUST share one linearization
transaction. A successful CAS without durable replay intent is forbidden.

** ASP-RFC-10.05-ARAJ-BINDING

The journal entry MUST bind canonical identity, candidate generation, and the
resulting authority revision. An entry from another generation or revision
MUST NOT be replayed.

** ASP-RFC-10.05-ARAJ-OUTBOX

Enqueue state MUST imply that the bound journal entry is durable. A queue token
without recoverable entry content is invalid.

** ASP-RFC-10.05-ARAJ-KEY

Every sink delivery MUST use the stable journal entry id as its idempotency
key. Retry MUST reuse that key and MUST NOT mint a new delivery identity.

** ASP-RFC-10.05-ARAJ-SINK

External sink acceptance and local acknowledgement are separate durable
events. Recovery MUST support a sink-accepted but locally unacknowledged state.

** ASP-RFC-10.05-ARAJ-ACK

The journal MUST record acknowledgement only when the sink's accepted key
matches the current journal entry id. A conflicting key MUST fail closed.

** ASP-RFC-10.05-ARAJ-READY

Fresh readiness MUST require local sink acknowledgement and MUST bind the
current authority revision. Delivery attempt count is not acknowledgement.

** ASP-RFC-10.05-ARAJ-RETIRE

Retirement MUST require fresh readiness followed by explicit rollback-window
closure. Sink acknowledgement alone cannot authorize retirement.

* Lean audit

The executable model is:

- =packages/proofs/ASPProof/ActivationRepairJournal.lean=

It proves:

- empty and atomic-commit journals satisfy the invariant;
- a head/enqueue split commit violates the invariant;
- crash after commit but before enqueue remains replayable;
- enqueue does not alter generation, revision, or entry id;
- duplicate delivery is idempotent for sink acceptance;
- delivery cannot advance activation generation or authority revision;
- crash after sink acceptance can still record acknowledgement;
- replay after lost acknowledgement preserves sink acceptance;
- a conflicting sink key cannot acknowledge the journal;
- commit without acknowledgement cannot derive readiness;
- readiness without rollback closure cannot retire; and
- proof-gated acknowledgement, readiness, rollback closure, and retirement
  preserve the journal invariant.

* Logic bugs found

** Entry-conditional invariants can pass vacuously

An invariant stating only “if an entry exists, it matches the head” accepts the
most dangerous state: a new head with no entry. Generation advancement must
itself require entry presence.

** “Transactional outbox” is ambiguous

An outbox is crash-safe only if entry creation shares the same transaction as
the state change it publishes. Writing the outbox immediately after CAS leaves
an unrecoverable crash interval.

** Sink success is not local knowledge

The sink can durably accept a request while the caller loses the response.
Treating this as an ordinary delivery failure creates duplicate effects unless
the same idempotency key is replayed.

** Attempt count is not evidence

One or many delivery attempts do not prove sink acceptance. Readiness must
depend on a matching durable acknowledgement.

** Retirement cannot follow acknowledgement directly

Sink acknowledgement establishes publication, not runtime health or rollback
safety. Fresh readiness and rollback closure remain independent gates.

* Remaining proof boundary

The model uses one journal entry and one sink acceptance slot. The next proof
must cover:

- several generations with concurrent journal entries;
- sink acceptance sets rather than one key;
- stale-entry replay after a newer generation wins;
- acknowledgement reordering across entries;
- journal compaction and tombstones;
- garbage collection without resurrecting retired work; and
- bounded token/search cost for recovering the minimal unresolved frontier.
