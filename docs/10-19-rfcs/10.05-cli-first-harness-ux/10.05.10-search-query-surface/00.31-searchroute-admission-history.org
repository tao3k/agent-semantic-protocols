#+title: RFC 10.05.31 — SearchRoute Admission History and Acknowledgement Recovery
#+author: ASP contributors
#+language: en

* Status

Draft.

RFC 10.05.30 proves atomic ledger transition and crash pre/post recovery.  This
RFC extends the ledger from a boolean run marker to a durable admission record
so concurrent attempts, lost acknowledgements, and conflicting retries have a
deterministic result.

* Problem

A boolean =committedRun(runId)= marker can reject a retry, but it cannot answer:

- which baseline receipt was consumed;
- which extension receipt was consumed;
- whether a retry requests the same receipt pair; or
- what acknowledgement should be returned after the original response is lost.

Two ledgers can expose identical boolean committed markers while storing
different receipt pairs.  The marker therefore loses information required for
safe acknowledgement recovery.

* Normative clauses

** ASP-RFC-10.05-AHR-RECORD

The durable value indexed by an evaluation-run identity MUST contain the
baseline and extension receipt identities.  A boolean committed marker is not a
sufficient admission record.

** ASP-RFC-10.05-AHR-LINEARIZATION

The atomic write of the previously absent admission record is the commit
linearization point.  Once one attempt has installed a record for a run
identity, every later attempt for that run MUST observe a non-empty record and
MUST NOT perform another commit.

For two concurrent attempts, the durable order MUST admit at most one absent-to-
present transition for the run identity.

** ASP-RFC-10.05-AHR-ACK-RECOVERY

A successful acknowledgement MUST be reconstructible from the durable
admission record.  If commit succeeds but the response is lost, an exact retry
MUST return the existing record without rerunning search, reevaluating the
frontier, or consuming either receipt again.

** ASP-RFC-10.05-AHR-CONFLICT

If a run identity already contains a record and a retry supplies a different
receipt pair, the ledger MUST return the existing record together with a
conflict result.  It MUST NOT overwrite the record or interpret the request as a
new run.

** ASP-RFC-10.05-AHR-NONIMPLICATION

None of the following is sufficient acknowledgement evidence:

- a boolean committed marker;
- absence of an in-memory response object;
- possession of fresh semantic-evaluation receipts;
- a retry using the same run identity but a different receipt pair; or
- a network timeout after the commit request.

* Mathematical model

The following Org-Babel Typst block is evaluated through stdin.

#+name: searchroute-admission-history-model
#+begin_src typst
#let AdmissionRecord = $ A = (
  i_"baseline-receipt",
  i_"extension-receipt",
) $

#let CanRecordCommit = $ "CanRecordCommit"(L, u, A) "iff" cases(
  A_"baseline" != A_"extension",
  L_"record"(u) = "none",
  "not" L_"consumed"(A_"baseline"),
  "not" L_"consumed"(A_"extension"),
) $

#let AtomicRecordCommit = $ "AtomicRecordCommit"(L_0, L_1, u, A) "iff" cases(
  "CanRecordCommit"(L_0, u, A),
  forall i, L_1_"consumed"(i) "iff" cases(
    L_0_"consumed"(i),
    i = A_"baseline",
    i = A_"extension",
  ),
  L_1_"record"(u) = "some"(A),
) $

#let SingleWinner = $ "AtomicRecordCommit"(L_0, L_1, u, A_0)
  "implies" forall A_1,
  "not" "CanRecordCommit"(L_1, u, A_1) $

#let AckRecovery = $ "AtomicRecordCommit"(L_0, L_1, u, A)
  "implies" cases(
    L_1_"record"(u) = "some"(A),
    "not" "CanRecordCommit"(L_1, u, A),
  ) $

#let ConflictingRetry = $ cases(
  L_"record"(u) = "some"(A_0),
  A_0 != A_1,
) "implies" "Conflict"(A_0, A_1) $

#let MarkerEquivalent = $ "MarkerEquivalent"(L_0, L_1) "iff"
  forall u,
  (exists A, L_0_"record"(u) = "some"(A))
  "iff"
  (exists A, L_1_"record"(u) = "some"(A)) $

#let MarkerLossCounterexample = $ cases(
  "MarkerEquivalent"(L_0, L_1),
  L_0_"record"(u) != L_1_"record"(u),
) "implies" "BooleanMarkerInsufficient" $

#let Main = (
  AdmissionRecord,
  CanRecordCommit,
  AtomicRecordCommit,
  SingleWinner,
  AckRecovery,
  ConflictingRetry,
  MarkerEquivalent,
  MarkerLossCounterexample,
)
#+end_src

* Lean correspondence

The executable model is:

#+begin_example
packages/proofs/ASPProof/SearchRouteAdmissionHistory.lean
#+end_example

The Lean module proves:

- atomic record commit persists the acknowledgement payload;
- the first linearized commit rejects a second commit for the same run;
- a lost acknowledgement is recoverable without recommit;
- a conflicting retry returns the existing committed record; and
- boolean-equivalent ledgers can contain different acknowledgement payloads.

* SearchLoop consequence

After a timeout, SearchLoop should perform one compact lookup by evaluation-run
identity.  A found record terminates the admission loop and returns its receipt
pair.  This avoids repeating evidence-graph traversal, model inference, cache
warming, and tool interaction merely because an acknowledgement packet was
lost.
