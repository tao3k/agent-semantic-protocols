#+title: RFC 10.05.10.00.37 — AND/OR Evidence Obligation Graph
#+startup: overview

* Status

Draft research specification.

This RFC corrects the structural target of Evidence Graph search. It does not
add CLI commands or authorize provider implementation.

* Problem

The phrase "shortest graph path" is insufficient for evidence search. A simple
path establishes a chain of reachability. Many executable search claims require
several independent premises:

- the provider was resolved;
- the selector is executable;
- the projection is compatible;
- the evidence root matches the active generation; and
- the route remains within budget.

These premises form an AND obligation. Reaching only the provider node does not
certify the whole claim, regardless of how short that path is.

Other goals are alternatives. For example, either of two provider-owned exact
selectors may realize the same source obligation. These form an OR obligation.

Without typed AND/OR semantics, adjacency cannot tell the Graph Router whether
to collect all outgoing branches or choose one. A shortest-path algorithm can
therefore return a structurally short but logically incomplete certificate.

* Decision

The Evidence Graph exposes typed obligation structure:

- =Atom=: one evidence fact must hold;
- =All(left, right)=: both child obligations must be realized;
- =Any(left, right)=: at least one child obligation must be realized.

The certified search target is:

#+begin_quote
a minimum feasible proof subgraph that realizes the root obligation
#+end_quote

not merely a shortest path to one reachable atom.

* Executable mathematical surface

#+begin_src typst
#let realizes(state, obligation) = {
  if obligation.kind == "atom" {
    state.at(obligation.name, default: false)
  } else if obligation.kind == "all" {

      and realizes(state, obligation.right)
  } else {
    realizes(state, obligation.left)

* Realization semantics

An evidence state realizes an atom when the corresponding parser-owned fact is
present and valid for the active generation.

It realizes =All(left, right)= only when it realizes both children. The proof
certificate contains both child certificates.

It realizes =Any(left, right)= when it realizes at least one child. The
certificate records which branch was selected; an OR proof cannot silently
change branch after admission.

AND and OR are logical structure, not ranking hints. A high-ranked atom cannot
compensate for a missing conjunct.

* Counterexample

Let the evidence state contain =provider-resolved=true= and
=selector-executable=false=.

- a path reaches the provider atom;
- the OR obligation =provider OR selector= is realized;
- the AND obligation =provider AND selector= is not realized.

Thus:

#+begin_quote
atomic reachability does not imply root-obligation realization.
#+end_quote

The counterexample directly captures the provider-ready versus
selector-executable gap found by the earlier executability RFC.

* Proof plans

A proof plan mirrors the obligation:

- an atom plan carries one parser-owned evidence witness;
- an AND plan carries both child plans;
- an OR plan carries exactly one selected child plan.

A Lean =PlanCertifies= derivation is structural evidence that the plan matches
the obligation. The soundness theorem states that any certified plan realizes
its root obligation.

This prevents a renderer, router, or cache from presenting a list of relevant
nodes as if it were a proof. Relevance projection can generate candidates;
certification requires a typed derivation.

* Cost and feasibility

Proof-subgraph cost uses RFC 00.36:

- AND children compose as required DAG branches;
- OR children are alternatives, so the router admits feasible branches and
  selects one;
- shared evidence nodes are charged once only when content identity proves they
  are the same reusable witness;
- consumable resources add across required branches;
- schedule span depends on sequential or parallel execution.

The optimization problem becomes:

1. generate proof-plan candidates;
2. reject plans that do not structurally certify the root;
3. reject plans that are not feasible under the current ledger and capability
   context;
4. minimize the canonical cost over the residual certified plans.

A shorter incomplete path never enters the optimization domain.

* Hyperedge representation

An AND obligation is naturally a directed hyperedge from a set of premises to
one conclusion. The implementation MAY encode hyperedges through explicit
obligation nodes, but the shared schema MUST preserve the grouping semantics.

Flattening:

#+begin_quote
={A, B} -> C=
#+end_quote

into independent edges =A -> C= and =B -> C= is unsound because it changes
conjunction into disjunction.

Provider-owned graph facts can contribute atoms and derivation edges. The
language-neutral Evidence Graph owns the =all=/=any= realization semantics.

* Cycles

Evidence graphs can contain recursive dependency and call relationships. A
cycle does not realize itself. A proof plan must be a finite derivation rooted
in independently witnessed atoms.

The router tracks obligation identity plus evidence generation in its visited
set. Revisiting the same unresolved obligation without a strictly improving
resource state is rejected as a non-progress transition.

* SearchLoop consequence

The interactive SearchLoop should return:

- the current root obligation;
- realized and unresolved child obligations;
- whether the next choice is AND completion or OR selection;
- compact candidate proof plans; and
- the cheapest missing evidence action.

This is more token-efficient than dumping a large graph. The agent sees the
smallest unresolved logical frontier and issues one focused next action.

The CLI remains thin. AND/OR structure belongs to the search packet and graph
schema, not a growing family of command flags.

* Python Turbo Graph consequence

The future Python layer SHOULD use:

- typed obligation nodes or hyperedges;
- sparse indexes for candidate atom and derivation discovery;
- a proof-plan constructor separate from raw adjacency traversal;
- structural sharing keyed by evidence identity; and
- feasibility/cost folds over certified proof DAGs.

SciPy sparse traversal can accelerate candidate expansion. It cannot decide
whether an edge group is conjunctive or disjunctive unless that semantics is
present in the graph contract.

* Required Lean obligations

The companion Lean model MUST prove:

- realization of =All= is equivalent to realization of both children;
- realization of =Any= is equivalent to realization of at least one child;
- the provider-only state reaches the provider atom;
- the provider-only state realizes the OR example;
- the provider-only state does not realize the AND example;
- any structurally certified proof plan realizes its obligation; and
- no proof plan can certify the missing-conjunct example.

The audit module emits these declaration families as Lean-generated JSON.

* Design finding

Earlier shortest-path language implicitly treated every graph branch as an
alternative. The Lean counterexample shows that this weakens required evidence:
one reachable atom would be accepted for a conjunctive goal. Typed obligations
change the search target from a path to a realizing proof subgraph while
retaining shortest-path algorithms as an internal accelerator for atomic and OR
subproblems.
