#+title: RFC 10.05.10.00.49 — Crash-Safe Execution Reconciliation
#+startup: overview

* Status

Draft research specification.

This RFC defines safe SearchLoop recovery when a process crashes near an
external model/tool side effect. It does not add CLI commands or authorize
implementation.

* Problem

RFC 00.48 proves semantic continuity for an in-memory or fully persisted trace.
A crash can occur between:

1. persisting an admitted state;
2. issuing an external request;
3. receiving the external outcome; and
4. persisting the completed receipt.

After restart, the durable checkpoint may say =executing= while the remote
outcome is unknown.

Blindly retrying can:

- duplicate model token cost;
- repeat a tool side effect;
- consume the same ledger reservation twice;
- create two outcome receipts for one admission; or
- violate request-bound cache and feedback semantics.

Treating the action as failed is also unsound because it may have succeeded
remotely.

* Decision

Recovery uses a closed =SafeResume= relation over:

- durable checkpoint phase;
- request/effect identity;
- authoritative remote observation; and
- resume action.

The resume actions are:

- =execute=: issue a request proven not to have started;
- =reconcile=: determine or safely replay the outcome under the same effect
  identity;
- =accept-completed=: attach an already completed result; and
- =stay-completed=: perform no external action.

An =executing + unknown= checkpoint permits only =reconcile=.

* Durable checkpoint

The checkpoint binds:

- trace digest;
- context digest;
- phase;
- admission digest;
- request digest;
- effect nonce or idempotency key;
- ledger reservation/revision;
- completion mode; and
- last durable receipt-chain head.

The checkpoint is written before issuing the external action. Phase and effect
identity are part of one durable transition.

* Remote observation

Recovery obtains an authoritative observation bound to request and effect
identity:

- =not-started=;
- =completed= with outcome receipt;
- =failed-before-effect=; or
- =unknown=.

Absence from a local log is not =not-started=. That conclusion requires a
provider or effect-owner guarantee.

* Safe execute

=execute= is permitted only when:

- checkpoint phase is =admitted=;
- observation is authoritatively =not-started=;
- request/effect identities match;
- ledger reservation remains current; and
- admission bundle remains execution-ready.

This is a continuation of the original admission, not a new route decision.

* Mandatory reconciliation

When outcome is unknown, SearchLoop enters =reconciling=.

Reconciliation may:

- query the provider by idempotency key;
- safely replay the same idempotent request;
- inspect a durable external transaction;
- wait for completion;
- produce a typed indeterminate failure; or
- request user/external authority when no safe automated resolution exists.

It MUST NOT allocate a new request digest and call that a retry.

Reconciliation consumes rounds and transitions. It remains subject to a bounded
recovery budget.

* Completed observation

If an executing checkpoint has a completed remote observation:

- validate request/effect binding;
- validate or reconstruct the outcome receipt;
- append the completion edge;
- preserve the original admission and completion mode; and
- apply causal feedback through RFC 00.47.

The external success does not reconstruct missing admission evidence.

* Ledger semantics

The ledger reservation remains held while outcome is ambiguous. Releasing it
and admitting another branch could overspend if the original action later
proves successful.

Reconciliation resolves the reservation to:

- consumed;
- safely released after proof of no effect; or
- quarantined with a bounded indeterminate receipt.

* Idempotency scope

An idempotency key is not globally meaningful. It binds:

- provider/effect owner;
- operation schema/version;
- payload digest;
- request digest;
- admission digest; and
- context generation.

Reusing a key with a changed payload is rejected.

* SearchLoop surface

The agent receives a compact recovery packet:

#+begin_src json
{
  "phase": "reconciling",
  "requestDigest": "...",
  "effectNonce": "...",
  "remoteStatus": "unknown",
  "ledgerStatus": "held",
  "allowedAction": "reconcile",
  "recoveryBudget": {
    "roundsRemaining": 2,
    "transitionsRemaining": 2
  }
}
#+end_src

The CLI does not expose a large recovery command tree. SearchLoop returns the
only proof-permitted next action.

* Python Turbo Graph consequence

The future Python runtime SHOULD:

- persist execution-intent checkpoints before side effects;
- use request-bound idempotency identities;
- recover through a closed resume relation;
- hold ledger reservations across ambiguous outcomes;
- distinguish retry from reconciliation; and
- append recovered completion receipts to the original trace.

* Required Lean obligations

The companion Lean model MUST prove:

- an ambiguous executing checkpoint permits reconciliation;
- the same checkpoint does not permit execute;
- it does not permit accept-completed;
- mismatched request or effect identity rejects all resume actions;
- an admitted/not-started checkpoint permits execute; and
- a completed checkpoint permits only stay-completed.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

The end-to-end trace theorem assumes each external edge has a durable result.
Crash timing introduces a third truth value between success and failure:
unknown effect. Lean's closed resume relation prevents that state from
inhabiting the execute constructor and exposes reconciliation as a required
SearchLoop phase.
