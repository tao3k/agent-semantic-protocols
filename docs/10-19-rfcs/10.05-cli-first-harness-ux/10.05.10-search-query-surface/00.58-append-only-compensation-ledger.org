#+title: 00.58 Append-Only Compensation Ledger
#+startup: overview

* Status

Draft.

This module refines the correction boundary introduced by
=00.57-non-destructive-resolution-correction.org=.  It specifies how a
correction that changes the effective economic meaning of a finalized search
effect is reflected in resource accounting without deleting or rewriting the
original receipt.

The design target is the SearchLoop hot path, but the accounting contract is
language neutral.  A future Python Turbo Graph implementation may realize this
model only after the shared RFC and proof obligations are stable.

* Problem

A final external-effect receipt can later be superseded by an authorized
correction.  For example, an immutable receipt may say that twenty token units
were consumed while a later authority establishes that those units must be
returned.

Changing the historical =consumed= field to zero is unsafe:

- the original observation is destroyed;
- audit replay can no longer explain why a prior route was rejected;
- cache and feasibility decisions lose their causal input;
- repeated correction delivery can silently create resources;
- a correction can be confused with an ordinary monotone resolution.

The ledger therefore needs two views:

1. an immutable historical view of gross effects; and
2. an append-only compensating view used to calculate current availability.

* Accounting State

For one resource dimension, define:

- =capacity=: original resource capacity;
- =available=: currently available resource;
- =held=: resource reserved by admitted but unresolved work;
- =quarantined=: resource whose external disposition is unknown;
- =grossConsumed=: cumulative immutable consumed history;
- =credits=: cumulative authorized compensation returned to availability.

The conservation invariant is:

This is deliberately not the equation

=available + held + quarantined + netConsumed = capacity=.

That equation is useful as a derived economic view, but it hides whether a
smaller net value came from erasing history or from an authorized compensation.
The canonical ledger retains both =grossConsumed= and =credits=.

* Adjustment Kinds

The ledger supports two correction-derived adjustments.

** Credit

A credit represents a correction from effective =consumed= to effective
=noEffect=:

- increase =available= by the corrected amount;
- increase =credits= by the same amount;
- leave =grossConsumed= unchanged.

A credit is allowed only when:

=credits + amount <= grossConsumed=.

This bound prevents cumulative credits from exceeding the immutable consumed
history.  It is a necessary local guard against double compensation, but it is
not sufficient authorization by itself.

** Debit

A debit represents a correction from effective =noEffect= to effective
=consumed=:

- decrease =available= by the corrected amount;
- increase =grossConsumed= by the same amount;
- leave =credits= unchanged.

A debit is allowed only when =amount <= available=.  The rule preserves
conservation and fails closed when the resource is no longer available.

Both operations are append-only with respect to historical counters:
=grossConsumed= never decreases and =credits= never decreases.

* Compensation Authorization Record

An accounting adjustment MUST be bound to a unique correction record.  The
record contains:

- =correctionDigest=;
- =authorityDigest=;
- =dimensionDigest=;
- =amount=;
- =revision=;
- =status=, either =pending= or =applied=.

A proposal contains the same identity fields, the expected revision, and the
adjustment kind.  A commit is authorized only when all identity fields and the
amount match, the expected revision equals the stored revision, and the stored
status is =pending=.

An authorized commit atomically:

1. applies the allowed ledger adjustment;
2. changes the compensation record to =applied=; and
3. increments its revision.

Once committed, replay of the same proposal is rejected because the record is
no longer pending and its revision has advanced.  The original effect receipt
and original correction receipt remain immutable.

* SearchLoop Contract

SearchLoop MUST NOT infer a compensation from a changed effective view alone.
It needs all of:

- an immutable original receipt;
- an authorized correction receipt;
- a pending compensation record bound to that correction, authority, dimension,
  and amount;
- an exact revision match;
- a dimension-local adjustment guard;
- one atomic ledger-and-record commit.

The compact agent-facing result should expose only decision-relevant fields:

#+begin_src json
{
  "correction": "sha256:...",
  "dimension": "tokens",
  "adjustment": "credit",
  "amount": 20,
  "revisionBefore": 7,
  "revisionAfter": 8,
  "status": "applied",
  "balancePreserved": true,
  "historyRewritten": false
}
#+end_src

Detailed receipts remain addressable through inspect rather than being repeated
through every SearchLoop round.

* Graph and Cache Consequences

A compensation changes current feasibility without changing the historical
evidence graph:

- the original effect node remains;
- the correction node supersedes its effective interpretation;
- the compensation node changes the accounting projection;
- dependent feasibility, route-ranking, and completion certificates may become
  stale;
- unrelated evidence and route proofs remain valid.

Therefore this RFC proves only local accounting and replay safety.  A following
module must define dependency-scoped invalidation and recomputation for cached
bounds and route certificates.

Model-prefix cache hits and search-result cache hits are distinct:

- a model-prefix cache hit can reduce prompt-computation cost but does not change
  ledger feasibility;
- a search-result cache hit can reuse graph evidence only while its dependency
  certificate remains valid;
- neither cache may authorize or replay compensation.

* Python Turbo Graph Consequences

A future Python implementation should separate:

- immutable effect and correction facts in the evidence store;
- an append-only compensation record store;
- a derived effective-view projection;
- resource-dimension ledgers;
- dependency-scoped certificate invalidation.

The graph router should consume a compact current feasibility projection.  It
should not scan the complete historical ledger during every loop, and it should
not encode compensation policy in string-based router heuristics.

* Lean Obligations

The accompanying Lean model establishes:

1. =ASP-RFC-10.05-ALC-BALANCE=: credit and debit preserve the
   conservation equation;
2. =ASP-RFC-10.05-ALC-GROSS-HISTORY=: gross consumed history never
   decreases;
3. =ASP-RFC-10.05-ALC-CREDIT-HISTORY=: cumulative credits never decrease;
4. =ASP-RFC-10.05-ALC-CREDIT-BOUND=: credits cannot exceed gross consumed
   under an allowed credit;
5. =ASP-RFC-10.05-ALC-AUTHORIZED-COMMIT=: an authorized
   ledger-and-record commit preserves balance;
6. =ASP-RFC-10.05-ALC-REVISION=: the commit revision advances exactly once;
7. =ASP-RFC-10.05-ALC-REPLAY=: a committed compensation record rejects
   replay.

The Lean kernel audit reports two axiom-free declarations and five
axiom-dependent declarations.  The dependency inventory is =propext= and
=Quot.sound=; no declaration depends on =sorryAx=.  AXLE MUST therefore receive
explicit policy decisions for both =propext= and =Quot.sound= rather than
treating an empty handwritten axiom list as evidence.

The model does not yet prove:

- dependency-closure invalidation of derived graph certificates;
- crash recovery for a distributed ledger-and-record commit;
- cross-dimension exchange rates;
- equivalence between provider receipts and external billing systems.

These remain explicit future obligations rather than hidden implementation
assumptions.
