#+title: RFC 10.05.10.00.39 — Certified Search Completion Modes
#+startup: overview

* Status

Draft research specification.

This RFC defines what SearchLoop may claim when proof-subgraph search stops. It
does not add CLI commands or authorize provider implementation.

* Problem

The minimum feasible AND/OR proof subgraph can require substantial exploration.
Requiring exact global optimality for every interactive search can spend more
tokens and rounds proving optimality than the selected route saves.

Stopping early is useful, but an incumbent route is not automatically optimal.
Without an explicit completion mode, the same result shape can ambiguously mean:

- every feasible omitted candidate was closed;
- the incumbent is within a certified bound; or
- search stopped with unresolved frontier.

That ambiguity is especially dangerous when a heuristic sparse projection finds
a good route quickly. Candidate quality does not certify omitted candidates.

* Decision

Every proof-carrying search result has exactly one completion mode:

1. =exact=: global feasible optimality is proven;
2. =bounded=: a declared objective-specific approximation bound is proven; or
3. =incomplete=: the incumbent is feasible, but an unresolved frontier remains.

The mode is part of the receipt and cannot be inferred from success status,
latency, or an empty rendered page.

* Executable mathematical surface

#+name: certified-search-completion-modes-math
#+begin_src typst
#let global-lower-bound(candidates, lower) = {
  candidates
    .filter(candidate => candidate.feasible)
    .all(candidate => lower <= candidate.objective)
}

#let exact-optimal(candidates, chosen) = (
  chosen.feasible
  and candidates
    .filter(candidate => candidate.feasible)
    .all(candidate => chosen.objective <= candidate.objective)
)

#let bounded-optimal(candidates, chosen, lower, factor) = (
  chosen.feasible
  and global-lower-bound(candidates, lower)
  and chosen.objective <= factor * lower
)

    (name: "best", feasible: true, objective: 10),

* Exact completion

An exact receipt proves:

- the selected proof plan structurally realizes the root obligation;
- the plan is feasible under the bound budget, ledger, capability, and cache
  context;
- every omitted feasible proof family has a certified lower bound; and
- the selected canonical cost is no worse than every such bound.

An empty queue is not sufficient. The queue may be empty because of a sparse
projection, expired cache entry, hidden provider failure, or exploration cap.
Exact completion requires frontier-closure evidence.

* Bounded completion

A bounded receipt contains:

- a feasible incumbent;
- a global lower bound for every feasible candidate;
- a declared factor or gap relation;
- objective identity and version; and
- the frontier certificate from which the lower bound was derived.

For a scalar objective, if:

#+begin_quote
=lower <= optimum= and =chosen <= k * lower=
#+end_quote

then:

#+begin_quote
=chosen <= k * optimum=.
#+end_quote

This is a sound multiplicative approximation certificate.

The factor does not automatically apply to the full lexicographic graph-cost
vector. Multiplication of a lexicographic vector has no protocol-defined
meaning. A bounded receipt MUST name the scalar objective or a separately
versioned vector-gap relation.

Examples of legitimate scalar objectives include:

- uncached token cost after feasibility admission;
- monetary provider cost;
- critical-path latency; or
- a versioned scalarization whose weights are present in the receipt.

Changing weights, cache context, or objective version invalidates the bound.

* Incomplete completion

An incomplete receipt proves only:

- the incumbent realizes the obligation;
- the incumbent is feasible; and
- the listed frontier remains unresolved.

It MAY report heuristic estimates and the best known lower bound. It MUST NOT
use =optimal=, =shortest=, or =globally no worse=.

Incomplete is a successful progressive-search state, not necessarily an error.
The agent can:

- execute the feasible incumbent;
- spend another bounded refinement round;
- switch objective;
- raise a budget; or
- return the open frontier to a parent SearchLoop.

* Counterexample

Let the true best feasible candidate cost 10 and the heuristic incumbent cost
12. Let a valid global lower bound be 6.

- the incumbent is not exact because 12 is not no worse than 10;
- it is a valid factor-2 result because =12 <= 2 * 6= and =6 <= 10=.

Reporting the result as exact is false. Reporting it as bounded with objective,
factor, and lower-bound evidence is sound.

* Stop policy

SearchLoop stop decisions compare the expected cost of another refinement with
the value of improving or closing the result. The policy can stop in bounded or
incomplete mode without weakening the certificate semantics.

Stop-policy estimates are advisory. They do not become optimality evidence.
The final completion mode is determined only by the available proof.

This preserves token efficiency:

- easy searches close exactly;
- expensive searches can close with a useful certified bound;
- highly uncertain searches expose the smallest open frontier.

* Sparse projection consequence

A sparse graph projection may generate the incumbent. Exact or bounded closure
still requires a certificate covering omitted full-graph candidates.

If the projection has only edge soundness, the result remains incomplete. If it
has distance completeness or a valid omitted-frontier lower bound, it can
support exact or bounded completion.

Projection quality and completion mode are separate receipt fields.

* SearchLoop surface

The agent-facing packet remains compact:

#+begin_src json
{
  "completion": {
    "mode": "bounded",
    "objective": "uncached-tokens.v1",
    "factor": 2,
    "incumbent": 12,
    "globalLowerBound": 6
  },
  "frontier": {
    "status": "bounded",
    "nextAction": "refine selector-compatible provider family"
  }
}
#+end_src

The public CLI does not gain separate exact/bounded command trees. SearchLoop
selects or requests a completion policy interactively.

* Python Turbo Graph consequence

The future Python engine SHOULD maintain:

- incumbent proof plan;
- feasible objective value;
- full-graph frontier lower bound;
- objective identity;
- completion-mode proof state; and
- compact next-refinement action.

Heuristic libraries can generate and prioritize candidates. Only proof-visible
lower bounds determine exact or bounded completion.

* Required Lean obligations

The companion Lean model MUST prove:

- a valid bound certificate implies factor-bounded global optimality;
- a factor-one certificate implies exact optimality;
- the example lower bound is globally valid;
- the heuristic example has a valid factor-two certificate;
- the heuristic example is not exact; and
- bounded soundness does not depend on the candidate enumeration order.

The audit module emits the theorem families as Lean-generated JSON.

* Design finding

Previous RFCs used global-optimality language once frontier certificates were
available, but did not define a safe result when the frontier remains only
partially closed. Lean separates the propositions: feasibility, exact
optimality, and factor-bounded optimality have different constructors. An
incumbent cannot accidentally inhabit the exact result type.
