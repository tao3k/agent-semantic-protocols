#+title: RFC 10.05.10.00.36 — Schedule-Aware DAG Resource Algebra
#+startup: overview

* Status

Draft research specification.

This RFC extends feasibility-first admission from a single route to a
SearchLoop plan containing sequential and parallel DAG branches. It does not
authorize a runtime implementation or add public CLI commands.

* Problem

RFC 00.35 proves that route optimization must filter infeasible candidates
before comparing their graph costs. Its feasibility predicate is route-local.
Route-local feasibility is not compositional:

- branch A can fit the remaining token budget;
- branch B can fit the same remaining token budget;
- A and B together can exceed it.

If two branches independently inspect the same budget snapshot, both can
produce valid local proofs and then double-spend the shared resource.

A second problem is that the canonical cost-vector fields do not share one DAG
composition operator:

- token and transition consumption is additive across parallel branches;
- sequential graph hops and rounds are additive;
- parallel graph hops and rounds contribute through the critical-path maximum.

Treating the entire vector as componentwise addition overstates parallel span.
Treating the entire vector as componentwise maximum understates consumable
resources.

* Decision

A DAG plan cost is split into two algebras:

1. =ConsumableCost=: uncached tokens and router transitions;
2. =ScheduleSpan=: graph hops and interaction rounds.

Sequential composition:

- adds consumable costs; and
- adds schedule spans.

Parallel composition:

- adds consumable costs; and
- takes the componentwise maximum schedule span.

Plan feasibility is checked against the composed plan, not inferred from
branch-local feasibility.

* Algebra

Let a plan cost be:

#+begin_quote
=(tokens, transitions; graph-hops, rounds)=
#+end_quote

where the semicolon separates consumable resources from schedule span.

For sequential composition:

#+begin_quote
=(t1 + t2, x1 + x2; h1 + h2, r1 + r2)=
#+end_quote

For parallel composition:

#+begin_quote
=(t1 + t2, x1 + x2; max(h1, h2), max(r1, r2))=
#+end_quote

Parallel composition assumes that the client can actually execute the branches
concurrently. Client parallelism is an execution accelerator, not required
provider behavior. When parallel execution is unavailable, the same plan uses
sequential composition.

* Local-feasibility counterexample

With a 20-token budget, branches A and B each consume 15 tokens. Each branch is
locally feasible against the original snapshot. Both sequential and parallel
composition consume 30 tokens and are globally infeasible.

Parallelism shortens the critical path but does not make model tokens free.
This is the same distinction SearchLoop must preserve when comparing fewer
agent rounds with lower aggregate token cost.

* Atomic reservation

Consumable resources require a ledger. Admission of a branch atomically:

1. checks its consumable cost against the current ledger;
2. reserves tokens and transitions; and
3. returns a new ledger state.

The feasibility proof and ledger transition belong to one receipt. A branch
cannot prove admission against an old ledger version and later consume a newer
one.

The ledger identity SHOULD bind:

- SearchLoop session;
- plan generation;
- evidence-root generation;
- cost-context generation; and
- monotonically increasing ledger revision.

After reserving 15 of 20 tokens, the remaining balance is 5. A second
15-token reservation is rejected. This turns shared-budget safety into a state
transition rather than a collection of independent Boolean predicates.

* Alternative and required branches

An OR branch selects one alternative and reserves only the selected branch.
An AND branch requires all children and composes their costs. The Evidence
Graph must expose which branching semantics applies; the Graph Router cannot
infer AND versus OR from adjacency alone.

Candidate exploration MAY speculatively estimate several OR alternatives.
Only an admitted execution branch consumes the authoritative ledger.
Speculative estimates do not become reservations.

* SearchLoop consequence

SearchLoop receipts distinguish:

- route-local estimated cost;
- composed plan cost;
- reserved consumable cost;
- remaining ledger balance; and
- sequential or parallel schedule interpretation.

A route that was locally feasible but lost a reservation race returns a
bounded =ledger-revision-drift= transition. Retrying consumes a transition and
must observe the new ledger revision.

* Python Turbo Graph consequence

The future Python graph layer needs:

- an immutable DAG cost fold;
- explicit AND/OR branch semantics;
- a versioned consumable-resource ledger; and
- atomic compare-and-reserve at the Graph Router boundary.

SciPy-style sparse matrices can accelerate reachability and lower-bound
queries, but they do not define the resource algebra or reservation semantics.
Those remain explicit proof-carrying graph contracts.

* Required Lean obligations

The companion Lean model MUST prove:

- each example branch is individually feasible;
- sequential composition of the branches is infeasible;
- parallel composition is also infeasible because tokens remain additive;
- parallel span differs from sequential span;
- a successful reservation preserves exact token accounting; and
- after the first reservation, the second branch cannot reserve the remaining
  ledger.

The modular audit emits a Lean-generated JSON manifest for these declaration
families.

* Design finding

The single-route =Feasible= predicate from RFC 00.35 cannot be lifted to a DAG
by checking every node independently. Lean requires a composition operator, and
the four canonical cost dimensions do not form one uniform componentwise
algebra. Splitting consumable resources from schedule span makes both the
parallel-round saving and the token double-spend counterexample explicit.
