#+title: RFC 10.05.10.00.51 — Authorized Quarantine Resolution
#+startup: overview

* Status

Draft research specification.

This RFC defines how quarantined reservations are eventually consumed or safely
released while preserving ledger conservation. It does not add CLI commands or
authorize implementation.

* Problem

RFC 00.50 quarantines a reservation when recovery budget is exhausted and the
external effect remains unknown. Quarantine prevents unsafe reuse, but it is not
a final accounting answer.

A later resolver may establish:

- the external effect completed, so the reservation was consumed; or
- no effect occurred, so the reservation can be released.

Without a conservation rule, resolution could:

- release capacity and also record it as consumed;
- drop quarantined capacity;
- create new available capacity;
- resolve the wrong request/quarantine record; or
- apply two contradictory resolutions.

* Decision

Quarantine resolution requires an authority bound to:

- quarantine digest;
- request and effect identity;
- ledger identity and revision;
- resolution evidence digest; and
- resolver authority identity.

The resolution evidence is a closed alternative:

- =effect-completed=; or
- =no-effect=.

The entire quarantined reservation moves exactly once:

- =effect-completed=: quarantined becomes consumed;
- =no-effect=: quarantined becomes available.

Total ledger capacity is preserved.

* Executable mathematical surface

#+name: authorized-quarantine-resolution-math
#+begin_src typst
#let total(ledger) = (
  ledger.available
  + ledger.consumed
  + ledger.quarantined
)

#let resolve(ledger, evidence) = {
  if evidence == "effect-completed" {
    (
      available: ledger.available,
      consumed: ledger.consumed + ledger.quarantined,
      quarantined: 0,
    )
  } else {
    (
      available: ledger.available + ledger.quarantined,
      consumed: ledger.consumed,
      quarantined: 0,
    )
  }
}

#let initial = (
  available: 70,
  consumed: 10,
  quarantined: 20,
)
#let completed = resolve(initial, "effect-completed")
#let no-effect = resolve(initial, "no-effect")

(
  initial-total: total(initial),
  completed-total: total(completed),
  released-total: total(no-effect),
  completed: completed,
  no-effect: no-effect,
)
#+end_src

* Ledger model

For the quarantined scope, ledger capacity is partitioned into:

- available;
- consumed; and
- quarantined.

The conserved total is:

#+begin_quote
=available + consumed + quarantined=.
#+end_quote

Held reservations have already become quarantined before this resolution phase.
A broader runtime ledger may include additional partitions, but their
conservation theorem must extend this one.

* Effect-completed resolution

Authoritative evidence that the effect completed produces:

#+begin_quote
=available' = available=

=consumed' = consumed + quarantined=

=quarantined' = 0=.
#+end_quote

No capacity is released for another route.

The resulting outcome receipt attaches to the original admission/request trace
and can enter causal feedback under RFC 00.47.

* No-effect resolution

Authoritative proof that no effect occurred produces:

#+begin_quote
=available' = available + quarantined=

=consumed' = consumed=

=quarantined' = 0=.
#+end_quote

Timeout, provider unreachability, or missing local logs are not no-effect
proofs.

* Exclusivity

=effect-completed= and =no-effect= are distinct evidence constructors. One
quarantine record accepts one terminal resolution.

The durable resolution record stores:

- prior quarantine-chain head;
- resolution evidence;
- resulting ledger revision; and
- terminal receipt digest.

A second resolution encounters an already-resolved revision and is rejected.

* Conservation theorem

For either evidence constructor:

#+begin_quote
=total(resolve(ledger, evidence)) = total(ledger)=.
#+end_quote

The Lean proof is independent of the example values.

For the example:

- initial ledger: available 70, consumed 10, quarantined 20;
- completed resolution: available 70, consumed 30, quarantined 0;
- no-effect resolution: available 90, consumed 10, quarantined 0;
- all totals equal 100.

* Authority binding

Resolution authority equality is checked before ledger mutation. A valid
no-effect proof for one request cannot release another request's quarantine.

Authority does not imply a particular outcome. It authorizes the verified
evidence constructor carried by the resolution receipt.

* Python Turbo Graph consequence

The future Python runtime SHOULD:

- resolve against an exact quarantine revision;
- use a closed evidence variant;
- update all ledger partitions atomically;
- verify conservation before commit;
- reject double resolution; and
- append the result to the original trace and feedback chain.

* Required Lean obligations

The companion Lean model MUST prove:

- total capacity is preserved for either resolution;
- resolved quarantine becomes zero;
- completed evidence leaves available capacity unchanged;
- no-effect evidence leaves consumed capacity unchanged;
- the two evidence constructors are exclusive;
- the example totals all equal 100; and
- authority identity mismatch rejects resolution.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

Quarantine safely prevents premature reuse but, without a conservation theorem,
later resolution can still duplicate or lose resources. Lean makes resolution
a total function over a closed evidence type and proves that both branches
preserve the same ledger total.
