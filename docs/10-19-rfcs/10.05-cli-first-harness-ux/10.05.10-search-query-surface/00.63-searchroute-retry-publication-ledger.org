#+title: RFC 10.05.63 — SearchRoute Retry Publication Ledger
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented refinement of RFC 10.05.62.  It defines the
authoritative idempotency-key ledger that serializes concurrent retry
publishers.  It does not prescribe a storage engine or implement Rust or
Python behavior.

* Abstract

RFC 10.05.62 proves safety for one retry publication state.  It does not
prevent two publishers from observing the same absent key and durably
publishing different certificates.

This RFC models publication as one atomic ledger operation:

1. if the key already has a winner, return that winner without republishing;
2. if the key is empty and the candidate is invalid, reject it;
3. if the key is empty and the candidate is valid, atomically install it as
   the winner.

Once installed, a winner is sticky.  Every later attempt recovers the same
winner, including an attempt whose candidate would not itself be eligible for
new installation.  Candidate validation authorizes installation into an empty
slot; it is not an authorization requirement for reading the already
authoritative winner.

* Logic defects exposed by the proof

A process-local sequence:

#+begin_example
if lookup(key) is none:
  write(key, candidate)
  return won
#+end_example

is not an atomic publication protocol.  Two publishers can both observe
=none=, write distinct certificates, and claim =won=.  Green validation and a
durable certificate do not repair the missing serialization point.

The Lean model also exposes a subtler distinction:

#+begin_example
validate(candidate) is required to install candidate
validate(candidate) is not required to recover existing winner
#+end_example

Validating the losing candidate before winner lookup can turn a normal retry
into a rejection even though a durable authoritative result already exists.

* Normative vocabulary

** Retry publication key

The publication key MUST bind the identity domain in which one result is
allowed.  It MUST include or cryptographically bind:

- workspace or evidence-ledger identity;
- ledger generation;
- agent request or retry identity;
- route/evaluation contract version;
- any tenant or authorization scope required to prevent cross-scope aliasing.

A human-readable retry label alone is not an authoritative key.

** Winner

The winner is the certificate stored in the authoritative publication-ledger
cell for one retry key.  The winner is immutable under this RFC.

** Atomic publication

Atomic publication is a linearizable operation over one key.  It returns one
of:

- =won(candidate)= after installing a valid candidate into an empty cell;
- =existing(winner)= when the cell already contains a winner;
- =rejected= when the cell is empty and the candidate is invalid.

** Losing retry

A losing retry is any publication attempt linearized after the winner was
installed.  It does not overwrite the winner.  It recovers
=existing(winner)=.

* Normative requirements

** ASP-RFC-10.05-RPL-KEY-SCOPE

The idempotency key MUST be authoritative and identity-scoped.  Two requests
from different ledger generations, workspaces, tenants, or incompatible
contract versions MUST NOT share a publication cell.

The key projection and comparison rule MUST be contract-visible and auditable.

** ASP-RFC-10.05-RPL-LOOKUP-FIRST

Atomic publication MUST check for an existing winner before validating a new
candidate.

When a winner exists, the operation MUST return that winner and MUST NOT
republish, overwrite, or reject based on the losing candidate.

Authorization to read the winner remains a separate requirement.  This clause
does not authorize cross-scope disclosure.

** ASP-RFC-10.05-RPL-EMPTY-INSTALL

Only a valid certificate may be installed into an empty cell.  Validation MUST
include the RFC 10.05.61 concurrent retry certificate and RFC 10.05.62
publication-state requirements.

The empty-cell check and winner installation MUST share one atomic
linearization point.

** ASP-RFC-10.05-RPL-WINNER-STICKY

After =won(candidate)=, every later atomic publication for the same key MUST:

- retain =candidate= in the ledger cell;
- return =existing(candidate)=;
- leave the durable publication identity unchanged.

No later candidate may replace the winner under this RFC.

** ASP-RFC-10.05-RPL-RECOVERY

An attempt receiving =existing(winner)= MUST recover the winner's durable
publication described by RFC 10.05.62.  It MUST NOT generate a second
publication merely because its own acknowledgment or candidate differs.

An invalid losing candidate MAY recover an existing winner because it is not
being installed.  The runtime MUST still enforce authorization to access the
winner.

** ASP-RFC-10.05-RPL-NONIMPLICATION

The protocol MUST preserve these explicit non-implications:

- process-local lookup followed by write does not imply atomic publication;
- two successful candidate validations do not imply two permissible winners;
- certificate durability does not imply winner installation;
- =existing(winner)= does not imply that the losing candidate was valid;
- per-key atomicity does not prove correct key scoping;
- winner uniqueness does not prove shortest graph-route optimality.

#+name: searchroute-retry-publication-ledger-model
#+begin_src typst
#let cell(ledger, key) = $upright("Cell")(#ledger, #key)$
#let valid(candidate) = $upright("Valid")(#candidate)$
#let publish(ledger, key, candidate) = $upright("Publish")(#ledger, #key, #candidate)$
#let install(ledger, key, candidate) = $upright("Install")(#ledger, #key, #candidate)$
#let won(candidate) = $upright("Won")(#candidate)$
#let existing(candidate) = $upright("Existing")(#candidate)$
#let rejected = $upright("Rejected")$
#let empty = $upright("None")$

#[
  For publication ledger $L$, retry key $k$, and candidate $c$, atomic
  publication is specified by three ordered cases.

  Existing winner recovery has priority:
  $
    #cell($L$, $k$) = w
    arrow.r.double
    #publish($L$, $k$, $c$)
    = (L, #existing($w$)).
  $

  An invalid candidate cannot fill an empty cell:
  $
    #cell($L$, $k$) = #empty
    and not #valid($c$)
    arrow.r.double
    #publish($L$, $k$, $c$)
    = (L, #rejected).
  $

  A valid candidate wins an empty cell:
  $
    #cell($L$, $k$) = #empty
    and #valid($c$)
    arrow.r.double
    #publish($L$, $k$, $c$)
    = (#install($L$, $k$, $c$), #won($c$)).
  $

  Winner installation is sticky.  If $c_1$ wins and $c_2$ is attempted
  afterward, then
  $
    #publish(
      install($L$, $k$, $c_1$),
      $k$,
      $c_2$
    )
    =
    (#install($L$, $k$, $c_1$), #existing($c_1$)).
  $

  No validity premise for $c_2$ is required because $c_2$ is not installed.

  In contrast, two non-atomic publishers may both observe
  $#cell($L$, $k$) = #empty$ and return distinct
  $#won($c_1$)$ and $#won($c_2$)$ claims.  Local empty observations therefore
  do not establish a single linearization order.
]
#+end_src

* SearchLoop cost relevance

Without winner stickiness, a lost acknowledgment or concurrent publisher can
create multiple evidence publications for one retry.  The agent then sees
conflicting graph nodes, repeats route evaluation, expands packets, and spends
additional interaction rounds and tokens.  Stable winner recovery lets the
agent reuse the same publication and preserve model-prefix cache locality.

This RFC proves publication uniqueness under one authoritative key.  It does
not prove that the key is scoped correctly, that the winning graph route is
globally shortest, or that a model cache will hit.

* Non-goals and next proof boundary

This RFC does not yet prove:

- correctness of composite idempotency-key construction;
- authorization-safe winner lookup;
- fencing across leader generations;
- replication and durable linearizability;
- bounded retention of winner cells;
- graph-route optimality.

The next proof layer should formalize the composite key and show that omitting
workspace identity, ledger generation, contract version, or tenant scope
creates concrete cross-domain aliasing counterexamples.
