#+title: RFC 10.05.73 — SearchRoute Cache Replica Rejoin Order
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented refinement of RFC 10.05.72.  It specifies the
state and historical ordering receipt required before a cache replica may
serve after rejoin.  It does not implement a distributed runtime.

* Abstract

A replica can eventually reach a final state in which cache generation,
fencing token, membership, and read flag all look current, while still having
served stale data during rejoin.  Final-state validation cannot reconstruct
whether a token was issued before state catch-up.

Safe rejoin therefore requires both final facts and strict milestone order:

#+begin_example
state installed
  < current token issued
  < serving membership published
  < reads enabled
#+end_example

The order is carried by a proof receipt rather than inferred from wall-clock
timestamps.

* Normative requirements

** ASP-RFC-10.05-CRRO-STATE

The replica MUST install at least the target cache/authorization generation
before obtaining serving authority.

** ASP-RFC-10.05-CRRO-TOKEN

After state installation, the replica MUST obtain an authentic, generation-
current RFC 10.05.72 serving token.

** ASP-RFC-10.05-CRRO-MEMBERSHIP

Serving membership MUST be published only after state installation and current
token issuance.

** ASP-RFC-10.05-CRRO-READ

Reads MUST remain disabled until state installation, token issuance, and
membership publication have all completed.

** ASP-RFC-10.05-CRRO-ORDER

The rejoin certificate MUST carry an authority-owned strict order receipt:

#+begin_example
stateInstalledStep < tokenIssuedStep
tokenIssuedStep < membershipPublishedStep
membershipPublishedStep < readsEnabledStep
#+end_example

Final Boolean state alone MUST NOT substitute for this receipt.

** ASP-RFC-10.05-CRRO-NONIMPLICATION

The protocol MUST preserve these explicit non-implications:

- current token does not imply replica state catch-up;
- final current state does not prove safe historical ordering;
- state catch-up and correct ordering do not authenticate a forged token;
- membership publication does not imply reads are safe;
- wall-clock order does not imply authority-owned milestone order;
- rejoin safety does not prove graph-route optimality.

* Mathematical model

#+name: searchroute-cache-replica-rejoin-order-model
#+begin_src typst
#let installed(state) = $upright("InstalledGeneration")(#state)$
#let target(state) = $upright("TargetGeneration")(#state)$
#let currentToken(state) = $upright("CurrentToken")(#state)$
#let membership(state) = $upright("MembershipPublished")(#state)$
#let reads(state) = $upright("ReadsEnabled")(#state)$
#let safe(state, order) = $upright("SafeRejoin")(#state, #order)$

#[
  Proper milestone order is
  $
    s_i < s_t
    and s_t < s_m
    and s_m < s_r.
  $

  Safe rejoin requires
  $
    #safe($S$, $O$)
    equiv
    #target($S$) <= #installed($S$)
    and #currentToken($S$)
    and #membership($S$)
    and #reads($S$)
    and (s_i < s_t < s_m < s_r).
  $

  A current token, published membership, and enabled reads do not imply safety
  when $#installed($S$) < #target($S$)$.

  Even when every final-state predicate is true, the ordering
  $s_t < s_i < s_m < s_r$ does not prove safe rejoin because token issuance
  preceded state installation.
]
#+end_src

The JSON audit remains modular and scoped only to this RFC.

* SearchLoop cost relevance

Correct rejoin preserves safe cache reuse without forcing global cold starts.
Incorrect ordering can serve revoked route evidence; disabling all rejoin cache
reuse instead increases graph searches, tokens, rounds, and model-prefix
disruption.

* Non-goals and next proof boundary

This RFC does not prove crash recovery between milestones, durable receipt
storage, leader uniqueness, or graph-route optimality.

The next proof layer should model crashes after each milestone and prove that
recovery resumes monotonically without repeating token issuance or enabling
reads from a partially completed rejoin.
