#+title: RFC 10.05.10.00.56 — Monotone Partial Resolution
#+startup: overview

* Status

Draft research specification.

This RFC defines how a per-dimension effect-resolution vector evolves over
time. It does not add CLI commands or authorize implementation.

* Problem

RFC 00.55 permits one resource dimension to remain unknown while others become
consumed or no-effect. A later observation can resolve the unknown dimension.

Without a monotonicity rule, updates can:

- move consumed back to unknown;
- change consumed to no-effect;
- change no-effect to consumed;
- increment revision without resolving any dimension; or
- repeatedly rewrite the same vector.

Such changes can release consumed resources, double-charge released resources,
or create an unbounded no-progress feedback loop.

* Decision

Each dimension follows a closed refinement relation:

#+begin_quote
=unknown -> unknown=

=unknown -> consumed=

=unknown -> no-effect=

=consumed -> consumed=

=no-effect -> no-effect=.
#+end_quote

There are no other ordinary refinement edges.

A vector revision is valid only when:

- every dimension refines monotonically;
- at least one unknown dimension becomes final; and
- revision increases by one.

* Executable mathematical surface

#+name: monotone-partial-resolution-math
#+begin_src typst
#let refines(before, after) = (
  before == "unknown"
  or before == after
)

#let resolved-count(vector) = (
  (if vector.tokens == "unknown" { 0 } else { 1 })
  + (if vector.money == "unknown" { 0 } else { 1 })
  + (if vector.provider-quota == "unknown" { 0 } else { 1 })
)

#let unknown-count(vector) = 3 - resolved-count(vector)

#let vector-refines(before, after) = (
  refines(before.tokens, after.tokens)
  and refines(before.money, after.money)
  and refines(before.provider-quota, after.provider-quota)
)

#let strict-revision(before, after) = (
  vector-refines(before.vector, after.vector)
  and resolved-count(before.vector) < resolved-count(after.vector)
  and after.revision == before.revision + 1
)

#let partial = (
  revision: 1,
  vector: (
    tokens: "unknown",
    money: "consumed",
    provider-quota: "consumed",
  ),
)
#let finalized = (
  revision: 2,
  vector: (
    tokens: "no-effect",
    money: "consumed",
    provider-quota: "consumed",
  ),
)
#let conflicting = (
  revision: 2,
  vector: (
    tokens: "no-effect",
    money: "no-effect",
    provider-quota: "consumed",
  ),
)

(
  partial-to-final: strict-revision(partial, finalized),
  partial-to-conflicting: strict-revision(partial, conflicting),
  unknown-before: unknown-count(partial.vector),
  unknown-after: unknown-count(finalized.vector),
)
#+end_src

* Dimension finality

=consumed= and =no-effect= are terminal within an ordinary resolution lineage.

Terminal means:

- a later receipt may add detail or evidence;
- accounting metadata may be enriched;
- a new graph/problem generation may use the result; but
- the outcome value itself cannot change.

Contradictory later evidence uses the correction protocol defined after this
RFC. It does not masquerade as ordinary refinement.

* Strict vector progress

Componentwise monotonicity alone permits a no-op update. A strict revision also
requires:

#+begin_quote
=resolvedCount(before) < resolvedCount(after)=.
#+end_quote

The three-dimension model satisfies:

#+begin_quote
=resolvedCount(vector) + unknownCount(vector) = 3=.
#+end_quote

Therefore, strict refinement implies:

#+begin_quote
=unknownCount(after) < unknownCount(before)=.
#+end_quote

* Bounded-run theorem

A partial-resolution run has at most:

#+begin_quote
=initial unknownCount=
#+end_quote

valid revision steps.

With token, money, and provider quota dimensions, the absolute maximum is
three. In normal operation, dimensions already resolved in the first outcome
receipt reduce the bound.

This bounds resolution updates independently from reconciliation polling. Many
polls can produce no new revision; only strict information progress enters the
resolution run.

* Example

Initial vector:

- tokens unknown;
- money consumed;
- provider quota consumed;
- revision 1.

Valid finalization:

- tokens no-effect;
- money consumed;
- provider quota consumed;
- revision 2.

Invalid update:

- tokens no-effect;
- money changes from consumed to no-effect;
- provider quota consumed.

The invalid update resolves tokens but rewrites a terminal money outcome, so the
whole vector revision is rejected.

* Ledger consequence

A valid finalization applies only the newly resolved dimension's quarantined
ledger movement:

- unknown to consumed: quarantined to consumed;
- unknown to no-effect: quarantined to available.

Already final dimensions do not move again. This prevents a new vector revision
from replaying earlier ledger mutations.

The vector revision and dimension-ledger revisions commit atomically.

* SearchLoop consequence

The compact update packet exposes:

#+begin_src json
{
  "resolutionRevision": {
    "before": 1,
    "after": 2
  },
  "changedDimensions": ["tokens"],
  "effectResolution": {
    "tokens": "no-effect",
    "money": "consumed",
    "providerQuota": "consumed"
  },
  "unknownRemaining": 0
}
#+end_src

No-op polls remain reconciliation receipts but do not create a new resolution
revision.

* Cache and feedback consequence

A final dimension can seed stable accounting/cache feedback. Unknown dimensions
remain excluded.

Finality is bound to request, effect nonce, resource schema, and evidence
authority. It is not a global fact about all future requests.

* Python Turbo Graph consequence

The future Python runtime SHOULD:

- represent outcomes as a closed enum;
- validate componentwise refinement;
- require at least one newly final dimension;
- increment vector revision exactly once;
- update only newly resolved ledgers;
- reject terminal-value rewrites; and
- expose changed/remaining dimensions compactly.

* Required Lean obligations

The companion Lean model MUST prove:

- consumed can refine only to consumed;
- no-effect can refine only to no-effect;
- strict refinement cannot be a self-loop;
- resolved count plus unknown count equals three;
- strict refinement decreases unknown count;
- partial-resolution run length is bounded by initial unknown count;
- the example token finalization is valid; and
- the conflicting money rewrite is invalid.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

Per-dimension outcomes permit useful partial completion but introduce a new
revision protocol. Lean separates ordinary monotone refinement from correction:
terminal values have no outgoing value-changing edge, while strict progress is
measured only by newly resolved unknown dimensions.
