#+title: RFC 10.05.81 — SearchRoute Cache Rejoin Verifier Lifecycle
#+startup: overview

* Status

Draft proof-bearing extension of RFC 10.05.80.

* Abstract

RFC 10.05.80 binds sink acceptance to an explicit verifier, but a verifier key
is not timeless.  Keys rotate, overlap during migration, and may be revoked.
Receipt issuance time and verification time therefore have different roles.

This RFC adds verifier-covered trust epoch and issuance revision fields.  A
receipt may authorize a current acknowledgement only when its trust epoch is
current or inside the configured previous-epoch overlap window, its issuance is
not in the future, and the epoch is not revoked at verification time.

A receipt issued before revocation may remain valid historical evidence while
being forbidden from authorizing a new current acknowledgement.

* Scope

The RFC models lifecycle admission against one trust-policy snapshot.  It does
not yet prove that distributed verifiers observe the same policy revision.

* Normative clauses

** ASP-RFC-10.05-CRVL-BINDING — Trust metadata is verifier-covered

The verifier-covered identity MUST contain:

- the complete RFC 10.05.80 delivery identity;
- trust epoch;
- receipt issuance revision.

Trust epoch and issuance revision MUST NOT be unsigned wrapper metadata.

** ASP-RFC-10.05-CRVL-CURRENT — Current authorization uses an admitted epoch

A receipt MAY authorize a current acknowledgement only when its trust epoch is
the current epoch or the configured previous epoch within its overlap window.
Any unlisted epoch MUST fail closed.

** ASP-RFC-10.05-CRVL-OVERLAP — Previous-epoch acceptance is bounded

The previous trust epoch MAY remain current-authorizing only through the
configured overlap-end revision.  After that revision it MUST fail current
authorization even when the receipt still verifies cryptographically.

** ASP-RFC-10.05-CRVL-TIME — Issuance and verification revisions are distinct

Receipt issuance revision MUST be less than or equal to verification revision.
A future-issued receipt MUST fail closed.

Implementations MUST NOT substitute wall-clock order for authority revisions.

** ASP-RFC-10.05-CRVL-REVOCATION — Revocation is effective at an authority revision

For an epoch revoked at revision =r=, current authorization MUST fail at every
verification revision greater than or equal to =r=.  A receipt issued at or
after =r= MUST also fail historical validation.

** ASP-RFC-10.05-CRVL-HISTORY — Historical validity is not current authorization

A verifier-accepted receipt issued strictly before its epoch's revocation MAY
remain historical audit evidence.  That historical status MUST NOT authorize a
new acknowledgement after revocation becomes effective.

** ASP-RFC-10.05-CRVL-ACK — Lifecycle admission gates obligation closure

Acknowledgement MUST require:

- the local RFC 10.05.79 acknowledgement predicate;
- sink, protocol, and edge binding;
- lifecycle-verifier acceptance;
- current trust authorization at the verification revision.

** ASP-RFC-10.05-CRVL-NONIMPLICATION — One policy snapshot does not imply global agreement

Proof against one lifecycle snapshot does not imply that every verifier node
observed the same current epoch, overlap boundary, or revocation state.

* Mathematical model

The executable model uses one current epoch, one previous epoch, and one
revocation record to exercise the lifecycle distinctions.

#+name: searchroute-cache-rejoin-verifier-lifecycle-model
#+begin_src typst
#let lifecycle(
  current,
  previous,
  overlap-end,
  revoked-epoch,
  revocation-effective,
) = (
  current: current,
  previous: previous,
  overlap-end: overlap-end,
  revoked-epoch: revoked-epoch,
  revocation-effective: revocation-effective,
)
#let identity(trust-epoch, issued-at) = (
  trust-epoch: trust-epoch,
  issued-at: issued-at,
)
#let epoch-in-window(policy, epoch, verification) = (
  epoch == policy.current
  or (
    policy.previous == epoch
    and verification <= policy.overlap-end
  )
)
#let not-revoked-at(policy, epoch, revision) = if (
  epoch == policy.revoked-epoch
) {
  revision < policy.revocation-effective
} else {
  true
}
#let can-authorize-current(policy, verification, value) = (
  value.issued-at <= verification
  and epoch-in-window(policy, value.trust-epoch, verification)
  and not-revoked-at(policy, value.trust-epoch, verification)
)
#let historically-valid(policy, value, verified) = (
  verified
  and not-revoked-at(policy, value.trust-epoch, value.issued-at)
)
#let policy = lifecycle(5, 4, 15, 4, 12)
#let current = identity(5, 11)
#let previous-before-revocation = identity(4, 11)
#let previous-after-revocation = identity(4, 13)
#let future = identity(5, 14)
#let unlisted = identity(3, 11)
#assert(can-authorize-current(policy, 13, current))
#assert(can-authorize-current(policy, 11, previous-before-revocation))
#assert(not can-authorize-current(policy, 13, previous-before-revocation))
#assert(not can-authorize-current(policy, 16, previous-before-revocation))
#assert(not can-authorize-current(policy, 13, future))
#assert(not can-authorize-current(policy, 13, unlisted))
#assert(historically-valid(policy, previous-before-revocation, true))
#assert(not historically-valid(policy, previous-after-revocation, true))
"ok"
#+end_src

* SearchLoop and graph-router consequence

The graph router can distinguish:

#+begin_example
currently authorized acceptance edge
historically valid but non-authorizing receipt
rejected receipt
#+end_example

Historical receipt evidence remains inspectable without allowing it to reopen
or mutate the current graph admission state.

* Remaining proof boundary

Different verifier nodes can evaluate the same receipt against different trust
snapshots during rotation or revocation propagation.

A follow-up RFC must bind acknowledgement to a linearized trust-policy snapshot:

- monotone policy revision;
- policy digest containing epochs, overlap, and revocations;
- verifier observation of that revision;
- acknowledgement CAS carrying the policy revision;
- rejection when admission state or policy revision changes concurrently;
- audit linkage from the closed edge to the exact policy snapshot.
