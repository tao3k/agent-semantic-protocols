#+title: RFC 10.05.60 — SearchRoute Authoritative Issue-Log Rotation
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented continuation of RFC 10.05.35.  It specifies the
semantic safety boundary for rotating or compacting the authoritative barrier
token issue log.  It does not prescribe a storage engine or implement a Rust
or Python runtime.

* Abstract

RFC 10.05.35 makes verifier acceptance sound with respect to an authoritative
issue relation.  That relation cannot be treated as an eternal, unchanging
Boolean table: production ledgers rotate generations, compact old records, and
retain revocations.

A compactor that copies only tokens referenced by currently visible
publications can delete tokens still needed by pending retries.  A compactor
that proves only live-reference coverage can add fabricated issue records.  A
rotation that preserves issuance but drops revocation can reaccept a token that
was already rejected.

This RFC separates historical origin from current acceptability and defines
safe rotation with three independent obligations:

1. no fabricated issuance;
2. coverage of every live issued reference;
3. monotone preservation of revocation.

* Logic defect exposed by the proof

The phrase “authoritative issue log” is incomplete unless rotation preserves
both positive and negative evidence.  Three tempting conditions are
insufficient:

#+begin_example
retain(currentPublicationReferences)
  is insufficient because pendingRetryReferences may remain live

cover(allLiveReferences)
  is insufficient because the new log may also fabricate unrelated records

copy(allIssuedTokens)
  is insufficient because dropping revocations can resurrect a token
#+end_example

The issue log therefore has two distinct semantic predicates:

- =issued(token)= records historical ledger origin;
- =revoked(token)= records a monotone negative decision.

A token is currently acceptable only when it is issued and not revoked.
Compaction may change the physical representation, but not these logical
obligations.

* Normative vocabulary

** Live reference

A token reference is live when any protocol state may still require its
authoritative origin evidence.  The live-reference root set MUST include at
least:

- tokens referenced by visible publications;
- tokens referenced by admitted but unacknowledged operations;
- tokens referenced by pending retry records;
- tokens protected by the RFC 10.05.33 concurrent-GC barrier;
- tokens required by an in-progress audit or recovery horizon.

Silence from a client is not proof that a retry reference is dead.

** Historical issuance

=issued(token)= means that the authoritative ledger issued the token.
Issuance is historical evidence and MUST NOT become false while a live
reference still depends on it.

** Current acceptability

=acceptable(token)= holds when =issued(token)= is true and =revoked(token)= is
false.  Authentic origin is necessary but not sufficient for current
acceptance.

** Safe issue-log rotation

For a pre-rotation state =before=, post-rotation state =after=, and live-root
predicate =live=, a rotation is safe exactly when:

- every token issued by =after= was issued by =before=;
- every live token issued by =before= remains issued by =after=;
- every token revoked by =before= remains revoked by =after=.

The requirements constrain logical evidence.  A runtime MAY move records to a
content-addressed archive or summarize them with a proof-carrying index, as
long as the predicates remain decidable from authoritative evidence.

* Normative requirements

** ASP-RFC-10.05-AILR-LIVE-ROOTS

The rotation planner MUST compute live roots from the union of publication,
retry, recovery, concurrent-barrier, and audit-horizon references.  Retaining
only visible-publication references is forbidden.

Root enumeration MUST be tied to a ledger generation or snapshot boundary.
References admitted concurrently with enumeration MUST be protected by the
write-barrier protocol of RFC 10.05.33.

** ASP-RFC-10.05-AILR-NO-FABRICATION

Every post-rotation issue record MUST resolve to a pre-rotation authoritative
issue record.  Live-root coverage alone MUST NOT authorize inserting a new
issue record.

Re-encoding, indexing, or archival movement MAY change record identity at the
storage layer, but the receipt MUST retain a verifiable link to the original
ledger issue evidence.

** ASP-RFC-10.05-AILR-LIVE-COVERAGE

For every live token that was authoritatively issued before rotation, the
post-rotation log MUST continue to resolve authoritative issuance.

The rotation MUST fail closed when live-root enumeration is incomplete or when
a retained record cannot be resolved after compaction.

** ASP-RFC-10.05-AILR-REVOCATION

Revocation is monotone across rotation.  A token revoked before rotation MUST
remain revoked afterward.  Rotation MUST NOT reinterpret a missing revocation
record as “not revoked.”

Explicit administrative unrevocation, if ever supported, requires a separate
versioned protocol and MUST NOT be represented as log compaction.

** ASP-RFC-10.05-AILR-ACCEPTANCE

If a post-rotation verifier accepts a token, safe rotation guarantees that the
token was authoritatively issued before rotation.  If the token was revoked
before rotation, safe rotation guarantees that it cannot be accepted after
rotation.

This clause composes with RFC 10.05.35 verifier soundness: the verifier targets
the post-rotation authoritative predicates, while the rotation receipt links
those predicates to the pre-rotation ledger history.

** ASP-RFC-10.05-AILR-NONIMPLICATION

The protocol MUST preserve these explicit non-implications:

- preservation of current-publication references does not imply preservation
  of retry references;
- live-reference coverage does not imply absence of fabricated issue records;
- issuance preservation does not imply revocation preservation;
- safe rotation does not by itself prove distributed linearizability or
  physical durability.

* Mathematical model

The mathematical source remains inside this Org document and is evaluated by
=typst eval= from stdin.  No =:file= header or generated Typst source is
required.

#+name: searchroute-admission-issue-log-rotation-model
#+begin_src typst
#let issued(state, token) = $upright("Issued")(#state, #token)$
#let revoked(state, token) = $upright("Revoked")(#state, #token)$
#let acceptable(state, token) = $upright("Acceptable")(#state, #token)$
#let live(token) = $upright("Live")(#token)$
#let safe(before, after) = $upright("SafeRotate")(#before, #after)$

#[
  An issue-log state $S$ has independent historical and negative predicates:
  $
    #acceptable($S$, $t$)
    equiv
    #issued($S$, $t$)
    and not #revoked($S$, $t$).
  $

  A safe rotation from $B$ to $A$ proves:
  $
    #safe($B$, $A$)
    equiv
    (
      forall t,
      #issued($A$, $t$) arrow.r.double #issued($B$, $t$)
    )
    and
    (
      forall t,
      #live($t$) and #issued($B$, $t$)
      arrow.r.double #issued($A$, $t$)
    )
    and
    (
      forall t,
      #revoked($B$, $t$) arrow.r.double #revoked($A$, $t$)
    ).
  $

  Therefore every live issued reference remains resolvable:
  $
    #safe($B$, $A$)
    and #live($t$)
    and #issued($B$, $t$)
    arrow.r.double #issued($A$, $t$).
  $

  Post-rotation acceptance preserves historical origin:
  $
    #safe($B$, $A$)
    and #acceptable($A$, $t$)
    arrow.r.double #issued($B$, $t$).
  $

  Revocation cannot be forgotten:
  $
    #safe($B$, $A$)
    and #revoked($B$, $t$)
    arrow.r.double not #acceptable($A$, $t$).
  $

  The Lean countermodels witness three invalid shortcuts:
  $
    upright("publication coverage")
    arrow.r.double.not upright("retry coverage"),
  $
  $
    upright("live coverage")
    arrow.r.double.not upright("no fabrication"),
  $
  and
  $
    upright("issuance copied")
    arrow.r.double.not upright("revocation copied").
  $
]
#+end_src

* Composition with earlier RFCs

RFC 10.05.35 owns ledger order and verifier soundness.  This RFC guarantees
that issue-log rotation preserves the authoritative predicate against which
that verifier is sound.

RFC 10.05.32 owns payload retention.  An issue record proving token origin is
not a substitute for the referenced evidence payload.

RFC 10.05.33 owns concurrent GC roots and its write barrier.  This RFC consumes
the resulting complete live-root predicate; it does not independently prove
that a runtime enumerated every concurrent reference.

RFC 10.05.34 owns publication visibility.  A visible publication contributes
roots to this RFC, while unacknowledged admission history and retries contribute
additional roots even when no publication is visible.

* SearchLoop cost relevance

Unsafe compaction converts a previously valid short route into an
unresolvable route.  The agent then repeats discovery, retrieves larger
packets, and loses model-prefix cache locality.  A resurrected or fabricated
token is worse: it may rank invalid evidence as fresh and send the graph router
down a short but semantically false path.

Safe issue-log rotation is therefore a correctness precondition for stable
route cost.  It does not itself prove the globally shortest graph path, minimum
token cost, minimum interaction rounds, or a model-cache hit.

* Non-goals and next proof boundary

This RFC does not yet prove:

- atomic acquisition of the live-root snapshot with concurrent admission;
- leader-transition uniqueness for sequence allocation;
- quorum agreement on the authoritative issue relation;
- physical fsync or replica durability;
- bounded storage growth for permanent revocations;
- graph-router optimality.

The next proof layer should connect the RFC 10.05.33 GC write barrier to this
RFC's full live-root union and prove that a concurrent retry admission cannot
fall between root enumeration and issue-log publication.
