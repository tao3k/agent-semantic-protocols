#+title: RFC 10.05.68 — SearchRoute Retry Authorization Stamp
#+author: ASP Search Protocol Working Notes
#+startup: overview

* Status

This RFC is a proof-oriented refinement of RFC 10.05.67.  It closes the
time-of-check/time-of-use gap between winner authorization and release.  It
does not implement an authorization service or Rust/Python runtime.

* Abstract

Authorization before lookup is necessary but insufficient when authorization
state may change before winner release.  A grant can be revoked, expired, or
superseded by a new authorization generation after an earlier decision was
recorded.

This RFC binds every positive authorization decision to an authorization
generation.  Winner release requires all three facts:

#+begin_example
authorizedAtDecision
and decision.authorizationGeneration = currentSnapshot.generation
and currentSnapshot.grantActive(decision.grant)
#+end_example

The release path rechecks this conjunction atomically with release.  A grant
that becomes active again in a later generation does not revive an old
decision.

* Logic defects exposed by the proof

A stored =authorized=true= bit is not a durable capability.  It says only that
a decision succeeded under an earlier snapshot.

Two races remain without generation binding:

- same-generation revocation after decision but before release;
- authorization generation advance followed by reuse or reactivation of the
  same grant identity.

Checking only the decision bit releases the winner in both cases.

* Normative requirements

** ASP-RFC-10.05-RAS-GENERATION

Every authorization decision MUST bind the authorization snapshot generation
under which it was produced.  Generation values MUST be allocated by the
authorization authority, not by caller wall-clock time.

** ASP-RFC-10.05-RAS-ACTIVITY

Winner release MUST recheck that the grant remains active in the current
authorization snapshot.  An earlier positive decision MUST NOT substitute for
current activity.

** ASP-RFC-10.05-RAS-RELEASE

A winner may be released only when:

1. the original decision was positive;
2. its generation equals the current authorization generation;
3. its grant is active in that current generation.

Failure of any condition MUST produce =denied=.

** ASP-RFC-10.05-RAS-REPLAY

A decision from an earlier generation MUST remain invalid after generation
advance, even when the same grant identity becomes active again.

Reactivation requires a new decision stamped with the new generation.

** ASP-RFC-10.05-RAS-ATOMICITY

The freshness recheck and winner release MUST share an atomic authorization
snapshot or equivalent proof-carrying transaction.  A second revocation race
between recheck and release is forbidden.

** ASP-RFC-10.05-RAS-NONIMPLICATION

The protocol MUST preserve these explicit non-implications:

- positive authorization at decision time does not imply authorization at
  release time;
- active grant identity does not make an old-generation decision current;
- equal wall-clock timestamps do not prove equal authorization generation;
- authorization generation equality does not imply grant activity;
- freshness safety does not prove timing-channel noninterference;
- authorization safety does not prove graph-route optimality.

* Mathematical model

The mathematical source remains embedded in Org and is evaluated by
=typst eval= through stdin.

#+name: searchroute-retry-authorization-stamp-model
#+begin_src typst
#let positive(decision) = $upright("Positive")(#decision)$
#let decisionGeneration(decision) = $upright("DecisionGen")(#decision)$
#let snapshotGeneration(snapshot) = $upright("SnapshotGen")(#snapshot)$
#let active(snapshot, grant) = $upright("Active")(#snapshot, #grant)$
#let safe(snapshot, decision) = $upright("SafeRelease")(#snapshot, #decision)$
#let release(snapshot, decision) = $upright("Release")(#snapshot, #decision)$
#let denied = $upright("Denied")$

#[
  Release safety is
  $
    #safe($S$, $D$)
    equiv
    #positive($D$)
    and #decisionGeneration($D$) = #snapshotGeneration($S$)
    and #active($S$, $G_D$).
  $

  A failed freshness check denies release:
  $
    not #safe($S$, $D$)
    arrow.r.double
    #release($S$, $D$) = #denied.
  $

  Same-generation revocation invalidates the prior decision:
  $
    #positive($D$)
    and not #active($S$, $G_D$)
    arrow.r.double
    not #safe($S$, $D$).
  $

  Generation advance invalidates the decision even if the grant is active:
  $
    #decisionGeneration($D$) < #snapshotGeneration($S'$)
    and #active($S'$, $G_D$)
    arrow.r.double
    not #safe($S'$, $D$).
  $

  A release function that checks only $#positive($D$)$ releases a stale winner
  and therefore does not implement this RFC.
]
#+end_src

=packages/proofs/ASPProof/SearchRouteAdmissionRetryAuthorizationStamp.lean=.

- =AuthorizationSnapshot= contains current generation and grant activity.
- =AuthorizationDecision= binds generation, grant, target key, and the original
  decision result.
- =SafeToRelease= encodes the three-part recheck.
- =releaseWithAuthorizationRecheck= denies every failed recheck.
- =safe_release_preserves_decision_generation_and_current_activity= proves the
  positive consequence.
- =failed_freshness_recheck_denies_release= proves fail-closed release.
- =same_generation_revocation_invalidates_prior_decision= proves revocation
  safety.
- =generation_advance_invalidates_reactivated_grant_decision= proves replay
  safety.
- =decision_bit_without_freshness_recheck_releases_stale_winner= is the
  executable TOCTOU counterexample.

The proof audit remains modular and scoped only to this RFC.

* SearchLoop cost relevance

Releasing a winner after authorization revocation can expose graph evidence or
route history across a policy boundary.  Incorrectly rejecting a genuinely
current decision forces repeated search and publication recovery.  Generation
stamps allow safe reuse while preventing stale authorization replay.

This RFC does not prove minimum graph distance, minimum tokens, minimum tool
rounds, or model-cache hits.

* Non-goals and next proof boundary

This RFC does not yet prove:

- atomic implementation of recheck and encrypted winner release;
- authorization issuer authenticity;
- timing, cache, or error-shape noninterference;
- replicated authorization-generation linearizability;
- graph-route optimality.

The next proof layer should model observational noninterference: unauthorized
requests must not distinguish occupied from empty winner cells through outcome,
payload, cache mutation, or protocol-visible timing class.
