#+title: RFC 10.05.75 — SearchRoute Cache Rejoin Transition Receipts
#+startup: overview

* Status

Draft proof-bearing extension of RFC 10.05.74.

* Abstract

RFC 10.05.74 makes cache-replica rejoin recovery monotone, but a durable phase
value alone is not evidence that the work represented by that phase completed.
A crash can persist the phase while losing the transition result, or persist a
later result while losing one of its predecessors.

This RFC makes every rejoin phase proof-carrying.  A durable record contains a
phase claim and a set of transition receipts.  The phase is admissible only
when the receipt set contains the complete predecessor chain required by that
phase and the receipt generations are strictly increasing.

This closes four false implications:

1. a persisted phase does not imply a persisted transition result;
2. a later receipt does not imply that every predecessor exists;
3. receipt presence does not imply receipt order;
4. distinct transition names do not imply distinct generations.

* Scope

This RFC specifies the logical admission contract for durable rejoin records.
It does not prescribe a storage engine, transaction API, serialization format,
or fsync mechanism.  Physical durability remains an implementation assumption
until a storage model supplies explicit crash and persistence semantics.

* Normative clauses

** ASP-RFC-10.05-CRTR-PHASE — A phase claim is proof-carrying

A durable rejoin record MUST be accepted only when its receipt set supports its
claimed phase.  A consumer MUST NOT infer support from the phase enumeration or
from monotonicity of phase values alone.

** ASP-RFC-10.05-CRTR-RECEIPT — Each completed transition has a durable receipt

Completing =state-installed=, =token-issued=,
=membership-published=, or =reads-enabled= MUST produce the corresponding
durable receipt before the record may claim that phase.

Receipt generation is authority-issued logical order.  Wall-clock time MUST
NOT be used as the ordering proof.

** ASP-RFC-10.05-CRTR-PREDECESSOR — Later evidence cannot replace a predecessor

Support for a phase MUST contain the receipt for that phase and every receipt
required by its predecessor chain.  A =reads-enabled= receipt therefore cannot
replace a missing =membership-published= receipt.

** ASP-RFC-10.05-CRTR-ORDER — Receipt generations are strictly increasing

For every adjacent pair in a supported transition chain, the predecessor
generation MUST be strictly smaller than the successor generation.  Equal
generations and reordered generations MUST fail closed.

** ASP-RFC-10.05-CRTR-ATOMICITY — Torn phase and receipt publication fails closed

If a crash makes a phase claim visible without the receipts required by that
phase, recovery MUST reject or roll back the phase claim.  Implementations MAY
use an atomic record, a write-ahead protocol, or another durability mechanism,
but the externally observable record MUST satisfy the same support relation.

** ASP-RFC-10.05-CRTR-NONIMPLICATION — Presence is not completion

Neither a later phase value nor an arbitrary set of present receipts proves a
valid completed chain.  Completion requires the named receipts, predecessor
closure, and strict generation order together.

* Design consequence

The durable object is no longer “the current phase”.  It is a small proof
object:

#+begin_example
phase claim + predecessor-closed receipt chain + strict authority order
#+end_example

This is intentionally independent of CLI complexity.  SearchLoop and the graph
router consume a compact admission fact; they do not need commands for
reconstructing crash history interactively.

* Remaining proof boundary

Strictly ordered generations establish transition order, but they do not bind a
receipt to:

- one rejoin attempt;
- one cache replica;
- one predecessor receipt payload;
- one phase result digest.

Consequently, receipts from different attempts could still be mixed while
satisfying the generation inequalities.  A follow-up RFC must add attempt
identity and predecessor/content digest binding before this model can justify a
cryptographically or content-addressed durable chain.
