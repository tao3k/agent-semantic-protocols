#+title: RFC 10.05.10.00.47 — Causal Execution Feedback
#+startup: overview

* Status

Draft research specification.

This RFC defines how execution outcomes feed future SearchLoop generations
without retroactively changing admission or completion proofs. It does not add
CLI commands or authorize implementation.

* Problem

Execution produces valuable observations:

- actual prompt and evidence tokens;
- model prefix-cache outcome;
- provider latency;
- selector or projection failure;
- new evidence; and
- success or failure.

These observations occur after admission. Treating them as earlier premises
reverses causality.

Examples of unsound conclusions include:

- observed cost 10 proves that a 20-token budget admitted a route planned at
  cost 100;
- successful execution proves the route was globally optimal;
- a post-hoc prefix hit proves a hit lease existed before execution;
- one provider failure invalidates every semantic witness; or
- an outcome silently mutates the context of the original admission bundle.

* Decision

Execution feedback is append-only:

1. preserve the immutable admission snapshot;
2. bind the outcome receipt to the admission and request identities;
3. use observations for accounting under the completed execution;
4. derive a new problem generation for future routing; and
5. transport or reopen certificates explicitly.

No post-hoc field can alter the proposition proven by the original admission
bundle.

* Admission snapshot

The immutable admission snapshot binds:

- admission digest;
- SearchLoop context;
- request digest;
- planned cost and budget;
- obligation, feasibility, ledger, and cost certificates;
- cache authority used for planning; and
- completion mode.

Execution references this object. It does not copy mutable Boolean summaries of
the certificates.

* Outcome receipt

An outcome receipt binds:

- admission digest;
- request digest;
- execution attempt identity;
- observed semantic and prompt token costs;
- prefix-cache observation;
- provider and selector outcome;
- latency and transition accounting; and
- evidence generated by the action.

A receipt with the wrong admission or request identity is rejected before its
observations update any model.

* Observed cost does not prove admission

Two hypothetical receipts can both report 10 observed tokens while their
admission snapshots differ:

- planned 15 under budget 20: feasible;
- planned 100 under budget 20: infeasible.

The observed token number alone cannot determine which admission proposition
holds. Only the preserved planned-cost certificate can.

The second pair is a logical counterexample, not a legal executable transition:
RFC 00.46 prevents the infeasible admission from reaching execution.

* Success does not prove exactness

Execution success establishes that one admitted action completed. It does not
cover omitted proof frontiers or compare the route with every feasible
alternative.

An incomplete or bounded incumbent remains incomplete or bounded after success.
Exactness comes only from the pre-execution completion certificate and is
preserved by the state-machine transition.

* Cache feedback

A post-hoc model prefix hit:

- records actual accounting cost;
- can calibrate future hit likelihood;
- can seed a later cache observation; but
- does not create an ex-ante lease for the completed request.

A semantic-cache observation:

- can add or validate evidence for the next generation;
- does not mutate the evidence identity used by the completed admission.

The two cache observations remain separate.

* Failure localization

An execution failure carries a typed failure owner:

- provider resolution;
- selector execution;
- projection compatibility;
- evidence validation;
- budget/ledger race;
- model request; or
- external capability.

Only affected certificate families reopen. A selector failure does not
automatically delete content-identity-valid semantic evidence.

Failure localization is part of token efficiency: the next SearchLoop inspects
the smallest invalidated frontier rather than rebuilding the graph.

* New generation

Applying feedback creates a new problem identity with:

- incremented generation;
- prior context digest;
- outcome receipt digest;
- updated provider/evidence/cache observations; and
- affected frontier identities.

Old certificates are:

- reused under exact identity;
- transported under RFC 00.45; or
- marked stale and reopened.

The old admission and completed receipt remain immutable audit history.

* Python Turbo Graph consequence

The future Python implementation SHOULD:

- store immutable admission snapshots;
- append request-bound outcome receipts;
- maintain planned and observed cost columns separately;
- generate new problem versions instead of mutating historical graph state;
- localize invalidated frontier families; and
- require bound transport for reused optimization certificates.

Observed-cost training data can improve heuristics. It cannot rewrite proof
history.

* Required Lean obligations

The companion Lean model MUST prove:

- bound receipts match both admission and request identity;
- a mismatched receipt is rejected;
- equal observed token cost does not imply equal admission feasibility;
- success of an incomplete admission does not imply exact completion;
- applying feedback strictly advances the problem generation; and
- feedback preserves the original admission snapshot.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

The state-machine completion edge preserves mode and context, but a later
runtime could still interpret observed success or low cost as stronger earlier
evidence. Lean separates admission feasibility, completion mode, and outcome
observations into independent propositions. There is no theorem from observed
cost or success to admission or exactness.
