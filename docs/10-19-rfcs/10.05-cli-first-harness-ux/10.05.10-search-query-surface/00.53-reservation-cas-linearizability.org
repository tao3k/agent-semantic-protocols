#+title: RFC 10.05.10.00.53 — Reservation CAS Linearizability
#+startup: overview

* Status

Draft research specification.

This RFC adds concurrent commit semantics to the reservation lifecycle from RFC
00.52. It does not add CLI commands or authorize implementation.

* Problem

The reservation disposition relation is intentionally nondeterministic:

- a held reservation may become consumed;
- it may become quarantined; or
- proof of no effect may release it.

Two workers can read the same held revision and independently build valid but
conflicting proposals. The closed state machine alone does not determine which
proposal commits.

If aggregate ledger and reservation record are updated separately, a crash can
also leave:

- capacity moved but record unchanged; or
- record advanced but capacity still in the old partition.

Both break the lifecycle conservation story.

* Decision

Every mutation is a compare-and-swap proposal containing:

- reservation digest;
- expected revision;
- target disposition;
- transition/evidence identity; and
- resulting ledger movement.

A proposal commits only when:

- reservation identity matches;
- expected revision equals current revision;
- disposition edge is legal; and
- ledger and record updates form one atomic lifecycle commit.

Commit increments revision by one. Any competing proposal that expected the old
revision becomes stale.

* Executable mathematical surface

* CAS proposal

=CanCommit(current, proposal)= proves:

- proposal reservation digest equals current reservation digest;
- proposal expected revision equals current revision; and
- current-to-target disposition is legal.

Provider success, timeout, or reconciliation evidence determines the proposed
target. It does not bypass revision matching.

* Commit

Commit preserves:

- reservation identity;
- reserved amount; and
- lifecycle trace parent.

It changes:

- disposition according to the legal edge; and
- revision from =r= to =r + 1=.

The commit receipt binds the proposal digest and resulting state digest.

* Competing-proposal theorem

Suppose two proposals both expect revision =r= and are legal against one
current state.

After the first proposal commits:

#+begin_quote
=current revision = r + 1=.
#+end_quote

The second proposal still expects =r=, so:

#+begin_quote
=r != r + 1=.
#+end_quote

It cannot commit against the new current state.

This is the linearization point. The theorem does not choose which proposal
wins; it proves that both cannot commit serially from one revision.

* Atomic lifecycle commit

One transaction contains:

- ledger before/after;
- reservation record before/after;
- legal aggregate ledger transition;
- legal record transition;
- exact movement matching the reservation amount and disposition edge;
- total-capacity conservation proof; and
- revision-advance proof.

For example:

- =held -> consumed= must use =consumeHeld(amount)=;
- =held -> quarantined= must use =quarantineHeld(amount)=;
- =quarantined -> released= must use
  =releaseQuarantined(amount)=.

A generic ledger movement with the right total but wrong partition is rejected.

* Crash atomicity

The durable store must commit aggregate ledger, reservation record, and receipt
chain head atomically or through an equivalent recoverable transaction protocol.

If storage exposes a prepared state, recovery treats it as reconciliation, not
as a completed transition.

* SearchLoop consequence

When a proposal loses the CAS race:

- no ledger mutation occurs;
- no side effect is retried;
- the worker receives the new revision;
- its transition budget is charged; and
- it recomputes the allowed next action from current state.

CAS failure is not evidence that the competing action succeeded externally. It
only means the local reservation state changed.

* Python Turbo Graph consequence

The future Python runtime SHOULD:

- use database-level compare-and-swap or serializable transactions;
- update ledger, record, and receipt head atomically;
- return the winning revision and receipt;
- reject stale proposals before side effects when possible; and
- represent prepared/uncertain commits through reconciliation.

* Required Lean obligations

The companion Lean model MUST prove:

- commit preserves reservation identity and amount;
- commit increments revision;
- two example proposals are both initially admissible;
- after one commits, the other stale proposal is rejected;
- atomic lifecycle commits preserve ledger total;
- atomic lifecycle commits advance record revision; and
- consumed/released terminal records accept no further CAS proposal.

The modular audit emits these theorem families as Lean-generated JSON.

* Design finding

RFC 00.52 proves arithmetic conservation and terminal states but not concurrent
uniqueness. Lean permits two different transitions from the same held record.
Revision-CAS supplies the missing linearization premise, while the atomic
lifecycle commit prevents ledger/record split-brain.
