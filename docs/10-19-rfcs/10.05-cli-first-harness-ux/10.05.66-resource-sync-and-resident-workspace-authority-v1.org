#+title: 10.05.66 Resource Sync and Resident Workspace Authority v1
#+author: ASP Maintainers
#+language: en
#+options: toc:2 num:nil

* Status

Proposed.

This RFC completes the process-local workspace registry contract from
=10.05.65-process-resident-workspace-db-registry-v1.org=.  A process-local
registry removes repeated opens inside one process, but it cannot prevent two
ASP CLI processes from opening and locking the same Turso database.  The v1
runtime therefore requires one resident authority for every workspace
identity.

* Command responsibility

** =asp sync=

=asp sync= reconciles declarative resources only:

- shared schemas and provider registry descriptors;
- ASP-owned agent configuration projections;
- versioned Org resources and other immutable resource artifacts;
- one content-addressed resource generation followed by one atomic active
  generation publication.

The command may perform network and filesystem staging before publication.
Staging never holds a workspace session, database connection, transaction, or
active-generation publication guard.

=asp sync= must not:

- create, refresh, validate, or write a provider activation;
- install, build, or execute a provider;
- open, migrate, bootstrap, query, or write a client database;
- open or mutate the agent session registry;
- materialize source-index, graph, Memory Search, or exact-selector state;
- acquire a workspace read lease or submit a workspace writer command;
- wait for a query or indexing operation to consume the new resource
  generation.

Publication sends a non-blocking resource-generation notification to the
resident authority.  Consumers observe the new immutable generation on their
next command boundary.  They do not call =asp sync= and =asp sync= does not
call them.

** Installation and activation reconciliation

Provider installation and activation reconciliation are owned by explicit
Global or Project install workflows.  They publish immutable provider
artifacts and one active provider-catalog generation.  Search and query load
that generation; they never repair it.  Missing or mismatched identity fails
closed with an actionable reconciliation receipt.

** Search, query, and indexing

Search and query resolve:

#+begin_example
workspace identity
  -> resident authority
  -> workspace session entry
  -> concurrent read lease or typed writer command
#+end_example

A command must not open =facts.turso= directly.  A high-change
=rootDepth=0= owner is resolved from live owner bytes and the resident
Memory Search overlay.  Publication of a later generation is an asynchronous
writer command and is never a prerequisite for returning the live result.

* Cross-process resident authority

There is one long-lived ASP runtime authority per =stateHome=.  It owns a map
from canonical workspace identity to resident workspace entries.  CLI, hook,
agent, and provider processes are clients of this authority; they do not own
Turso handles.

Each workspace entry owns:

- one initialized Turso =Database= handle;
- a small fixed read pool or a connection type proven safe for concurrent
  reads;
- one writer task that exclusively owns the writer connection;
- one load-once Memory Search generation plus a live-owner overlay;
- generation and performance counters.

Different workspace entries share no database connection, transaction, writer
queue, or initialization cell.  They execute concurrently.

Authority discovery uses a state-home-local IPC endpoint and a generation
identity receipt.  Endpoint creation elects one authority process.  Losing
processes connect to the elected authority; they never fall back to opening the
workspace database.  A stale endpoint is replaced only after its owner
identity is proven dead.

* Deadlock prevention by construction

The runtime does not expose database mutex guards or writer connections to
callers.

** Registry rule

The registry map guard is held only long enough to clone or insert an
=Arc<WorkspaceEntry>=.  No filesystem operation, IPC, database open, schema
bootstrap, channel send, or =await= occurs while that guard is held.

** Initialization rule

Workspace initialization is one shared future per workspace identity.
Initialization of workspace A never waits for initialization, a read lease,
or the writer lane of workspace B.

** Read rule

A read lease contains only a read-pool permit and immutable generation
snapshot.  A caller must release the read lease before awaiting a writer
receipt.  The API does not accept a read lease as part of a writer command.

** Write rule

Callers submit owned, typed commands through a bounded workspace-local queue.
The writer task alone owns the writer connection and creates an immediate
transaction after dequeuing a command.  It commits or rolls back before
receiving the next command.  No =MutexGuard<Connection>= is part of a public or
crate-visible API.

** Publication rule

Network fetch, provider execution, parsing, hashing, and resource staging
complete before a database writer command is submitted.  Database
transactions contain only deterministic database work.  Active resource
generation publication does not occur inside a database transaction.

These ownership rules replace lock-order documentation and bounded lock
retries.  A Turso =file is locked by another process= error is a P0 authority
violation, not a retryable query result.

* Required receipts

Every =asp sync= completion emits a typed v1 receipt containing:

- previous and active resource-generation digests;
- staged and published resource counts;
- =activationWrites=0=;
- =dbOpens=0= and =dbTransactions=0=;
- =providerInvocations=0=;
- =sessionRegistryOpens=0=;
- =sourceIndexWrites=0=;
- resident notification status without waiting for consumption.

Every workspace command receipt identifies:

- resident authority generation;
- workspace identity;
- registry hit or initialization;
- read-pool lease or writer-queue sequence;
- database opens, connection creations, schema bootstraps, and transactions;
- queue wait and operation latency.

* Required gates

1. Run concurrent =asp sync= and search/query traffic.  Sync must report zero
   database and activation effects while search/query remains available.
2. Start multiple CLI processes against one workspace.  Exactly one resident
   workspace entry may open the database and own the writer connection.
3. Run at least 256 concurrent readers and 32 writers for one workspace.
   There must be no lock retry, lock error, starvation, or lost receipt.
4. Run the same load across at least four workspaces.  One blocked writer must
   not delay another workspace.
5. Cancel readers, writers, clients, and the authority during each lifecycle
   phase.  Every accepted writer command must receive committed, rolled-back,
   or authority-terminated status.
6. Model the registry, initialization cell, read lease, and writer queue with
   deterministic concurrency testing.  The model must reject a read-to-write
   upgrade and any guard held across an =await= boundary.
7. Installed cold and warm receipts must remain inside their declared
   millisecond budgets.  Raising a timeout is not an accepted fix.

* Migration

The process-local =WorkspaceDbRegistry::process()= remains an implementation
detail only inside the resident authority process.  Direct CLI construction,
direct Turso open, exposed =writer_connection()= guards, query-time activation
reconciliation, and sync-time database work are removed rather than retained
as compatibility paths.
