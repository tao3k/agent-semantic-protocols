#+title: 10.05.69 Turso Resident Memory Search v1
#+startup: overview

* Status

Draft implementation contract.

* Decision

ASP Search v1 keeps Turso as the single persistent and transactional search
authority.  “Memory Search” names the resident execution mode over an already
opened workspace Turso database; it does not name a second Rust-owned index or
an independently synchronized in-memory database.

The production path MUST NOT copy an active generation into a parallel
=HashMap= authority and MUST NOT open a separate =:memory:= database.  A
=:memory:= Turso database is permitted only for isolated fixtures.

* Query ownership

- Exact structural selector lookup uses a prepared, indexed Turso query on the
  active generation and workspace identity.
- Lexical retrieval uses the Turso full-text-search surface when the registered
  schema declares the corresponding FTS index.
- Semantic similarity uses Turso vector values and distance/index methods when
  the query pack declares a semantic axis.
- Graph expansion consumes the same generation rows and relation tables.  It
  MUST NOT publish a second generation identity.

All query modes share one canonical workspace identity, active generation,
resident database handle, read-lease pool, and per-workspace writer lane.

Ordinary =search= snapshot acquisition is also a query boundary.  The
high-change =rootDepth=0= path captures the current provider scope into the
command's in-memory projection and performs zero CAS writes, envelope
publication, manifest writes, database bootstrap, or activation
synchronization.  The =rootDepth=1= path may consume an already committed
generation, but a missing generation is a typed cold-required result; it MUST
NOT call an =ensure= or materializer from the query boundary.  Generation
publication belongs only to the workspace writer lane.

* Resident execution

The first workspace admission opens and validates the Turso database once,
prepares the exact-selector statements, and binds the active generation
identity.  Later queries perform only:

1. resident workspace lookup;
2. read-lease acquisition;
3. prepared statement binding;
4. result projection.

The installed exact-selector consumer reaches the resident lookup only through
the typed workspace-owner IPC =ReadResidentSelector= operation.  Its response
joins the active source-index generation to the active provider generation and
returns parser-owned byte projection facts.  A short-lived =asp= process MUST
NOT construct =ProviderSearchWorkspaceSession=, open Turso locally, or load a
file-backed exact-selector fixture.  It may materialize a byte range from the
live owner only after the owner content digest matches the resident candidate.

Warm queries MUST report zero database opens, zero schema bootstraps, zero
manifest writes, zero provider processes, and zero source scans.

The resident owner endpoint uses a UID-private short runtime root selected by
the workspace DB transport itself.  It MUST NOT inherit =TMPDIR= or
=ASP_STATE_HOME= because either path may exceed the platform Unix-domain socket
budget.  The root is mode =0700= and owned by the current UID; the published
workspace receipt remains under the canonical project state tree and carries
the workspace identity, owner epoch, binding token, and short socket path.
Provider and protocol callers MUST NOT construct this runtime root themselves.

Provider member roots are containment-scoped children of the canonical
workspace root.  They MUST NOT be compared to the workspace root using path
equality.

* Receipt separation

Compile and bootstrap costs are reported independently from query latency.

- =compileReceipt= covers Cargo compilation and the complete Turso/Search
  dependency closure.
- =bootstrapReceipt= covers the first workspace database open, schema
  verification, statement preparation, and active-generation binding.
- =runtimeReceipt= begins only after bootstrap and covers the prepared query
  execution and projection.

A runtime performance gate MUST execute the already built artifact directly.
It MUST NOT invoke Cargo, activation reconciliation, =asp sync=, schema
bootstrap, or provider installation.

* Fixture boundary

=MemorySearchFixture= is a Turso database fixture and scenario generator.
It MUST use the same schema, generation transaction, prepared queries, and
=TursoMemorySearchBackend= as installed ASP.

An isolated fixture may use a transient Turso database.  It MUST NOT use a
Rust-owned map, a generic alternate backend, or a reference search
implementation.  Fixture and installed execution differ only in database
lifetime and receipt scope.

The standalone =MemorySearchIndex= and generic
=MemorySearchBackend= surfaces are removed.  Turso is the only search
authority and the only acceptance backend.

Rust domain type names do not carry protocol-version suffixes.  The v1
identity is owned by schema filenames, =schemaId=, and =schemaVersion: "1"=.

* Provider owner acquisition

Provider execution publishes one complete parser-owned projection for the
requested owner.  The provider request carries
=projectionMode: "complete-owner"= and MUST NOT carry the user's lexical
query.  A provider response is admitted only when it echoes that projection
mode and reports =projectionCompleteness: "complete-owner"=.

The user's query is applied after publication by the resident Turso read path.
An empty query result therefore cannot publish an empty complete-owner
generation or poison later searches.

This contract is language-neutral.  Every registered provider that declares
owner projection support uses the same request and response schemas.  Rust,
TypeScript, Python, Julia, Gerbil Scheme, Org, and future providers are lazily
admitted from their registry descriptors; ASP core contains no
language-specific workspace or package-manager branch.

Global provider catalog admission is leaf-scoped.  Each provider leaf records
the digest of its own language descriptor, not the digest of the complete
multi-language registry.  A Rust descriptor change invalidates only the Rust
leaf; it MUST NOT make Gerbil Scheme, Julia, Python, TypeScript, or Org
unroutable.  The requested language leaf is validated lazily before its first
provider use.  Unrequested provider leaves do not participate in query-time
admission.

The Global provider catalog is published atomically by Global binary/provider
reconciliation from the registered provider manifests and installed runtime
artifacts.  Global plugin installation only installs client integration; it
MUST NOT load a project activation or derive provider identity from the current
project.  Project activation, =asp sync=, and query execution never repair the
Global catalog.

Catalog publication consumes the typed provider install receipts produced by
binary reconciliation directly in memory.  It MUST NOT reopen receipt files,
reopen provider binaries, or rehash provider binaries.  An
install receipt atomically binds the artifact content digest, artifact metadata
digest, and execution-command digest; catalog publication MUST NOT recompute
execution identity per language leaf.  An
unchanged generation performs no catalog write and reports
=binaryByteReads=0=, =changedLeafCount=0=, and =catalogWrite=false=.  A changed
provider receipt replaces only its language leaf before the generation is
atomically published.  Languages that deliberately share one registered
provider binary may share that binary's artifact receipt, while retaining
separate provider-registry and query-pack identities.

Provider reconciliation first compares the installed artifact metadata identity
with the signed install receipt.  A match reuses the receipt with
=providerBinaryByteReads=0= and does not re-enter CAS installation or content
hashing.  Metadata drift is the only path that performs full content
verification and atomically replaces the receipt.

Query-time Global catalog leaf admission performs the same signed metadata
identity check and reads zero provider bytes.  A metadata mismatch fails closed
and requires explicit Global reconciliation; query execution MUST NOT rehash a
provider binary or repair its receipt.  Full artifact content verification
belongs only to the installer drift path.

The catalog publication fixture enforces a 5 ms cold atomic-publication budget
and a 1 ms unchanged warm-publication budget.  The receipt also reports
=elapsedMicros= so installed reconciliation can be held to the same gate.

The catalog keeps provider-registry identity and query-pack identity as
different digests.  Exact generation binding uses the registered
=exactQueryPackIdentityDigest=; it MUST NOT substitute the catalog
=queryPackDigest=, the digest of the whole registry, or the provider command
descriptor.  Catalog integrity digests are algorithm-tagged
=(blake3-256:<hex> or sha256:<hex>)=, while exact-selector Merkle identities
are the canonical 64-character BLAKE3 values required by
=provider-native-exact-request.v1=.  These are distinct typed identities, not
two spellings of one value.

Catalog publication derives =exactParserIdentityDigest= once from provider id,
execution-command digest, and the language-local provider-registry digest.  It
derives =exactQueryPackIdentityDigest= once from the canonical query-pack
descriptor.  The installed exact-query hot path copies both values into the
provider request without stripping prefixes, reopening descriptors, reading
provider bytes, or hashing query-time state.  Every language provider consumes
the same request schema and must reject a catalog leaf that omits either exact
identity.

An attached binary Memory Search fixture retains its complete generation-header
authority in every resolved projection: language id, provider id, parser
identity, query-pack identity, workspace root, workspace identity, and
generation identity.  A typed =source= or =callable-skeleton= resident hit is
admitted only when the live Global catalog exact identities, requested
language/provider, live owner content digest, and projection mode all match
that header and record.  The consumer MUST NOT discard header authority and
fall back to a provider subprocess merely because the projection is typed.
After the fixture has been attached, a valid warm hit reports zero provider
subprocesses and performs no activation write, database open, schema bootstrap,
or cache write.

The embedded registry materializes each language's manifest, registry
descriptor, and query-pack digests once.  Catalog publication and validation
consume that typed identity table; they MUST NOT repeatedly parse or hash the
embedded registry per language leaf.

* Required gates

- exact selector hit, miss, and stale-generation rejection;
- root workspace plus nested member-root containment;
- thirty-two concurrent readers with one resident workspace admission;
- concurrent readers plus one serialized writer generation replacement;
- no cross-workspace global lock;
- a deeply nested =TMPDIR= and State Home still produce a private socket within
  the platform path budget;
- installed cold bootstrap receipt separated from warm runtime receipts;
- catalog publication after provider reconciliation reads zero provider bytes
  and an unchanged warm publication writes no catalog;
- warm exact-selector latency below the configured millisecond gate;
- FTS and vector queries remain generation-bound and workspace-bound.
