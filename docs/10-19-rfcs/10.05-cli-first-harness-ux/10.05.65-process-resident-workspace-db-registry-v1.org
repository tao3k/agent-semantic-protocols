#+title: Workspace-scoped single database owner v1
#+startup: overview

* Status

This RFC defines the only database lifetime, concurrency, durability, and
client-access contract for provider-backed incremental search.

The backend is Turso 0.7 in MVCC mode.  One workspace has one canonical
=live/client/facts.turso= and one live database-owner process.  The owner is
the only process permitted to construct a Turso =Database= for that file.
=asp= commands, hooks, search/query routes, agents, and providers use typed IPC
to the owner and never open =facts.turso= directly.

This supersedes request-local opens, cross-process database opens, cache-home
database variants, and the D3 MVCC-to-multiprocess-WAL proposal.  Existing
canonical MVCC files remain MVCC.  There is no WAL fallback, compatibility
database, global database, or second storage backend.

* Ownership chain

#+begin_example
canonical project root
  -> WorkspaceIdentityV1
  -> canonical State Home workspace client path
  -> live/client/facts.turso
  -> elected WorkspaceDbOwner and owner epoch
  -> one Turso 0.7 MVCC Database
  -> owner-internal read connections and transactions
  -> typed IPC operation and receipt
#+end_example

Exactly one live owner binds the workspace identity, canonical logical path,
process identity, start time, owner epoch, IPC endpoint, protocol version,
Turso version, MVCC mode, schema capability receipt, and lifecycle counters.

Different workspaces and worktrees have different owners, endpoints, epochs,
databases, and transaction domains.  They make progress independently and
cannot read or mutate each other's facts.

* Canonical resolution and pre-open failure

Before IPC, election lock, or database open, a client MUST:

1. resolve the canonical project root through State Home;
2. derive =WorkspaceIdentityV1= and the canonical database logical path;
3. require that identity to equal the typed provider scope;
4. reject caller-supplied database paths; and
5. bind the IPC request to that workspace and the expected owner epoch, when
   known.

Identity/path mismatch fails before election or open.  A stale endpoint cannot
serve a request for a different owner epoch.

* Typed IPC is the only client surface

Search consumers MUST use the typed source snapshot admitted by provider
dispatch for the resolved workspace.  A search command MUST NOT collect a new
=CompleteGeneration= or rematerialize the workspace snapshot on its query
path.  If the requested workspace differs from the admitted snapshot scope, the
router fails closed and requests a correctly scoped snapshot; it never repairs
the mismatch with a filesystem scan.

The published resident endpoint MUST carry the content digest of the shared V1
IPC transport schema.  A client validates workspace identity, IPC schema
identity, and transport contract identity before it reuses an endpoint.  A
contract mismatch is an unhealthy epoch and triggers owner election for the
current transport; process liveness alone is not a valid health proof.  The
digest is derived from the small schema artifact, never by reading the ASP
binary on a query path.  This prevents a newly installed client from sending a
widened V1 request to an older resident that can deserialize the envelope while
lacking the new operation semantics.

Exact query has one public projection surface:
=--projection source|callable-skeleton=.  Removed flags are absent from the
parser model; they MUST fail as unknown arguments at CLI admission and MUST NOT
survive as compatibility branches or agent-facing migration diagnostics.

IPC read lanes are demand-driven rather than fixed-size. Their upper bound is
derived from the host's available parallelism, while connections are created
lazily only when concurrent demand occupies the currently live lanes. A
sequential client therefore retains one persistent lane; concurrent readers
expand only up to the machine-derived bound.

The resident owner exposes one serialized writer lane. It publishes its
endpoint only after the canonical workspace database, schema, and owner epoch
have been bootstrapped and validated. Clients must never open =facts.turso=
directly: search and query consumers acquire typed IPC read leases from the
live owner. Repeated reads for one snapshot/query identity are single-flight
and may reuse the resident in-memory read model; Turso remains the durable
authority.

All ASP CLI, hook, search/query, agent, and provider processes use one
versioned IPC protocol.  IPC operations are typed; callers cannot send SQL,
database paths, Turso builder options, or connection handles.

A request contains protocol/schema versions, workspace identity, request ID,
idempotency key, owner epoch expectation, typed operation/payload, deadline,
cancellation identity, caller role, and authority receipt.

A response contains request ID, workspace identity, serving owner epoch,
typed result/failure, database-session and transaction receipts, transaction
queue/batch/commit counts, durability state after writes, and owner
restart/takeover evidence when the request crossed an epoch.

Inventory reads, owner probes, Tree-sitter query reads, inventory and
owner-result publication, exact-selector persistence, and final audits are IPC
operations.  Public APIs accepting =db_path=, exposing a Turso connection, or
opening =facts.turso= are forbidden.  Only the owner-bootstrap boundary may
consume its already validated canonical path.

* Owner election, start, and recovery

A filesystem lock adjacent to workspace state exists only for owner election,
start, stale-owner recovery, and crash takeover.  It is not a database read
lock, write lock, transaction lock, or normal IPC request lock.  No client
holds it while executing a database operation.

#+begin_example
resolve workspace
  -> connect to advertised owner endpoint
  -> if live and epoch matches, use typed IPC
  -> otherwise acquire election lock
  -> re-check endpoint and epoch
  -> start or take over exactly one owner
  -> owner opens and validates canonical MVCC database
  -> atomically publish endpoint and new epoch
  -> release election lock
  -> connect through typed IPC
#+end_example

The endpoint/epoch record is fsynced before releasing the lock.  A waiter
re-checks after acquiring the lock and cannot start a second owner merely
because its first connection failed.

Crash takeover never deletes, copies, renames, replaces, or converts a
nonempty canonical database.  The new owner opens the same MVCC file, runs
restart and capability validation, and publishes a new epoch.  Failure leaves
the canonical file unchanged and returns a typed failure.

* Turso 0.7.1 MVCC and single-writer contract

The owner constructs exactly one Turso =Database=.  It owns reusable read
connections, one writer actor and queue, schema state, and
checkpoint/restart state.

Concurrent clients submit typed write operations to the owner.  Exactly one
owner-local writer actor admits them in deterministic queue order and groups
compatible operations into bounded MVCC write transactions.  A batch records
the admitted request IDs/idempotency keys, ordering key, operation count,
transaction count, commit result, and per-request publication result.  One
failed operation cannot partially publish the remainder of a batch.

Reads remain concurrent and use stable MVCC snapshots.  The writer actor does
not serialize reads, owner election, unrelated workspace owners, provider
execution, or client request parsing; it serializes only mutation of one
workspace database.

Pinned Turso 0.7.1 currently reports a same-row concurrent write as generic
=Error("Write-write conflict")=, including when the conflict is observed by
the second =UPDATE=.  Production MUST NOT classify that string, retry it, or
admit multiple database writers.  A future pinned Turso version may replace
the single-writer rule only after a capability gate proves a stable typed
conflict such as =Busy=/=BusySnapshot= across the production schema.  Typed
conflict retry is therefore a future capability, not a v1 runtime contract.

=turso_sdk_kit= is not a direct ASP dependency or architecture surface.  It
may appear only as a transitive implementation detail of the pinned =turso=
crate; ASP protocols, IPC types, receipts, and owners MUST NOT depend on it.

* Durability, checkpoint, shutdown, and restart

The resident registry records monotonic last-activity for every workspace
service. Accepted IPC, lease acquisition, and lease release are activity;
health inspection alone is not. A service whose canonical workspace path no
longer exists is immediately retirement-eligible. A service whose path still
exists is retirement-eligible only after at least one hour without activity,
with no in-flight request and no live lease.

Retirement is a checkpoint boundary, not deletion. The registry first closes
admission, drains requests and leases, executes =OwnerDurabilityBoundary=,
publishes the shutdown receipt, and only then removes the workspace entry and
endpoint. A new request racing with retirement either observes the still-live
generation or starts a new uniquely elected service after endpoint retirement;
it must never attach to a partially retired owner or create a second owner.

Committed writes use one typed mode:

- =ResidentBatch= proves committed MVCC visibility and records pending
  checkpoint state; or
- =OwnerDurabilityBoundary= flushes state and performs the Turso 0.7
  MVCC-supported checkpoint for shutdown, takeover, or explicit durability.

Receipts record cache flushes, checkpoint operation/outcome, pending-log state,
owner epoch, and Turso version.  They do not use WAL-only checkpoint modes or
infer durability from file size.

Graceful shutdown stops write admission, drains admitted transactions,
performs an owner durability boundary, closes all connections and the
=Database=, then retires the endpoint.  Restart opens the same canonical MVCC
file and validates schema objects, critical generations/digests, and committed
rows before readiness publication.

* Tree-sitter incremental state

Tree-sitter reasoning search remains:

#+begin_example
initial audit, budget 0
  -> enumerate and batch-probe complete current inventory
  -> publish changed inventory
  -> schedule read, budget 1
  -> parse and publish at most one owner
  -> publish updated exact inventory and query result
  -> final audit, budget 0
  -> render typed state and continuation
#+end_example

Audits do not schedule work.  Continuation is a later starting point, never
completeness proof.  =Complete= requires a current query-owner result for every
owner matching query digest, owner path/content digest, and inventory
generation.

Path-explicit source projection may be memory-only.  Every database-backed
read/write remains IPC and cannot open a fallback database.

* Provider-time source mutation

The route records owner metadata and content digest before provider execution,
then re-stats it:

- metadata-only change with identical content commits post-provider metadata;
- content change fails with =owner-mutated-during-parse=; and
- failed mutation validation publishes neither fingerprint nor query result.

Provider execution stays outside the database owner and returns typed facts
through IPC.  Activation/preflight do not inject project-source fixtures.

* Superseded D3 multiprocess-WAL proposal

The earlier D3 proposal to detect MVCC, logically copy it to a temporary
multiprocess-WAL database, and replace canonical =facts.turso= is superseded.
Its format detection, schema/row copy, digest comparison, sidecar switch,
retained-old files, migration receipt, and multiprocess-WAL open rules are not
runtime contracts.

Existing canonical MVCC databases MUST NOT migrate to WAL.  New databases are
Turso 0.7.1 MVCC.  Experimental D3 runtime code and its migration fixture are
deleted; only the RFC evidence remains.  No D3 component may be restored as
runtime, migration support, compatibility logic, or fallback.

The failed temporary fixture is evidence: Turso rejected =query_only=ON=,
accepted the numeric spelling, and exposed =__turso_internal_mvcc_meta=, which
cannot be recreated as a user table.  The new design avoids schema-copy
inference by keeping and validating the canonical MVCC database in place.

* Capability gates

All gates use temporary databases created by the actual production bootstrap;
a handwritten reduced schema is insufficient.  No gate touches real user
=facts.turso=.

Turso 0.7.1 MVCC and its index support are upstream experimental capabilities.
Their production-schema behavior is an explicit unresolved blocker, not an
assumed property of this design.  The architecture is admitted only after the
gates below pass on the pinned Turso build.  Until then the owner MUST report
=mvcc-capability-unproven= and MUST NOT serve production database operations.

** Production schema and values

- Validate the actual table/index/view/trigger object set under MVCC.
- Exercise every production index through representative generation,
  inventory, query, capture, artifact, and exact-selector operations.
- Round-trip =NULL=, =BLOB=, integer, real, and text through actual admitting
  columns; do not invent a legacy table for coverage.
- Validate foreign keys, uniqueness, generated columns, =STRICT=,
  =WITHOUT ROWID=, and =sqlite_sequence= when present.
- Fail the capability on any unsupported production object or value.

** Checkpoint and restart

- Commit nonempty facts across production table families.
- Run the MVCC-supported durability boundary.
- Close all connections and the =Database=.
- Start a new owner epoch on the same temporary path.
- Compare schema object set, table/row counts, critical generation/digest
  identities, and canonical typed-row digests.
- Repeat after forced owner termination.

** Crash, takeover, and multiple processes

- Kill the owner while idle, reading, pre-commit, post-commit/pre-ack, and
  checkpointing.
- Prove exactly one takeover epoch, no dual owner, and unchanged canonical
  path.
- Drive one workspace from at least two client processes through typed IPC;
  direct Turso opens outside the owner must be zero.
- Reject stale endpoints/epochs and keep unrelated workspaces progressing.

** MVCC concurrency

- Run concurrent stable reads while concurrent clients submit writes to one
  workspace writer actor.
- Record submissions, queue depth/wait, deterministic batch membership,
  transactions, commits, failures, and duplicate idempotency suppression.
- Include at least 100 concurrent clients and a 10,000-owner scenario.
- Prove no lost update, dirty read, partial publication, duplicate logical
  write, second database writer, or cross-workspace serialization.

** Upstream conflict characterization

- A test-only Turso 0.7.1 characterization opens two write connections and
  reproduces a same-row conflict.
- It asserts the current generic =Error("Write-write conflict")= behavior so
  upstream drift is visible.
- It is not a runtime classification contract and MUST NOT justify string
  matching, retry, or multiple production writers.
- A separate future gate requires typed =Busy=/=BusySnapshot= before any
  multi-writer or conflict-retry design can be proposed.

** Latency

Each gate records wall/CPU time, opens, IPC round trips, queue wait/depth,
batch size, transactions, commits, and checkpoint cost.

| Path | Initial required budget |
|-
| Warm owner-local memory projection | p50 <= 1 ms, p99 <= 5 ms |
| Warm typed IPC database read | p50 <= 2 ms, p99 <= 10 ms |
| Warm queued single-writer MVCC write | p50 <= 5 ms, p99 <= 20 ms |
| Existing-owner first request for cold workspace entry | p50 <= 10 ms, p99 <= 50 ms |
| Owner start, MVCC open, capability-ready publication | measured by phase; accepted baseline becomes fixed regression gate |

Owner-start attribution separates process start, Turso open, schema/restart
validation, and IPC publication.  A budget cannot be raised to hide an
unattributed delay.

Failure of any required schema/index, value, checkpoint, restart, takeover,
multi-process, concurrency, or latency gate fails closed with a named
capability receipt.  There is no fallback to WAL, direct open, SQLite,
recreation, delete-and-sync, or a second storage path.

* No-legacy contract

Production routing must physically exclude:

- public database APIs accepting =db_path=;
- direct =facts.turso= opens from CLI, hook, search/query, agent, or provider;
- request-local open/bootstrap wrappers;
- multiprocess-WAL flags for canonical =facts.turso=;
- MVCC-to-WAL migration, dual-read, and retained-old runtime paths;
- SQLite/cache-home/project-checkout database routing;
- one global database for unrelated workspaces;
- filesystem locks held during normal reads/writes;
- activation/preflight source fixtures; and
- completion inferred from absent continuation.

* Verification matrix

| Scenario | Required receipt |
|-
| Wrong root/scope identity | fail before election, IPC, or open |
| 100 same-workspace clients | one owner epoch and one Turso Database |
| Two client processes | one IPC owner; external direct opens zero |
| Two workspaces/worktrees | independent owners and progress |
| Actual production bootstrap | all required objects/indexes supported in MVCC |
| Production value fixture | actual NULL/BLOB/integer/real/text round-trip |
| 100 concurrent clients | concurrent submit, deterministic batches, one writer |
| Concurrent reads/writes | stable snapshots, one writer, no lost update |
| 10,000 owners | batched publication/search with attributed timing |
| Durability plus restart | committed schema/rows/digests preserved |
| Crash at each lifecycle phase | one takeover, no dual owner, unchanged path |
| Stale endpoint/epoch | typed rejection and endpoint refresh |
| Unsupported MVCC capability | fail closed; no WAL/direct-open fallback |
| Two cold owners, budget 1 | Partial, scheduled 1, remaining 1 |
| Final budget-0 audit pending owner | Partial with typed cursor |
| All query-owner results current | Complete, remaining 0 |
| Warm replay | source reads/parses/writes all zero |
| Provider-time content mutation | fail closed; no partial commit |

Moving database access behind IPC does not itself change public search packets.
If owner epoch, queue, batch, conflict, or durability fields become agent-facing,
update 10.06 and shared schemas before implementation.
