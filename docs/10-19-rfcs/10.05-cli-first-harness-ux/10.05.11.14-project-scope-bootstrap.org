#+title: 10.05.11.14 Project Scope Bootstrap
#+startup: overview

* Status

Normative.

* Problem

Project resolution currently admits source scopes only after candidate source
paths are present, while the runtime waits for project scopes before admitting
those paths into a workspace generation.  This creates a bootstrap cycle:

#+begin_example
ProjectScope -> source candidates -> ProjectScope
#+end_example

The cycle leaves runtime generation in =building= and prevents parser-owned
source access from repairing the provider that owns the missing scope.

* Two-phase generation

Workspace generation is constructed in two ordered phases:

1. =package-anchor generation=: Git/worktree identity plus package-manager
   manifests, lockfiles, and their Merkle evidence.
2. =scoped source generation=: provider-produced project scopes materialize
   source candidates, language projection, selectors, and module graph.

The package-anchor generation is sufficient input for provider project
resolution.  It does not require an earlier language source scope.

Each programming-language provider owns the package-manager semantics required
to derive scope.  The shared schema and provider registry supply the validated
language ID, provider ID, default target-root descriptor, and source-extension
descriptor through
=agent.semantic-protocols.registered-language-source-scope= schema version 1.
The generic scope materializer contains no language literal.
Default target conventions and explicit manifest paths are semantic inputs.
Candidate source paths may prove existence or completeness, but MUST NOT be
required to create the scope itself.

For Cargo, the Rust provider applies the target-root and extension descriptors
registered for its language ID even when the request contains only
=Cargo.toml=.  Explicit target paths derive their parent source roots directly
from the manifest.  Workspace member scopes are derived from the workspace
manifest and member manifests in the same package-anchor generation.

Document providers such as Org and Markdown do not implement programming
language package resolution.  Their scope remains Git scope minus ignore and
policy exclusions.

* Atomic publication

The runtime publishes no partial source generation.  Project scopes, source
snapshot evidence, canonical selectors, language projection relations, module
graph, and tombstones are committed under one generation digest.  Failure in
any provider leaves the preceding generation active and returns a bounded
reconciliation receipt.

* Root-depth behavior

- depth 0 uses the resident package-anchor and source generations without
  filesystem or database reopen
- depth 1 overlays changed manifest/source evidence and recomputes only affected
  package scopes and selector segments
- neither depth may invoke install, activation sync, or release resolution

* Required gates

- manifest-only package requests produce non-empty exact source scopes
- scope derivation is independent of candidate source-path presence
- workspace members and explicit/default targets are covered
- registered-language fixtures enforce the shared response schema
- project-resolution cold fixture is at most 1ms and reports zero DB opens
- concurrent workspaces use independent scope generations
- concurrent sessions for one workspace share one immutable generation
- source scopes, selectors, module graph, and tombstones publish atomically
