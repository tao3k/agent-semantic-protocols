#+TITLE: ASP Client Server Authority
#+STATUS: accepted

Parent architecture: [[file:10.05-interactive-graph-first-progressive-searchloop.org][RFC 10.05 SearchLoop]].

* Problem

Language runtimes with material warm-up cost, including Julia, cannot be modeled
as commands on the query path. Process creation, VM initialization, package
loading, and provider warm-up are lifecycle work. Treating them as query work
produces multi-second cold latency and makes health, cancellation, and shutdown
unobservable.

* Decision

ASP Runtime Server owns one Tokio =AspClientServerAuthority= per activated server
provider. The authority is a single-writer task. Commands enter through bounded
=tokio::sync::mpsc=, replies use =oneshot=, and committed lifecycle state is
published through =watch=. No synchronous lock or shared mutable map is part of
the provider request path.

** Rust client-server hard cut

The public Rust provider lifecycle command is =asp-rust serve=.  Provider
runtime transport namespaces are not public CLI subcommands.  The CLI keeps no
alias parser, argument-shape guard, or command-specific diagnostic for removed
commands.  This paragraph supersedes any older command spelling in this
section.

Rust follows the same HTTP-first =asp-client-server= contract as Julia.  The
provider manifest declares =http-json= transport and the
=asp-client-server serve= lifecycle command.  ASP Runtime Server is the only
owner allowed to start, warm, health-check, drain, or stop the Rust client.

The public =asp rust ...= command is a typed Runtime IPC facade only.  It never
starts the Rust provider, resolves a workspace, opens a provider cache, or owns
provider lifecycle state.  The former =asp-rust runtime serve= command is
removed, not aliased.  Provider projection and project-resolution operations
remain typed protocol operations behind the resident client-server; they are
not permission to restore one-shot CLI execution.

Rust admission is single-flight per provider artifact and manifest identity.
Concurrent workspaces receive isolated request identities, cancellation tokens,
and terminal responses while sharing only an immutable, committed warm client.
Lazy load is driven by the activated language extension set before publication
of =Ready=; an idle client may be drained only by the Runtime authority.  Every
transition and request publishes the shared lifecycle/OpenTelemetry evidence
required by native Scenario and Live Corpus qualification.

** ASP Client Server contract and catalog routes

The Runtime-published loopback HTTP endpoint is the single client authority.
Each client performs =Initialize -> catalog -> Request -> Cancel/Cancelled ->
Shutdown= over =POST /protocol/frame=.  The immutable catalog uses structured
=schemaId= and =schemaVersion= "1" references.  Canonical provider routes are
=<language>.search=, =<language>.query=, and =<language>.search.owner=; their
request and response schema IDs are respectively the runtime search,
provider-native exact, and provider-native owner contracts.  The Runtime Server
performs the workspace-generation Tokio watch barrier before dispatch.  A
=Building=, =Failed=, or =Cancelled= generation is a typed admission response;
the client never reads an older generation.

CLI language commands are facades over this HTTP catalog.  They MUST NOT call
provider transport, resident projections, provider caches, or local workspace
generation/session APIs directly.  Provider lifecycle and cancellation remain
owned by the server's bounded =mpsc=, =oneshot=, and =watch= tasks; no second
CLI authority or fallback route is permitted.

** Cross-process Runtime readiness contract

The supervisor pre-binds one per-owner Tokio =UnixDatagram= readiness sink
before spawning the detached daemon.  The daemon publishes typed
=Starting=, =Ready=, =Failed=, or =Cancelled= receipts to that sink.  The
datagram is only a bounded notification channel: in-process status remains the
Runtime Server's =watch= authority, and the parent accepts a readiness event
only when it matches the current owner and endpoint binding.  The parent waits
on the readiness datagram or the owner terminal event; it MUST NOT poll files,
use a 30-second readiness deadline, or run a 10ms probe loop.

Every readiness receipt binds =requestId=, =readinessToken=, =processId=,
=ownerEpoch=, =endpointBindingToken=, =runtimeBinaryIdentity=,
=artifactCatalogDigest=, and =transportContractDigest=.  Stale epoch,
token, process, artifact, or endpoint messages are typed ignored evidence.
The central Schema Manager owns
=agent.semantic-protocols.runtime-server-readiness=, Schema Version 1;
language packages MUST materialize this schema and MUST NOT copy or redefine
it.

For every Ready HTTP =search=, =query=, and =search.owner= request, the
acceptance gate is warm p50 <= 250 microseconds, p99 <= 700 microseconds, and
hard max < 1000 microseconds.  A non-Ready typed admission response has the
same hard max.  Startup, provider build, and generation admission are separate
measurements and MUST NOT block or count as query latency.  Receipts record
HTTP codec, catalog/generation gate, Tokio mpsc/oneshot, resident provider,
and response-serialization segments; the 300 microsecond headroom is part of
the contract.  No timeout is used to implement this SLA.

Live Corpus qualification records the same boundary as an executable contract.
For a Ready session the only admitted effects are =mpsc=, =oneshot=, =cancel=,
and =response=.  Process creation, compilation, filesystem preparation, database
writes, generation mutation, provider activation, and control polling are
forbidden Ready effects and are measured outside the Search/Query distribution.
The Version 1 plan and receipt both bind one initialization per session, zero
non-Ready dispatches, zero residual tasks, p50 <= 250 microseconds, p99 <= 700
microseconds, and max <= 1000 microseconds.  A decoder that omits any of these
fields is contract drift and fails qualification; removing the field from the
plan or treating build time as Runtime latency is not a repair.

** Package authority and dependency DAG

=agent-semantic-client-protocol= owns only version-one typed frames, catalog,
and route bindings.  =agent-semantic-client-server= owns the transport-neutral
HTTP/JSON session and cancellation protocol and MUST NOT depend on
=agent-semantic-client-db=.  =agent-semantic-client-db= owns Runtime state,
workspace admission, durable registry, and generation receipts.  The public
=agent-semantic-client= owns the Runtime HTTP client facade and agent-facing
client composition.  =agent-semantic-provider-transport= owns provider process
transport and resident provider actors.  A future
=agent-semantic-runtime-server= package owns daemon assembly, Runtime HTTP
dispatcher, resident search service, and identity handoff; it MUST NOT depend
on =agent-semantic-client=.

The =agent-semantic-client= package is only CLI composition, parser, command
facade, and renderer ownership.  It MUST NOT own the Runtime daemon, HTTP
session, durable workspace database, provider transport, or a second Runtime
HTTP client facade.  Until the runtime-server package extraction is complete,
the existing server modules remain a tracked Batch gate; each extraction batch
must move the module and strengthen the authority test before deleting its
protocol wrapper.

** Development installation authority

The Runtime invoker is fail-closed: a source/current executable whose identity
does not equal the active candidate MUST NOT spawn the stable Runtime path.  The
typed repair is =asp install binary=; there is no silent fallback to an older
binary.  The transition is candidate -> readiness -> healthy.  If readiness or
health qualification fails, the previous healthy artifact remains authoritative.

Provider source selection belongs to State Home, not to the install command's
current directory.  =ASP_STATE_HOME= owns the committed development source
registry.  An entry binds language ID, provider ID, absolute source root,
provider manifest digest, and the provider-owned workspace-install descriptor.

=asp install language <language>= MUST consult that registry before release
resolution.  When a valid development entry exists it executes the declared
provider-owned workspace install from that source root and atomically publishes
the resulting artifact and activation receipts.  It MUST NOT contact a release
registry, accept a path fallback, or fall through to a pinned release after a
development build failure.

Only a language without a committed development entry is eligible for the
pinned-release path.  =--project= is not a provider source selector and MUST NOT
participate in installation authority.  Project-local activation, when
supported, consumes the already installed canonical provider artifact; it does
not choose or rebuild provider source.

The lifecycle is:

#+begin_example
Declared -> Starting -> Warming -> Ready -> Draining -> Stopped
                                  \-> Failed
#+end_example

=Ready= binds the installed artifact digest, manifest digest, runtime contract
digest, endpoint identity, health generation, and supported operations. Queries
subscribe to the committed receipt. Starting or warming returns a typed
=asp-client-server-not-ready= result immediately; a query never starts or warms a
language runtime.

* ASP Client Server contract

Every server-capable implementation under =languages/*-harness= implements the
same =agent.semantic-protocols.asp-client-server= schema family. Descriptor,
bootstrap, lifecycle, request, response, error, and shutdown packets use the
=asp-client-server= namespace; a language harness must not mint a private server
schema family.

* ASP Client Protocol ecosystem

Provider HTTP is an internal transport between ASP Server and one admitted
language provider.  Downstream tools use the separate
=agent.semantic-protocols.client= protocol and never connect to provider
endpoints.  The client protocol is schema-first and transport-neutral.  Its
published catalog declares protocol identity, server capabilities, admitted
semantic methods, request and response schema identities, typed errors,
cancellation behavior, streaming behavior, typed parameter slots, and the active
workspace generation.  Parameter slots are executable admission rules rather
than documentation: unknown parameters, missing required values, type drift,
and client-supplied RuntimeContext fail closed.

An ASP client follows a closed lifecycle: =initialize=, capability negotiation,
semantic requests or notifications, request-scoped cancellation, =shutdown=,
and =exit=.  Unlike LSP, client initialization does not discover or start a
language process.  It negotiates only client-visible capabilities against the
already admitted ASP Server catalog.  A method missing from that immutable
catalog fails closed.  Dynamic provider activation changes the server catalog
by an atomic generation publication; it never mutates an established catalog
in place.  Initialization binds one =sessionId= to one =workspaceIdentity=;
subsequent frames cannot cross that isolation boundary.

The catalog and provider-process lifecycle are distinct authorities.  A
content-addressed provider installation publishes one complete capability
descriptor.  ASP Server validates that descriptor against the built-in
provider identity constraint and retains it across Runtime owner handoff.  The
descriptor, workspace language evidence, and Ready workspace generation form
the immutable catalog input.  Whether a provider session actor is absent,
starting, ready, draining, or stopped MUST NOT remove a Server-local
=search=, =query=, or =search.owner= method from that catalog.

Provider session actors are workspace-and-language scoped producers of native
semantic facts.  Extension and project-resolution events submit lazy
activation intents to the sole Runtime Tokio supervisor.  Activation,
cancellation, and drain update the provider-session state machine; they do not
mutate installed capability identity and they never run in client
=initialize= or a Ready query hot path.  The implementation MUST NOT use one
"live provider register" as both capability catalog and process-liveness
registry.

The canonical HTTP/JSON binding uses one ASP Server loopback origin and typed
request, response, event, and cancellation frames.  A local Runtime IPC binding
MAY encode the same frames, but it is not a second protocol authority.  Both
bindings validate the same schema identities and produce the same terminal
receipt.  Client libraries in Rust, TypeScript, Python, Julia, Gerbil, DSLs, or
future languages can therefore be generated from the catalog without knowing
ASP implementation details.  The language-neutral conformance suite is an
executable protocol asset: every client implementation runs the same lifecycle,
generation, unknown-method, parameter, cancellation, and isolation vectors.

Clients cannot launch, warm, restart, drain, or stop providers; select a
provider-private transport; inspect provider argv or environment; publish a
workspace generation; or bypass schema validation.  Cancellation is scoped to
one client session and request identity.  Concurrent clients have isolated
request namespaces, budgets, event cursors, and caches while sharing immutable
server generations and content-addressed facts.

* Schema bundle authority

The Rust Schema Manager and Runtime Server are the only authorities that
resolve, verify, cache, materialize, and publish schema bundles.  The public
surface is the transport-neutral =asp.schema.bundle= method carried as a typed
=ClientFrame= on the existing Runtime gRPC service.  A request selects one
registered profile by its exact =languageId= and =rootSetIds= and may carry
=knownBundleDigest=.  The registry has no =profileId= and the route does not
invent one.  Its profile receipt is exactly ={languageId, rootSetIds,
bundleDigest}=.  Every separate entry binds =familyId=, =schemaId=,
=schemaVersion=, =name=, and =digest=; each returned document repeats the entry
identity and digest.  The Version 1 response is =ready= with canonical receipt,
sorted entries, digest, and schema documents; =unchanged= with the same
canonical receipt and entries; or a typed =failed= terminal.

A declarative language profile names root schemas and provider-owned schemas.
SchemaManager resolves the full reference closure and validates the closed
catalog.  Its =materialize=, =verify=, and =publish-client= commands remain thin
offline build adapters over that same authority.  They may package a generated
wheel or SDK artifact, but they do not create a second transport or a
language-local schema protocol.

The Manager may remove only a stale file named by its previous receipt and
never deletes or overwrites a provider-owned schema.  Language clients do not
read receipt files, enumerate root sets, or verify content digests.  Rust,
Python, Gerbil Scheme, and every future client consume the shared route/API;
adding a language requires one profile declaration and conformance fixtures,
not a language-specific parser, copier, verifier, or ASP Server branch.

* HTTP transport

ASP Client Servers use loopback HTTP/JSON with a persistent Tokio connection pool.
One shared =agent-semantic-http-json= runtime owns Tokio/Hyper accept, connection,
body-limit, drain, and JSON response behavior.  Provider transport and the
public ASP Client Protocol compose that runtime; neither carries a private HTTP
server implementation.  Public clients send the shared client frame to
=POST /protocol/frame= and use =GET /health= only for transport health.

The ASP authority allocates the endpoint, starts the installed server artifact,
polls its health route outside the query path, validates the returned contract,
and atomically publishes =Ready=. Requests are admitted only when their operation
is present in that exact receipt.

HTTP session state is keyed by =(workspaceIdentity, sessionId)=.  The session
admission lock is released before semantic dispatch, so cancellation and other
isolated sessions remain routable while a request is running.

Julia uses HTTP.jl and is server-only. It does not expose a framed-stdio runtime
or one-shot provider command. Julia package loading and cache construction finish
before its health response becomes Ready.

* OpenTelemetry

Every transition and request emits provider, language, artifact, contract,
endpoint-generation, and lifecycle-attempt attributes. Required measurements are
startup and warm-up duration, health latency, request latency, active requests,
typed failures, cancellations, restarts, shutdown duration, and leaked-task count.
Telemetry is observational and never controls readiness.

* Provider workspace toolchain isolation

Provider workspace dependency materialization and build commands execute only
through the shared Tokio provider-process supervisor.  Their Version 1
descriptor may declare exact inherited variables in =removeEnv= and bounded
variable families in =removeEnvPrefixes=.  The provider transport removes
those values before applying the descriptor-owned =env= map and spawning the
single supervised process group.  Empty or malformed identities and duplicate
entries fail closed.

This is one transport capability, not a provider shell wrapper or a second
build authority.  A provider selects only the isolation required by its native
toolchain; for example, a Homebrew Gerbil/Gambit build removes inherited Nix C
toolchain variables instead of mixing SDK headers and flags.  Cancellation,
descendant cleanup, memory accounting, and single-writer artifact publication
remain owned by the same supervisor and Runtime artifact guard.

Dependency materialization, compilation, linking, artifact publication,
provider activation, and Ready-generation admission are preparation evidence.
Their durations are reported separately and MUST NOT be included in Runtime
=search= or =query= latency distributions.

* Shutdown and failure

Shutdown closes admission, drains accepted requests, asks the server to stop,
waits for the child, and aborts only after the typed drain deadline owned by the
Runtime Server. Dropped request receivers cancel their queued work. Closing the
command channel terminates the writer task. Restart creates a new endpoint
generation; receipts from an older generation are never reusable.

* Acceptance

Acceptance MUST prove invoker-active identity, readiness generation equality,
and preservation of the prior healthy slot after a failed candidate.  The
receipt records structured source and active executable identities so these
checks do not require re-reading the binary contents.

- 256 concurrent requests share one server and one startup attempt.
- Starting and Warming are returned without blocking the caller.
- Ready requests perform no process creation, package loading, or filesystem
  discovery.
- cancellation, closed channel, repeated publication epoch, clean shutdown, and
  zero residual task behavior are deterministic Tokio tests.
- Julia HTTP health, request, malformed JSON, unknown operation, and shutdown are
  exercised against the native artifact.
- warm request p99 is measured independently from server startup and warm-up.
- Rust Schema Manager materialize followed by verify is deterministic, offline,
  atomic, and leaves provider-owned schemas untouched.
- Rust, TypeScript, Python, Julia, Gerbil, and one fixture DSL consume the same
  client catalog and pass initialize, request, cancellation, unknown-method,
  generation-drift, shutdown, and trace-context conformance scenarios.

** Hot Path Architecture and proof obligations

The ASP Client data plane has one transport architecture: a persistent,
multiplexed Hyper/Tokio connection (HTTP/2 where negotiated).  HTTP/2
multiplexing is a transport property, not a second client/server authority.
Initialize and catalog validation happen once per workspace/session; the
validated immutable catalog, route bindings, endpoint binding, and Ready
generation are retained by that session.

Each warm =search=, =query=, or =search.owner= request then performs exactly
one typed request on that connection.  It MUST NOT read the endpoint file,
discover a candidate, build or admit a generation, activate or await a
provider, perform a second HTTP hop, or revalidate the immutable catalog.
Bounded =mpsc=, =oneshot=, and typed cancellation remain the only request
coordination primitives.  Non-Ready admission returns immediately with its
typed state and the same hard latency bound; startup, provider activation, and
generation publication are separate measurements and never block or count as
query latency.

The warm acceptance budget is p50 <= 250 microseconds, p99 <= 700
microseconds, and hard max < 1000 microseconds.  Telemetry records separate
HTTP codec, catalog/generation gate, Tokio mpsc/oneshot, resident provider, and
response serialization segments, preserving at least 300 microseconds of
headroom.  No timeout implements this SLA.

Lean obligations model a =ReadyEffects= projection and prove it excludes
=Process=, =Filesystem=, =DbWrite=, =GenerationMutation=,
=ProviderActivation=, and =ControlPoll=.  Scenario and Live Corpus acceptance
must both exercise the same persistent client session and verify these effects,
the segment telemetry, the non-Ready immediate response, and the same
initialize/catalog/request/cancel/shutdown contract across every language.

Live Corpus admission resolves =sourceInventory=, routes, and provider identity
from the Runtime provider-plane snapshot for the active generation.  The
compile-time provider identity register is not a capability authority and MUST
NOT be used to materialize or qualify a corpus.  Missing Runtime registration,
generation conflict, or missing provider-owned inventory fails closed with the
provider-plane receipt.

An explicitly targeted =(languageId, providerId)= corpus invokes that
provider's declared project-resolution capability after locked-revision and
language-extension admission.  Project entry markers are discovery hints for
untargeted CompleteGeneration scans; they are not a second admission gate for
an explicit provider target.  The Runtime MUST NOT mutate an upstream corpus
or invent a provider-specific marker merely to satisfy auto-discovery.

** Southbound ProviderSession stream contract

The public northbound HTTP/JSON catalog is an adapter only.  The sole
southbound business authority is =RuntimeStreamService=, whose admitted
provider session is a bidirectional Tokio stream represented by the canonical
=ProviderSession= contract in =crates/agent-semantic-runtime-server/proto/asp-provider-stream.proto=.  Its
wire implementation will use Tonic; the proto and Schema Manager remain the
central authority, and language directories contain only managed materialized
copies.

Ready =search=, =query=, and =search.owner= are Runtime-local operations over
the immutable Ready generation and MUST NOT take a provider-stream or second
HTTP hop.  Activation, generation admission, provider facts/capabilities,
cancellation, and drain use the ProviderSession stream.  Provider HTTP health,
request, and shutdown operations MUST NOT exist; no HTTP fallback or parallel
authority is permitted.

The Runtime daemon MUST bind the canonical provider-plane Unix socket before
publishing Ready, serve =ProviderSession= from the same
=RuntimeServerTaskScope= as the northbound adapter and resident generation
owner, and drain it through the same typed shutdown signal.  A proto service or
loopback test that is not mounted by the daemon is not an admitted transport.
The provider-plane socket path published by the Runtime endpoint is the sole
local authority; a second TCP listener, provider HTTP listener, or CLI process
route is forbidden.

** Northbound route intent contract

Northbound =search=, =query=, and =search.owner= requests carry user intent
only: language identity, scope/owner intent, and route-specific query fields.
They MUST NOT carry runtime-owned generation, source, parser, provider, catalog,
or artifact identities. The Runtime Server resolves those identities from the
validated session catalog and immutable Ready generation. Provider-native DTOs
are internal server/provider contracts and are not northbound inputs. Non-Ready
sessions return a typed admission response without consulting a prior generation
or invoking a provider.
