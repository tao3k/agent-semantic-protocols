#+TITLE: ASP Client Server Authority
#+STATUS: proposed
#+PROPERTY: rfc_layer provider-server-authority

Parent architecture: [[file:10.05-interactive-graph-first-progressive-searchloop.org][RFC 10.05 SearchLoop]].

* Problem

Language runtimes with material warm-up cost, including Julia, cannot be modeled
as commands on the query path. Process creation, VM initialization, package
loading, and provider warm-up are lifecycle work. Treating them as query work
produces multi-second cold latency and makes health, cancellation, and shutdown
unobservable.

The same category error also appears when a long-lived server copies the shape
of an editor protocol without preserving the stronger invariants required by a
semantic search runtime.  A persistent process alone does not create a fast or
correct data plane.  The following observed failures are architectural, not
isolated implementation bugs:

- a language request discovers a repository candidate, enqueues generation
  work, waits for publication, or opens durable state before reading;
- a queued admission snapshot is returned as if it were a terminal, forcing
  the client to retry and making exactly-once behavior unknowable;
- the edge-triggered =accepted= bit is treated as readiness even though a
  replayed Ready terminal correctly has =accepted=false=;
- a targeted provider projection is reused as a complete workspace generation;
- client initialization, provider activation, generation admission, and query
  execution share one latency and failure domain;
- semantic unit tests bind private sockets, so an AF_UNIX sandbox policy is
  mistaken for a search failure;
- a transport closes without one typed terminal and exposes raw =early eof=;
- mutable labels, activation counters, paths, or process observations are used
  as freshness evidence instead of content identity;
- lexical matching, native-finder behavior, graph reasoning, cache population,
  and rendering form an implicit fallback chain rather than an admitted plan.

These failures recreate weaknesses commonly seen around LSP deployments:
mutable per-client document replicas, workspace-scale rescans, best-effort
cancellation, stale responses without generation identity, dynamic capability
drift, and opaque progress.  ASP keeps the useful LSP lesson--one long-lived
server and a typed request lifecycle--but rejects those mutable and
client-authoritative semantics.

* Beyond LSP: normative architecture

** What ASP keeps and what ASP rejects

ASP keeps five proven server-protocol ideas:

1. a long-lived server rather than one subprocess per request;
2. explicit initialize, request, cancellation, shutdown, and exit phases;
3. method discovery through one negotiated catalog;
4. request identity and exactly one terminal response;
5. incremental change ingestion instead of mandatory full rescans.

ASP strengthens them with invariants an editor protocol normally does not
provide:

- the server reads an immutable, content-addressed =WorkspaceGeneration=;
- every result binds workspace, source root, generation, schema catalog, and
  algorithm identity;
- the client never owns a mutable shadow workspace, index, cache, provider, or
  publication pointer;
- cold lifecycle work and warm semantic reads are different methods on
  different scheduling lanes;
- all queues are bounded, cancellation has reserved control capacity, and a
  connection produces exactly one typed Ready, Error, or Cancelled terminal;
- Rust, Gerbil Scheme, Python, TypeScript, Julia, Org, Markdown, and future
  languages publish facts into the same language-neutral search algebra;
- a cache hit is a proof of exact content identity, not evidence inferred from
  a timestamp, path, label, process, or activation counter.

** Four authority planes

The Runtime is one process authority with four non-interchangeable planes:

#+begin_example
control plane     initialize, catalog, health, cancel, drain, ensure-ready
write plane       source mutation, parser projection, generation publication
resident read     exact selector, lexical postings, owner graph, bounded merge
provider stream   activation, parser facts, diagnostics, graph preparation
#+end_example

The control plane has reserved capacity and never waits behind data requests.
The write plane is single-writer per workspace generation.  The resident read
plane is read-only and lock-free after it acquires one immutable generation
lease.  The provider stream may prepare facts for the next generation but
cannot mutate the generation visible to a request.

No public language method crosses planes.  In particular, =search=, =query=,
=source-index.lookup=, and =search.owner= never invoke candidate discovery,
Git, a database, a provider process, generation admission, publication, health
polling, or endpoint discovery.

** Cold lifecycle and warm request state machines

*** Bootstrap is a bounded observation, not a lifecycle loop

The public client performs exactly one observation of the Runtime authority
tuple =(artifact digest, publication nonce, owner epoch, endpoint binding)=.
That observation MUST return one typed =Ready=, =Starting=, =Failed=, or
=Cancelled= terminal without polling, sleeping, retrying, or waiting for a
filesystem endpoint to appear.  A non-ready observation is a control-plane
receipt; it is not permission for the query path to discover, spawn, install,
or rebuild anything.

The normative decision table is:

| cancellation observed | owner alive | endpoint bound | terminal |
|-----------------------+-------------+----------------+----------|
| yes                   | any         | any            | =Cancelled= |
| no                    | yes         | yes            | =Ready= |
| no                    | yes         | no             | =Failed(endpoint-authority-diverged)= |
| no                    | no          | no             | =Starting(supervisor-scheduled)= |
| no                    | no          | yes            | =Failed(stale-endpoint-authority)= |

A process is never Runtime authority by itself.  Therefore a live daemon with
a missing or non-matching endpoint is not =Starting= and cannot be repaired by
client polling: it is a fail-closed identity divergence owned by the Runtime
supervisor.  Conversely, an absent owner and endpoint may schedule one
single-flight supervisor recovery, but the initiating client still returns the
typed =Starting= receipt immediately.

Cancellation is transitive across the complete client process tree.  When the
CLI receives cancellation, it closes the request scope, signals the spawned
client child if one exists, waits for that exact child to terminate, and emits
one =Cancelled= terminal.  A cancelled client with a live orphan query process
is a protocol violation.  Cancellation never terminates the resident Runtime
owner and never mutates a published generation.

The resident daemon MUST NOT acquire the supervisor transaction, invoke its
own successor handoff, or wait for its own exit receipt.  On observing a newer
content-bound publication, the daemon has exactly one authority: publish a
typed =successor-required= activation observation, preserve the pending
candidate without acknowledging or rolling it back, drain every owned service,
publish its own exit receipt, release the owner election, and exit.  Only an
external supervisor may then acquire the supervisor transaction and admit the
pending successor.  This ordering prevents the self-deadlock
=owner-election + supervisor-transaction + await-own-exit=.

Client connection lifecycle:

#+begin_example
Disconnected
  -> Connected(endpoint binding verified once)
  -> Initialized(identity and immutable catalog bound once)
  -> GenerationReady(ensure-ready terminal bound once)
  -> ReadyRequests*
  -> Draining
  -> Closed
#+end_example

Workspace generation lifecycle:

#+begin_example
Absent -> Restoring -> Ready
   \        \-> Failed
    -> Building -> Publishing -> Ready
          \-> Cancelled | Failed
Ready -> BuildingSuccessor -> PublishingSuccessor -> Ready'
#+end_example

=Initialize= binds identity and the immutable method catalog only.  It does
not scan a workspace or activate a provider.  The server-owned
=asp.workspace.generation.ensure-ready= cold method restores or builds one
=CompleteGeneration=, joins the same attempt when another caller owns it, and
waits for the same attempt's terminal.  A queued or Building receipt is
progress, never a read barrier.  =accepted= reports only whether that call
inserted work and is not part of Ready identity.

After one Ready terminal, language methods are pure resident reads.  If a
caller bypasses preflight, a language method returns immediate typed
=query-not-ready= without attempting recovery.  A client retry never supplies
missing server progress semantics.

** One protocol, two persistent stream directions

The public northbound transport is the canonical Tonic gRPC =ClientFrame=
service over persistent HTTP/2.  The southbound transport is the canonical
Tonic bidirectional =ProviderSession= stream.  They are two directions of one
Runtime protocol architecture, not parallel authorities.  JSON is an optional
CLI/debug rendering of a typed terminal; it is not the hot wire format and is
never reparsed inside the resident search engine.

Northbound gRPC carries initialize/catalog, ensure-ready, language requests,
cancellation, terminal responses, events, shutdown, and exit.  Southbound gRPC
carries provider registration, activation, parser deltas, generation-bound
facts, diagnostics, cancellation, and drain.  Ready search/query is
Runtime-local and does not make a southbound hop.

One response stream reader demultiplexes request IDs.  A bounded data semaphore
admits at most 32 concurrent calls per session; at least one independent
control slot remains available for cancellation, health, and drain.  Per-key
single-flight is used only for cold readiness and publication, never to
serialize independent Ready reads.

Every admitted request produces exactly one terminal.  Handler error, task
panic, peer closure, decode failure, cancellation race, and drain race are
mapped at the frame owner.  Raw EOF, an empty response, and success-without-
terminal are protocol violations, not retry signals.

** Sandbox-safe endpoint contract

The Runtime Server is the only listener owner.  A CLI, test, provider, or agent
sandbox never binds a Runtime socket.  Production clients only connect to the
binding named by the validated endpoint receipt.  Semantic unit tests invoke
the transport-neutral frame service directly; dedicated transport integration
tests alone bind a listener.

An endpoint receipt binds transport kind, canonical address, owner epoch,
binding token, Runtime binary content digest, protocol catalog digest, and
maximum frame size.  Endpoint files are bootstrap evidence read once per
connection, never per request.  A permission failure before gRPC handshake is
typed =transport-unreachable= with the exact OS error and endpoint identity; it
does not start, restart, install, or replace the Runtime.

Supported Host environments MUST provide one admitted northbound binding that
their sandboxes can connect to.  The default is a short Unix-domain socket in a
UID-scoped shared Runtime directory.  A Host may provide an inherited connected
descriptor or a loopback HTTP/2 binding, but it must carry the identical
=ClientFrame= protocol and endpoint identity.  There is no client-side
transport fallback chain: binding selection is an atomic Runtime publication.

Acceptance includes real connect-only probes from every supported Host sandbox
profile.  Bind permission and connect permission are tested separately.  An
=EPERM= from an unauthorized test listener is not evidence that the production
client path is broken; an =EPERM= connecting to the published production
binding is a release-blocking endpoint-contract failure.

The endpoint descriptor therefore publishes a *transport capability*, not a
bare socket pathname.  A capability is usable only when the Runtime has bound
the endpoint identity and =ClientFrame= protocol identity and the Host has
declared that the selected binding is reachable from the caller's sandbox
profile.  Socket existence, server health, matching artifact bytes, and a
successful out-of-sandbox probe do not establish caller reachability.

The language-neutral metadata contract is
=schemas/runtime-client-transport-capability.v1.schema.json=.  An inherited
descriptor is deliberately out of band and never serialized into that schema:
the metadata binds the endpoint, protocol, Host sandbox profile, and real
reachability receipt, while the Host transfers the connected handle directly
to the client process.

Transport selection is atomic and fail-closed.  The client selects the one
published capability before opening a socket.  An absent or unreachable
capability returns one typed =transport-unavailable= terminal before I/O; it
does not first attempt a global =/tmp= socket, translate =EPERM= into lifecycle
state, retry under a different transport, spawn another Runtime, or disable
Hook policy. A Host may publish exactly one of the UID-scoped Unix binding,
an inherited connected descriptor, or loopback HTTP/2.  All three mount the
same Runtime-owned =ClientFrame= service and carry the same endpoint identity;
none is a second admission, generation, cache, or provider authority.

The sandbox matrix is part of publication acceptance.  Each supported Host
profile runs a real connect-only probe against the candidate capability before
it becomes Active/Healthy.  Publication fails when any required profile cannot
reach the binding.  This makes a repeated production =EPERM= impossible for an
accepted profile by construction, rather than recoverable by client policy.

The selected capability also owns client bootstrap admission.  A sandboxed
client carrying an inherited connected descriptor MUST NOT first probe the
published control socket, infer lifecycle state from a failed connect, or
become a Runtime supervisor.  It reads the endpoint identity snapshot, then
performs initialization and request dispatch on the inherited =ClientFrame=
channel.  Runtime observation, recovery, and replacement remain Host
supervisor operations.  A sandboxed client without a complete usable
capability returns typed =transport-unavailable= before socket I/O; it never
falls through to pathname bootstrap, spawn, retry, or Hook configuration.

This rule is necessary even when the data request itself already supports an
inherited descriptor.  A pathname-based control preflight in front of that
request recreates the same Host =EPERM= bug one layer earlier and can
misclassify a healthy Runtime as stopped.  Control-plane preflight and
data-plane dispatch are therefore one atomic transport selection, not two
independently selected routes.

** Unified native rg, Tantivy, syntax, and graph Search Layout

=rg=, Tantivy, syntax, and graph reasoning are not intent-derived fallbacks.
The shared planner admits the caller's exact native blocks into a =SearchLayout=
with explicit ordering and bounded composition:

#+begin_example
SearchLayout
  -> NativeRgBlocks*          exact admitted rg argv over immutable bytes
  -> TantivyQueryBlocks*       parsed native Tantivy query grammar
  -> SyntaxBlocks*             producer-native syntax argv
  -> NativeSyntaxSelectors*    exact parser-owned selector materialization
  -> GraphBlocks*              bounded native GQL or PGQL argv
  -> DeterministicSettlement   one generation-bound typed packet
#+end_example

The Runtime invokes the admitted =rg= executable with the exact caller argv
against a reconstruction of the immutable source generation.  It does not
translate that argv into an in-process regex subset.  Tantivy parses and
enforces its native query grammar independently; it does not accept a simple
unparsed search string in place of that grammar.

Each native block preserves its exact argv and occurrence index.  Tantivy
posting lists are immutable, generation-local, and ordered by stable
owner/selector identity.  Intersection, WAND/top-k pruning, and rank features
are deterministic for the same layout and generation.

=asp-python-graphs= owns graph algorithms and offline calibration, not the
core query lifecycle.  Provider/graph facts required by the resident graph
path are published into the immutable generation and evaluated by the resident
bounded router.  An explicitly requested Python graph escalation uses its
already-warm gRPC stream under a separate compute budget and returns facts for
a future generation or a separately typed graph result; it never blocks or
mutates the core =search/query= transaction.  Python process startup, imports,
NumPy/SciPy allocation, and graph cache construction are cold preparation.

Exact =query= does not enter lexical or graph ranking.  It hashes the parser-
owned structural selector and owner identity, reads the exact map, validates
the bound content digest and byte proof, and returns the requested projection.

** Cross-language amortization and shared Rust compute core

The language dimension is an input fact vocabulary, not an execution topology.
All languages share one Runtime listener, connection/session pool, bounded
scheduler, generation authority, Merkle owner tree, exact map, lexical engine,
graph router, ranking implementation, memo policy, telemetry model, and
terminal encoder.  There is no Rust-query server, Scheme-query server,
Python-query server, or language-specific cache on the northbound path.

The heavy online computation is implemented once in the shared Rust service
core:

#+begin_example
agent-semantic-runtime-server
  -> agent-semantic-search
  -> agent-semantic-search-projection resident segments
  -> shared Merkle/content identity
#+end_example

This shared Rust core is not the =asp-rust= language provider.  =asp-rust= owns
Rust syntax and project facts just as =asp-gerbil-scheme= owns Scheme facts.
Making another language call the Rust provider for ranking or indexing would
create a cross-language provider authority and is forbidden.  Providers
perform parser-native work on the write/provider plane and publish the same
language-neutral owner, selector, lexical, relation, and diagnostic facts into
the next immutable generation.

The protocol provider-ID namespace is =asp-<languageId>=.  This identity is
language-scoped even when multiple languages share one implementation package
or executable: Org is =asp-org= and Markdown is =asp-md=, while =orgize= may
remain their package, binary, or parser authority.  A package name, executable
name, parser authority, or embedded implementation marker MUST NOT be copied
into =providerId=.  Conversely, assigning =asp-org= or =asp-md= does not imply
that separate binaries with those names exist; provider identity and execution
topology are independent contracts.

Consequently the Ready cost for any language =L= is:

#+begin_example
T_ready(L) = T_frame
           + T_session_generation_lease
           + T_shared_plan
           + T_shared_resident_index
           + T_shared_merge_encode
#+end_example

There is no =T_provider_start(L)=, =T_provider_rpc(L)=,
=T_language_binding(L)=, =T_db(L)=, or =T_workspace_scan(L)= term.  Language
differences may change the number of admitted facts visited under the same
explicit budget, but not the sequence of services or authorities.

Generation preparation is amortized independently:

#+begin_example
C_successor = C_shared_manifest_and_merkle
            + sum(C_changed_owner_parse(L))
            + C_changed_shared_segments

amortized_cost_per_read = C_successor / Ready_reads_before_successor
#+end_example

Unchanged owner arenas and postings segments are content-addressed and reused
across successor generations.  Multiple clients and sessions share the same
immutable resident segments.  They never duplicate a parser projection or
graph cache merely because their generated client language differs.

Generated Rust, Python, Gerbil Scheme, TypeScript, or Julia client bindings are
thin =ClientFrame= codecs.  They do not contain ranking, cache, generation, or
fallback behavior.  Their conformance budget measures the same server receipt;
language binding startup is reported separately from Runtime service time.

Cross-language comparison therefore uses normalized work units rather than
language-specific wall time alone:

| phase | normalized denominator | required receipt |
|-
| parser publication | changed source bytes and changed owners | bytes/second, owners/second, facts/owner |
| immutable storage | admitted source KLoC and relation count | segment bytes/KLoC, bytes/relation, reused bytes |
| cold successor | changed owner count | parse, segment-build, Merkle, commit microseconds |
| cold load | immutable segment bytes | validation and mmap/load microseconds |
| warm exact | one selector | visited entries, service-core and transport nanoseconds |
| warm lexical | postings actually visited | postings, blocks skipped, merge nanoseconds |
| warm graph | nodes and edges actually visited | nodes, edges, frontier peak, merge nanoseconds |

The provider receipt ends at canonical fact publication.  The Ready receipt
starts at the shared Rust planner.  This boundary prevents a fast parser from
hiding an expensive shared query, and prevents a slower parser from making the
resident query appear language-dependent.  No generated binding, FFI shim,
language VM, provider RPC, or provider-private database is admitted between
those two receipts.

The shared fact ABI is declarative data, not executable language callbacks.
Its minimum projections are owner identity, exact selector, lexical tokens,
structural facts, relations, source ranges, and diagnostics, each bound to the
same owner content digest.  Adding a language means implementing this
publication contract and its conformance corpus; it does not add a search
engine implementation.

=asp-python-graphs= is a cold/write-side graph construction, algorithm
calibration, and executable-oracle service.  It may build generation-bound
CSR/adjacency, embeddings, or other graph artifacts through its persistent
gRPC stream.  The shared Rust service validates and publishes those immutable
artifacts.  Ready graph routing uses the resident Rust router over the
published artifact; it does not call Python.  A separately requested
Python-native analysis is a different typed method with its own compute SLA and
cannot be included in or block the sub-millisecond core Search/Query budget.

** Transport ablation instead of transport-owned semantics

Transport overhead is measurable and removable because transport adapters call
the same transport-neutral frame service.  The required ablation matrix is:

| lane | purpose | owns semantics |
|-
| direct service-core | algorithm and state baseline | yes |
| persistent local gRPC/HTTP2 | canonical production northbound path | no |
| optional HTTP/JSON adapter | debug/interoperability comparison only | no |

The HTTP adapter, when built, owns only codec and connection adaptation.  It
cannot own a session registry, generation watch, provider lifecycle, cache, or
different error mapping.  Removing it changes no method, schema, state
transition, or test oracle.  Production acceptance compares direct service-core
and gRPC receipts to quantify =T_transport=; an HTTP adapter may be measured as
an explicit ablation but cannot set the cross-language budget or silently
replace gRPC.

One warm connection amortizes endpoint discovery, handshake, initialize,
catalog validation, and ensure-ready.  Benchmarks therefore report at least:

#+begin_example
T_cli_process_start
T_connect_once
T_initialize_once
T_ensure_ready_once
T_service_core_per_request
T_grpc_codec_and_roundtrip_per_request
T_optional_http_adapter_per_request
#+end_example

Only the last three are transport ablation evidence; only service-core plus the
canonical gRPC roundtrip participate in the Ready SLA.  Combining cold setup
with a one-shot command and reporting the result as server latency is invalid.

The executable receipt is
=schemas/semantic-ready-search-ablation-receipt.v1.schema.json=.  It binds the
workspace/source/generation/schema/algorithm/plan identities, normalized plan
budget and observed work, zero forbidden Ready effects, transport timing
segments, exactly one terminal, and result digest.  JSON Schema owns the wire
shape; the shared Rust validator owns cross-field arithmetic such as observed
work not exceeding its budget and timing segments reconciling with the total.

Cross-language qualification uses the same plan shapes and budgets against one
real large repository per language.  It compares exact lookup, multi-seed
lexical, rg-compatible literal/regex, owner/test routing, and resident graph
routing.  A language passes only if its receipts show the same zero provider
RPC, zero DB, zero source-scan, zero generation-mutation effects and the same
p50/p99/max thresholds.  Slower native parsing is charged to successor build,
not hidden in Ready latency.

** Lean architecture inventory and legacy-impact closure

Lean is not used to claim that wall-clock nanoseconds are mathematically true.
It proves the closed authority/effect/cost structure that makes the executable
measurement meaningful.  =ASPInteractiveSearchLatency.lean= defines the only
admitted Runtime owners, capabilities, Ready effects, plan budgets, terminal
cardinality, and transport projection.  In particular it proves that:

- a language provider cannot own Search planning;
- a generated client cannot own generation publication;
- gRPC and HTTP adapters cannot own terminal or resident-cache semantics;
- provider RPC, workspace scan, durable DB access, generation mutation,
  endpoint discovery, and client retry are forbidden Ready effects;
- transport projection preserves the complete semantic receipt;
- duplicate terminals and the previous 10 millisecond warm budget are rejected.

The code audit MUST generate an =ArchitectureInventory= from Cargo
features/dependencies, method catalogs, Runtime route registrations, provider
descriptors, Rust call/re-export edges, and exported client APIs.  The inventory
contains both owner/capability surfaces and enabled directed edges classified as
=cargoFeature=, =cargoDependency=, =rustReexport=, =runtimeRoute=, or =rustCall=.
Every surface must satisfy =architectureInventoryAdmitted=.

Lean applies two different legacy gates because treating them as one hides
impact:

1. =sourceInventoryHardCut= rejects any legacy owner that remains in the
   production inventory, even if no current route reaches it;
2. =architectureImpactClosed= computes transitive reachability and rejects
   both a production entry that can reach a legacy owner and a legacy owner
   that can reach the shared Runtime authority.

Therefore removing a command name or direct call is not closure.  A deprecated
helper that remains behind an enabled Cargo feature, dependency, re-export,
route registration, or intermediate call remains a constructive Lean
counterexample.  CI MUST generate the inventory rather than maintain a hand
written allow-list, validate it with
=schemas/search-architecture-inventory.v1.schema.json=, feed its normalized
digest into Lean, and validate Lean's result with
=schemas/search-architecture-proof-receipt.v1.schema.json=.  A rejected proof
receipt retains the exact unknown nodes, capability violations, legacy owners,
and reachability paths; an admitted receipt is schema-constrained to empty
impact and an empty axiom list.
Removal is complete only when the source inventory contains no legacy row and
every production feature set is impact-closed.

Rust, the provider harness, and Schema Manager are fact producers only.  They
emit source selectors, declared ownership/capability claims, the actual
=server_client_methods= catalog, and Cargo/parser edges; they do not classify a
node as legacy, decide =ownerMayHold=, compute reachability, or emit an
=admitted= decision.  Those judgments exist exactly once in Lean.  Unknown
inventory nodes fail closed instead of being silently omitted.  The Lean
checker emits stable shortest counterexample paths and its proof receipt is the
only architecture-admission result consumed by CI and the Rust refactor loop.

The producer side MUST NOT rescan an entire crate merely to apply a Harness
policy.  Cargo resolution, the language parser, the Runtime method catalog, and
the provider descriptor each emit their already-observed package-local fact
fragment.  Schema Manager performs only canonical sort, duplicate elimination,
reference closure, and content addressing over those fragments.  Its
=SearchArchitectureFactInventory::from_facts= API deliberately accepts a
declared owner such as =legacy-client-fallback= without deciding whether that
owner is valid.  Incremental cost is proportional to the changed fact fragment
plus Merkle-path repair, not to total source bytes.

The refactor loop is therefore directional and non-circular:

#+begin_example
RFC taxonomy
  -> Cargo/parser/Runtime neutral facts
  -> Schema Manager immutable inventory digest
  -> Lean owner/capability/reachability proof
  -> shortest counterexample report
  -> Rust deletes or rewires exactly those reported edges
  -> regenerate until Lean admits an empty impact set
#+end_example

Rust MUST NOT contain a second evaluator equivalent to the Lean predicates.
Rust tests assert faithful fact production and removal of a reported edge;
Lean tests assert that the resulting graph has no legacy row, no capability
violation, no production-to-legacy path, and no legacy-to-authority path.

** Merkle identity and cache architecture

The Merkle tree is the invalidation authority, not merely an audit checksum.
The admitted generation commits:

#+begin_example
workspace root
  -> owner path + owner content digest
    -> parser projection digest
    -> exact selector segment digest
    -> lexical postings segment digest
    -> relation/graph segment digest
#+end_example

Cache layers are explicit and never hidden:

1. =L0 SessionBinding=: endpoint, catalog, route table, and Ready generation;
2. =L1 ResidentGeneration=: atomic workspace pointer and immutable segment
   handles;
3. =L2 OwnerArena=: exact, lexical, structural, and relation data keyed by
   owner content digest;
4. =L3 DurableCAS=: validated immutable segments and publication journal used
   only by restore/build, never queried by the Ready path;
5. =L4 QueryMemo=: optional bounded result memo keyed by exact generation,
   normalized plan digest, ranking version, and output budget.

Positive and negative memo entries are safe only inside the exact immutable
generation.  They have no wall-clock freshness claim and are discarded by
generation pointer replacement.  A source change recomputes the affected
owner leaves and O(log N) Merkle path, reuses byte-identical owner arenas, and
publishes one successor generation.  Removed owners create tombstones.  No
request clears a global cache or scans for freshness.

Python graph artifacts additionally bind graph algorithm/version, numeric
backend identity, source generation, node/edge schema digests, and seed-plan
digest.  They cannot be reused across a changed source root or algorithm even
when a label or path is unchanged.

Live Corpus exposes cache state deliberately: =cold-build= begins without a
resident or durable generation for the run-scoped workspace; =cold-load=
opens a validated durable generation into Memory; =warm-read= reuses the exact
resident binding; =released= removes only that run-scoped resident lease.
Each operation reports what it loaded, reused, wrote, or evicted.

** Complexity and latency budgets

The sub-millisecond contract applies to resident service time on an existing
gRPC connection, not shell startup, executable loading, Runtime bootstrap,
provider startup, generation build, or terminal rendering in a new CLI
process.  Those phases have separate receipts.

For bounded result size =K= and query clauses =Q=:

- exact selector lookup: expected O(1), no allocation proportional to workspace;
- literal/regex candidate filtering: O(candidate bytes), after postings/trigram
  pruning, never O(workspace bytes) on the Ready path;
- lexical retrieval: O(sum of visited postings + K log K), with a declared
  visited-postings budget;
- graph routing: O(V_b + E_b) inside an explicit bounded frontier;
- owner mutation: O(changed owner bytes + changed facts + log owner count);
- generation publication: O(changed segments + manifest), independent of
  unchanged source bytes.

Required Ready service budgets:

| segment | p99 budget |
|-
| gRPC decode + catalog/session gate | 120 microseconds |
| generation lease + plan admission | 80 microseconds |
| exact or bounded lexical/rg-compatible read | 300 microseconds |
| deterministic merge + typed encode | 150 microseconds |
| reserved headroom | 50 microseconds |

The end-to-end Ready target remains p50 <= 250 microseconds, p99 <= 700
microseconds, and hard max < 1000 microseconds for bounded exact and lexical
requests.  The same hard maximum applies at 32 concurrent calls without
starving cancellation.  A benchmark reports every segment; no timeout is used
to manufacture compliance.

The strict sub-millisecond interactive deadline applies to bounded exact,
single lexical and Query reads.  Cold
=asp.workspace.generation.ensure-ready= is a control-plane admission wait and
MUST NOT inherit that deadline.  The composite
=asp.workspace.search.playbook= is also not an exact-read latency class: its
resident =rg= and Graph stages may consume the complete generation-derived
cardinality envelope, so its cancellation and northbound transport deadline
bound the request while phase telemetry records the actual work.  Both paths
remain bounded by deterministic input, single-flight capacity where
applicable, cancellation and exactly-one terminal semantics, but an exact-read
budget cannot convert valid Building progress or a bounded composite Search
projection into failure.
The client keeps the same request open until Ready, Failed or Cancelled; it
does not abandon a builder and retry with a second request.  Cold elapsed time
is measured and qualified independently from the sub-millisecond warm-read
budget.

The method catalog owns this dispatch classification exactly once.  The
service dispatcher, gRPC pending-call transport, and CLI session wrapper MUST
preserve it unchanged.  An adapter MUST NOT replace the method-derived class
with a process-global response deadline.  In particular, the gRPC response
wait for =asp.workspace.generation.ensure-ready= remains open for its typed
Ready, Failed, or Cancelled terminal; only explicit protocol cancellation may
end valid Building progress.  Ready read methods retain the bounded interactive
deadline at every layer.

The optional loopback HTTP/JSON provider adapter has the same separation.
Health and shutdown are lifecycle probes and retain a bounded lifecycle
deadline.  A generation-time provider request frame has no adapter-local wall
clock deadline: its bound is owned by the admitted generation task, resource
lease, typed cancellation, and provider drain protocol.  Consequently an HTTP
client-wide timeout MUST NOT turn a valid parser projection still making
progress into a provider failure.  This does not widen or weaken the
sub-millisecond northbound Ready-read deadline because provider projection is
never part of Ready request dispatch.

** Backpressure, cancellation, and scheduling

Capacity is admitted before semantic work.  Saturation returns typed
=resource-exhausted= immediately with capacity and retry class; the server does
not create an unbounded task or queue.  Cancellation is keyed by session and
request ID, travels over reserved control capacity, and causes exactly one
Cancelled terminal.  Dropping the client receiver cancels queued work but does
not roll back an already committed generation.

Cold workspace readiness is single-flight by workspace and candidate identity.
Provider activation is single-flight by provider artifact and manifest
identity.  Query memo fill may be single-flight by generation and plan digest.
These keys never share a global mutex.  Immutable generations allow unrelated
queries to run concurrently without a write lock.

** Provider relevance is artifact-bound

A registered provider capability is declarative evidence, not execution
authority.  The active provider set for a =CompleteGeneration= is the exact
intersection of the Runtime provider register and the immutable installed-
artifact document.  Registration rows without a content-proven artifact are
inactive and MUST NOT enter source discovery, parser scheduling, generation
identity, or the public language method catalog.

Consequently, an inactive Julia capability cannot prevent a Rust workspace
generation from becoming Ready.  This is not best-effort fallback: the Julia
provider has no authority in that Runtime generation, while the Rust provider
remains fail-closed against its exact selected artifact.  If a request targets
an inactive provider, it returns typed =provider-artifact-missing= before
generation admission.  If two active artifacts claim the same language and
operation, admission returns typed =provider-ambiguous=.

The Runtime computes the intersection once per immutable provider artifact
catalog generation.  Ready reads do not scan registration rows or the
filesystem.  Adding or replacing an artifact creates a successor provider
catalog generation; it never mutates the active set behind an existing Ready
workspace generation.

** Incompatible persisted generations are inert inputs

A structurally complete pointer from an older workspace-generation schema is
not current generation authority.  Cold admission MUST classify it as
=incompatible-schema=, exclude it from active-base, epoch, owner-journal and
cache identity decisions, and build a current-schema =CompleteGeneration= via
the sole Runtime publisher.  The old bytes remain untouched as rollback
evidence until the atomic current publication commits; clients neither delete
nor migrate them.  Therefore an incompatible but decodable pointer cannot
block a current rebuild, and it can never be reused merely because its atomic
slot checksum is valid.  Malformed current-schema bytes still fail closed as
corruption rather than being silently reclassified as absent.

** Failure containment

Failures stay in the plane that owns them:

- endpoint permission or handshake -> =transport-unreachable=;
- catalog/schema mismatch -> =protocol-catalog-mismatch=;
- no Ready generation -> =query-not-ready=;
- failed generation attempt -> typed admission terminal with stage and attempt;
- stale selector -> =selector-generation-mismatch=;
- selected provider unavailable -> provider capability failure, not workspace
  loss; an unrelated inactive capability cannot block the selected provider;
- graph service unavailable -> typed graph-escalation failure, core lexical
  generation remains readable;
- malformed/closed stream -> exactly one frame-level failure, never raw EOF.

No failure authorizes client retry, provider-private cache use, targeted-scope
promotion, local file scanning, Runtime restart, installation, or an alternate
transport.

The implementation order is normative:

RFC and cost model

=accepted=true=; a Ready request has no write/provider/process/DB effects;

has exactly one terminal; bounded capacity preserves a control lane; and cache

Runtime tests MUST demonstrate one cold readiness attempt, same-attempt wait,
one CompleteGeneration commit, one resident publication, warm dispatch with
zero candidate discovery/build/provider/DB/filesystem work, 32-call bounded
concurrency, cancellation under saturation, EOF injection, stale/cross-content
rejection, and deterministic replay.  Live Corpus runs those gates on a real
large repository for every language, with explicit =cold-build=, =cold-load=,
=warm-read=, ten sequential, 32 concurrent, and at least three failure-
injection rounds.

* Decision

ASP Runtime Server owns one Tokio =AspClientServerAuthority= per activated server
provider. The authority is a single-writer task. Commands enter through bounded
=tokio::sync::mpsc=, replies use =oneshot=, and committed lifecycle state is
published through =watch=. No synchronous lock or shared mutable map is part of
the provider request path.

** Rust client-server hard cut

The public Rust provider lifecycle command is =asp-rust serve=.  Provider
runtime transport namespaces are not public CLI subcommands.  The CLI keeps no
alias parser, argument-shape guard, or command-specific diagnostic for removed
commands.  This paragraph supersedes any older command spelling in this
section.

Rust follows the same server-first =ProviderSession= stream contract as every
language.  The provider manifest declares the canonical gRPC stream capability;
it does not publish a private HTTP listener.  ASP Runtime Server is the only
owner allowed to start, warm, health-check, drain, or stop the Rust provider.

The public =asp rust ...= command is a typed Runtime IPC facade only.  It never
starts the Rust provider, resolves a workspace, opens a provider cache, or owns
provider lifecycle state.  The former =asp-rust runtime serve= command is
removed, not aliased.  Provider projection and project-resolution operations
remain typed protocol operations behind the resident client-server; they are
not permission to restore one-shot CLI execution.

Rust admission is single-flight per provider artifact and manifest identity.
Concurrent workspaces receive isolated request identities, cancellation tokens,
and terminal responses while sharing only an immutable, committed warm client.
Lazy load is driven by the activated language extension set before publication
of =Ready=; an idle client may be drained only by the Runtime authority.  Every
transition and request publishes the shared lifecycle/OpenTelemetry evidence
required by native Scenario and Live Corpus qualification.

** ASP Client Server contract and catalog routes

The Runtime-published Tonic gRPC endpoint is the single client authority.
Each client performs =Initialize -> catalog -> Request -> Cancel/Cancelled ->
Shutdown -> Exit= over the persistent =ClientFrame= stream.  The immutable catalog uses structured
=schemaId= and =schemaVersion= "1" references.  Canonical provider routes are
=<language>.search=, =<language>.query=, and =<language>.search.owner=; their
request and response schema IDs are respectively the runtime search,
provider-native exact, and provider-native owner contracts.  The Runtime Server
performs the workspace-generation Tokio watch barrier before dispatch.  A
=Building=, =Failed=, or =Cancelled= generation is a typed admission response;
the client never reads an older generation.

CLI language commands are facades over this gRPC catalog.  They MUST NOT call
provider transport, resident projections, provider caches, or local workspace
generation/session APIs directly.  Provider lifecycle and cancellation remain
owned by the server's bounded =mpsc=, =oneshot=, and =watch= tasks; no second
CLI authority or fallback route is permitted.

The language facade MUST NOT advertise =check= or =evidence= as standalone
commands.  Language-owned policy verification belongs to build and CI APIs,
not the Runtime request catalog.  A language provider publishes syntax,
parser-owned facts, and typed projections into the immutable Runtime
generation; it does not construct or analyze an Evidence Graph.  Ascent and
GQL consume those generation-bound facts and own Evidence Graph derivation.
The resulting graph, graph facts, and receipts remain typed Runtime data, but
their data semantics do not create an =asp <language> evidence= command.
Help output and removed-command handling MUST be derived from this boundary
rather than preserving the former one-shot provider command menu.

** Cross-process Runtime readiness contract

The supervisor pre-binds one per-owner Tokio =UnixDatagram= readiness sink
before spawning the detached daemon.  The daemon publishes typed
=Starting=, =Ready=, =Failed=, or =Cancelled= receipts to that sink.  The
datagram is only a bounded notification channel: in-process status remains the
Runtime Server's =watch= authority, and the parent accepts a readiness event
only when it matches the current owner and endpoint binding.  The parent waits
on the readiness datagram or the owner terminal event; it MUST NOT poll files,
use a 30-second readiness deadline, or run a 10ms probe loop.

Every readiness receipt binds =requestId=, =readinessToken=, =processId=,
=ownerEpoch=, =endpointBindingToken=, =runtimeBinaryIdentity=,
=artifactCatalogDigest=, and =transportContractDigest=.  Stale epoch,
token, process, artifact, or endpoint messages are typed ignored evidence.
The central Schema Manager owns
=agent.semantic-protocols.runtime-server-readiness=, Schema Version 1;
language packages MUST materialize this schema and MUST NOT copy or redefine
it.

For every Ready gRPC =search=, =query=, and =search.owner= request, the
acceptance gate is warm p50 <= 250 microseconds, p99 <= 700 microseconds, and
hard max < 1000 microseconds.  A non-Ready typed admission response has the
same hard max.  Startup, provider build, and generation admission are separate
measurements and MUST NOT block or count as query latency.  Receipts record
gRPC codec, catalog/generation gate, Tokio mpsc/oneshot, resident engine,
and response-serialization segments; the 300 microsecond headroom is part of
the contract.  No timeout is used to implement this SLA.

Live Corpus qualification records the same boundary as an executable contract.
For a Ready session the only admitted effects are =mpsc=, =oneshot=, =cancel=,
and =response=.  Process creation, compilation, filesystem preparation, database
writes, generation mutation, provider activation, and control polling are
forbidden Ready effects and are measured outside the Search/Query distribution.
The Version 1 plan and receipt both bind one initialization per session, zero
non-Ready dispatches, zero residual tasks, p50 <= 250 microseconds, p99 <= 700
microseconds, and max <= 1000 microseconds.  A decoder that omits any of these
fields is contract drift and fails qualification; removing the field from the
plan or treating build time as Runtime latency is not a repair.

=agent-semantic-client= or on any ASP language provider.

The =agent-semantic-client= package is only CLI composition, parser, command
facade, and renderer ownership.  It MUST NOT own the Runtime daemon, transport
session, durable workspace database, provider transport, Search compute, or a
second Runtime client facade.  Until the runtime-server package extraction is complete,
the existing server modules remain a tracked Batch gate; each extraction batch
must move the module and strengthen the authority test before deleting its
protocol wrapper.

** Development installation authority

The Runtime invoker is fail-closed: a source/current executable whose identity
does not equal the active candidate MUST NOT spawn the stable Runtime path.  The
typed repair is =asp install binary=; there is no silent fallback to an older
binary.  The transition is candidate -> readiness -> healthy.  If readiness or
health qualification fails, the previous healthy artifact remains authoritative.

Provider source selection belongs to State Home, not to the install command's
current directory.  =ASP_STATE_HOME= owns the committed development source
registry.  An entry binds language ID, provider ID, absolute source root,
provider manifest digest, and the provider-owned workspace-install descriptor.

=asp install language <language>= MUST consult that registry before release
resolution.  When a valid development entry exists it executes the declared
provider-owned workspace install from that source root and atomically publishes
the resulting artifact and activation receipts.  It MUST NOT contact a release
registry, accept a path fallback, or fall through to a pinned release after a
development build failure.

Only a language without a committed development entry is eligible for the
pinned-release path.  =--project= is not a provider source selector and MUST NOT
participate in installation authority.  Project-local activation, when
supported, consumes the already installed canonical provider artifact; it does
not choose or rebuild provider source.

The lifecycle is:

#+begin_example
Declared -> Starting -> Warming -> Ready -> Draining -> Stopped
                                  \-> Failed
#+end_example

=Ready= binds the installed artifact digest, manifest digest, runtime contract
digest, endpoint identity, health generation, and supported operations. Queries
subscribe to the committed receipt. Starting or warming returns a typed
=asp-client-server-not-ready= result immediately; a query never starts or warms a
language runtime.

* ASP Client Server contract

Every server-capable implementation under =languages/*-harness= implements the
same =agent.semantic-protocols.asp-client-server= schema family. Descriptor,
bootstrap, lifecycle, request, response, error, and shutdown packets use the
=asp-client-server= namespace; a ASP language provider must not mint a private server
schema family.

* ASP Client Protocol ecosystem

The southbound =ProviderSession= stream is an internal fact-publication
transport between ASP Server and one admitted language provider.  Downstream tools use the separate
=agent.semantic-protocols.client= protocol and never connect to provider
endpoints.  The client protocol is schema-first and transport-neutral.  Its
published catalog declares protocol identity, server capabilities, admitted
semantic methods, request and response schema identities, typed errors,
cancellation behavior, streaming behavior, typed parameter slots, and the active
workspace generation.  Parameter slots are executable admission rules rather
than documentation: unknown parameters, missing required values, type drift,
and client-supplied RuntimeContext fail closed.

An ASP client follows a closed lifecycle: =initialize=, capability negotiation,
semantic requests or notifications, request-scoped cancellation, =shutdown=,
and =exit=.  Unlike LSP, client initialization does not discover or start a
language process.  It negotiates only client-visible capabilities against the
already admitted ASP Server catalog.  A method missing from that immutable
catalog fails closed.  Dynamic provider activation changes the server catalog
by an atomic generation publication; it never mutates an established catalog
in place.  Initialization binds one =sessionId= to one =workspaceIdentity=;
subsequent frames cannot cross that isolation boundary.

The catalog and provider-process lifecycle are distinct authorities.  A
content-addressed provider installation publishes one complete capability
descriptor.  ASP Server validates that descriptor against the built-in
provider identity constraint and retains it across Runtime owner handoff.  The
descriptor, workspace language evidence, and Ready workspace generation form
the immutable catalog input.  Whether a provider session actor is absent,
starting, ready, draining, or stopped MUST NOT remove a Server-local
=search=, =query=, or =search.owner= method from that catalog.

Provider session actors are workspace-and-language scoped producers of native
semantic facts.  Extension and project-resolution events submit lazy
activation intents to the sole Runtime Tokio supervisor.  Activation,
cancellation, and drain update the provider-session state machine; they do not
mutate installed capability identity and they never run in client
=initialize= or a Ready query hot path.  The implementation MUST NOT use one
"live provider register" as both capability catalog and process-liveness
registry.

The canonical northbound binding is one persistent Tonic gRPC =ClientFrame=
stream.  An optional loopback HTTP/JSON adapter MAY encode the same frames for
debugging and interoperability, but it is stateless, is not a second protocol
authority, and is excluded from the production Ready path.  Direct service-core,
gRPC, and optional HTTP projections validate the same schema identities and
produce byte-equivalent semantic payloads and the same terminal receipt.
Generated Rust, TypeScript, Python, Julia, Gerbil, DSL, or future-language
clients contain only codecs and session calls; they do not contain Search,
Merkle, cache, graph, ranking, or admission logic.  The language-neutral conformance suite is an
executable protocol asset: every client implementation runs the same lifecycle,
generation, unknown-method, parameter, cancellation, and isolation vectors.

Clients cannot launch, warm, restart, drain, or stop providers; select a
provider-private transport; inspect provider argv or environment; publish a
workspace generation; or bypass schema validation.  Cancellation is scoped to
one client session and request identity.  Concurrent clients have isolated
request namespaces, budgets, event cursors, and caches while sharing immutable
server generations and content-addressed facts.

* Schema bundle authority

The Rust Schema Manager and Runtime Server are the only authorities that
resolve, verify, cache, materialize, and publish schema bundles.  The public
surface is the transport-neutral =asp.schema.bundle= method carried as a typed
=ClientFrame= on the existing Runtime gRPC service.  A request selects one
registered profile by its exact =languageId= and =rootSetIds= and may carry
=knownBundleDigest=.  The registry has no =profileId= and the route does not
invent one.  Its profile receipt is exactly ={languageId, rootSetIds,
bundleDigest}=.  Every separate entry binds =familyId=, =schemaId=,
=schemaVersion=, =name=, and =digest=; each returned document repeats the entry
identity and digest.  The Version 1 response is =ready= with canonical receipt,
sorted entries, digest, and schema documents; =unchanged= with the same
canonical receipt and entries; or a typed =failed= terminal.

A declarative language profile names root schemas and provider-owned schemas.
SchemaManager resolves the full reference closure and validates the closed
catalog.  Its =materialize=, =verify=, and =publish-client= commands remain thin
offline build adapters over that same authority.  They may package a generated
wheel or SDK artifact, but they do not create a second transport or a
language-local schema protocol.

The Manager may remove only a stale file named by its previous receipt and
never deletes or overwrites a provider-owned schema.  Language clients do not
read receipt files, enumerate root sets, or verify content digests.  Rust,
Python, Gerbil Scheme, and every future client consume the shared route/API;
adding a language requires one profile declaration and conformance fixtures,
not a language-specific parser, copier, verifier, or ASP Server branch.

* gRPC transport and transport ablation

ASP clients use one persistent, multiplexed Tonic gRPC connection to the
Runtime-owned =ClientFrame= service.  The Runtime is the only listener owner;
clients connect and never bind a socket.  The connection carries initialize,
ensure-ready, request, cancellation, shutdown, and exactly-one terminal frames.
Session state is keyed by =(workspaceIdentity, sessionId)=, and the session
admission lock is released before semantic dispatch so cancellation and other
isolated sessions remain routable while a request is running.

The service-core API below Tonic is the semantic baseline.  Removing gRPC in an
in-process benchmark, or adding the optional HTTP/JSON debug adapter, MUST NOT
change planning, generation selection, cache keys, result ordering, or terminal
state.  The ablation receipt reports =serviceCoreNs=, =grpcCodecNs=,
=grpcTransportNs=, and optional =httpAdapterNs= separately.  A transport may
encode/decode frames and enforce body or message limits; it may not discover a
provider, build an index, select a cache, retry a request, or synthesize a
terminal.

The ASP authority allocates and publishes the endpoint only after the installed
artifact, catalog, and health identities agree.  Queries consume that immutable
binding.  Transport health is observed outside the query path and is not
workspace-generation readiness.

Julia, Python, Gerbil Scheme, TypeScript, and future languages do not implement
private request servers.  Their managed ProviderSession clients publish typed
facts during cold/write phases; package loading and fact construction complete
before readiness.  No framed-stdio or one-shot provider command is a production
route.

* OpenTelemetry

Every transition and request emits provider, language, artifact, contract,
endpoint-generation, and lifecycle-attempt attributes. Required measurements are
startup and warm-up duration, health latency, request latency, active requests,
typed failures, cancellations, restarts, shutdown duration, and leaked-task count.
Telemetry is observational and never controls readiness.

* Provider workspace toolchain isolation

Provider workspace dependency materialization and build commands execute only
through the shared Tokio provider-process supervisor.  Their Version 1
descriptor may declare exact inherited variables in =removeEnv= and bounded
variable families in =removeEnvPrefixes=.  The provider transport removes
those values before applying the descriptor-owned =env= map and spawning the
single supervised process group.  Empty or malformed identities and duplicate
entries fail closed.

This is one transport capability, not a provider shell wrapper or a second
build authority.  A provider selects only the isolation required by its native
toolchain; for example, a Homebrew Gerbil/Gambit build removes inherited Nix C
toolchain variables instead of mixing SDK headers and flags.  Cancellation,
descendant cleanup, memory accounting, and single-writer artifact publication
remain owned by the same supervisor and Runtime artifact guard.

Dependency materialization, compilation, linking, artifact publication,
provider activation, and Ready-generation admission are preparation evidence.
Their durations are reported separately and MUST NOT be included in Runtime
=search= or =query= latency distributions.

* Shutdown and failure

Shutdown closes admission, drains accepted requests, asks the server to stop,
waits for the child, and aborts only after the typed drain deadline owned by the
Runtime Server. Dropped request receivers cancel their queued work. Closing the
command channel terminates the writer task. Restart creates a new endpoint
generation; receipts from an older generation are never reusable.

* Acceptance

Acceptance MUST prove invoker-active identity, readiness generation equality,
and preservation of the prior healthy slot after a failed candidate.  The
receipt records structured source and active executable identities so these
checks do not require re-reading the binary contents.

- 256 concurrent requests share one server and one startup attempt.
- Starting and Warming are returned without blocking the caller.
- Ready requests perform no process creation, package loading, or filesystem
  discovery.
- cancellation, closed channel, repeated publication epoch, clean shutdown, and
  zero residual task behavior are deterministic Tokio tests.
- Julia ProviderSession registration, fact publication, malformed frame,
  cancellation, drain, and shutdown are exercised against the native artifact.
- warm request p99 is measured independently from server startup and warm-up.
- Rust Schema Manager materialize followed by verify is deterministic, offline,
  atomic, and leaves provider-owned schemas untouched.
- Rust, TypeScript, Python, Julia, Gerbil, and one fixture DSL consume the same
  client catalog and pass initialize, request, cancellation, unknown-method,
  generation-drift, shutdown, and trace-context conformance scenarios.

** Hot Path Architecture and proof obligations

The ASP Client data plane has one transport architecture: a persistent,
multiplexed Tonic/Tokio gRPC connection over HTTP/2.  HTTP/2 multiplexing is a
transport property, not a second client/server authority.
Initialize and catalog validation happen once per workspace/session; the
validated immutable catalog, route bindings, endpoint binding, and Ready
generation are retained by that session.

Each warm =search=, =query=, or =search.owner= request then performs exactly
one typed request on that connection.  It MUST NOT read the endpoint file,
discover a candidate, build or admit a generation, activate or await a
provider, perform a second transport hop, or revalidate the immutable catalog.
=asp.workspace.generation.ensure-ready= is the distinct server-owned cold
preflight that establishes this invariant once per client connection.  It may
join one in-flight complete-generation attempt; it is not part of the warm
Search/Query latency distribution and is never implemented by retrying the
language request.
Bounded =mpsc=, =oneshot=, and typed cancellation remain the only request
coordination primitives.  Non-Ready admission returns immediately with its
typed state and the same hard latency bound; startup, provider activation, and
generation publication are separate measurements and never block or count as
query latency.

The warm acceptance budget is p50 <= 250 microseconds, p99 <= 700
microseconds, and hard max < 1000 microseconds.  Telemetry records separate
gRPC codec, catalog/generation gate, Tokio mpsc/oneshot, resident engine, and
response serialization segments, preserving at least 300 microseconds of
headroom.  No timeout implements this SLA.

Lean obligations model a =ReadyEffects= projection and prove it excludes
=Process=, =Filesystem=, =DbWrite=, =GenerationMutation=,
=ProviderActivation=, and =ControlPoll=.  Scenario and Live Corpus acceptance
must both exercise the same persistent client session and verify these effects,
the segment telemetry, the non-Ready immediate response, and the same
initialize/catalog/request/cancel/shutdown contract across every language.

Live Corpus admission resolves =sourceInventory=, routes, and provider identity
from the Runtime provider-plane snapshot for the active generation.  The
compile-time provider identity register is not a capability authority and MUST
NOT be used to materialize or qualify a corpus.  Missing Runtime registration,
generation conflict, or missing provider-owned inventory fails closed with the
provider-plane receipt.

An explicitly targeted =(languageId, providerId)= corpus invokes that
provider's declared project-resolution capability after locked-revision and
language-extension admission.  Project entry markers are discovery hints for
untargeted CompleteGeneration scans; they are not a second admission gate for
an explicit provider target.  The Runtime MUST NOT mutate an upstream corpus
or invent a provider-specific marker merely to satisfy auto-discovery.

** Southbound ProviderSession stream contract

The public northbound Tonic gRPC =ClientFrame= service is the production
transport.  An HTTP/JSON catalog surface, when built, is a stateless debug
adapter only.  The sole
southbound business authority is =RuntimeStreamService=, whose admitted
provider session is a bidirectional Tokio stream represented by the canonical
=ProviderSession= contract in =crates/agent-semantic-runtime-server/proto/asp-provider-stream.proto=.  Its
wire implementation will use Tonic; the proto and Schema Manager remain the
central authority, and language directories contain only managed materialized
copies.

Ready =search=, =query=, and =search.owner= are Runtime-local operations over
the immutable Ready generation and MUST NOT take a provider-stream or second
HTTP hop.  Activation, generation admission, provider facts/capabilities,
cancellation, and drain use the ProviderSession stream.  Provider HTTP health,
request, and shutdown operations MUST NOT exist; no HTTP fallback or parallel
authority is permitted.

The Runtime daemon MUST bind the canonical provider-plane Unix socket before
publishing Ready, serve =ProviderSession= from the same
=RuntimeServerTaskScope= as the northbound adapter and resident generation
owner, and drain it through the same typed shutdown signal.  A proto service or
loopback test that is not mounted by the daemon is not an admitted transport.
The provider-plane socket path published by the Runtime endpoint is the sole
local authority; a second TCP listener, provider HTTP listener, or CLI process
route is forbidden.

** Rank before parser-owned selector projection

The resident Search route MUST preserve the complete bounded lexical candidate
count as receipt evidence while applying expensive parser-owned selector
projection only after the immutable generation graph has ranked the frontier.
The v1 ranked-owner projection budget is 16 owners per request.  The receipt's
=candidateCount= remains the full lexical candidate count; it MUST NOT be
rewritten to the projection count.

When graph ranking is available, the Runtime projects the first 16 distinct
ranked owner paths.  When the operation does not admit graph ranking, it uses
the first 16 distinct lexical owners in deterministic resident order.  Both
paths remain bound to the same workspace generation.  This ordering prevents a
100-candidate lexical read from forcing 100 owner-catalog walks before ranking.

The projection budget is protocol-visible work control, not a hidden cache and
not a provider-private heuristic.  It does not authorize filesystem reads,
provider RPC, database reopen, client retry, or a second search authority.
Changing the lexical candidate budget, ranked projection budget, or fallback
ordering requires the RFC/schema/Lean path before provider implementation.

The generation-bound resident query cache stores one immutable shared result.
A warm hit clones only the shared handle; it MUST NOT deep-clone the bounded
hit payload or its lexical query-key vectors.  The shared value cannot outlive
or cross its resident generation because the generation owns both the cache and
the mmap authority.  Publication creates a new generation and therefore a new
cache; no invalidation heuristic or background cache clearing participates in
request-time correctness.

** Bounded northbound response partitions

The bidirectional gRPC session is a stream of bounded envelopes.  It is not a
license to encode an arbitrarily large logical response in one protobuf
message.  Every encoded =ClientFrame= that exceeds the fixed envelope budget
MUST be split into ordered response partitions on the existing session.  Each
partition carries the original request identity, zero-based index, total
partition count, the digest of the complete encoded response, and bounded
bytes.  The client admits one terminal only after all partitions are present,
ordered, within the declared count and byte budgets, and the reconstructed
digest matches.  Duplicate, missing, conflicting, cross-request, oversized,
or digest-mismatched partitions fail closed and never mutate the Ready
generation.

The envelope budget is a protocol constant shared by server and client; it is
not a global flag.  Increasing Tonic's process-wide decoding limit is rejected
because it merely moves the failure threshold, permits unbounded per-session
memory, and gives different clients different acceptance semantics.  The
partition accumulator has both a per-response encoded-byte ceiling and the
existing session cap of 32, and is removed on terminal, cancellation, stream
failure, or disconnect.  Small warm responses remain one envelope and do not
pay partition allocation or hashing costs.  Large cold/source projections use
the same multiplexed Tokio stream and remain outside warm Search/Query latency
budgets.

** Northbound route intent contract

Northbound =search=, =query=, and =search.owner= requests carry user intent
only: language identity, scope/owner intent, and route-specific query fields.
They MUST NOT carry runtime-owned generation, source, parser, provider, catalog,
or artifact identities. The Runtime Server resolves those identities from the
validated session catalog and immutable Ready generation. Provider-native DTOs
are internal server/provider contracts and are not northbound inputs. Non-Ready
sessions return a typed admission response without consulting a prior generation
or invoking a provider.

** Scheme structural-index boundary

The Gerbil Scheme provider's =semantic-structural-index= packet is a
provider-local parser/interface format.  It is not a Graph-Turbo request, does
not declare =asp-python-graphs= as an owner or consumer, and does not create a
second ranking authority.  ASP Server treats it as a Scheme-provider output;
it is not a cross-language Rust or Python service contract.  Graph-Turbo
algorithm packets use their separate =asp-python-graphs= service contract.
No structural-index field may infer a Graph-Turbo service dependency from the
fact that both paths use the ASP Server.

** Resident graph evaluation hard cut

The legacy northbound =asp.graphs.evaluate= method is rejected architecture.
It accepts client-supplied graph, source-snapshot, workspace-generation, and
algorithm identities and may open an =asp-python-graphs= generation during a
Ready Search request.  That design creates a second generation authority,
makes client input authoritative over Runtime state, and adds provider RPC,
Python scheduling, and lease mutation to the sub-millisecond read path.

The replacement method is =asp.graph.evaluate=.  Its V1 request carries only
intent: language identity, Search surface, normalized query terms, optional
seed identifiers, and a bounded traversal budget.  It never carries graph
bytes, source-snapshot identity, workspace-generation identity, provider
identity, or an algorithm selector.  The Runtime Server resolves the exact
workspace/generation binding from the admitted session and evaluates the
immutable resident graph through the shared Rust Search compute core.  Its
Ready result returns that resolved binding and bounded work counters.  In
particular, =providerRpcCount=, =durableReadCount=, and
=generationMutationCount= are exactly zero.

=asp-python-graphs= remains a cold-plane artifact producer and an explicitly
requested offline-analysis service.  It may compute graph artifacts before a
CompleteGeneration publication, but it cannot serve =search=, =query=,
=search.owner=, or =asp.graph.evaluate=, and it cannot own a resident cache.
There is no alias or compatibility route from =asp.graphs.evaluate= to
=asp.graph.evaluate=; old callers fail as an unknown method and must migrate to
the intent-only contract.

Runtime-source acquisition is a separate ASP Runtime cache contract.  Its
wire-level =indexOwner= is =asp-server=: the Runtime Server owns source-index
generation, persistence, lookup, and runtime-source checkout admission.  The
embedded DB engine may remain the implementation/provider provenance (for
example =db-engine-source-index=) inside that server, but it is not a second
protocol authority and it is not a Scheme structural-index provider, Rust
provider, or Graph-Turbo service.  Provider guide output must therefore invoke
the Runtime cache without an obsolete =--index-owner= override.
