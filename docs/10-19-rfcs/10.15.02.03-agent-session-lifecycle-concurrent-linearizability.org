#+title: RFC 10.15.02.03 — Agent Session Lifecycle Concurrent Linearizability

* Status
Focused formal verification is complete. This RFC refines [[file:10.15.02.02-agent-session-lifecycle-crash-recovery.org][RFC 10.15.02.02]]. The Lean source, compiled module, direct audit, and runner pass; all 19 theorem declarations are axiom-free. No Rust implementation is authorized in this session.

* Problem
Two main-session controllers, duplicated Hook deliveries, or restarted processes may read the same lifecycle snapshot and race to claim one intent. The same race exists when indexing a host receipt, binding a child generation, and ingesting terminal command completion.

Process-local mutexes cannot establish correctness across restart or multiple controllers. Linearization authority belongs to the durable revisioned ledger.

Lean constructs a two-winner counterexample when ordinary writes are admitted: two controllers can share slot, generation, intent key, and commit revision while carrying different controller identities. Therefore winner uniqueness is an explicit CAS/log property, not a consequence of stable keys alone.

* Intent-claim linearization
For one slot, generation, intent key, and commit revision, a linearizable claim log contains one complete commit record. Consequently controller identity and payload digest are unique.

#+name: agent-session-linearizable-claim
#+begin_src typst
#let In(c, l) = $c in l$
#let SameId(a, b) = $upright("sameIntentRevision")(a, b)$
#let Controller(c) = $upright("controllerId")(c)$
#let Payload(c) = $upright("payloadDigest")(c)$
$
  forall l, a, b,
  upright("LinearizableClaimLog")(l) and In(a, l) and In(b, l) and SameId(a, b)
  => Controller(a) = Controller(b) and Payload(a) = Payload(b).
$
#+end_src

* Non-atomic counterexample
Stable keys without CAS do not prevent two winners. This formula is constructively inhabited by the Lean model.

#+name: agent-session-non-atomic-two-winner
#+begin_src typst
#let SameId(a, b) = $upright("sameIntentRevision")(a, b)$
#let Controller(c) = $upright("controllerId")(c)$
$
  exists a, b,
  SameId(a, b) and Controller(a) != Controller(b).
$
$
  upright("LinearizableClaimLog") =>
  not exists a, b, SameId(a, b) and Controller(a) != Controller(b).
$
#+end_src

* Ledger-wide uniqueness
The receipt index admits one payload and effect identity per intent. The binding ledger admits one child and target per slot generation. The terminal ledger admits one command and effect per dispatch identity.

#+name: agent-session-linearizable-ledgers
#+begin_src typst
#let SameIntent(a, b) = $upright("sameIntent")(a, b)$
#let SameGeneration(a, b) = $upright("sameSlotGeneration")(a, b)$
#let SameDispatch(a, b) = $upright("sameDispatch")(a, b)$
$
  SameIntent(a, b) => upright("effect")(a) = upright("effect")(b).
$
$
  SameGeneration(x, y) => upright("child")(x) = upright("child")(y)
    and upright("target")(x) = upright("target")(y).
$
$
  SameDispatch(p, q) => upright("command")(p) = upright("command")(q)
    and upright("effect")(p) = upright("effect")(q).
$
#+end_src

* Linearization order
Claim, host-receipt index, and binding commit have distinct increasing durable revisions. A binding may not precede the claim whose intent authorized it.

#+name: agent-session-linearization-order
#+begin_src typst
#let Claim(o) = $upright("claimRevision")(o)$
#let Receipt(o) = $upright("receiptRevision")(o)$
#let Binding(o) = $upright("bindingRevision")(o)$
$
  forall o,
  Claim(o) < Receipt(o) and Receipt(o) < Binding(o)
  => Claim(o) < Binding(o).
$
#+end_src

* Lean-discovered corrections
1. Stable intent keys do not by themselves prevent two winners.
2. Winner uniqueness is a durable CAS/log invariant.
3. Losing controllers reuse a matching committed intent and never call the host again.
4. Same key with payload drift is a hard conflict.
5. Receipt, binding, and terminal ledgers need their own uniqueness constraints.
6. Claim revision strictly precedes receipt revision, which strictly precedes binding revision.
7. None of these guarantees rely on controller identity, process lifetime, or process-local locks.
