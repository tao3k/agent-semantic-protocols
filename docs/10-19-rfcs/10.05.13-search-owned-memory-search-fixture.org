#+title: Search-owned Turso Memory Search Fixture
#+startup: overview

* Status

Accepted v1 contract aligned with 10.05.69.

* Ownership

=agent-semantic-search= owns Memory Search resolution semantics, fixture
scenarios, and performance receipts.  Turso is the single runtime and fixture
search authority.  The fixture does not implement a generic backend, a Rust
map index, or a second generation model.

Protocol versions belong to schema filenames, =schemaId=, and
=schemaVersion: "1"=.  Rust domain types do not use =V1= suffixes.

* Production-shaped flow

#+begin_example
MemorySearchFixture
  -> source-index generation transaction
  -> WorkspaceDbRegistry resident session
  -> TursoMemorySearchBackend
  -> MemorySearchResolution
#+end_example

Fixture publication and runtime lookup are separate phases.  Publication uses
the production source-index transaction.  Lookup uses the same resident
workspace session and indexed Turso statement as installed ASP.

* Resolution contract

The backend returns exactly one typed outcome:

- =live-hit=
- =live-relocated=
- =ambiguous=
- =kind-mismatch=
- =missing=
- =generation-mismatch=

Identity is bound to workspace, active generation, language, provider, parser,
query pack, canonical item, and owner content digest.

* Provider boundary

Provider owner acquisition always publishes =complete-owner= projections.
User query text is not a provider acquisition input and is applied only by the
resident Turso consumer.  The same schema-owned provider method is available
to every registered language and is lazily loaded from the provider registry.

* Required scenarios

1. exact item remains in its owner;
2. item moves to one sibling owner;
3. two owners contain the same unscoped identity;
4. symbol survives with a different item kind;
5. generation changes after relocation;
6. empty generation with Merkle root depth zero;
7. concurrent readers share one resident generation;
8. nested project roots reuse one canonical workspace session;
9. every registered language either passes the owner-projection fixture or
   fails closed as an explicitly unsupported capability.

* Performance receipt

Every fixture and installed execution reports generation load latency, indexed
lookup latency, candidate count, source bytes, DB opens and queries, provider
processes, cache writes, and resolution state.

Warm lookup requires zero provider processes, zero source scans, zero database
opens, zero schema bootstraps, and zero writes.  Compile and bootstrap receipts
are measured separately from runtime lookup.
