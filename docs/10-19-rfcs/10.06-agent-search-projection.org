* Search projection summary

** Runtime cache ownership

Each language/provider identity owns one resident entry and one bounded
mailbox.  Concurrent admissions observe that entry's published lifecycle state
and enqueue through the same mailbox.  A separate single-flight map, waiter
registry, or query-owned lazy-start state machine is prohibited; this rule
supersedes older single-flight wording in this section.

ASP Server is the sole Tokio-owned =asp-client-server= lifecycle
authority.  Hook demand may request a language runtime only through the server
admission operation; extension identity MUST map to exactly one registered
language/provider identity before admission.  Concurrent requests for the same
identity MUST share one single-flight lazy start.  The server MUST retain a
reference-counted lease while demand exists and MUST close an idle runtime
after the lease/idle policy expires; close and restart are server-owned
terminal operations.

Lean owns the architecture-level counterexample model for this boundary.  The
model MUST prove that two admitted operations cannot observe one another's
overlay or cancellation state, that a cache hit implies equality of every
authority component, that partial publication is never readable, and that each
admitted or cancelled operation reaches at most one terminal receipt.  Schema
validation and Tokio scenario tests provide the concrete identity and event
witnesses consumed by those refinement claims.

Every admitted provider identity MUST equal =asp-= concatenated with the
request's canonical =languageId=.  Implementation artifact identity is carried
separately and cannot influence provider routing or cache equality.  A receipt
whose =providerId= does not derive from =languageId= is identity-invalid before
Runtime dispatch, even when the referenced binary or package exists.

Concurrent agent reads share immutable resident segments, never mutable
request state.  Each Tokio task owns its operation-local cancellation token,
deadline, result channel, telemetry span, and optional overlay identity.  Cache
keys include workspace identity, generation digest, source-root digest,
provider-catalog digest, language/provider identity, selector or query digest,
and projection kind.  A cache entry missing any authority component is invalid,
not a weak hit.  Publication is atomic; partial parser or graph generations are
not visible to query tasks.

Project understanding is syntax-granular and graph-complete rather than
document-oriented.  Owner/item selectors, exact source scopes, project
resolution, imports, calls, types, tests, and provider-owned relations retain
their provenance and completeness independently.  A client can fan out many
bounded reads against one generation and fan them into one evidence receipt;
it cannot infer whole-project absence from a partial parser, resolver, or
provider projection.

LSP-style capability negotiation is accepted only as an immutable admission
comparison between the client request and the catalog-published provider
contract.  Runtime clients cannot dynamically register methods or mutate a
Ready actor's capability set.  Cancellation is cooperative and operation
scoped, but it never abandons a response: the Tokio owner must publish exactly
one cancelled or completed terminal receipt.  Progress tokens belong to the
control and observability planes; they never reopen admission, extend a query
deadline, or enter ranking and result identity.

Every start, ready, query, failure, close, and restart emits one terminal
OpenTelemetry receipt carrying =operationId=, =extensionId=, =languageId=,
=providerId=, =workspaceIdentity=, =generationDigest=, =rootDigest=,
=transport=, and terminal status.  The CLI is an adapter and MUST NOT expose
provider process creation or transport details to the Hook.

*** Cold client first-result gate

Lifecycle, publication, and cancellation are Tokio-owned.  Once admission has
produced a Ready capability, the Tokio task executes search, owner-proof, and
exact-projection reads synchronously against the leased immutable mmap segment.
No Tokio channel, IPC round trip, timer, or scheduler handoff is part of the
measured resident read.  Scenario and Live Corpus qualification use the same
receipt and require zero provider, scheduler, filesystem, database, and socket
work.  Increasing a deadline cannot qualify a path that violates this boundary.

The primary search performance gate is a cold client reading an already
published generation.  A cold client is a newly started CLI or agent process
with no process-local Runtime connection, generation lease, or mmap handle.
It is not a workspace bootstrap and it does not authorize preparation work.

The first search request from that client MUST resolve the immutable Runtime
locator, connect to the existing Runtime Server, validate a nonzero active
generation capability, open or lease the published mmap generation, and read
the requested projection.  That path MUST NOT start or ensure the Runtime
Server, admit or rebuild a generation, wait for a generation builder, start a
language provider, open Turso, walk the workspace, acquire a publication lock,
repair activation, or retry through a local cache implementation.

If the Runtime endpoint, active capability, or published generation is absent,
the request MUST return an immediate typed terminal receipt.  Workspace
bootstrap and generation construction belong to an explicit control-plane
operation and MUST NOT be hidden inside search latency.

Warm-search measurements are secondary.  They measure reuse of the connection,
generation lease, mmap pages, and decoded table metadata only after the cold
client gate passes.  A warm result cannot qualify an implementation whose first
request performs synchronous preparation.

The cold-client gate records at least elapsed time, Runtime control roundtrips,
mmap opens, provider invocations, database opens by the client, workspace walks,
generation admissions, generation rebuilds, and fallback attempts.  Provider
invocations, client database opens, workspace walks, generation admissions,
generation rebuilds, and fallback attempts MUST all be zero for a query against
an already published generation.

*** Incremental Merkle generation boundary

=WorkspacePathMerkleTreeV1= is the canonical snapshot-identity and proof
algorithm for v1 generations.  Its sorted leaf array and pairwise level
construction require materializing the complete ordered leaf set; the presence
of an owner delta does not make v1 tree construction incremental.  Implementors
MUST NOT describe full v1 reconstruction or per-owner proof precomputation as
an incremental cache update.

A generation that promises work proportional to changed owners MUST use a new
versioned shared Merkle contract with stable path-addressed nodes, immutable
structural sharing, explicit base-generation and base-root preconditions, and a
typed successor root.  The new contract must be defined in shared schemas
before any provider implementation.  It may not silently change v1 root or
proof semantics.

The shared contracts are
=agent.semantic-protocols.workspace-path-merkle-tree.v1= and
=agent.semantic-protocols.workspace-merkle-delta.v1=.  The tree contract owns
the path-radix algorithm identity, generation/root binding, node-table digest,
and inclusion-proof shape.  The delta contract owns mutation idempotency,
base-generation and base-root compare-and-swap, typed upsert/remove operations,
the successor root, and touched/written/reused-node counters.  A successful
incremental delta records =fullMerkleRebuilds= as zero.  Incremental updates
are additive within this single v1 contract; they do not introduce a second
public schema version or a dual-read migration path.

Query code MUST NOT rebuild the v1 tree on a miss or fall back to Turso or
provider parsing.  An unsupported incremental capability returns a typed
fail-closed receipt.

The v1 incremental lifecycle is explicit: a query has no hidden build edge;
=WorkspaceGenerationDelta= is the mutation payload; =base_generation_digest=
is the compare-and-swap authority; and =PublishOwnerDeltaCommand= is the sole
writer entry point.  A rejected base digest MUST leave both the active pointer
and epoch unchanged.  A successful delta MUST publish exactly once and retain
the previous generation as readable while the new generation is admitted.

*** Merkle owner read plane

The canonical workspace Merkle tree is generation evidence and a resident
search index, not a client cache.  Generation publication MUST derive owner
leaf digests, owner-subtree digests, and inclusion proofs from the shared
=WorkspacePathMerkleTreeV1= contract.  Runtime code MUST NOT duplicate the
hashing algorithm or derive a second root from cache-private state.

The immutable search mmap segment MUST carry a sorted owner-to-proof index
bound to the same workspace root and generation digest as its generation
authority.  A warm owner proof read performs one bounded mmap lookup and MUST
NOT open Turso, start a provider, walk the workspace, reconstruct the Merkle
tree, or enqueue a generation rebuild.

The V1 generation carries two distinct typed identities: =sourceSnapshot.rootDigest=
commits the source snapshot representation, while =ownerMerkleRootDigest=
commits the canonical WorkspacePathMerkleTreeV1 owner-proof tree.  They MUST
not be interchanged.  Owner-proof readers verify against the latter; source
snapshot consumers verify against the former.

The public read contract is
=agent.semantic-protocols.runtime-merkle-owner-read-request= v1 and
=agent.semantic-protocols.runtime-merkle-owner-read-receipt= v1.  A hit
returns the source-blob digest, owner-subtree digest, and canonical inclusion
proof.  A miss remains bound to the requested owner path, generation digest,
and workspace root.  Proof validation failure is terminal generation
corruption; it MUST NOT fall back to a client-local scan or database lookup.

Owner upsert, tombstone, and relocation continue to enter through the existing
typed Runtime data-plane operations and the single resident writer.  They
publish one immutable successor generation and atomically replace the bounded
pointer.  Concurrent readers observe either the complete previous generation
or the complete successor generation.  Cache-control =invalidate= and
=rebuild-source-index= are not substitutes for owner-delta publication.

The schema-owned v1 mutation set also includes =apply-owner-delta=.  It carries non-empty
=changedPaths= or =removedPaths= plus a stable =mutationId=.  Its explicit =fallbackPolicy= is
either =fail-closed= or =full-generation=: the former returns a typed failure when incremental
application is unavailable, while the latter authorizes only the Runtime Server resident writer
to rebuild the complete generation.

Provider execution and agent-facing clients MUST NOT inspect, open, migrate, or write a
client-directory database or cache manifest.  They MUST NOT replay prompt-output or search-packet
artifacts from a client-owned cache.  Cache status and every cache mutation use the Runtime Server
v1 typed IPC action set; the resident generation is the only reusable search authority.

The legacy =asp cache migrate= command is removed.  Database format migration is an internal
Runtime Server owner responsibility and is never exposed as a client-side cache lifecycle.

When the required resident generation or capability is unavailable, the client returns the typed
Runtime Server failure unchanged.  It does not fall back to client-local replay, direct database
access, manifest reconstruction, or provider-private cache ownership.
Public programming-language search is a Runtime Server operation.  A language
facade MUST submit a typed provider-search request to the workspace Runtime
Server and render its typed receipt.  It MUST NOT instantiate a provider
backend or spawn a provider process in the CLI process.  Provider resolution,
generation admission, process execution, cache publication, timeout and
OpenTelemetry terminal events belong to one Tokio task owned by the Runtime
Server.

The provider-search request and receipt use disjoint versioned schemas.  The
request carries a typed query plan rather than forwarded argv.  The receipt
carries provider, catalog, generation and root identities plus the validated
search packet.  Raw provider stdout is transport evidence only and is never a
successful public response.  There is no local-backend compatibility mode.


Public exact-source query and derived search projection are separate typed
operations, even when one language facade dispatches both.  A
=--projection source= request resolves one parser-owned selector and returns
source bytes with typed source authority.  A =--projection callable-skeleton=
request selects the derived-projection contract directly; it is never a
fallback for unavailable source and cannot widen its admitted generation.

Providers produce the complete inline callable-skeleton authority envelope.
Runtime validates that envelope before generation publication, interns its
generation, parser, query-pack, provider, and language identity into one
immutable evidence context, and publishes the compact projection plus the
evidence context in the same generation mmap.  Agent-facing clients receive
one canonical root selector and an =evidenceContextRef=; they do not receive
per-node authority copies or repeat the complete selector identity AST.

Both inline and referenced encodings remain schema version =1=.  Inline is the
provider-to-Runtime admission encoding.  Referenced is the Runtime-to-agent
resident encoding.  The reference is content-addressed and resolves only
inside the same admitted immutable generation.  A missing, mismatched, or
cross-generation reference is typed generation corruption and MUST NOT fall
back to a client database, provider execution, source read, or identity
reconstruction.

The protocol remains schema version =1= while Runtime-internal mmap layouts
carry their own independently evolving layout identity.  Adding the evidence
context catalog changes that internal identity.  Runtime MUST classify an
older exact-projection layout as =RecoveryRequired= before reporting the
workspace generation Ready, then republish the complete generation from its
canonical durable materialization.  A decoder MUST NOT infer layout
compatibility from the public schema version or reinterpret table bytes added
by a later layout.

The root node inherits =rootSelector=.  A descendant node may carry a
packet-local selector reference beginning with =$root=; clients resolve it by
concatenation with the canonical root selector.  The full selector string MUST
appear only once in a root-only packet.  Runtime publication, not presentation
rendering, removes redundant authority data, so JSON and compact text views
consume the same referenced resident payload.

Exact-source requests and derived-projection requests use disjoint request and
response schemas; a component receiving the wrong schema fails closed before
rendering or caching the payload.

Recommended next work is a typed action owned by the Runtime Server.  Free-form
command strings are not protocol authority and must not cross the Runtime,
CLI, Hook, or agent boundary.

Every agent-facing =search= response carries a typed decision graph feature:
schema-owned semantic graph facts are projected into role-typed aliases,
grouped relation edges, a legend-declared search root, algorithm-owned rank,
inline next actions, exact locators, and explicit omission/avoidance facts.

** Provider-scoped incremental generation projection

*** Exact projection scope and observability

Exact selector resolution MUST execute inside the Runtime Server data plane as
one typed operation: generation read, cache lookup, provider-owner repair,
selector relocation, overlay rebind, and terminal receipt publication.  The
CLI and protocol adapter MUST NOT reproduce that sequence or classify misses.

Every exact-projection span and terminal receipt MUST identify the requested
selector, resolved selector when present, language/provider identity,
projection kind, admitted projection scope, active generation and root
digests, owner/source digest, provider catalog and executable digests, cache
state, relocation state, and a typed terminal reason.  A selector excluded
from the admitted production scope (for example a =cfg(test)= item when no
all-targets generation is admitted) is =projection-scope-omitted=; it is not
=owner-missing= and MUST NOT be reported as cache corruption.

Production, test/all-targets, and live-corpus projections are separate
admission scopes.  A query MUST name or inherit exactly one admitted scope;
Runtime MUST never silently widen scope, rebuild a generation, or clean cache
to satisfy an exact miss.  OpenTelemetry export is derived from the same typed
receipt, so diagnostic text, metrics, traces, and Runtime behavior cannot
disagree about the cause.
*** RuntimeServer-centered cache authority
Fallback release transfer MUST be one-shot. Before =Drop= schedules a Tokio
cleanup task, it MUST mark the transferred guard so cancellation during runtime
teardown cannot re-enter =Drop= and recursively schedule another cleanup task.
Cancellation before the cleanup future's first poll MUST fail closed and leave
stale recovery to the next canonical owner.


Resident lifecycle I/O MUST be Tokio-owned. Singleton socket acquisition, liveness
probing, stale recovery, endpoint adoption handshakes, and normal release MUST use
async Tokio tasks with explicit deadlines and cancellation propagation. Blocking
=std::net= or =std::fs= operations MUST NOT execute on core RuntimeServer worker
threads. The normal shutdown path MUST await socket release and inode-checked
cleanup; =Drop= is only a fail-safe scheduling boundary and MUST NOT be the primary
lifecycle protocol. A timed-out or cancelled probe MUST fail closed without
unlinking a possibly live socket.

RuntimeServer ownership is state-home scoped and executable-authoritative. When a
state home publishes a canonical =runtime/bin/asp=, only an executable resolving to
that canonical binary may acquire the resident election and lifetime singleton
socket for that state home. Debug and test daemons MUST use an explicitly isolated
=ASP_STATE_HOME= and MUST fail closed before binding production resident sockets.
The singleton listener establishes lifetime ownership, not service readiness:
successful resident adoption additionally requires a healthy endpoint handshake
whose owner epoch and binding token identify the same resident. A workspace
generation rebuild, invalidation, staleness, or admission failure is workspace
scoped and MUST NOT place the global RuntimeServer in =draining= or close unrelated
workspace-owner endpoints; global draining is reserved for explicit supervisor
replacement or runtime artifact transition.
The Runtime Server is the sole live owner of cache admission, source-index generations,
Turso connections, MVCC publication, and the resident writer queue.  Agent-facing
=asp cache= commands are typed IPC adapters only; they MUST NOT open =facts.turso=,
bootstrap or migrate a client database, publish a second local-cache generation, or
take ownership from the resident server.

Warm validation and cold construction are internal Runtime writer-lane actions.
They enter the same RuntimeServer admission and atomic publication queue and
return typed internal receipts containing admitted generation identity and cache
provenance.  They are not public Agent-facing cache commands and do not create
an alternate CLI-side lifecycle.

When RuntimeServer admission =Failed= is projected as =Stale=, the typed cache-control
receipt MUST carry non-empty failure provenance owned by RuntimeServer.  Client code
MUST NOT generate, synthesize, or overwrite that provenance.

The v1 cache authority is the resident RuntimeServer, not the CLI process.  The server
owns both the active in-memory generation lease and the durable canonical generation.
Healthcheck MUST project these two server-owned states as one coherent cache view: an
active Ready lease MUST NOT be reported as Missing merely because no durability
transition receipt is present.

One state home MUST have exactly one resident RuntimeServer.  The daemon MUST hold a
stable Unix singleton socket for its complete lifetime in addition to the existing
election guard and transport sockets.  Endpoint JSON is discovery metadata and MUST
NOT be treated as the lock.  A later launcher that cannot bind the singleton socket
MUST adopt or connect to the resident owner and exit without starting another server.
It MUST NOT unlink a live singleton socket.  Stale socket recovery is permitted only
while holding the election guard and after a kernel connection probe proves that no
listener owns the socket.

=status= remains read-only.  Runtime recovery may re-admit a compatible durable
canonical generation as an active lease without a cold rebuild.  Only incompatible
cache identity, absent canonical materialization, or a Runtime-owned query-demand
admission permits cold construction.

Incremental cache work is internal to the resident server.  Changed and removed owner
sets are coalesced by the existing writer queue under one stable =mutationId=, applied
to syntax, source-index, EvidenceGraph, and query projections, and then published as
one atomic generation.  Tree-sitter remains one public query surface; incremental is
an internal execution strategy and MUST NOT become a sibling public result or trace.
When an incremental delta cannot preserve cache identity or atomic publication, the
server MUST fail closed or perform an explicit full-generation fallback and expose
that fallback in its typed receipt.

The public v1 cache-control action set is =status= and explicitly scoped
=invalidate=; source-index lookup remains a read projection.  =status= is
read-only.  Every mutation carries a stable =mutationId= and is serialized by
the resident writer queue.  Import, refresh, rebuild, and flush aliases are not
public recovery routes.  Runtime may retain private writer commands for the
same work, but they cannot be emitted as an Agent next action or parsed as a
client-owned cache lifecycle.

A direct CLI database open that fails because the RuntimeServer holds the Turso lock is
not a recoverable operating mode; it is a conformance counterexample proving that cache
authority escaped the server boundary.  Stopping the RuntimeServer to make such a CLI
path succeed MUST NOT be used as the normal repair.

*** Single Tree-sitter public surface
Tree-sitter owns the single public query and result projection.  Incremental parsing,
generation acquisition, refresh, and reuse are internal execution properties of that
Tree-sitter query.  =incremental= MUST NOT identify a sibling mode, result type,
renderer, trace set, terminal state, or next action.


The merge boundary is the query-result state model, not the presentation
layer.  The provider MUST first combine parser matches, incremental admission
state, counters, continuation, and terminal status into one result.  Exactly
one renderer then projects that result.  Implementations MUST NOT render a
Tree-sitter summary and an incremental summary independently and join the two
strings, even when the joined text happens to contain only one visible trace
header.

Tree-sitter and incremental execution are orthogonal dimensions of one search
projection.  =tree-sitter= identifies the parser/query backend;
=incremental= identifies how that backend acquires and refreshes its admitted
generation.  One invocation MUST mint exactly one =traceSetId= and emit exactly
one agent-facing receipt.  Incremental inventory, cache decisions, mutation
counters, and completeness are nested execution evidence of the Tree-sitter
result; they are not a second search result or a sibling trace set.  The
compact/default renderer MUST NOT emit both a =[search-treesitter]= block and a
separate =[query-treesitter-incremental]= block for the same request.  It emits
one merged terminal state and one =recommendedNext= action.  Explicit debug
projection MAY retain backend subtraces, but every subtrace references the same
=traceSetId= and cannot independently emit a terminal state or next action.
Deduplication is fail-closed on request identity, provider-workspace identity,
query digest, and admitted generation.

The language-neutral conformance surface is
[[file:../../schemas/agent-facing-search-trace-receipt.v1.schema.json][agent-facing-search-trace-receipt.v1]].  This is the sole v1 contract; an
incremental backend refinement does not create another protocol version.

A language-scoped source-index lookup MUST derive its index owner from the
registered provider for the requested =languageId= when no explicit
=index-owner= is supplied.  It MUST NOT fall back to the global source-index
snapshot or request complete-generation admission.  The admitted generation
and its receipt MUST remain bound to that =languageId=, =providerId=, and
=providerWorkspaceIdentityDigest=; =providerProcessCount= and provider command
receipts MUST exclude every unrelated provider.

The lookup MUST consume the registered provider source envelope or its admitted
generation snapshot.  A resident transport path such as =live/client= is not a
provider workspace contract and MUST NOT be scanned as a substitute source
checkout.

Search projection consumes
=agent.semantic-protocols.incremental-search-generation.v1=.  The receipt binds
one provider-workspace generation, the requested search operation, its
completeness, every owner acquisition decision, generation-root continuity,
and mutation counters.  Graph admission MUST reject a projection whose
=languageId=, =providerId=, or =providerWorkspaceIdentityDigest= differs from
the selected route.

The graph layer does not receive source blobs.  It receives indexed
parser-fact projections containing owner path, content digest, structural
selector, signature, item identity, capture name, and parser byte span.  The
selected language provider owns canonical selector and signature production;
ASP owns provider-scoped storage, incremental generation admission, graph
ranking, and rendering.

Owner/items discovery and exact-query reads MUST acquire the same admitted
=RuntimeResidentReadClient= binding of =workspaceIdentity=,
=generationDigest=, and =rootDigest=.  Selector discovery MUST NOT project a
provider-native owner catalog while exact query reads a different Runtime
generation.  A generation or root mismatch is a typed =stale-generation=
terminal result with =candidates=[]=.  The consumer MUST NOT refresh or repair
authority, invoke a provider, reopen a database, or wait on a timeout.

Search and exact-query consumers first attempt the immutable published
generation.  Missing or failed generation authority submits one non-blocking
=query-demand= command to the Runtime Server's workspace admission coordinator
and returns =workspace-generation-required.v1= with =state=in-progress=.  The
consumer never receives a builder, database, provider, source-index, or
cancellation capability.  Concurrent requests join the Runtime-owned
single-flight, request loss does not cancel it, and a failed attempt is eligible
for the next query-triggered Runtime retry.  Hook and Agent lifecycle are not
admission owners.  Search MUST NOT bypass this path with a filesystem scan,
direct database open, stale generation pointer, manual =asp sync=, cache import,
source-index refresh, or ChoicePlane recovery.

For an unchanged explicit owner, the receipt MUST report
=decision=unchanged= and all mutation/process counters as zero.  For a changed
or new owner it MUST report one source read, one provider parse, one owner
upsert, one Merkle leaf write, and only the number of ancestor nodes actually
updated.  =fullWorkspaceWalks= and =fullMerkleRebuilds= are always zero for
ordinary search.

Workspace Tree-sitter projection reads only the selected provider generation.
If that generation is complete and has no dirty owners, it is a read-only
Turso query with zero provider parses and zero generation writes.  Otherwise
its packet is explicitly =partial= unless all dirty or unindexed owners were
completed within the bounded incremental budget.  Partial evidence may close
an identity or existential claim, but it cannot close enumeration or absence.
The receipt reports =incrementalBudget=, =dirtyOwnerCount=,
=processedOwnerCount=, and =remainingOwnerCount=.  Source reads, provider
parses, owner writes, and Merkle leaf writes MUST NOT exceed either the
incremental budget or the dirty-owner count.  The owner-items operation retains
the stricter maximum of one for each counter.

Tree-sitter capture projections are query-specific facts.  Their cache identity
is the tuple of provider-workspace identity, query digest, owner path, and owner
content digest.  A projection reports capture name and capture span together
with the canonical selector, signature, and item span of the smallest
containing complete-owner item.  Query-cache admission fails closed when the
capture has no containing item projection after one bounded same-owner refresh.

The projection packet distinguishes an =exact= provider owner inventory from a
=known= inventory.  =remainingOwnerCount= is exact only for the former; for the
latter it is a lower bound over known dirty or unindexed owners.  Therefore a
partial packet backed by a known inventory cannot prove enumeration or absence,
including when =remainingOwnerCount= is zero.  Continuation identity binds the
provider workspace, query digest, current generation, inventory state, and the
next owner cursor so another invocation cannot resume a different query or
generation accidentally.

** Project-resolution projection

Project resolution initiated by a language-scoped search or cache operation is
provider-local.  Missing provider-specific runtime dependencies fail with a
typed receipt for that provider.  They MUST NOT cause eager resolution or
runtime preparation for other registered providers.  Complete registry
resolution remains an explicit unscoped control-plane operation.

Project, package, target, dependency, and source-scope facts are projections of
the Level 0
[[file:10.05-cli-first-harness-ux/10.05.11.04-project-semantic-guidance-v1.org][Project Semantic Guidance v1]]
receipt. Search MUST consume those digest-bound facts and MUST NOT infer
project boundaries from source-envelope contents, indexed paths, or database
state.

Search graph admission starts from the same =ProjectResolution= that owns
inventory scope.  The projection layer MUST NOT infer package ownership from
path prefixes, source extensions, activation arrays, or whichever owner was
indexed first.  It admits typed project-resolution nodes for repository, worktree,
project entry, package, target, source scope, manifest, lockfile, and dependency
identity.

The required project-resolution relations are:

- =instantiates= from one stable project identity to its worktree instance;
- =declares= from project entry or package manifest to packages and targets;
- =member-of= from package to language workspace;
- =owns-source= from package target to a resolved source scope;
- =depends-on= for internal package edges and external dependency identities;
- =derived-from= from every resolved scope to its manifest-explicit or
  package-manager authority; and
- =bounded-by= from a resolved scope to the repository candidate generation.

Every owner, item, test, finding, and dependency node projected by ordinary
search MUST be reachable from exactly one admitted source scope or carry a
typed ambiguity result.  A path that is merely present in the Git candidate
snapshot is not yet a language owner.  A declared package target whose source
path is absent from the live candidate snapshot remains a package-graph fact
but is projected as =source-missing= rather than silently removed.

Projection admission validates the repository, worktree, project, provider
parser, candidate, manifest, lock, and resolution generation identities.  A
search-generation receipt whose project-resolution generation differs from the active
project resolution is stale and MUST NOT be ranked or rendered.  Incremental
owner mutations may advance the search generation without reparsing the
package graph; manifest, lockfile, project-entry, index-membership, or provider
project-parser changes invalidate only their affected package-graph closure.

Project-resolution completeness is independent from parser-index completeness.
=project-resolution= is =exact= only when every manifest-declared member and
target was resolved or has a typed unresolved state.  An exact project
resolution with a partial parser generation may prove package ownership but
cannot prove item enumeration.  A partial project resolution cannot prove
package absence, owner absence, dependency absence, or whole-workspace query
closure.

Compact search receipts report the selected =projectId=,
=projectInstanceId=, =packageId=, =targetId=, and
=projectResolutionGeneration= when those facts affect routing.  They omit
repeated path data but never omit scope authority, completeness, ambiguity, or
the relation that makes an owner reachable.

*** Live Corpus qualification completeness

Only the release publication authority may turn a locked Live Corpus checkout
into an immutable resident search projection.  The public Runtime has no Code
Prepare or indexing operation.  The published Ready receipt binds the lock
resource, revision, provider/language identity, workspace generation, source
root, projection completeness, and terminal OpenTelemetry event.  A partial or
incremental generation cannot prove owner enumeration or absence and must never
be promoted to Ready.  Missing Ready evidence is a typed, immediate read
failure; it never schedules discovery or waits for publication.

Merkle owner-proof changes require two independent qualifications over the
same versioned receipt.  Scenarios exercise Ready, missing, stale, tampered,
and generation-transition states.  Live Corpus exercises every locked resource
and every registered provider language against real owner/selector sets.  Both
validate the proof against the same generation digest, root digest, owner path,
owner content digest, and selector identity.  They also assert zero provider,
scheduler, filesystem, database, and socket operations on the warm read path.
A timeout, cancellation, or elapsed-budget failure is evidence of an invalid
architecture, not a successful bounded fallback.

The fast scenario suite MUST adversarially exercise the lifecycle contract
before Live Corpus qualification: concurrent demand for one identity proves a
single start; distinct overlay identities prove result isolation; cancellation
proves exactly one terminal response; bounded-mailbox saturation proves typed
backpressure; a capability mutation after Ready is rejected; and stale
generation/root identities fail before provider dispatch.  These scenarios use
native Tokio and HTTP, assert correlated terminal OpenTelemetry receipts, and
contain no Python transport fixture or subprocess-per-query fallback.

The Live Corpus suite repeats the same request, response, lifecycle, cache-key,
and telemetry assertions for every language/provider resource in the canonical
lock.  It additionally proves syntax-granular owner/item/exact-source and
cross-file project-graph behavior on real large libraries.  Scenario success
without Live Corpus evidence is implementation evidence only; Live Corpus
success without the adversarial scenarios cannot prove concurrency isolation
or lifecycle safety.  Both are required for qualification.

Qualification consumes that receipt without mutation.  Any attempt to build,
restore an unqualified materialization, invoke a provider, or repair a missing
projection while measuring search/query latency is a typed terminal failure.
A Live Corpus qualification is complete only when the qualification plan and
the canonical corpus lock have identical resource sets and matching
=languageId=/=providerId= identities. Every case MUST publish one admitted
generation receipt, one positive resident-search receipt, one deterministic
parser-owned exact-query receipt, one typed zero-match receipt, and correlated
OpenTelemetry terminal events. The receipt MUST retain revision, Git tree,
generation/root digests, selector identity, candidate count, and separate
resident-read/service/total latency.

Qualification MUST execute against canonical State Home checkouts and the
Runtime Server data plane. Provider package roots, synthetic fixtures, raw
source reads, direct provider processes, and CLI-local caches are not evidence
for this gate. Project-resolution success without parser-index completeness, or
search success without an exact-query receipt, is incomplete and MUST fail
closed.

* Problem

The current compact search output started as line protocol:

#+begin_src text
|owner src/tool_action.rs role=source ...
|item command_source_paths kind=fn read=src/tool_action.rs:221:241
|code path=src/tool_action.rs lineRange=221:241 nodes=... text="..."
|synthesis algorithm=bounded-reachability-depth1 ...
#+end_src

That shape is better than raw source, but it still repeats paths, field names,
and owner context.  More importantly, it makes the agent reconstruct graph
relations from flat lines.  The hidden graph is already present in
=semantic-graph.v1= and =searchSynthesis=, but the prompt-facing rendering does
not expose the graph as the agent's attention surface.

Human formatting is the wrong target.  An LLM does not need a pretty diagram,
a Markdown report, or a source-like outline.  It needs a minimal structure that
preserves the next reasoning decision.  That structure must be part of the
whole =search= interface, not a special =owner= view.

* LLM reasoning model
When warm source-index, owner-item, or selector-proof evidence misses, the subagent receipt must still be a GraphRoute artifact. It should return a compact route state such as =bounded-cold-scan= / =needs-cold-scan= with the miss reason, boundedness, and process-count constraints as evidence. It must not silently convert the miss into broad finder output, source snippets, line ranges, confidence labels, or a flat command log. The parent agent should see the recovery route and decide whether to authorize the next exact action.


ASP search subagents return the same graph slice that normal compact search
renders. They must not fan in by dumping every selected owner/item selector as
an independent receipt. A valid subagent receipt is one graph-route projection
per independent branch: ranked =evidence= nodes, typed relations, a single
primary =next= action, optional bounded alternatives, and compact =avoid=/=omit=
facts. This keeps the parent model on the =EvidenceGraph -> GraphRoute ->
compact ranked evidence -> recommended next action= path instead of forcing it
to rebuild the graph from flat lines.

For code work, the useful prompt-facing unit is not a line of source text.  It
is a decision node connected to other nodes by typed relations:

- owner, package, dependency, item, block, test, finding, and read window nodes
- relation labels such as =contains=, =imports=, =covers=, =calls=, =guards=,
  =returns=, =writes=, and =frontier=
- graph-derived attention order
- executable follow-up actions
- exact locators for expansion or edit preparation
- explicit omission and anti-action facts

This is a code reasoning graph, not a visual graph.  The provider should
compress repeated syntax, but it must not compress away relation labels,
rank order, next actions, locators, or omission reasons.

** Callable skeleton compact selector references

The provider-owned callable-skeleton payload MUST retain its complete typed
selector authority.  The shared protocol projection layer MAY render that
payload for an agent with one canonical root selector, written as =R=, and
root-relative child references such as
=R/segment/branch/ordinal-4=.  A child reference is packet-local shorthand,
not a new selector identity; resolving it for an exact query means appending
the emitted suffix to the packet's canonical root selector.

This compact rendering belongs to the shared projection/core layer.  The CLI
MUST only select and dispatch the projection, and a language provider MUST NOT
reimplement the renderer.  Providers remain responsible for canonical root
and child selectors and MAY maintain provider-owned schemas for language facts
that do not fit the shared callable-skeleton contract.

The compact view MUST state what it omits, MUST report source and rendered byte
costs, and MUST not repeat generation, parser, or query authority on every
node.  Full authority remains available in the typed payload; an exact child
query returns the selected source segment.  This separation keeps large
callables cheap to inspect without weakening selector or generation identity.

** Materialized selectors and graph-only evidence
*** Immutable exact-projection generation

Exact-selector materialization MUST construct the immutable workspace Merkle
levels once per candidate generation.  Inclusion proofs are owner facts, not
selector work: one owner proof is derived from those precomputed levels and is
reused by every selector emitted for that owner.  Implementations MUST NOT
rebuild workspace Merkle levels per owner or per selector.  For =O= admitted
owners and =S= selectors, tree construction is =O(O)=, owner-proof derivation is
=O(O log O)=, and selector attachment is =O(S log O)= only for copying and
validating the already-derived proof.  A projection packet produced through
proof reuse MUST be byte- and digest-equivalent to direct enrichment.

A canonical structural selector is a provider parser declaration identity, not a lexical occurrence. Only a complete-owner parser projection may create it. Search, graph ranking, renderers, re-export adapters, and query clients MUST NOT infer an item kind, enclosing owner, implementation owner, trait owner, or declaration path from matched text. A reference occurrence may point to a declaration identity only through a typed parser-produced relation; without that relation it remains graph-only evidence and is not executable as an exact selector.

The language-neutral v1 identity has exactly one representation:
=languageId + kind + symbol + ordered scopes[]=.  Each scope is
=relation + kind + symbol=.  Trait ownership, implementation ownership,
lexical ownership, conditional-compilation scope, namespace, class, and future
language frames are represented only as ordered scopes.  Flat sibling fields
such as =implOwner=, =implementationOwner=, =traitOwner=, or =lexicalOwner=
are non-conforming duplicates and MUST NOT appear in provider batch items,
shared schemas, source-index rows, graph nodes, or render packets.  The typed
identity, encoded structural-selector fragment, and decoded identity MUST be
equal before a selector can enter a generation.

Owner bytes, their complete declaration selector set, derived projections, content digest, and rootDepth overlay identity form one immutable epoch. Search may render a selector only from the same leased epoch that exact query uses to resolve it. A moved, replaced, deleted, untracked, or reparsed owner advances the workspace writer lane atomically; no query-time repair may combine a selector from one generation with owner bytes from another. Re-exports, modules, structs, enums, traits, impls, methods, associated items, cfg-scoped declarations, and macro-produced declarations retain their provider-emitted kind and enclosing identity without aliasing.

Exact query is an immutable data-plane consumer, never a generation writer.
The lifecycle supervisor MUST arrange readiness independently of an explicit
ASP search/query tool call.  PreTool may read a terminal readiness receipt, but
MUST NOT wait for or start project materialization on the command's latency
budget.  PostTool mutation admission owns changed-path publication.  The query
process MUST NOT compare live source bytes, derive a language from a prior
owner snapshot, publish or tombstone an owner overlay, expose an owner-specific
repair IPC, or request a whole-generation Ready gate.  It opens the published
generation pointer or returns =active-workspace-generation-required=.  A
present but unreconciled pointer fails closed at the lifecycle boundary rather
than mutating generation state from the read path.

=snapshot-item-kind-mismatch= and =item-not-in-live-owner= are valid diagnostics only for externally supplied invalid selectors or corrupted persisted evidence. A selector emitted by ASP Search and consumed against its bound generation MUST never reach either state. Cross-generation fixtures MUST prove this invariant for live edits, moves, tombstones, untracked owners, re-exports, and repeated method names.

Projection availability is independent from canonical item identity.  When the
requested selector exists in the leased generation but that generation does not
contain the requested derived projection, the resolver MUST return
=source-unavailable= with
=projection-mode-not-in-active-generation=.  It MUST NOT reinterpret the
missing projection mode as =snapshot-item-kind-mismatch=, because the item's
provider-emitted kind and scoped identity already matched.  A real
=snapshot-item-kind-mismatch= therefore requires a same-symbol candidate whose
canonical item kind differs from the requested selector; fixtures MUST cover
both branches.

**** Active artifact handoff identity

An installed exact-projection generation MUST preserve both identities across
the activation boundary:

- the artifact digest identifies the immutable fixture bytes;
- the generation digest identifies the workspace/search generation that those
  bytes are allowed to serve.

The canonical logical locator is:

#+begin_example
exact-selector-generation/<generation-digest>/<artifact-digest>.fixture
#+end_example

The active artifact kind MUST be
=exact-selector-generation-fixture=.  A resident consumer MUST validate the
typed artifact kind, canonical locator, artifact digest, and generation digest
before resolving a selector.  It MUST NOT open Turso to recover a missing
generation identity, infer the identity from fixture contents, substitute the
artifact digest for the generation digest, or fall back to a wrapper source
snapshot.

Publication is a cold durability operation.  Installed selector resolution is
a load-once memory operation: after the active artifact is admitted, lookup
MUST perform no database opens, provider subprocesses, manifest writes, source
walks, or artifact byte reads beyond the single fixture load.

The workspace-generation publication request MUST carry the complete typed
exact-selector projection-record set alongside =generation_identity= and
=artifact_root=.  A source snapshot by itself is insufficient because it does
not preserve selector projection mode, parser-fact identity, or source byte
range.

The source-index generation and exact-selector fixture MAY be written in
separate durability operations, but they MUST become visible through one active
generation reconciliation.  A failed source-index transaction may leave an
unreferenced content-addressed fixture; it MUST NOT leave an active receipt
that exposes only one side of the generation.  The publication receipt MUST
therefore carry the exact-selector active-artifact input into the same
reconciliation that admits the source-index generation.

An executable selector is complete only when the published search generation
contains all three parts of the same identity:

- the canonical item selector and owner identity;
- the exact-query materialization proof, including the source blob digest,
  inclusive byte bounds, and source-slice digest;
- the exact-selector projection packet produced by the activated language
  parser and query pack.

These parts MUST be committed as one immutable generation.  A selector row
without its materialization proof or projection packet is not a partial cache
hit and MUST NOT be promoted to =readSelector=.  Graph-only facts remain
discovery evidence and cannot acquire executable status from a path, symbol, or
line-range heuristic.

The active generation MUST publish a content-addressed Memory Search artifact
that can be opened once and shared by exact-query consumers.  The artifact
identity includes the workspace identity, root digest, language/provider
identity, parser identity, query-pack digest, and projection payload digest.
Changing any input creates a new generation; consumers invalidate by replacing
the generation handle, never by mutating or repairing individual selector rows.

After the generation handle is active, exact-selector lookup and projection
MUST be read-only:

- no provider process spawn;
- no Turso open or query;
- no source-envelope publication or manifest write;
- no Merkle rebuild or filesystem source materialization;
- no retry loop that hides a missing or incomplete generation.

Cold load measures opening the already-published immutable artifact.  Warm load
measures lookup through the resident generation handle.  Both are hard
performance contracts with explicit receipts; a budget breach fails the gate.
Concurrent callers MUST share one generation initialization and MUST receive the
same deterministic hit or the same cached initialization failure.

The command router only selects the generation and projection mode.  It does
not reconstruct materialization from source paths and does not own a second
selector cache.  Installed CLI and resident-agent paths consume the same
published artifact and return the same projection packet.


An EvidenceGraph node identity is not automatically an executable source
selector. Providers may emit graph-only nodes for call sites, relations,
observations, errors, and other parser facts that do not have an independently
materializable query item. Those nodes retain their typed graph identity and
relations, but they MUST NOT be rendered as =readSelector= values or embedded
in an exact =query --selector= action.

Every compact graph route separates graph evidence from reading capability:

- =evidenceSelector= identifies a graph node and may be non-executable.
- =readSelector= is optional and is present only for a parser-owned item
  accepted by the provider's exact query reader.
- =enclosingReadSelector= connects graph-only evidence to its smallest
  enclosing materialized item when that relation is known.

The recommended exact read action may use only =readSelector= or
=enclosingReadSelector=. If neither exists, GraphRoute must recommend bounded
owner/item expansion rather than manufacture a selector. This is a shared
invariant: every selector carried by a recommended exact-read command must
execute through that provider's exact query surface. A scenario gate must
exercise the invariant across every registered language provider.

** Search closure, quality proof, and query handoff

Agent-facing =search= is the reasoning plane. Exact =query= is the evidence
materialization plane. A resident search loop MUST NOT expose =query= grammar,
line ranges, provider-private selector syntax, or shell commands as choices.
When search has closed enough evidence for source understanding or editing, it
returns a =SearchClosureReceipt= containing an =EvidenceScope= and a
=QueryHandoff=. The main agent may then execute only the exact =query= commands
described by that handoff.

The invalid design is:

#+begin_src text
asp <language> search --scope <scope-id> --choice read:R1
#+end_src

That shape mixes reasoning search with exact source materialization and lets a
prompt-visible choice become a read authority. =read:R1=, selector strings, and
projection details are receipt data, not public search actions.

The corrected boundary is:

#+begin_src text
resident search loop
  -> SearchClosureReceipt
       EvidenceScope
       QueryHandoff

main agent
  -> asp <language> query --selector <exact structural selector> --workspace .
#+end_src

=SearchClosureReceipt= is not a polished summary. It is a replayable closure
claim derived from the event stream and graph proof. It MUST carry a
=qualityProof= whose terminal decision is validator-computed, not model-filled.
Flat labels such as =strong=, =closed=, =top1-confirmed=, or =recall-covered=
are not sufficient unless they are derived from typed obligations and proof
refs.

The core receipt shape is:

#+begin_src text
SearchClosureReceipt
  evidenceScope:
    scopeId
    intent
    workspaceSnapshotRoot
    graphRoot
    obligations[]
    evidenceChain
    qualityProof
  queryHandoff:
    groups[]
      id
      mode: single|serial|parallel-all|parallel-first-proof|parallel-disambiguate|hybrid
      joinPolicy: all-required|first-exact|disambiguate-all|complete-enumeration|best-supported
      queries[]
        id
        languageId
        selector
        projection
        reason
  closureProof:
    allowed
    resultKind: partial|clarification|handoff|answer|protocol-error
    searchClosure: open|closed|failed
    loopTerminal
    eventStreamRoot
    graphRoot
    workspaceSnapshotRoot
    gateEventRefs[]
#+end_src

Claim closure is obligation-driven. Exact selector identity closes only an
=identity= obligation; it does not close enumeration, absence, causal-flow, or
cross-language handoff claims. The v1 claim classes are:

| Claim class | Closure rule |
|-------------+--------------|
| =identity= | unique canonical selector plus owner snapshot proof |
| =existential= | at least one exact support path |
| =enumeration= | complete admitted scope, untruncated enumeration, snapshot/provider proof |
| =absence= | complete negative proof over the admitted scope; ordinary no-hit is partial |
| =causal-flow= | continuous typed edges with exact pivots when required |
| =handoff= | provider/language admission proof plus downstream scope receipt |

Freshness is two-dimensional. =acquisition.mode= records how evidence was
obtained, such as =live-parser=, =validated-cache=, =cold-scan=, or
=snapshot-replay=. =freshness.verdict= records whether the evidence matches the
requested source authority: =verified=, =mismatch=, or =unknown=. A validated
cache hit can be strong evidence when it is bound to the same source snapshot,
provider identity, parser facts, and artifact digest. The unsafe state is cache
without snapshot proof.

Runtime quality proof MUST express what it can actually know: selector
uniqueness, provider admission, obligation coverage, truncation, snapshot
continuity, ambiguity, and coverage of declared semantic axes. Runtime MUST NOT
claim benchmark-only metrics such as true precision or recall. Benchmarks derive
precision/recall from golden sets; receipts expose identity and coverage proof.

The search loop is an execution DAG over evidence obligations, not just a single
choice chain. A ChoicePanel may present one choice that represents a whole
execution bundle, including serial or parallel branches, a join policy, cost,
and stop condition. The runtime should auto-advance deterministic transitions
and ask the resident model only when a semantic choice or budget tradeoff
remains.

Parallel execution is legal only when independence is proven: no data
dependency, a shared immutable snapshot/provider/query-pack authority,
independent obligations or axes, a deterministic join rule, and no loss of
enumeration or absence completeness. Default is serial. Cross-language ownership
disambiguation MUST use =disambiguate-all=, never first-hit-wins.

Choice validation remains compare-and-swap over:

#+begin_src text
loopId
sessionEpoch
step
panelId
graphRootDigest
choiceId
choicesDigest
executionPlanDigest
#+end_src

A stale or invented choice records an invalid attempt, changes no graph state,
executes no provider action, and consumes no search budget. Only repeated
invalid attempts or an explicit protocol attack may become =protocol-error=.

*** Proof-carrying context reconciliation

**** Exact-selector relocation coverage

An =asp.exact-source-snapshot-envelope.v1= is not a complete relocation
authority merely because its =sourceSnapshot.rootDigest= names the complete
workspace.  The envelope MUST carry one of these root-bound coverage proofs:

- =full-workspace=: every live owner leaf is materialized and
  =owners.length == sourceSnapshot.leafCount=.
- =selector-relocation-closure=: the live parser materializes the requested
  owner plus the complete owner-candidate closure for the canonical item
  identity.  The proof binds the requested selector, ordered owner set, parser
  identity, query-pack identity, and =sourceSnapshot.rootDigest=.

The exact-query consumer MAY return =item-not-in-live-owner=,
=owner-not-in-snapshot=, or any other terminal missing state only when the
coverage proof is complete for the current root.  A partial envelope without
that proof is =source-unavailable= with
=reasonKind=relocation-coverage-incomplete=; it is never negative evidence.

When source-index state is =cold-required=, =package-drift=, or its provider
digest is not committed by the current source-snapshot root, the wrapper MUST
materialize a fresh selector relocation closure before invoking =query=.  It
MUST NOT reuse an older owner-only envelope.  Implementations MAY use an
in-memory symbol/owner map and Merkle multiproof so this remains a
millisecond-scale operation without materializing the whole workspace.

**** Decision status

The architecture keeps =ContextReconciler= as a deterministic internal phase
of =GraphRouter=.  It is not a new public router, it is not a second closure
authority, and it does not move exact-query authority out of =QueryHandoff=.

The following direction is admitted:

- prior graph evidence may be reused only after claim applicability and proof
  freshness have been re-evaluated;
- valid proof branches may be crossed without replaying their search actions;
- invalidation may reopen only the obligations that depend on stale evidence;
- =SearchReasoningRouter= is reserved for bounded semantic alternatives rather
  than ordinary cache or lifecycle recovery;
- model context may contribute intent, hypotheses, and route priors, but never
  evidence authority.

The following stronger claims are *not* admitted yet:

- the current runtime can already close the Rust buffer-reuse example from
  memory;
- the current Python provider can already jump from the FastAPI HTTP selector
  to an executable WebSocket sibling selector;
- =supportOwners ∩ changedPaths = ∅= is a sufficient freshness proof;
- PPR, Dijkstra, or Yen path rank can admit a proof or close an obligation;
- the labels =MEMORY_CLOSED=, =MEMORY_JUMP=, =MEMORY_REBASE=,
  =PARTIAL_REFRESH=, =AUTO_EXECUTE=, =REASONING_CHECKPOINT=, and
  =COLD_SEARCH= form one mutually exclusive router state machine.

Rust implementation remains blocked until the entry gates in
[[*Context-reconciliation benchmark contract][Context-reconciliation benchmark contract]]
are satisfied.

**** Authority boundary

The authority split is:

#+begin_src text
GraphRouter
  ContextReconciler
    validate bindings
    evaluate claim applicability
    admit or reject ClosureProof inputs
    propagate invalidation
    compile the residual obligation DAG
    project a decision requirement

  SearchRouter
    execute only actions that reached ActionAdmitted
    require ExecutionGrantIssued immediately before provider invocation

  SearchReasoningRouter
    compare bounded semantic alternatives
    propose hypotheses or search axes
    never admit evidence and never issue SearchClosureReceipt

  QueryHandoff
    retain the exact structural-selector boundary
    materialize an admitted exact projection when required
#+end_src

=GraphRouter= remains the sole admission and closure authority.  Reconciliation
may reuse an existing =ClosureProof=, produce a new =QualityGateEvaluated=
event, or require a new =JoinEvaluated= event, but it cannot declare closure
without a valid =SearchClosureReceipt=.

=SearchRouter= remains execution-only.  The existence of a cached selector,
projection, route, or prior action does not imply =ActionAdmitted= and cannot
substitute for =ExecutionGrantIssued=.

**** Reconciliation result is a product, not a seven-way enum

The reconciliation result MUST preserve orthogonal protocol axes.  The
following is a contract sketch, not a Rust implementation commitment:

The former labels are derived views over this product:

| Legacy label | Required projection; never an authority by itself |
|--------------+--------------------------------------------------|
| =MEMORY_CLOSED= | =closureState= is =finalized=, the residual obligation set is empty, and the referenced =SearchClosureReceipt= is valid |
| =MEMORY_JUMP= | at least one proof is retained and deterministic residual work begins from a non-root frontier |

| =PARTIAL_REFRESH= | proof reuse is partial and invalidation reopened a strict subset of obligations |

These views may coexist.  For example:

- rebase, partial refresh, and deterministic execution may occur together;
- partial refresh may expose a genuine reasoning checkpoint;
- cold search may be required while provider lifecycle is blocked;
- evidence may be closed while cached projections still require redelivery
  after context compaction.

Protocol implementations MUST NOT encode the views as one mutually exclusive
enum.

**** Deterministic reconciliation algorithm

For a new intent, =ContextReconciler= evaluates these stages in order:

1. Normalize the intent into typed mandatory and optional obligations.
2. Bind the request to exact workspace, dirty-overlay, provider, parser,
   query-pack, schema, policy, and graph revisions.
3. Locate prior =ClosureProof= candidates by typed claim identity, not lexical
   similarity alone.
4. Evaluate claim implication through a registered predicate rule.
5. Re-evaluate every referenced =QualityGateEvaluated= input against the
   current bindings.
6. Propagate invalidation through reverse proof dependencies and joins.
7. Select the maximal valid frontier antichain that preserves every open
   obligation.
8. Compile a residual obligation DAG from the open obligations and their
   prerequisites.
9. Project =deterministic=, =search=, =reason=, =clarify=, or =blocked=.
10. Issue closure only when the residual set is empty and
    =SearchClosureReceipt= validation succeeds.

The algorithm MUST be a deterministic reducer over typed packet state.  Model
reasoning may create or rank candidate claim mappings, but those mappings enter
the reducer as untrusted candidates.

**** Claim applicability and implication

Keyword overlap is not claim applicability.  Every reusable claim family MUST
be registered with:

- a stable predicate identifier and version;
- a canonical parameter schema;
- a quantifier and declared scope;
- an evidence class;
- explicit variance or monotonicity rules;
- an implication checker version.

Exact parameter equality is the default.  A wider implication relation is
allowed only when the registered predicate proves it.

#+begin_src text
proved claim
  predicate = dependency_scope_lifetime
  framework = fastapi
  transport = http
  scope = function
  quantifier = one-runtime-path

requested claim
  predicate = dependency_scope_lifetime
  framework = fastapi
  transport = websocket
  scope = function
  quantifier = one-runtime-path

result
  identity/topology anchors may be retained
  conclusion reuse is rejected
#+end_src

The internal evaluation outcomes are:

- full implication: the old proof may close the matching new obligation;
- anchor only: selectors or topology may seed the residual search, but the old
  conclusion cannot close it;
- reopen: the prior claim family matches, but freshness or scope validation
  failed;
- contradicted: admitted evidence conflicts with the old conclusion;
- no match: the prior claim is irrelevant.

These are internal evaluation outcomes.  They do not replace
=QualityGateEvaluated=, =ClosureProof=, or =SearchClosureReceipt= as canonical
protocol records.

At minimum, the implication checker MUST reject:

- existence as proof of complete enumeration;
- one hit as proof of absence;
- exact identity as proof of causal flow;
- a local positive claim as proof of repository-wide uniqueness;
- =find-one= evidence as proof of =find-all=;
- claims whose quantifier, scope, transport, feature set, platform, or policy
  parameters differ without a registered monotone rule.

**** ClosureProof support closure

The earlier =supportOwners= concept is too weak.  Reuse is admitted through the
support closure already owned by =ClosureProof=.  The proof MUST bind every
input whose semantic change could alter the conclusion:

- canonical source anchors and source blob digests;
- parser facts and projection digests;
- provider, parser, query-pack, schema, and policy identities;
- transitive semantic dependencies used by the derivation;
- build manifests, feature selections, generated inputs, and toolchain
  identities when they affect the claim;
- dirty-overlay, rename, deletion, symlink, and submodule state;
- the declared scope-completeness proof for absence, uniqueness, enumeration,
  or coverage claims;
- the claim predicate, parameters, quantifier, and evidence class;
- the derivation algorithm and join-policy versions;
- workspace inclusion proofs for all current-root anchors.

Therefore:

#+begin_src text
supportOwners ∩ changedPaths = empty
#+end_src

is neither sufficient nor necessary.

It is not sufficient when a feature manifest, generated input, parser identity,
query pack, policy, transitive dependency, or enumeration scope changes.  It is
not necessary when the source owner changed in a way that leaves all admitted
parser facts and the typed conclusion invariant.

An implementation may use changed paths as a fast invalidation index, but a
path comparison never becomes the closure proof.

**** Branch and join reuse

A branch outcome is reusable only when its =ClosureProof= remains valid under
the current bindings.  A join is reusable only through =JoinEvaluated= and MUST
bind:

- the digests of the consumed branch proofs, not branch names alone;
- the exact mandatory and optional obligation set;
- the join-policy identifier and version;
- shared prerequisites and cross-branch dependencies;
- the union of admitted support bindings;
- negative or enumeration scopes when present;
- the output claim and output proof digest.

For a diamond graph:

#+begin_src text
          split
         /     \
       B1       B2
         \     /
           J
#+end_src

the rules are:

- if =B1= and =B2= remain valid and the new obligations are covered by the
  current =JoinEvaluated= record, reconciliation may cross =J=;
- if =B1= remains valid and =B2= is stale, invalidation reopens =B2= and any
  downstream proof depending on the old join;
- if both branches remain valid but a new mandatory obligation is added,
  reconciliation continues from the valid frontier without replaying the
  branches;
- if the join policy, shared prerequisite, or claim parameters changed, the old
  join is rejected even when both owner blobs are unchanged;
- conflicting admitted branch outcomes require =decisionRequirement=reason=;
  missing branch evidence requires search or blocked, not reasoning-generated
  facts.

**** Proof rebase

Rebase never mutates an old receipt into a current receipt.  It validates a
provenance-preserving mapping and emits new current-root proof bindings.

Rebase policy is evidence-class dependent:

| Evidence class | Minimum rebase rule |
|----------------+---------------------|
| content-local positive fact | source blob, parser, query pack, schema, policy, and projection facts are unchanged; generate a new workspace inclusion proof |
| dependency-closed fact | every transitive support input and derivation identity is unchanged |
| scope-complete fact | the entire declared enumeration or absence scope is unchanged and completeness is re-proven |
| runtime or external fact | do not Merkle-rebase; rerun the owning observation |

A valid rebase produces a new =QualityGateEvaluated= result and a new
=ClosureProof= bound to the current root.  It may reference the old proof as
provenance, but it MUST NOT reuse the old =SearchClosureReceipt= identity as a
current closure receipt.

Deleted anchors, unmapped renames, ambiguous case-folding, changed symlink
targets, parser/query-pack drift, or incomplete scope mapping reopen affected
obligations.

**** Planner frontier projection and canonical residual obligation DAG

The complete residual obligation DAG is the canonical reconciliation state.
It MUST preserve every open, refuted, blocked, inconsistent, and
refresh-required obligation together with dependency edges, join requirements,
and invalidation causes.  A frontier, boundary, or antichain is a derived
planner projection and MUST NOT replace the residual DAG, determine closure, or
enter proof identity.

The antichain rules below apply only when a planner requests a compact ready
boundary.  Any =MUST= in those rules constrains that optional projection, not
the canonical reconciliation result.  Cost, rank, PPR, Dijkstra, Yen, AO*,
set-cover, or beam-search changes MAY change the projection without changing
evidence truth or the residual-DAG digest.

The frontier is not one scalar "deepest node".  In a DAG, two equally deep
valid nodes may be incomparable and jointly required.  Reconciliation MUST
return a maximal antichain of valid nodes such that:

- every retained node has valid prerequisites;
- every open mandatory obligation is reachable from at least one frontier
  node;
- no retained node silently drops a required sibling branch;
- downstream joins are retained only when their =JoinEvaluated= inputs remain
  valid.

The residual obligation DAG is compiled by subtracting obligations closed by
admitted proofs, then restoring every prerequisite required by the remaining
open obligations.  It records:

#+begin_src text
originalProgramRef
retainedProofRefs[]
invalidatedProofRefs[]
closedObligations[]
openObligations[]
irrelevantBranches[]
executionNodes[]
joinNodes[]
residualDigest
#+end_src

Residual compilation MUST preserve shared prerequisites and MUST NOT assume
that one action is sufficient for one changed branch.

PPR, Dijkstra, and Yen remain heuristic facilities:

- PPR may expand candidates from retained context nodes;
- Dijkstra may rank an additive single-source path;
- Yen may retain alternative paths for a bounded reasoning checkpoint.

They MUST NOT admit =ClosureProof=, validate =JoinEvaluated=, determine claim
implication, or issue =SearchClosureReceipt=.  A multi-obligation residual DAG
with fan-out and joins is not reduced to a single Dijkstra path.

**** Projection cache and model-context residency

Evidence validity and model delivery are separate.

#+begin_src text
evidence admitted
projection cached
projection delivered to current model context
projection believed resident after host events
#+end_src

=contextEpoch=, when available, is delivery metadata.  It is not a proof of
workspace, provider, parser, query-pack, schema, policy, or graph freshness.

When an admitted projection is cached but no longer resident after compaction,
the delivery plan may redeliver the cached projection without restarting the
parser.  The system may claim =zero parser restart= only when the cached
projection and its proof validate.  It may claim =zero query/delivery action=
only when the host supplies a trustworthy delivery-residency acknowledgement.

If the host cannot attest residency, safe behavior is compact cached
redelivery.  The system MUST NOT infer that the model remembers code from the
conversation transcript.

**** Execution and lifecycle separation

Evidence state, provider capability, resident liveness, and execution authority
are distinct.

A deterministic residual action does not become executable until:

1. the action is validated against the live snapshot and policy;
2. =ActionAdmitted= binds its exact =actionKey= and attempt identity;
3. the configured provider or resident target is live and canonical;
4. =ExecutionGrantIssued= is created just in time;
5. terminal receipt identity is committed exactly once.

Provider parse failure, owner-outside-workspace, low-quality no-hit,
=needs-cold-scan=, lifecycle mismatch, DB lock, timeout, and repeated
=recommendedNext= are distinct terminal or recoverable classifications.  None
may be converted into absence, closure, or successful memory reuse.

*** Calibrated router authority and admission contract

This subsection is normative architecture.  It sharpens router ownership
without asserting that the contract is already implemented.

- =GraphRouter= is the deterministic state and transition evaluator.  It is
  the sole authority for graph state, admissible transitions, obligation
  coverage, and closure.
- =SearchReasoningRouter= produces =RouteProposal= values only.  A proposal may
  recommend a semantic choice or budget, but it cannot mutate graph state,
  admit a transition, satisfy an obligation, or declare closure.
- =SearchRouter= executes only an admitted stage.  It cannot author or admit a
  route, and its execution receipt returns to =GraphRouter= for evaluation
  before any later stage may execute.

Before the first evaluation, the request MUST have a typed initial intent and
an explicit set of obligations.  Every admitted transition MUST identify the
obligations it advances, and =Closed= is legal only when =GraphRouter= can
account for every required obligation with validated closure evidence.

=GraphRouteEvaluation= has exactly these outcomes:

- =Closed= :: all required obligations have validated closure evidence.
- =Execute= :: exactly one admissible next transition is proven and its stage
  may be admitted for execution.
- =NeedsReasoning= :: a =ReasoningCheckpoint= may obtain a permitted semantic
  choice or budget proposal.
- =NeedsClarification= :: required typed intent, user-owned information, or
  authority is missing or contradictory.
- =Blocked= :: no legal progress can be admitted because an invariant,
  capability, or required evidence condition has failed and neither reasoning
  nor clarification can repair it.

When obligations remain, the runtime MUST NOT execute unless =GraphRouter= can
prove exactly one admissible transition.  Failure to prove that fact escalates
to =NeedsReasoning=, =NeedsClarification=, or =Blocked= according to the typed
cause.  Escalation is therefore a proof boundary, not a claim that the runtime
understands semantic ambiguity.

The admission path is:

#+begin_example
RouteProposal -> deterministic validator -> admitted RouteProgram
#+end_example

The validator is owned by the =GraphRouter= boundary and rejects stale,
invented, unreachable, unauthorized, obligation-losing, or over-budget
proposals.  =PlanOnce= means that one reasoning pass may propose multiple
stages; it does not mean validate once.  Every stage MUST be validated against
the then-current graph state, obligations, budget, and receipts immediately
before admission.

=ChoicePanel= is one projection of =ReasoningCheckpoint=, not the checkpoint
contract itself.  Other projections may collect the same permitted choice, but
all resulting proposals pass through the same validator.  Resident memory is
advisory only: it may seed a proposal, but it cannot establish graph facts,
cover obligations, admit a stage, or prove closure.

=QueryHandoff= remains the authoritative query-materialization boundary.  The
question whether a future internal typed query should precede or live inside
=QueryHandoff= is unresolved and MUST NOT be inferred from this router split;
until a separate contract revision resolves it, no router takes query
materialization authority from =QueryHandoff=.

P0 invariants and anti-claims:

- There is exactly one admissibility and closure authority: =GraphRouter=.
- No =RouteProposal= or remembered route is executable before validation.
- No admitted earlier stage grants admission to a later stage.
- No executor receipt self-certifies obligation coverage or closure.
- =NeedsReasoning= records an admissibility proof gap; it does not certify
  machine understanding.
- This contract does not claim a Rust or other provider implementation exists.

*** Design argument

This change is not a formatting improvement for compact search output. It moves
agent search memory, routing discipline, progressive reasoning, and stop
conditions out of prompts and into a stateful, replayable runtime contract.

The previous prompt-centered model gave the language model too many hidden
responsibilities:

- remember which owners and selectors were already tried;
- decide when a broad search should narrow into an exact selector;
- distinguish cache acceleration from source authority;
- infer whether a no-hit was a true absence proof or merely a weak search miss;
- avoid stale choices after graph state changed;
- decide whether independent evidence branches could safely run in parallel;
- decide when a polished answer was actually terminal.

Those responsibilities are protocol responsibilities. The model may choose
between bounded semantic alternatives, but it must not own state authority,
selector syntax, cache truth, join legality, or terminal closure.

The new invariant is:

#+begin_src text
LLM chooses among bounded semantic choices.
Runtime owns state, evidence graph, event replay, quality gates, and closure.
Provider owns parser facts and exact materialization.
#+end_src

This is why =search= and =query= are separated by plane rather than by
convenience:

| Plane | Public use | Owns | Must not own |
|-------+------------+------+--------------|
| =search= | reasoning intent and closure receipt | discovery, disambiguation, evidence graph, obligations, quality gates | exact source materialization by prompt-visible read action |
| =query= | exact materialization after handoff | structural selector projection, code/outline/skeleton | broad discovery or route reasoning |

The handoff is deliberate. After =search= closes, the main agent should have
less freedom, not more: it receives exact query work items that are already
bound to language id, selector, projection, reason, and evidence lineage.

*** Why =search --choice read:*= is invalid

=search --choice read:R1= looks attractive because it keeps one public command
family, but it collapses two different authorities:

1. a reasoning-loop choice selected by a model;
2. an exact source materialization capability accepted by a parser.

Once those are mixed, a prompt-visible token such as =read:R1= can accidentally
become read authority. That reintroduces the same failure modes the search loop
was meant to remove:

- the model can replay a stale read choice from an old graph root;
- the model can confuse a graph-only evidence node with an executable selector;
- the runtime has to interpret prompt-visible labels as capability IDs;
- a search loop can consume source before proving the evidence scope is closed;
- query authority becomes coupled to the resident search lifecycle.

The correct design keeps =read:R1=, if present at all, inside receipt data. The
runtime materializes a =QueryHandoff= from validated =EvidenceScope= state. The
main agent then executes exact =query= commands generated from that handoff. A
failed or stale handoff is a query/materialization failure, not a new search
choice.

*** Selector closure is not search closure

The core correctness bug this RFC prevents is:

#+begin_src text
exact selector found
  != user claim proved
#+end_src

Examples:

| User claim | Exact selector proves | Still open |
|------------+-----------------------+------------|
| "What item owns this symbol?" | identity of one item | nothing, if expected cardinality is one |
| "Find all constructors" | one constructor identity | complete enumeration of admitted scope |
| "There is no producer" | maybe no local hit | negative completeness over all admitted providers |
| "Rust owns this behavior" | Rust ingress or candidate owner | cross-language disambiguation |
| "A triggers B" | one endpoint identity | typed edge chain from A to B |

This is why =obligations[]= are mandatory. Each obligation declares a
=claimClass=, expected cardinality, admitted scope, and closure rule. A terminal
receipt is valid only when every mandatory obligation is closed or explicitly
waived by a non-terminal result kind such as =partial=, =clarification=, or
=handoff=.

Claim classes have different proof burdens:

- =identity= closes with unique selector identity and owner snapshot proof.
- =existential= closes with at least one exact support path.
- =enumeration= closes only with untruncated complete enumeration over the
  admitted scope.
- =absence= closes only with a negative-completeness proof. Ordinary no-hit is
  partial evidence.
- =causal-flow= closes only with continuous typed edges, and exact pivots where
  the graph edge is not independently materializable.
- =handoff= closes only when provider/language admission proves the downstream
  owner and records a downstream scope receipt.

Any output containing "all", "none", "only", "does not exist", "belongs to
Rust", or "fully migrated" must map to one of these closure rules. If it does
not, the receipt must fail closed.

*** Runtime quality versus benchmark quality

Runtime quality proof is not a self-score. It is a set of facts the runtime can
prove from events, graph roots, provider packets, and source authority.

Runtime may prove:

- selector identity is unresolved, a candidate set, unique exact, or relocated
  exact;
- provider and language admission matched the requested scope;
- every mandatory obligation has support paths or remains open;
- an enumeration was untruncated and covered the admitted roots;
- a negative query was complete over the admitted scope;
- acquisition used live parser, validated cache, cold scan, or snapshot replay;
- observed snapshot roots and artifact digests matched the request authority;
- ambiguity remains between owners, languages, providers, or semantic axes;
- budget, packet size, and branch counts stayed inside policy.

Runtime must not claim:

- true precision or recall against the real world;
- gold =precision@1=, =precision@3=, or =recall@3=;
- that a user's natural-language intent was fully captured in an open world;
- that a top-ranked candidate is "correct" without identity proof.

Benchmark suites compute those external metrics from golden sets. Receipts
expose the proof inputs that make benchmark failures diagnosable.

*** Freshness and cache authority

Cache is an acquisition mode, not a freshness verdict. A cache hit can be
authoritative when it is bound to the same:

- workspace source snapshot root;
- provider identity and provider activation digest;
- parser/query-pack identity;
- index artifact digest;
- graph artifact digest.

The unsafe state is:

#+begin_src text
cache hit + missing or mismatched source authority
#+end_src

Therefore quality proof splits:

#+begin_src text
acquisition.mode:
  live-parser | validated-cache | cold-scan | snapshot-replay

freshness.verdict:
  verified | mismatch | unknown
#+end_src

=validated-cache + freshness.verified= may close obligations. =validated-cache
+ freshness.unknown= may rank candidates but cannot authorize terminal closure.
=freshness.mismatch= must force retry, partial, or fail-closed.

| language mismatch | fail closed or handoff, no ownership claim |

Invalid choice attempts do not consume search budget and do not mutate graph
state. The system should tolerate occasional weak-model mistakes. It should
escalate to =protocol-error= only after a threshold or attack pattern.

*** Execution DAG and parallelism

The search loop is an execution DAG over obligations. A ChoicePanel can offer
one choice that represents an execution bundle:

#+begin_src text
choice
  execution.mode
  branches[]
  joinPolicy
  cost
  expectedGain
  stopCondition
#+end_src

Default is serial. Parallel execution is legal only when runtime proof shows:

1. no data dependency between branches;
2. shared immutable =workspaceSnapshotRoot=;
3. fixed provider activation and query-pack authority;
4. distinct obligations or independent evidence axes;
5. deterministic join policy;
6. no loss of enumeration, absence, or cross-language completeness.

Allowed modes:

| Mode | Legal use |
|------+-----------|
| =single= | one deterministic next transition |
| =serial= | later branch depends on earlier evidence |
| =parallel-all= | independent mandatory branches all required |
| =parallel-first-proof= | existential alternatives where any exact proof closes |
| =parallel-disambiguate= | competing owners/languages/providers |
| =hybrid= | staged serial setup, parallel evidence, serial closure |

Allowed join policies:

| Join policy | Closure behavior |
|-------------+------------------|
| =all-required= | any mandatory branch failure yields partial/fail-closed |
| =first-exact= | existential exact proof closes and cancels remaining alternatives |
| =disambiguate-all= | all competing routes must produce discriminators before closure |
| =complete-enumeration= | any uncovered scope forbids terminal |
| =best-supported= | ranking only; never terminal by itself |

Cross-language ownership must use =disambiguate-all=. A Rust branch returning
first cannot claim ownership while TypeScript, Python, Julia, Gerbil, or other
admitted providers remain unresolved.

Parallel branches must join deterministically. Branch-local graph deltas are
merged by branch id and semantic identity. If the same selector appears with
different source blob digests, the join emits =GraphMergeConflict= and
=FreshnessMismatch=; terminal closure is forbidden.

* Research line and invariants

A projection-independent =StructuralSelector= parser MUST be the single owner of selector syntax: exact language id, owner path, =#item= marker, item kind, and item name. Query projection layers may attach =fromHook= and code/outline/skeleton semantics, while hook policy may restrict accepted selector kinds and require the selected language, but neither layer may split or validate selector text again. Language-family or dialect relationships do not make selector language ids interchangeable: for example, Gerbil selectors use =gerbil-scheme://=, not =scheme://=. A selector is parsed once and the typed value is carried through command-intent matching and trusted materialization.

This RFC is the protocol surface for the research line:

#+begin_src text
Agent Compact Code Graph: typed decision graph for LLM code navigation
#+end_src

The claim is not that code should be made to look like a graph.  The claim is
that agent-facing code graph serialization is a typed decision interface.  Its
purpose is to expose the smallest graph slice that preserves:

1. what entities exist
2. why they were selected
3. how they relate
4. what order the agent should attend to them
5. what executable follow-up actions are safe
6. what source/code facts were intentionally omitted

The durable pipeline is:

#+begin_src text
parser/compiler/static-analysis facts
  -> semantic JSON packet
  -> typed code/repo graph
  -> ranked frontier and typed capability actions
  -> typed render IR
  -> safe ARI line serialization
  -> agent prompt

typed capability action
  -> trusted materializer
  -> executable argv
#+end_src

Natural-language context terms filtered out of automatic =search pipe=
=queryClauses= are analyzer/history facts, not ARI seed facts. They may be
stored with receipts for calibration, but compact graph seed nodes,
materialized =rg-query-set= actions, and best-owner/package-cohesion evidence
must be built from code-facing path, package, symbol, and domain-concept axes.

For the graph-turbo first stage, query-derived anchor candidates are only allowed after the query-pack quality gate and package-cohesion gate pass. Low-quality or low-cohesion packets must not manufacture extra =query-anchor= item nodes from weak natural-language coverage, because that inflates apparent graph certainty without proving an owner. In those cases the first-stage frontier should prefer exact fd anchors when they contain strong symbols, or package-local =owner-items= transitions when a finder preview has already produced owner candidates. Broad =rg-query-set= remains a refinement action, not the default first action when owner/package evidence is weak. Term promotion and suppression must be evidence-derived; ASP must not encode fixed ecosystem-symbol lists such as API, SDK, CLI, UI, HTTP, Tokio, Playwright, Vite, Effect, or library-specific API names as graph-turbo seed rules. Those labels are searchable project facts, not protocol constants. If such a label improves search, the provider must expose it through parser-owned declarations, semantic handles, package/dependency facts, type surfaces, or finder evidence, and graph-turbo must rank that evidence rather than recognizing the string directly.
Low-cohesion finder previews must also pass an owner-seed strength gate before they become the first action. A preview owner produced by only one strong owner seed is still useful evidence, but not enough to outrank split query-pack refinement or best-owner coverage. This prevents project-name-level fd hits from selecting entrypoint or aggregate owners ahead of parser/finder-local evidence, while keeping exact multi-symbol owners eligible for first-stage =owner-items=.
Best-owner scoring must be deterministic across header rendering, graph request construction, and action materialization. Ties should prefer owners with more matched symbol terms, then configuration/package-owner paths, before falling back to stable path order. Recomputing quality in separate render phases must not let map iteration reorder the recommended action.
Query-conditioned structural owner roles may participate in best-owner scoring:
when a query has no strong test/spec/fixture/case/template/example intent,
secondary artifact owners should rank below source owners. A mixed
implementation query that only mentions a single artifact role should not let a
test corpus, unit-test corpus, fixture, baseline, template, example, sample,
demo, or benchmark owner become the primary =owner-items= action under low
package cohesion unless that owner is also a strong finder-preview owner. When
the query explicitly asks for those artifact roles with multi-token intent, they
remain eligible. This is structural graph evidence, not an ecosystem symbol
shortcut.

Low-cohesion fallback =owner-items= actions must also pass a query-axis coverage
gate. If the selected fallback owner covers fewer than half of the terms in the
materialized owner-items query, graph-turbo should prefer query-pack refinement
over an executable but partial selector. This keeps selector-ready from becoming
a false precision signal while preserving explicit artifact-role queries and
strong finder-preview owners.

Query-wrapper refinement must also be replay-aware. When an explicit
=rg-query-set= or repeated =-query= command has already materialized the current
multi-clause probe, its next frontier must not recommend the same
=multi-clause-rg-query= as the first action again. The first follow-up should
move to a different evidence axis, such as =fd-query= owner discovery or
package-local owner expansion, while keeping =multi-clause-rg-query= as a lower
ranked retry only when the user or analyzer needs another lexical refinement.
This prevents deep searches from spending an extra turn repeating the same
query wrapper instead of converging on an owner.

Query-wrapper path ranking should prefer owners with stronger normalized query
axis coverage before basename exactness. Normalization may split language-neutral
identifier shapes such as camelCase, PascalCase, snake_case, kebab-case, and path
segments into additional searchable axes, but it must not promote fixed
ecosystem/library labels. A path that covers =resolve=, =module=, =name=, and
=compiler= is stronger than a path that only basename-matches =module=, even if
both are executable source files.

The =rg-query-set= to =fd-query= handoff must preserve raw query tokens in the
materialized =fd= command. Compact coverage fields may still render normalized
lowercase terms, but the executable handoff should keep identifier boundaries
such as =resolveModuleName= so the next path-ranking stage can derive
language-neutral identifier axes.

When a first-stage pipe packet is low quality because the query is broad or package-drifting, graph-turbo should still materialize a bounded =fd-query= owner-discovery action from owner/path-axis terms even when no symbol term is present. This prevents a wide content =rg= turn from becoming the only route to owner recovery. The selected fd terms must exclude ASP protocol/action words such as query, fd, rg, owner, graph, turbo, command, and frontier; it must not exclude or promote ecosystem/library labels through fixed word lists.

Graph-turbo owner candidate ranking must prefer evidence-dense local owners before first-seen candidate order. A weak early owner with only one local item hit must rank below an owner that covers more query axes, has denser parser/finder-local hits, exposes more distinct local symbols, or has stronger path/fd/package-path evidence. First-seen order is only a deterministic tie-breaker after those language-neutral evidence signals. This ranking rule is algorithmic and parser/finder-owned; it must not hard-code ecosystem labels, library names, or project-specific symbols as shortcut boosts.
Owner candidate ranking may also consume package-axis coverage as a cluster signal. When two owners have comparable local evidence, the owner whose path-derived package cluster covers more query axes across its candidate set should outrank a first-seen owner from a package cluster with weaker aggregate coverage. The package cluster is derived from path topology, such as workspace member and package-root path segments, not from repository-specific package names, ecosystem labels, or library symbols. This prevents monorepo source-index drift from selecting a cross-package owner merely because it appeared earlier while preserving deterministic first-seen order as the final tie-breaker.

Provider-emitted path-role owners may participate in ranking only when the role is explicit evidence from a language provider, source-index row, or shared schema field. ASP core must not derive package surface, initializer, or index semantics from filename lists; without provider-owned role evidence, ranking falls back to query-axis coverage, parser/finder-local evidence, package/topology coverage, and stable path order.
When =fd-query= recovers an owner and materializes =owner-items=, the handoff query must not forward the flat fd query unchanged. It should remove protocol/action words such as query, search, fd, rg, owner, frontier, action, and command; prefer declaration-friendly semantic terms and language-neutral morphology variants before path-only owner axes; and keep path-covered terms only as backoff evidence. This prevents a correct owner recovery step from immediately selecting a file-header or path-window selector instead of the owner-local implementation item.

Path-role facts such as package surface, package initializer, module index, public barrel, test artifact, fixture, template, example, or benchmark are provider/language-owned evidence. ASP core and graph-turbo must not infer those roles from filename lists such as language-specific package entrypoints. When such facts matter, the language provider must emit them through parser-owned declarations, provider graph facts, source-index metadata, or a shared schema field; graph-turbo may then consume the explicit role evidence as a bounded ranking signal.
Package-path augmentation is a bounded missing-axis repair, not a recursive package fanout. If native finder candidates already cover an underscore/package query axis through path, symbol, or text evidence, ASP must not rescan the entire package tree and add every descendant file only because an ancestor directory matches the package term. When augmentation is needed, it should target only package axes missing from the current candidate set, preserve query-owner seed semantics through path-derived package coverage, and keep the trace count as analyzer evidence. This is a performance and precision rule: package names are path/topology evidence, not permission to inflate candidate count.

Secondary artifact roles such as tests, examples, fixtures, templates, and benchmarks are bounded query-wrapper ranking penalties, not absolute masks. Under equal or close query-axis evidence source owners should remain preferred, but a concrete secondary owner with clearly stronger query-axis coverage must outrank a low-coverage source-adjacent path.

Owner-local selector ranking may create query-axis window candidates when declaration-name matches are too weak. The candidate must be derived from the current owner file, the materialized query terms, and parser-owned item/block boundaries or a bounded local context window; it must clear a high query-axis coverage gate before competing with declaration candidates through deterministic query-axis coverage. This is an algorithmic graph-turbo selector-quality rule, not a fixed ecosystem-symbol shortcut: providers must not hard-code library, framework, or package-specific labels to manufacture selector confidence.

Graph-turbo must also carry an explicit first-stage topology state model. Topology is the analyzer/status decision layer that records which evidence graph was available before the first stage chose owner discovery, owner-local expansion, query-pack refinement, dependency topology, test reachability, or selector-code expansion. It is not another agent-facing stdout field bundle. Normal =search= output should continue to expose only compact graph facts that directly help the next action. Developer/history mode and sandtable reports may persist topology snapshots so quality analysis can connect a bad answer to the graph shape and transition that caused it.

Topology state is language-neutral and evidence-derived. It may use packet facts such as query-pack quality, package cohesion, matched query axes, owner candidate density, parser/finder-local hits, selector miss/coverage state, repeated-action memory, source-index/finder/provider provenance, latency, and packet size. It must not encode ecosystem labels, library names, or project-specific symbols as rules. If a domain label matters, it must enter through parser-owned declarations, provider semantic facts, dependency/package facts, finder evidence, or analyzer receipts.
Candidate acquisition and graph construction MUST preserve one snapshot
continuity boundary.  A dynamic overlay carries the exact
=SourceSnapshotEvidence= produced while its candidates were collected.  The
source acquisition trace MUST retain that snapshot and any artifact digest
actually produced by that acquisition.  It MUST NOT synthesize a source-index
artifact identity for an ephemeral overlay.  Graph-turbo MUST
graph-turbo MUST compare the acquisition snapshot root with the request base
snapshot before ranking any candidate.  A mismatch is a deterministic retry or
snapshot miss; candidates from one snapshot MUST NOT be labeled or ranked as
evidence from another.  Source-index refresh does not substitute for this
check, because a query gate may intentionally select the dynamic overlay
instead of the persisted index.

Owner-item graph artifacts use the domain
=asp.graph-owner-item-artifact.v1=.  The digest is =blake3= over
length-delimited bytes for the snapshot root, owner path, query, route state,
and every ordered graph evidence field.  A renderer receives that digest; it
MUST NOT accept a snapshot root, source-index digest, debug string, or fixed test
literal as a substitute for the graph artifact identity.

Topology must model monorepo and submodule boundaries as first-stage graph facts. A workspace that declares submodules, nested language harnesses, or package roots is not a flat owner namespace: topology nodes must connect the workspace to provider roots and submodules, and submodules must connect to owner paths that live under their declared path. Owner ranking, seed planning, and action scope selection may then consume these membership edges as language-neutral cluster evidence. The rule is path/topology derived; it must not special-case this repository, a package name, a language ecosystem, or any library symbol.

Project and dependency topology roots are provider-owned facts. ASP core must not discover them by repository-wide scan limits, hard-coded ignored-directory lists, or language-specific filename tables. Each language provider manifest declares its project markers and dependency markers from its native package/project manager surface, such as Cargo manifests, npm/pnpm/yarn package files, Python project files, Julia project manifests, or Gerbil package descriptors. Graph-turbo may consume those declared marker files as =language-project=, =project-marker=, and =dependency-marker= nodes, but deeper package membership, dependency paths, project references, source roots, and lockfile semantics remain provider/package-manager facts. Document providers that have no package manager should declare empty topology markers rather than letting ASP infer one.
Graph-turbo ranking may consume that topology through language-neutral score adjustments. The first implemented adjustment is =localEvidence=: owner nodes with dense owner-local graph support, such as contained item/syntax nodes or covering test nodes, receive a bounded score boost, while path-only owner seeds with no local evidence receive a bounded penalty. The score reason is emitted as =topology-local-evidence= in rank explanations. This is an algorithmic graph rule over node kinds and relations; it must not special-case ecosystem names, framework labels, package names, or project-specific symbols.

Dependency seed caches must use provider-emitted dependency-topology packets and their fingerprint inputs. ASP core must not add language-id branches for manifest filenames, workspace expansion, lockfile semantics, or dependency parsing; those facts belong to the language provider contract and the shared dependency-topology schema.
Sandtable validation should report topology snapshots and topology transitions alongside outcomes. A deep Rust or TypeScript question should be replayable as:

#+begin_src text
question -> seed-quality -> topology-state -> action-frontier ->
command/result receipts -> answer -> analyzer judgment -> graph-turbo change plan
#+end_src

The quality question is then precise: did the first-stage topology expose the right owner/package/item/dependency/test shape before the agent spent turns? This gives graph-turbo a stable optimization target beyond adding output values.

The large-library report chain must treat first-stage topology adjustments as explicit ablation axes. The query-first-stage batch includes =no-local-evidence= and =no-topology-membership= alongside =no-query-seed-prior=, =no-package-cohesion=, and =no-query-clause-coverage=, and sandtable summaries persist the variant list plus local-evidence/topology-membership benchmark metrics for analyzer/report use. The optimization-analysis packet should rank all query-first-stage ablations, attach comparison deltas against the winning variant, and expose dedicated focus entries so reports can tell whether disabling owner-local topology evidence or submodule/package membership evidence helped or hurt. These fields are calibration evidence for graph-turbo; they must not be rendered as required normal =search= stdout.

The same analyzer packet may expose cost summaries and performance bottleneck
ranks derived from receipt metrics such as elapsed time, ASP command count, and
stdout bytes. These are report-chain calibration facts for deciding where to
optimize graph-turbo execution, such as route selection or invariant graph work
reuse. They are not ARI seed fields and must not be required in normal
=search= stdout.

Graph-turbo sparse backend caching must use a structural backend fingerprint,
not the full rank fingerprint. The sparse backend depends on graph structure and
profile relation weights, while rank fingerprints also include seeds, query
clauses, query-adjustment policy, budgets, and render/window settings. Reusing
the backend across query-first-stage ablation variants is an algorithmic
performance optimization; it must preserve the full rank fingerprint on the
result packet so calibration can still distinguish variant behavior.

Runtime computation caches may also reuse graph/profile/seed-bound work after
the sparse backend is stable. Multi-source hop depth, typed PPR, and reachable
edge filtering are deterministic for the structural backend fingerprint, seed
ids, max depth, and PPR personalization weights. Benchmark and result packets may
expose =depthCacheStatus=, =pprCacheStatus=, and
=reachableEdgesCacheStatus= as analyzer/report evidence. These statuses measure
execution reuse; they must not change graph ranking semantics.

Terminology is deliberately narrow:

Analyzer-only observability is deliberately outside ARI. Developer/history
mode may persist command receipts, prompt-output bytes, replay artifacts, and
machine-oriented analysis metadata as cache artifacts, but normal =search=
stdout must continue to expose only the compact graph facts useful for the
agent's next reasoning step. The sidecar metadata exists for sandtable
analysis, graph-turbo calibration, repeated-trigger diagnosis, latency/size
measurement, and report generation. It must not become a required field in the
agent-facing render surface, and providers must not depend on client-specific
developer-mode switches to satisfy the shared search contract.

- =frontier= means locator/next-action candidates selected from typed facts.
- Owner/topology-only graph slices MUST NOT expose =rank=, =frontier=,
  =rankedEvidence=, or =evidenceFrontier= as agent next-action selectors. If a
  graph only contains owner, workspace, provider-root, submodule, search, or
  query nodes, the renderer should collapse it to compact owner evidence plus
  explicit omissions. Repeating topology rank/frontier in that state is a
  route-efficiency risk, not useful graph guidance.
- =ARI= means the line-oriented agent render interface: the last-mile stdout
  serialization read by an agent, not the internal data model.
- =typed render IR= means the renderer-owned object model between JSON packets
  and ARI lines.  It contains typed aliases, locators, rank, frontier, omit,
  avoid, and display fields, never preformatted command strings.
- =compact graph render= means the prompt-facing serialization format for those
  facts; it is not a second kind of frontier.
- =code compact= means parser/format-aware code projection used by query/code
  surfaces.  Search/frontier output must not pretend to be code compact.

LLMs may infer structure, but the protocol must not depend on inference for
grammar.  Compact graph output therefore follows six invariants:

- Typed Node: every alias declares a node kind.
- Typed Target: every alias target declares a target role such as =path=,
  =term=, =pkg=, =symbol=, or =range=.
- Typed Edge: every relation has an explicit relation label.
  Visible edge endpoint rule: prompt-visible =evidenceEdges= may only reference aliases that are defined in prompt-visible =evidenceNodes=. Full graph/debug surfaces may retain edges to omitted nodes, but the default =search pipe --view seeds= projection must filter or rewrite those edges so the agent never has to infer a missing alias definition.
- Algorithmic Rank: =rank= comes from =searchSynthesis.algorithm=, not renderer
  sorting.
- Executable Frontier: every =frontier= entry maps to a schema-owned typed
  follow-up action before any ARI text is emitted.
- Bounded Locator: every read/edit/query frontier has an exact locator or a
  target that the provider can recover into one.

Line selector compatibility is intentionally narrow. Compact graph aliases, =syntax= rows, action frontier entries, and default owner/item rows must put parser-owned identities in executable selector fields: =structuralSelector=, semantic handle ids, native fact ids, owner path plus item name, or a compiled tree-sitter query recipe. They may carry =displayLineRange= and =sourceLocatorHint= beside that identity so humans can inspect the range and the trusted materializer can perform an exact source transport later.

The trusted materializer never converts a display/source-locator hint into an
executable query.  Search discovery returns parser-owned structural selectors.
Exact materialization emits only
=asp <language> query --selector <structuralSelector> --projection source= or
=--projection callable-skeleton=.  Production code must not recover actions by
parsing =@path:start:end= aliases from ARI text.

The public exact-query CLI is a closed typed surface.  It MUST parse
=--selector=, the required =--projection=, and optional diagnostic =--json=
before activation loading, Runtime Server lookup, generation recovery, or
provider dispatch.  Unknown arguments fail at that boundary.  Historical
=--code= and =--names-only= flags are removed contracts, not deprecated aliases:
no provider, hook guide, fixture, or installed runtime may parse or recommend
them.

* Agent-driven search flow boundary

The compact graph renderer is part of an agent-driven search flow.  It does not
move natural-language intent parsing into the harness.

The intended flow is:

#+begin_src text
user intent
  -> agent/LLM interprets the task
  -> agent reads search guide and provider capabilities
  -> agent runs search prime for the initial graph frontier
  -> agent chooses a typed reasoning profile and selectors
  -> provider returns schema-backed graph facts/evidence
  -> agent chooses query/read/edit/test actions
#+end_src

=search guide= tells the agent which deterministic flows and evidence profiles
exist.  =search prime= returns an initial graph frontier without user intent.
=search reasoning <profile>= consumes typed selectors chosen by the agent and
returns schema-backed facts.  None of these commands accepts natural-language
=--goal=, =--intent=, or task prose, and none of them performs agent planning.

Valid reasoning commands are shaped by guide-declared profiles:

#+begin_src shell
<lang-harness> search reasoning owner-query \
  --owner <project-path> \
  --query <term> \
  [--dependency <pkg>] \
  [--view facts|seeds|both] \
  .

<lang-harness> search reasoning query-deps \
  --query <term> \
  --dependency <pkg> \
  [--view facts|seeds|both] \
  .

<lang-harness> search reasoning owner-tests \
  --owner <project-path> \
  [--view facts|seeds|both] \
  .

<lang-harness> search reasoning finding-frontier \
  --query <rule-id-or-diagnostic-id> \
  [--owner <project-path>] \
  [--view facts|seeds|both] \
  .
#+end_src

The graph feature is the prompt-facing projection for guide, prime, and
reasoning evidence.  It compresses the returned facts and frontier into a
low-token graph, but the agent still owns intent-to-flow selection.

* Non-goals

This RFC does not introduce a new top-level =graph= command.  Discovery remains
=search= with views such as =seeds=, =hits=, =graph=, and =both=.
=asp graph render= is a machine adapter for rendering a
validated packet; it is not an agent-facing discovery command and must not
replace =search= in agent workflows.

This RFC does not make graph projection an =owner= special case.  Prime, owner,
dependency, query-set, ingest, tests, policy, and item-oriented search/query
surfaces should all expose graph facts when they can produce parser-owned nodes,
edges, rank, or next actions.

This RFC does not make Mermaid, DOT, Graphviz, or Markdown diagrams a prompt
protocol.  Those formats are trained priors, but they are diagram-first and
too verbose for the harness's agent path.

This RFC does not replace JSON schema packets.  =semantic-graph.v1= and
=semantic-search-packet.v1= remain the canonical machine contract.

* Canonical data boundary
** Typed search projection boundary

Language providers MUST produce a schema-valid =SemanticSearchPacketV1= from
parser-owned facts before any agent-facing rendering occurs. A provider MUST
NOT render graph, owner, evidence, or topology text and then reparse that text
to recover semantic facts.

The only rendering flow is:

#+begin_src text
SemanticSearchPacketV1
  -> SearchProjectionRequestV1
  -> SearchProjectionRenderer
  -> RenderedSearchProjectionV1
#+end_src

=SearchProjectionRequestV1= selects a semantic projection such as =owner=,
=evidence=, or =topology=. Output density is an independent renderer option
with values such as =terse=, =standard=, and =expanded=. Density MUST NOT
create a parallel packet type, graph model, cache authority, or renderer
interface.

=SearchProjectionRenderer= has one implementation boundary owned by the
lightweight =agent-semantic-search-projection= kernel. Language harnesses,
root ASP, and client adapters
consume that boundary; they MUST NOT own copied graph renderers, item seed
parsers, line-protocol reparsers, or language-private projection pipelines.

Canonical item identity remains provider-owned. The shared renderer validates
and transports =CanonicalItemSelector= without reconstructing it from
=ownerPath=, =read=, source ranges, symbol strings, or language-specific
hints. A missing canonical selector is a typed projection error, never an
owner-only fallback and never a range selector.

All registered-language gates MUST prove the following invariants against real
provider packets:

- the provider packet validates before rendering;
- owner, evidence, and topology projections consume the same packet identity;
- changing density does not change nodes, selectors, ranks, or evidence facts;
- no provider-local renderer or text-to-packet semantic bridge is reachable;
- line ranges remain display metadata and cannot become item identity.


The graph feature is a renderer over schema-owned facts:

#+begin_src text
provider parser facts
  -> semantic-search-packet nodes/edges/searchSynthesis/nextActions
  -> typed render IR
  -> safe ARI encoder
  -> agent compact graph feature

semantic-search-packet typed action
  -> trusted materializer
  -> argv
#+end_src

Provider-private maps must not determine prompt-visible rank, relation labels,
or next actions.  If a relation or action changes the agent's decision, it must
be representable in the JSON packet before it is rendered in compact graph
output.

Project topology is a shared graph fact layer, not a Rust-specific dependency
shortcut.  The root ASP adapter may emit only language-neutral topology facts it
can prove without parsing a provider manifest: the invocation workspace root,
the current provider root, and VCS-registered submodules such as =.gitmodules=
entries.  Language-specific package, target, module, import, and test topology
belongs to the active provider and must be projected through provider-owned
graph facts.  In a multi-language repository with nested submodules, the shared
graph starts with =workspace=, =provider-root=, and =submodule= nodes, then lets
Rust, TypeScript, Python, Julia, Gerbil, Org, or future providers add their own
package/module facts under those roots.  This keeps topology useful for search
ranking while preventing the ASP binary from hard-coding Cargo, tsconfig,
pyproject, Project.toml, gerbil.pkg, or other language layouts.

Topology must participate in the graph request, not only in debug output.  A
=graph-turbo-request= may include the =topology= surface, shared topology node
kinds such as =workspace=, =provider-root=, and =submodule=, and shared
relations such as =has_provider_root= and =has_submodule=.  If topology changes the
seed frontier, owner ranking, or next action order, that influence must be
explainable from those packet facts or provider-owned topology facts.

ARI keeps the useful line interface and removes the unsafe part: untyped,
injectable inline strings that production code later splits to recover
semantics.  JSON packets remain the source of truth for nodes, edges, locators,
rank, frontier, actions, profiles, trace, explanations, omission, avoidance,
and metrics.  ARI is only the prompt serialization of a typed render IR derived
from that JSON packet.

The safe ARI encoder owns escaping, single-line safety, locator canonicalization,
renderer-assigned alias stability, field length limits, control-character and
ANSI removal, and display truncation.  It must not derive rank, infer missing
relations, choose actions, or materialize commands.

Production code must not recover actions by ad hoc parsing ARI lines such as
=rank=..., =frontier=..., =A.code=, or =next=owner:...=.  A strict ARI parser is
allowed only for golden tests, fuzzing, replay/backcompat, transcript recovery,
and debug validation.  Executable commands are built only from typed capability
actions and registry/workspace policy by a trusted materializer.

Provider facts may supply parser-owned data, capability ids, targets, locators,
and safety constraints; they must not supply executable shell strings as search
facts.  Every ARI alias, locator, frontier action, and omit/avoid reference must
correspond to a node or action in the source JSON packet.

The incremental fast-search landing path is to expose typed =actionFrontier[]=
facts in the =semantic-graph-turbo-request.v1= packet before or alongside
prompt-visible ARI action rows.  This applies to =search pipe= and the
query-wrapper surfaces =asp fd -query= and =asp rg -query=.  Each action fact
carries the renderer action id, action kind, capability id, target, target role,
and typed fields such as =selector=, =ownerPath=, =query=, =queryClauses=,
=scope=, =recipe=, or =names=.  It must not carry =command=, =argv=, or
provider-supplied shell strings.  The visible =nextCommand= line remains a
display convenience materialized from these typed facts, not a protocol fact
that production code parses back into an action.  =search pipe --view
graph-turbo-request= is the typed packet spelling for this migration.

For =asp rg -query= query-wrapper output, repeated =-query= clauses mean the
agent has already accepted a query-pack refinement.  In that case the typed
=actionFrontier[]= should rank =multi-clause-rg-query= ahead of the broad
=fd-query= recall fallback.  A single flat =asp rg -query= recall probe may
still rank =fd-query= first to discover owner scope before content search.
The packet-level =queryTerms= field is the lexical term set used for seed and
rank calculation; it must not include display-only query-pack separators such as
=+=.

Graph-turbo seed selection is also a schema-owned phase, not an implicit detail
hidden behind =seedIds=.  A request may carry =seedPlan= with =phase=,
=algorithm=, =reason=, query/fallback booleans, candidate and owner counts,
selected seed count, and the selected =seedIds=.  The first phase prefers a
normalized query seed when the agent supplied query text, then falls back to
bounded owner seeds only when there is no query seed.  These diagnostics are
machine-packet facts for sandtable analyzers and replay; normal agent-facing
search output should expose only decision-level actions such as =recommendedNext=
and =avoid=, not raw seed counters.  An analyzer can therefore separate
seed-quality defects from ranker defects before blaming the later graph traversal
or compact render.

When =seedPlan.recommendedActions= contains both =split-query-pack= and
=narrow-owner-scope=, the action frontier may promote an =rg-query-set= action
ahead of broad single-query recall.  The promotion is deliberately gated on both
signals: =split-query-pack= alone is an analyzer hint, and =nextQueryPackHint=
alone is display guidance.  A concrete owner-local path such as =owner-items=
must remain the preferred action when seed diagnostics show a single stable owner
instead of owner drift.  Implementations should derive this from an internal
typed seed decision or seed-action intent; =recommendedActions= remains a
report/analyzer projection, not the authority that production action planning
parses as behavior.

* Dependency topology cache boundary

A dependency-topology cache hit is authoritative only when the current invocation recomputes the manifest and lockfile fingerprints and validates every contributing source-file hash committed by the packet. If any fingerprint is missing or mismatched, the cache state is =stale=, contributes no dependency nodes or semantic negatives, and routes to the explicit provider/feed refresh path. A previously validated packet or unchanged provider-registry fingerprint MUST NOT authorize reuse.

Graph-turbo may consume dependency topology as schema-owned evidence, but it
must not cache source text as a ranking shortcut.  The stable cache boundary is
manifest and lockfile state plus parser-owned usage locators:

#+begin_src text
manifest/lockfile fingerprint -> dependency/version nodes
source imports -> import-site/api-symbol locators
docs/tests/examples -> evidence edges
graph-turbo profile -> frontier rank
#+end_src

=semantic-dependency-topology.v1= owns this packet shape.  It records the
language id, package manager, manifest hash, lockfile hash, package name,
source files that contributed import-site evidence, and typed graph nodes such
as =package=, =dependency=, =dependency-version=, =import-site=, and
=api-symbol=.  Edges such as =depends_on=, =version_locked=, =imports=,
=uses_api=, =documented_by=, =example_of=, and =tested_by= are graph facts for
ranking and search-scope narrowing.

The contract is intentionally evidence-first:

1. manifests and lockfiles are the dependency truth

2. source scans only attach usage locators to known dependencies

3. packet fingerprints cover topology facts and source-file hashes, not source
   text bodies

4. providers may omit this packet until they can emit equivalent facts, but they
   must not replace it with provider-private dependency heuristics when the
   facts change search frontier behavior

This keeps dependency API calibration available to =search pipe= and
=query-deps= without teaching agents to broad-grep for third-party API terms or
reuse stale code windows from a content cache.

Field names are canonical, not provider aliases.  For example, query-set count
is derived from root-level =querySet=, and source read locators on graph
frontier actions use =searchSynthesis.seeds[].read=.  The shared renderer must
not accept alternate names such as =locator= or =readLocator= because aliases
let providers drift while producing superficially similar prompt text.

The prompt-facing graph renderer is shared protocol logic.  Native language
providers own parser facts and schema-valid packets; they do not own separate
long-term compact graph render algorithms.  The renderer lives in
=agent-semantic-protocol= so Rust, TypeScript, Python, Julia cache paths, local
ASP cache hits, and Cloud Flight results project through the same alias,
edge, rank, frontier, profile, omit, and avoid rules.

Language providers under =languages/= invoke the renderer through a process
boundary:

#+begin_src shell
asp graph render --packet - --view seeds
#+end_src

That shell-out is the provider integration boundary, not a temporary escape
hatch.  Provider crates and packages must not link or vendor the renderer
library, including =languages/rust-lang-project-harness=.  The target hot path
described by RFC 008 is ASP's Rust-side cache/query/render path over validated
provider packet artifacts or native index rows.

* Projection grammar

The projection has one view-native header line and a small set of compact fact
lines:

#+begin_src text
[search-<view>] (q=<query>|owner=<path>|root=<path-or-.>) [querySet=<n>|terms=<n>] [selector=<selector>] [scope=<scope>] [view=<view>] alg=<searchSynthesis.algorithm>
legend: aliases ID:kind; node ID=kind:role(value)!next; edge SRC>{DST:rel}; frontier ID.next
aliases=G:search,...
ID=<nodeKind>:<targetRole>(<target>)[!<action>]
G>{ID:relation,ID:relation}
SRC>{DST:relation,DST:relation}
(SRC,SRC)>DST:relation
rank=ID,ID,ID frontier=ID.action,ID.action
entries=profile(ID,ID=>return+return),profile(ID=>return)
omit=<omitted-semantic>[,<omitted-semantic>]
avoid=<anti-action>[,<anti-action>]
#+end_src

This graph projection is schema-derived and prompt-facing.  The default
agent-facing =--view seeds= output renders the minimal graph frontier as
view-native =search= output, aliases, and the combined =rank= / =frontier=
line.  It must not also render independent =|seed= or =|synthesis= rows as a
second action protocol.

The same shape applies to code-level graphs:

#+begin_src text
[search-query] q=<query> selector=<path> alg=<algorithm>
ID=<nodeKind>:<targetRole>(<target>)[@<path-or-range>][!<action>]
SRC>{DST:relation,DST:relation}
rank=ID,ID,ID frontier=ID.action,ID.action
entries=profile(ID,ID=>return+return),profile(ID=>return)
omit=<omitted-semantic>[,<omitted-semantic>]
#+end_src

Alias ids are packet-local.  They are stable only within one rendered packet
and must not be copied into source paths, JSON paths, or edit commands.
=targetRole(target)= tells the agent and parser how to interpret the target
value.  =!action= declares an action available from a node.  =frontier=
selects the seed actions for this packet from those node actions.  The
=entries= line is optional and names guide-declared reasoning profiles whose
typed selectors match aliases rendered in this packet; each selector inside
=profile(...)= is a packet-local alias id, and the =...=>...= suffix names the
return entries exposed by that profile.  The
micro-legend line is the minimal grammar contract for agents that have not
recently read this RFC.
Every selector alias used by an =entries= row must resolve to the current
packet's =aliases=...= declaration, and known shared profile selectors
must resolve to the profile's node-kind catalog.  For example,
=owner-query(O,Q=>...)= requires =O= to resolve to an =owner= alias and =Q= to
resolve to a =query= alias; =query-deps(O,T=>...)= is invalid even if =O= and
=T= are otherwise valid graph aliases.  This is a parser-checkable contract, not
a compatibility hint for the model to infer.  The structured catalog lives in
=semantic-compact-graph-render.v1.schema.json= as =reasoningProfileContracts=,
and =semantic-search-packet.v1.schema.json= validates implemented profile
packets against the same selector order and return-entry contract.

Profile names are shared protocol catalog entries, not compatibility aliases or
provider-private labels.  The initial catalog is =owner-query=, =query-deps=,
=owner-tests=, =finding-frontier=, and =feature-cfg=.  Adding another
prompt-facing profile name requires a schema/RFC update first so every provider
can either emit the same meaning or deliberately omit it.
Provider guides should print this catalog explicitly, for example
=|catalog reasoningProfiles=owner-query,query-deps,owner-tests,finding-frontier,feature-cfg entries=owner-query,query-deps,owner-tests,finding-frontier,feature-cfg routes=read-frontier=.
Direct-read or repair flows that are not reasoning profiles must be rendered as
routes or commands rather than as =entry= rows.
Provider-specific guide lines may list fewer =entries= than the shared catalog
until that provider implements the matching reasoning command.  Rust carries
=finding-frontier= and =feature-cfg= through the existing =--query= selector
slot; adding =--finding= or =--feature= would be a new public command surface and
needs its own RFC/schema pass.
When a provider implements one of these profiles, the returned packet must carry
the selector as a typed graph action, for example =nextActions=[{kind:"finding",
target:<finding>}]= or =nextActions=[{kind:"feature", target:<feature>}]=, so
the shared renderer can emit =F:finding= / =F:feature= aliases and concrete
=entries= rows without relying on model inference.

The aliases declaration is strict in compact mode: every alias id that appears
in node lines, edges, =rank=, or =frontier= must be declared with its node kind,
for example =aliases=G:search,O:owner,S:symbol,S2:symbol=.  A prefix
legend such as =S*=symbol= may be introduced later as a dense-mode extension,
but it is not the default compact grammar because it requires parser and LLM
inheritance rules that are not otherwise needed.

=G= is the packet-local search root.  It is declared by the legend entry
=G:search= and by appearing as an edge source such as =G>{...}=.  Renderers
must not emit a standalone root alias line such as =G=search:result!query=:
that line repeats the legend, looks like an actionable node, and increases the
chance that an agent treats the root as a follow-up target.  =G= gives
synthesis-derived edges a real source node without making the =rank= /
=frontier= line act as a graph node.  =G= is not a recommended follow-up action
and must not appear in =rank= or =frontier=.  When a provider has no
parser-owned =imports=, =calls=, or =covers= edges for a surface, it may still
render honest synthesis-derived relations from =G= such as =selects=,
=matches=, =covers=, =uses=, =imports=, =contains=, =explains=, =flags=, and
=gates=.

* Line protocol atomics

Compact graph output is line protocol.  Each rendered graph fact is a complete
line atom.  The micro-legend and aliases declaration lines are each valid only
as one complete line, for example:

#+begin_src text
legend: aliases ID:kind; node ID=kind:role(value)!next; edge SRC>{DST:rel}; frontier ID.next
aliases=G:search,O:owner,T:test
#+end_src

Renderers, schema examples, JSON fixtures, and sandtable assertions must not
split this line into structural fragments such as:

#+begin_src json
["aliases=", "G:search,O:owner"]
#+end_src

That shape is invalid even though =aliases=...= itself is valid.  It
turns a declaration key into a standalone assertion and makes the next line
look like a continuation.  The standalone root alias =G=search:result!query=
is also forbidden by this RFC.

When tests need resilient substring matching rather than exact output matching,
they may assert a stable prefix that includes the first alias assignment, such
as =aliases=G:search=.  They must not assert only the bare =aliases= key.
Exact-output fixtures should store the full aliases declaration line.  JSON
arrays that model =stdoutContains= are lists of independent line substrings,
not a way to continue a graph grammar token across elements.

* Owner search example

#+begin_src text
[search-owner] q=src/classifier.rs scope=tests/unit/classifier/routes alg=bounded-reachability-depth1
legend: aliases ID:kind; node ID=kind:role(value)!next; edge SRC>{DST:rel}; frontier ID.next
aliases=G:search,C:owner,M:owner,P:owner,W:test,R:test
C=owner:self(root)!items
M=owner:path(src/command/mod.rs)!owner
P=owner:path(src/protocol.rs)
W=test:path(wrappers.rs)!tests
R=test:path(raw_search.rs)!tests
G>{C:selects,W:covers,R:covers,M:selects,P:selects}
C>{M:imports,P:decision}
(W,R)>C:covers
rank=C,W,R,M,P frontier=C.items,M.owner,W.tests,R.tests
avoid=raw-read
#+end_src

This says:

- =C= is the selected owner and its next action is =items=
- =M= and =P= are frontier owners
- =W= and =R= are tests that cover =C=
- =G= tells the agent these nodes were selected by this search result, not by
  source-order adjacency
- the attention order is =C,W,R,M,P=
- the selected seed actions are =C.items,M.owner,W.tests,R.tests=
- raw source reads are explicitly not the next action

The paths appear once.  The owner/test roles appear once.  Same-relation test
edges are grouped.  The agent does not have to infer rank from output order.

* Query item example

#+begin_src text
[search-query] q=command_source_paths selector=src/tool_action.rs terms=1 view=seeds alg=exact-item
legend: aliases ID:kind; node ID=kind:role(value)!next; edge SRC>{DST:rel}; frontier ID.next
aliases=G:search,I:item,A:item,L:item,B:item,P:item
I=item:symbol(command_source_paths)@221:241!code
A=guard:range(range_paths.nonempty@224:226)!read
L=loop:range(path_like_tokens@228:239)!read
B=branch:range(embedded.empty@230:233)
P=branch:range(embedded.present@234:238)
G>{I:selects,A:contains,L:contains}
I>{A:return,L:collect}
L>{B:push_path,P:push_embedded}
rank=I,A,L,B,P frontier=I.code,A.read,L.read
omit=trivia,comments,blank-lines
#+end_src

For same-file code graphs, =@start:end= inherits =root=.  Cross-file nodes
must include a project-root-relative path before the range, for example:

#+begin_src text
T=test:range(tests/tool_action.rs@12:30)!tests
#+end_src

The compact graph is not an editable source replacement.  It is a reasoning
surface that tells the agent which item or block to expand through provider
query/read actions.

Owner-local item search uses the same rule, but the selected owner is context
and the matched items are the immediate frontier.  The header must preserve the
fact that this is an owner-local item query rather than an ordinary owner
frontier:

#+begin_src text
[search-owner] q=crates/agent-semantic-hook/src/tool_action.rs pkg=crates/agent-semantic-hook selector=items querySet=6 alg=item-frontier
legend: ID=kind:role(value)!next; edge SRC>{DST:rel}; frontier ID.next
aliases: graph:{G=search,O=owner,Q=query,I=item,H=hot}
O=owner:path(crates/agent-semantic-hook/src/tool_action.rs)!owner

I2=item:symbol(collect_tool_actions)@rust://crates/agent-semantic-hook/src/tool_action.rs#item/function/collect_tool_actions!syntax

H2=hot:symbol(nested_action_from_tool_use)@rust://crates/agent-semantic-hook/src/tool_action.rs#item/function/nested_action_from_tool_use!syntax
syntax I selector=rust://crates/agent-semantic-hook/src/tool_action.rs#item/method/payload_string/scope/implementation-owner/type/ToolAction
syntax I2 selector=rust://crates/agent-semantic-hook/src/tool_action.rs#item/function/collect_tool_actions
syntax I3 selector=rust://crates/agent-semantic-hook/src/tool_action.rs#item/function/nested_tool_actions
syntax H selector=rust://crates/agent-semantic-hook/src/tool_action.rs#item/function/command_source_paths
syntax H2 selector=rust://crates/agent-semantic-hook/src/tool_action.rs#item/function/nested_action_from_tool_use

G>{O:selects,Q:matches}
O>{I:contains,I2:contains,I3:contains,H:contains,H2:contains}
Q>{I:matches,I2:matches,I3:matches,H:revise,H2:revise}

rank=H,H2,I,I2,I3,O
frontier=H.syntax,H2.syntax,I.syntax,I2.syntax,I3.syntax
revise=command_intent->command_source_paths,from_action->nested_action_from_tool_use
omit=code,projection-nodes,large-item-text
avoid=inline-code-in-search,raw-read,repeat-owner
#+end_src

This avoids a common search loop: after =search owner <path> items --query ...=,
the selected owner has already been expanded, so =O.owner= is not the next
frontier action.  The owner remains in =rank= as context, but hot revision
targets and matched items rank first and their bounded =code= or =outline=
actions are the recommended follow-up.  Edges keep the meanings separate:
=G>{Q:matches}= says the search matched the owner-local query, =Q>{I:matches}=
says the item matched it, =Q>{H:revise}= says a query term should be revised to
a parser-owned candidate, and =O>{I:contains,H:contains}= records ownership.
Owner-item search output must not inline source code.  It gives exact
structural selectors/frontier only; a follow-up exact =query --projection
source= is the source extraction boundary.

The seed-view renderer is a single selector-preserving projection interface,
not a second symbol search.  Once an item locator carries a canonical
=structuralSelector=, the renderer MUST bind the item node to that complete
selector and MUST NOT reduce it to =syntax:<symbol>=.  Two methods with the
same symbol but different implementation-owner or trait-owner scopes are two
different item nodes and remain independently executable.  This rule applies
to every registered language provider; language-specific parsers produce the
canonical identity, while the shared rendering contract preserves it.

* Compression rules

Compression may remove repeated syntax.  It must not remove decision
semantics.

Allowed compression:

- move shared path context into =root= or =base=
- use =self= for the root owner
- replace repeated paths with packet-local aliases
- group same-relation edges
- attach next action with =!action=
- select seed actions with =frontier=
- omit default/healthy facts
- pack large packets with semicolons in dense mode
- omit graph-debug rows such as =scores=, =paths=, =trace=, =explain=,
  =cache=, and =metrics= from prompt-visible =search pipe --view seeds= output
  when the same response still preserves parser-owned facts, typed relations,
  =queryCoverage=, exact =S1=, and =nextCommand=

Forbidden compression:

- remove relation labels such as =imports=, =covers=, =guards=, or =returns=
- remove =rank=
- hide next or seed actions inside prose
- render seed actions from a path list that is not derived from the graph
- drop exact read locators for hot nodes
- use alias ids as path values
- invent relation labels that are not backed by parser/schema facts
- shorten semantic words without a declared legend and enough packet size to
  amortize that legend

* Read-loop and failure-loop memory

The graph-turbo request may carry =readMemory.seenSelectors=.  These selectors
are not advisory prose.  They are an algorithm input: ranked/frontier nodes
whose exact selector is already present in memory must be suppressed before the
agent-facing frontier is rendered.  The result packet must expose
=algorithmMetrics.readMemorySuppressedCount= and add =seen-selector= to
=avoid= when suppression occurs, so tests and sandtables can prove the loop was
prevented rather than merely observed after the fact.

ASP's =search pipe= runtime reads this memory from
=$PRJ_CACHE_HOME/agent-semantic-protocol/read-loop-memory.json= before building
the graph-turbo request.  The runtime accepts both =seenSelectors=[...]= and
=entries=[{selector:...}]= so sandtable-produced memory can be replayed without
lossy translation.  If the memory packet carries =projectRoot= and it does not
resolve to the current project root, the runtime must ignore it.

Sandtable observations also project command-output memory:

- =readLoopMemory= records exact selector reads, owners, line ranges, command
  fingerprints, output bytes, result fingerprints, read counts, and avoid
  reasons such as =duplicate-read=, =manual-window-scan=, and =repeat-owner=.
- =failureLoopMemory= records executable failure-frontier actions selected from
  =asp <lang> search failure --from-last-check --workspace . --view seeds= output.
- =failureFrontierOutputPrecision= records whether the failure frontier kept
  failure facts, assertions, hot blocks, query profiles, omission facts, avoid
  facts, and executable frontier actions.

These memory packets are part of the loop contract.  A future provider or
client optimization may reduce tokens only if it preserves these facts and the
corresponding precision gates.

* Compact and dense modes

Compact mode is the default for agent exploration.  It keeps one alias line per
high-impact node and one edge line per source or grouped relation.

Dense mode may pack aliases and edges with semicolons:

#+begin_src text
legend: aliases ID:kind; node ID=kind:role(value)!next; edge SRC>{DST:rel}; frontier ID.next

Dense mode is valid only when it preserves the same relation labels, rank,
actions, frontier actions, locators, =omit=, and =avoid= facts as compact mode.
Providers should prefer compact mode for small packets because line boundaries
are useful LLM anchors.  Dense mode is for high-volume graph output where path
and field-name deduplication saves more tokens than the lost line anchors cost.

* Search interface mapping

** Read-only source-index storage boundary

Agent-facing source-index lookup, search, and inspection are strict read-only
operations. They MUST open the Turso client database through a read-only
connection and MUST NOT require write permission on the client directory or
database file. A successful read path creates or mutates no database, WAL,
shared-memory, lock, manifest, layout, or cache-generation file.

The read path MUST NOT bootstrap tables or migrate columns. Schema convergence
belongs to explicit write-intent bootstrap, refresh, import, and rebuild
operations. If a historical source-index schema lacks a required table or
column, lookup returns the structured =cold-required= state with an explicit
=asp cache source-index rebuild --workspace <root>= next action. It does not
run =ALTER TABLE=, classify the condition as =busy=, or escape into a broad
finder/provider fallback.

The performance and recovery gate executes lookup while filesystem writes to
the resolved client directory are denied. The gate requires a bounded lookup
receipt, zero provider processes, zero native finder processes, and an
unchanged client-directory snapshot before and after the command. Lock-pressure
tests remain separate: =busy= is reserved for a real Turso lock conflict, while
=cold-required= means the persisted read model needs an explicit write-side
rebuild.

** Merkle graph artifact authority

EvidenceGraph persistence is a disposable, content-addressed projection of a
pinned source snapshot. It is never mutable workspace truth. Every graph write
MUST receive =SourceSnapshotEvidence= and derive its artifact identity with the
shared BLAKE3 derived-artifact key over at least:

#+begin_src text
artifactKind = evidence-graph
schemaId = asp.evidence-graph-artifact.v1
snapshotRoot = sourceSnapshot.rootDigest
providerDigest = sourceSnapshot.providerDigest
#+end_src

Entity and edge identity MUST be scoped by that graph artifact digest. A path,
language id, node id, or selector is not sufficient isolation. Implementations
MUST NOT upsert different snapshots into one unversioned graph table, and a
reader MUST NOT query graph facts without the pinned source snapshot.

Graph lookup returns exactly one authority state:

- =current=: the expected artifact exists, its persisted source snapshot is
  byte-for-byte equivalent to the requested evidence, and only rows belonging
  to that artifact may be returned;
- =missing=: no graph artifact has been materialized in the derived cache;
- =stale=: graph artifacts exist, but none is authoritative for the requested
  snapshot or the persisted evidence does not match it.

=missing= and =stale= return no graph-owned selectors. They request explicit
projection import or rebuild and never become =no-owner-item-match= or another
deterministic semantic negative. Exact selector resolution remains owned by
=snapshotRoot -> path leaf -> blobDigest -> parser artifact=; graph cache state
has no veto over that chain.

Legacy unscoped =asp_graph_entity= and =asp_graph_edge= storage is removed at
write-side bootstrap because it is a disposable cache. The canonical storage
uses graph-artifact metadata plus artifact-scoped entity and edge tables. A
structural packet import that cannot supply =SourceSnapshotEvidence= MUST NOT
persist an EvidenceGraph projection; generation labels or timestamps are not
substitutes for snapshot authority.

Compact graph receipts expose =authority=, =snapshotRoot=, and
=graphArtifactDigest=. JSON search traces carry the typed source snapshot and
artifact digest. The shared contract is
=derived-source-artifact-evidence.v2=, whose expected digest is available in
all states and whose resolved digest is available only for =current=.

** Exact structural selector boundary

An exact code read is a parser-owned operation, not a file, line-range, or
source-locator read. Every provider MUST classify the input before dispatch:

- a =ready= receipt contains one parser-owned structural selector and its
  identity;
- a =selector-not-materialized= receipt is returned when a query only has a
  file path, line range, source locator hint, project root, or an otherwise
  non-structural identity; and
- a =projection-stale= receipt is returned when a previously materialized
  selector cannot be justified by the current projection.
- a =provider-index-gap= receipt is returned when the provider cannot
  materialize a structural selector for a known owner at all.

The exact-read route MUST NOT fall through from either non-ready state to a
legacy =read-selector=, direct-file, source-window, or line-range route. Those
inputs are display hints only. A provider may expose a separately named
explicit direct-read command when the public product needs one, but it is not
part of exact selector query semantics and must not be selected automatically.

All providers emit the versioned =semantic-exact-selector-receipt.v1= contract.
The receipt carries the structural selector, its language/dialect identity,
status, reason code, and a bounded next action. It gives the main agent an
honest recovery choice rather than silently reading a broad source body.

A =provider-index-gap= is an explicit repair obligation, not a reason to
permit arbitrary raw reads or revive legacy routing. Its receipt names the
provider owner and directs the main agent to repair that provider's selector
projection through the managed ASP workflow. The hook must recognize this
receipt and offer that bounded repair action; repeatedly sending the agent
through resident-child bootstrap without a new actionable step is invalid.

** Incremental selector projection cache

Selector projection is incrementally reusable only through one canonical cache
identity: schema version, provider ABI, selector dialect, normalized workspace
anchor, package/module graph digest, and source digest. Relative workspace
paths such as =./gerbil-scheme= MUST NOT be part of the identity. Provider
projection caches and compiled package caches may store different payloads, but
they MUST derive their identity from this same record.

On an ABI, anchor, module-graph, source, or selector-dialect mismatch, the
provider returns =projection-stale= and rebuilds only affected modules through
an explicit write-intent route. It does not consume a historical artifact or
fall back to a line/file read. A cache artifact is reusable only when it has a
complete structural-selector projection marker for the requested module.

Conformance scenarios cover a stale relative-root artifact, workspace anchor
change, missing structural projection, warm selector hit, and one-module
incremental rebuild. Every scenario asserts zero legacy read-selector,
source-window, provider, and native-finder fallback for exact reads.

Graph is a feature of the whole search interface.  The provider should compute
schema-backed graph nodes, edges, rank, and next actions whenever the selected
search surface can justify them.

=--view seeds= should render the minimal graph feature needed for action
selection: header, aliases for selected/frontier nodes, enough edges to justify
the frontier, =rank=, =frontier=, and =avoid= when relevant.  It is not a
separate seed protocol.

=--view graph= should render the fuller compact graph projection: aliases,
grouped edges, =rank=, =frontier=, =omit=, =avoid=, and any graph facts needed
to explain the selected search surface.

=--view both= may render the graph feature followed by bounded hit, item,
finding, or code facts that are not yet compactly represented by aliases and
edges.  Those extra facts must reference the same graph nodes or locators; they
must not introduce an independent ranking or seed set.

* Seed and synthesis integration

=seed= is not an independent line family in this RFC.  A seed is a selected
frontier action over a graph node.  Compact output renders it inside the
combined =rank=... frontier=...= line, where each =ID.action= must correspond
to a node alias that declares =!action= or to an action represented in the JSON
packet.

=synthesis= is not an independent prose summary in this RFC.  Synthesis is the
graph algorithm evidence that selects the rank, frontier, omit/avoid facts, and
next actions:

#+begin_src text
searchSynthesis.algorithm -> header alg=
searchSynthesis selected/order/frontier -> rank= and frontier=
searchSynthesis edit/test/window/finding frontier -> typed aliases and edges
searchSynthesis.seeds -> frontier=
avoidNextActions -> avoid=
#+end_src

RFC 006 does not define independent =|seed= or =|synthesis= prompt-facing
rows.  Providers that still emit them are pre-RFC-006 implementations and must
converge on the graph-integrated form.  Renderer tests should assert =rank=,
=frontier=, aliases, grouped edges, and =avoid= instead of accepting duplicate
seed/synthesis rows as a second contract.

* Rank semantics

=rank= is not cosmetic output order.  It is the agent attention order selected
by =searchSynthesis.algorithm=.

Renderers must not sort aliases alphabetically, by path length, by file system
order, or by original source order when the graph algorithm provides a frontier
or attention order.  If several nodes have equal algorithmic rank, the provider
may keep parser/source order inside that tie.

* Schema implications

Before implementing this renderer broadly, verify that the shared schemas can
represent every prompt-visible fact:

- node alias source: =nodes[]=
- target roles: =nodes[].targetRole=, =nextActions[].targetRole=, or
  schema-owned render action specs
- typed relations: =edges[]=
- rank algorithm and order: =searchSynthesis=
- frontier seed actions: =searchSynthesis.seeds= or graph/search synthesis
  action fields
- node-local next actions: =nextActions= or graph/search synthesis action
  fields
- anti-actions: =avoidNextActions=
- omitted facts and expansion locators: query/read projection metadata

If a field is missing, extend the schema before provider-specific projection or
rendering.  Do not hide projection-only decisions in language-private =fields=
maps.

The durable boundary is:

#+begin_src text
protocol   = schema-owned JSON packet
projection = schema-owned JSON field pruning
compaction = content payload transform with declared lossiness
rendering  = stdout serialization
#+end_src

Graph/frontier/rank/action evidence stays in protocol packets and JSON
projections.  Compact graph text is not a protocol, and production code must
not parse compact graph text back into actions.  The historical
=semantic-compact-graph-render.v1= template may describe retired/debug stdout
grammar, but it does not supersede =semantic-search-packet.v1=,
=semantic-graph-turbo-result.v1=, or =semantic-graph-turbo-summary.v1= as the
trusted machine surface.

Compact mode belongs to content payloads such as code, Markdown, Org, logs,
test output, and schema JSON.  Those payloads must carry =contentKind=,
=criticality=, =lossiness=, =validFor=, =notValidFor=, =preserved=, =omitted=,
and an exact-source expansion route when the compact body is not source of
truth.  Code compaction is parser/language-aware and conservative; document
compaction may be metadata-heavy, but normative RFC text, proof notes, review
judgments, and security policy must use conservative criticality settings.

** Owner-query seed prior

The =owner-query= graph turbo profile must not treat every seed as an equal
personalization source when both query seeds and owner/source seeds are present.
In real search sessions, the seed set often contains a query node plus owner
seeds selected by a fast finder or previous frontier. If those owner seeds are
equal to the query seed, personalized PageRank can amplify an early wrong owner
and drift toward implementation wrappers or adjacent packages even when the
query contains more specific algorithm terms.

For =owner-query=, typed PPR personalization is query-aware:

- query seed nodes keep the strongest prior because they represent the current
  user intent rather than a candidate owner.
- owner, item, field, hot, type, and collection seeds receive a prior derived
  from query-token coverage over schema-owned node text.
- single-token queries keep the previous equal-seed behavior; the weighted prior
  is a deep-query optimization, not a replacement for read-loop guards.
- package-like query tokens, such as =asp_graph_turbo=, also contribute a
  package/path cohesion adjustment: nodes whose path or owner path contains the
  package token are preferred, while same-token matches outside the matching path
  are treated as weaker evidence.
- when a query-wrapper packet had to augment candidates from package path search,
  the first seed phase may add a bounded runtime owner anchor in addition to the
  query seed.  This is still a ranking input, not prompt-visible analyzer noise:
  agent-facing search output should show the next action, while sandtable
  packets keep the owner seed and =seedPlan= evidence for replay.
- request packets may carry =queryClauses= as the normalized query-pack clauses
  that produced =queryTerms=. The Python graph-turbo rank objective uses those
  clauses as independent coverage units: nodes covering more than one clause get
  a sparse-score bonus, and a clause containing a package-like token is covered
  only by package/path evidence for that token.
- request packets may carry an optional =queryAdjustmentPolicy= for analyzer and
  ablation runs.  The default production policy enables seed prior, package
  cohesion, and query clause coverage.  Ablation packets may disable one channel
  at a time to measure quality contribution; normal search renderers should not
  print these internal switches.
- seeds with no query-token coverage keep only a small floor weight so they
  remain reachable evidence, but they must not dominate graph diffusion.

This is an algorithm rule, not an analyzer/report field. Analyzer sidecars may
record drift, repeated search loops, and first-action quality, but the fix
belongs in the graph ranking prior before rank/diversity/frontier projection.
Diversity repair remains a top-k coverage guard; it is not a substitute for a
correct personalization vector.

** Native prime packet boundary

=semantic-search-prime.v1= is the authority for native prime discovery. The provider constructs a typed packet containing workspace identity, the stable =owner-rank-frontier= algorithm, semantic capability identifiers, evidence state, owners, typed frontier actions, entries, omissions, and avoid constraints. Capability identifiers describe semantic operations rather than executable spellings such as =fd-query= or =rg-query=. Compact =rank=, =frontier=, and =recommendedNext= rows are projections of this packet and MUST NOT introduce a second command grammar or hardcoded Rust-only fallback. Executable argv, when available, is materialized separately from typed action fields.

Search capability availability is the activated provider's typed =ProviderSearchCapabilities= record. The packet binds query-pack descriptor identity and recipe ids separately as composition provenance; recipes and term roles are not capabilities. Every frontier action =requiredCapability= MUST resolve to the typed search-capability record, while any selected =recipeId= MUST resolve to the query-pack recipe set. Missing capability evidence and unresolved capability or recipe references are invalid packets.

The shared schema is defined before provider implementation. Rust owns acquisition and rendering but not the packet vocabulary; other language providers register the same action/capability contract through their harness manifests and activation query packs. A missing or invalid packet is an explicit capability state, not permission to restore =native-fd-prime-frontier-v1=.

** Graph turbo packet boundary

The pre-acquisition query budget MUST admit an explicit multi-clause query pack
or a query containing a parser-owned typed =Symbol= anchor.  Character-shape
heuristics such as dots, slashes, digits, hyphens, or underscores are not a
substitute for typed query evidence.  Flat queries without typed anchors remain
subject to bounded resource budgets; weak coverage and low cohesion after
admission are resolved by =queryQuality=, =packageCohesion=, rank, and the action
frontier rather than a pre-search specific-anchor denial.

The explicit =--view graph-turbo-request= surface MUST serialize the same enriched
=semantic-graph-turbo-request.v1= packet that would be sent to the graph-turbo
ranking boundary.  Selecting this view MUST NOT, by itself, suppress bounded
provider =search semantic-facts= enrichment when semantic intent, provider
capability/context, and bounded candidates are present.  The search facade MUST
consume the active source-index generation derived from =ProjectResolution=;
no retired scope-discovery command, scope packet, or package-root topology walk
is a fallback route.  Unsupported providers,
provider errors, missing context/capability, non-semantic queries, and empty
bounded candidate sets remain valid empty enrichment outcomes and SHOULD be
distinguished by an explicit =sourceTrace= reason rather than collapsed into an
undifferentiated =skipped= state.

Ontology-oriented queries MUST NOT depend on a lexical source hit as the only
way to establish the bounded candidate frontier for provider semantic facts.
When lexical acquisition yields no usable source owner, ASP may project only
owners already present in the active source index and reachable from the
admitted =ResolvedSourceScope= facts.  It MUST NOT walk package roots, rebuild
scope from extensions, invoke a query-free workspace/topology provider command,
or invoke =search semantic-facts= with empty stdin.  If the active generation
cannot supply a bounded owner frontier, semantic-facts enrichment remains empty
with an explicit typed source-trace reason.

Provider semantic-facts intent requires compound typed evidence: either at
least two ontology terms, or one ontology term paired with a typed =Symbol=
anchor.  A single overloaded natural-language word such as =set=, =list=, or
=map= MUST NOT by itself activate workspace-topology/provider-facts acquisition.

The router MUST obtain semantic-facts intent axes, fact kinds, packet schema
references, roles, and trigger terms from the activated provider's versioned
=semanticFactsDescriptor=.  Shared search owns typed clause/role matching and
language-neutral axis semantics; it MUST NOT contain a fixed cross-language
term list.  Provider manifests own language spellings and aliases such as Rust
=Vec=, Python =list=, TypeScript =Effect=, Julia =Vector=, or Gerbil collection
forms.  When an activated provider has no descriptor, the router treats
semantic-facts intent as unavailable rather than guessing from the language ID.

=asp-graph-turbo= is a typed ranking engine for parser-owned graph facts, not a
compact text protocol.  Its durable output is =semantic-graph-turbo-result.v1=,
which records the selected profile, seed nodes, ranked node ids, ranking
budget, frontier actions, relation edges, scores, typed paths, cache trace,
algorithm trace, rank explanations, and algorithm metrics.  A lighter
agent-facing surface is =semantic-graph-turbo-summary.v1= or another explicit
JSON projection that names which fields are included and omitted.  Text rows
such as =queryPack=, =evidenceFrontier=, =actionRank=, =recommendedNext=, and
=nextCommand= are renderings of schema-owned actions; they are not a second
grammar that Rust, Python, or an agent should parse as authority.

Action materialization must start from typed JSON objects.  A =query-code=
action carries a capability, language id, selector, workspace policy, and
safety constraints in the packet; the trusted materializer then builds argv.
It must not derive argv by parsing display text such as =rank=..., =frontier=...,
or a compact alias DSL.

Graph turbo must not infer missing relation labels, node roles, or frontier
actions from prose.  Any prompt-visible rank or action produced by the turbo
engine must be visible in the result packet before another renderer serializes
it for an agent.

SciPy-first typed graph intelligence engine.

=asp-graph-turbo= remains a SciPy-first typed sparse ranking engine for the
agent hot path.  The default runtime path should continue to use lightweight
SciPy sparse matrices, typed relation policy, graph cache fingerprints, and
schema-owned request/result packets.  PyG, GNN message passing, and
=HeteroData= export are optional lab/offline research surfaces only: they must
not become default package dependencies, default CLI execution paths, hook
runtime requirements, or fallback conditions for search/query/read-plan.

The next graph-turbo investments should strengthen ASP's own typed facts and
deterministic sparse scoring before any learned reranker is considered.  The
priority order is typed fact graph quality, profile-specific sparse scoring,
failure/read-loop feedback, and command-inflation metrics.  Current result
metrics expose read-loop guard counts for direct code actions, duplicate
selectors, adjacent range windows, and same-owner scans.  Future fact quality
signals such as provenance, confidence, freshness, and profile transition
evidence should remain packet-visible so rank explanations, =frontierActions=,
=omit=, and =avoid= can be audited outside the Python implementation.  The
artifact timeline report also projects cached direct-code read-loop risk through
=readLoopRisk= JSON and =[graph-turbo-read-loop]= text evidence so historical
agent runs can be evaluated before another live replay.

The =asp <language> search failure= surface is a graph-turbo adapter, not a
Rust-owned renderer.  The facade may parse the last check transcript, collect
candidate facts, and construct a =semantic-graph-turbo-request.v1= packet with
=profile=failure-frontier=.  It must not rank failure facts, decide the
frontier order, or synthesize =frontierActions= outside the graph-turbo result.
The =failure-frontier= profile owns failure, assert, owner, hot, key, evidence,
and test node transitions; the compact =[search-failure]= text is only a
projection of that profile result.
Failure-frontier follow-up reads are =query-code= actions in the result packet.
Compact output may render them as =C1.query-code(...)!query-code= rows for
prompt readability, but it must not render or require retired
=H.code=>asp ... query --selector ...= command strings as the machine contract.
The default =[search-failure]= projection is an agent prompt surface, so it
must keep failure facts, candidate owners, hot blocks, query profiles,
frontier actions, =omit=, and =avoid=, while omitting diagnostic rows such as
=scores=, =paths=, =cache=, =trace=, =explain=, and =metrics=.  Those
diagnostics remain available through graph-turbo packet/result debug surfaces;
removing them from seeds is valid only when the selected hot-block frontier and
failure facts are unchanged.

The check projection route follows the same boundary.  =asp <language> check
changed --workspace . --view seeds= and =asp <language> check --changed --workspace . --view seeds=
execute the provider check without forwarding the ASP =--view seeds= flag,
persist the failing transcript as the last-check artifact, and then render
=search failure --from-last-check --view seeds= through the graph-turbo
=failure-frontier= profile.  =search failure --view graph-turbo-request= is a
debug/schema surface for auditing that request packet; it is not the default
agent prompt surface.

Graph turbo requests are schema-owned too.  A caller that wants the Python
ranking engine to run =typed-ppr-diverse= should send
=semantic-graph-turbo-request.v1= with =profile=, =algorithm=, =seedIds=,
=budget=, typed =graph.nodes[]=/=graph.edges[]= facts, optional
=kindBudgets=, and optional =windowMerge= controls.  Default fast-search
candidate packets should include owner/item/test facts plus hot range nodes
when a candidate locator is known, connected through typed edges such as
=owner->item contains=, =item->hot contains=, and =owner->test covers= so path
ranking can select direct code follow-ups without reparsing compact text.
When the bounded candidate set exposes data-shape intent, such as field, type,
collection, map, set, or list terms, the request should also carry typed
semantic nodes for =field=, =type=, and =collection=.  High-concurrency,
resource-lifecycle, and API-usage terms such as =concurrency=, =queue=,
=stream=, =scope=, or =fiber= may also request semantic facts as candidate
context: the provider should expand only from stdin-selected candidate owners,
not from an unbounded whole-repository structural scan.  This keeps real API
queries able to see parser-owned data-shape evidence without sacrificing the
lexical/API relevance of the ranked frontier.  These are schema-visible graph
facts rather than compact-renderer heuristics: =field= records the owner, field
name, type text, collection kind, locator, and matched text; =type= records the
field type; and =collection= records the collection family.  The default
owner-query adapter connects them through typed edges such as =query->field
matches=, =owner->field contains=, =field->type has_type=,
=field->collection collection_of=, =type->collection collection_of=, and
=field->hot contains=.  This lets graph turbo project field-level selectors for
questions such as =Vec collection fields= or =Effect concurrency Stream Scope=
without requiring the agent to run a second owner search, broad lexical, or
tree-sitter guide probe after the ranked frontier has selected the evidence
boundary.
For Rust, these data-shape facts are provider-owned parser facts produced by
the harness's =syn= project scan.  Search-pipe lexical candidates may seed
priority, but they must not be the authority or the only files parsed for
=field=/=type=/=collection= facts; otherwise a lexical =Vec= hit outside the
struct owner prevents the graph from ever seeing the field evidence.
Provider alignment uses the command shape =search semantic-facts <query>
--json= with candidate lines on stdin.  The JSON response is provider-owned
=nodes=/=edges= graph fact payload that ASP appends to the graph-turbo request.
Rust owns these facts with =syn=, Python owns them with =ast=, TypeScript owns
them with the TypeScript compiler API through the provider parser layer, and
Julia owns them with JuliaSyntax-derived field facts in the Julia harness.
Unsupported providers may return a non-zero command result; ASP treats that as
no extra facts so rollout can be incremental without breaking existing search.
Field nodes should preserve the exact field declaration locator for display
and metadata, and may also expose a parser-owned =contextLocator= for code
projection.  When =contextLocator= is present, branch =query-selector= commands
should use that bounded field context selector rather than a single declaration
line, so the next read contains enough surrounding structure without forcing a
manual widening search.
When provider-owned =field= nodes are present in an =owner-query= result, the
bounded fanout projection should select branches from those field nodes first
and must not fill the remaining branch budget with same-owner lexical =item= or
=hot= matches merely to reach the branch cap.
When a projected branch already has an exact selector, prompt-visible compact
output may make =query-code= the first next action for that branch only when the
query packet is confidence-gated by =queryQuality= and =packageCohesion=.
=search-reasoning= is still available for branch expansion, but it is a
follow-up after reading the exact selector or a fallback when no exact selector
exists.  Rendered =actionRank=, =actionFrontier=, =recommendedNext=, and
=nextCommand= should preserve that confidence-gated ordering so the agent does
not spend turns on owner reasoning before it has consumed the ranked evidence
boundary, and does not read code when a broad seed only deserves more locator
recall.  Sandtable and hook diagnostics should therefore treat
=prime -> pipe -> query-code= as a complete complex-pipe success only when the
pipe result exposes a high-confidence exact selector; =search-reasoning= is
measured as optional branch expansion in that case, not as a required stage.
The prompt-visible top-three fanout is a conditional frontier, not the default
read plan.  The ranked graph may retain branch identifiers internally for audit
and debug views, but =search pipe --view seeds= should expose executable next
steps through =A*= action rows.  Secondary selectors and reasoning branches
belong in explicit advisory/debug surfaces, without runnable =asp ...= commands
or exact secondary selector ranges in the default seeds view.  A
commands/advisory surface may materialize those branch commands only after an
explicit request or after the primary selector evidence is known insufficient.
The seeds view is a decision packet, not a graph-debug dump.  When an exact
primary selector is projected, prompt-visible seeds output should keep the
primary graph facts, =evidenceFrontier=, =actionRank=, =actionFrontier=,
=recommendedNext=, =nextCommand=, compact =evidenceNodes= / =evidenceEdges=,
compact policy, cache/metric summaries, and avoid/stop guidance, while omitting
score vectors, typed path lists, full algorithm traces, and rank explanations.
Debug callers can still request the graph-turbo packet/result surfaces for
those diagnostics; agents deciding the next command should not pay that token
cost by default.
Output compaction is precision-preserving only.  It may remove diagnostic
volume such as score vectors, typed path lists, full traces, and rank
explanations, but it must not remove parser-owned semantic evidence that
changes the agent's decision.  For field/type/collection questions, seeds
output must still expose the primary =field=, =type=, =collection= facts,
the =has_type= / =collection_of= relationships, query coverage, the selected
=A*= action, and the same =nextCommand=.  If a proposed compaction hides
those facts or changes the selected frontier, it is a correctness regression,
not a token optimization.
Language =guide= output is a pre-search tool map.  Once a pipe result has
projected an exact primary selector, guide should not be run as a post-selector
confirmation step; diagnostics may count =guideCommands= so this drift is
visible in live sandtable reports.
Live sandtable reports are prompt-only.  A live scenario descriptor must not
script =asp= commands, allowed tools, required command families, or an
=agentSdk.prompt= payload.  Its single user input is the
=deepQuestionCases[].question= text, and the runner derives one Claude SDK
prompt execution from that question while forcing repository
=.claude/settings.json= loading.  Any =asp search=, =asp query=, hook denial,
or hook recovery command observed during the run must be produced by the
client, repo hook, and ASP guidance at runtime.  Deterministic command replays
remain useful as provider/facade contract fixtures, but they are not live
sandtable simulations and should live outside discoverable sandtable scenario
paths.
Command-line arguments may override request profile, seeds, or budget for
local debugging, but provider integration should prefer the request packet so
the algorithm input and response can be audited together.  The response is
=semantic-graph-turbo-result.v1= and must echo the effective profile,
algorithm, seed ids, budget, per-kind budget, merged windows, profile
compatibility, typed paths, graph cache, algorithm trace, rank explanations,
algorithm metrics, plus prompt-visible =profiles=, =omit=, and =avoid= facts
used by compact graph-frontier rendering.  Graph cache state is owned by the
Python ranking engine; persistent backend entries live under =$PRJ_CACHE_HOME=
or the git toplevel =.cache=, and the packet fingerprint must include graph
nodes, edges, profile, seeds, budgets, path, and window controls so changed
source facts do not replay stale rankings.

Language implementations may use their ecosystem's normal graph algorithm
library, such as Python =NetworkX= or Julia =Graphs.jl=, for traversal,
centrality, and reachability.  These libraries are implementation dependencies:
the durable protocol remains the schema-owned graph turbo result packet and
does not expose provider-local library names as ranking algorithms.

For Python MVP 11 P1, =typed-ppr-diverse= is implemented over a SciPy sparse
CSR backend.  The algorithm constructs a profile-filtered typed adjacency
matrix, runs personalized PageRank from =seedIds=, filters by profile depth,
applies diversity and per-kind budgets, merges overlapping/nearby source
windows, and emits profile compatibility evidence.  NetworkX can be useful for
experimentation, but the production Python turbo path should use SciPy sparse
linear algebra because P2 flow/path ranking and P3 trace/cache evidence also
depend on stable matrix-oriented graph state.

Python MVP 11 P2 adds typed path evidence to the same response packet:
=sourceSinkFrontier= records the effective sources and sinks,
=typedPaths= records constrained shortest and k-shortest typed paths, and
=flowLite= records the local path ranking order.  The path evidence is
schema-owned response data, not another compact prompt protocol.

Python MVP 11 P3 adds auditability around the algorithm run:
=packetFingerprint= is the canonical request/graph hash, =graphCache= reports
the sparse backend cache status, =algorithmTrace= lists the stable algorithm
steps, =rankExplanations= explains each ranked node, and =algorithmMetrics=
records sandtable-friendly counts such as path count, ranked count, merged
window count, and cache status.  Owner-query query adjustments must also be
visible here for analyzer mode: trace and metrics record how many nodes received
seed-prior, package-cohesion, and query-clause coverage effects, and rank
explanations name the non-zero query adjustments for ranked nodes.

Python MVP 11 P4 uses ablation and calibration packets to turn those metrics into
an improvement plan.  Ablation variants include one-channel removals for
=no-query-seed-prior=, =no-package-cohesion=, and =no-query-clause-coverage=, and
the report exposes a =queryFirstStage= signal when those variants change rank,
score, or query-adjustment metrics.  Calibration packets may include
=guardrails.queryFirstStage= with the active constants and allowed ranges; this
records the tuning boundary for reports without silently changing production
weights.

Python MVP 12 makes the ranking policy explicit rather than allowing the
algorithm to consume unweighted or all-graph edges.  Graph turbo must normalize
missing edge weights through a shared relation policy before constructing the
CSR matrix: =selects= 1.2, =matches= 1.5, =repairs= 1.8, =contains= 1.0,
=calls= 1.2, =covers= 1.4, =imports= 0.8, =uses= 0.9, =flows-to= 1.6, and
=split= 0.7.  Provider-compatible aliases such as =covered_by= and
=depends_on= may map to the same initial weights as their canonical relation
families, but unknown unweighted relations must not silently become neutral
rank edges.

Each profile owns a node-kind bonus map and an explicit transition mask.  The
initial bonuses are =owner-query= field +0.4, hot +0.35, collection +0.3, type
+0.28, item +0.25, test +0.15, owner +0.1; =prime= owner +0.3, query +0.2,
dependency +0.15, test +0.15; and =read-frontier= window +0.4, symbol +0.3,
range -0.2.  The initial typed transitions are =owner-query= query->item,
query->field, query->type, query->collection, owner->item, owner->field,
item->hot, field->hot, field->type, field->collection, type->collection,
owner->test; =query-deps= query->owner, owner->dependency, dependency->owner,
owner->test; and =read-frontier= range->symbol, range->window, symbol->window.  The result
packet's =profileCompatibility= evidence must expose allowed relations,
allowed transitions, and kind bonuses so another renderer or agent does not
have to infer the policy from rank output.

Diversity is a score adjustment layer over typed PPR, not a prompt heuristic.
The initial penalties are same owner 0.25, same symbol name 0.4, and repeated
same kind beyond the soft budget 0.3; contiguous windows that can merge receive
a 0.5 bonus.  Explicit per-kind budgets remain hard caps.  This policy is meant
to suppress repeated outputs such as =semantic_string_type= x8 while still
preserving parser-owned rank evidence for distinct owners, symbols, tests, and
windows.

* Implementation order

1. Keep this RFC as the language-neutral contract.
2. Audit =semantic-graph.v1= and =semantic-search-packet.v1= for alias,
   action, rank, frontier seed, synthesis, omission, and avoid coverage.
3. Keep graph/frontier/action authority in JSON packets and JSON projections;
   treat =semantic-compact-graph-render.v1= as ARI/retired/debug stdout grammar
   rather than a trusted graph/frontier/action protocol surface.
4. Introduce or preserve a typed render IR and safe ARI encoder boundary before
   renderer string templates; keep any ARI parser restricted to tests, replay,
   backcompat, transcript recovery, and debug validation.
5. Add schema tests for any missing fields or template vocabulary drift.
6. Implement projection/materializer tests that prove prime, owner, query-set,
   ingest, tests, and item query outputs derive next actions from schema-owned
   graph facts before any text rendering.
7. Replace renderer assertions that target independent =|seed= or
   =|synthesis= rows with assertions over =rank=, =frontier=, =avoid=, aliases,
   and grouped edges.
8. Align Rust, TypeScript, and Python provider integration tests to the same
   examples and surface classes by asserting packet construction plus shell-out
   rendering, not provider-local renderer implementations.
9. Add sandtable scenarios that measure command count, token size, repeated
   search loops, and hook-recovery clarity.
10. Use real-project traces before widening graph rendering beyond the proven
   surfaces; require every =--view seeds= follow-up action to remain
   graph-derived from the start.

- The JSON packet remains the source of truth for graph data.
- =seed= and =synthesis= are represented through graph aliases, =rank=,
  =frontier=, and =avoid= rather than as independent prompt-facing protocols.
- Providers produce the same graph meaning across Rust, TypeScript, Python, and
  Julia.  Julia uses the compiled =asp-julia-harness= plus cacheable search
  packets, not a workspace-managed exception.
* Finder-confirmed path precedence

When an agent or query wrapper supplies an explicit path-like target, or when the
finder layer returns a file path that matches the requested path intent, the
search action frontier must prefer a concrete owner-items action for that path
before generic scoped-rg refinement. This is especially important for paths that
are outside a language provider's parser index, such as sandboxed `.data`
fixtures, because parser-ranked owners can otherwise drift to nearby indexed
packages.

For neutral `asp fd -query` output, the recommended next action SHOULD infer the
language from the matched owner path when the path extension is language-specific
and materialize an executable `asp <language> search owner <path> items --query
...` command. If language inference is ambiguous, the frontier may keep an
owner-items hint without a materialized command, but it must not rank a
package-level scoped-rg action ahead of an exact finder-confirmed path.
* Provider/ASP Topology Boundary
Language harnesses own native parsing and publish query-free, shared-schema
projection artifacts; ASP imports their normalized facts and owns heavyweight
derived topology artifacts.  A projection may expose parser-owned manifest,
dependency, package-root, source-root, owner, selector, and typed relation
facts, but it MUST NOT receive a user query, candidate list, rank, view, next
action, or search command.  ASP must build and cache reasoning trees, source
symbol indexes, dependency source indexes, documentation indexes, and
route-selection state from the imported facts.  Normal =search= stdout exposes
only the next-action facts useful to the agent; developer/history and sandtable
analyzers may persist the heavier ASP topology/index receipts for quality and
latency analysis.  A warm search reads Turso and the ASP acceleration model
only; it never invokes a harness parser or provider search command.

The first-stage project topology is not inferred from Compact Render rows or
from candidate paths.  ASP projects the admitted provider =ProjectResolution=
into the typed chain =workspace -> provider-root -> language-project ->
project-marker/package -> target -> source-scope -> owner=.  Git/Native
candidate discovery supplies possible owner nodes; only a provider-resolved
source scope may add =admits_owner= or =expects_owner=.  Compact text is a
lossy view of this graph and MUST NOT be parsed back into topology or action
identity.

An owner-items miss uses =search-owner-missing-topology.v1=.  Its bounded graph
contains at most the active workspace/language/generation/missing-owner anchors,
three relevant language projects, four relevant source scopes, and a typed
action frontier.  Historical SearchLoop state stores these node ids and edges,
so an Agent may jump to a previously materialized project/scope node without
replaying Native discovery or the failed owner lookup.

Selector-seeded graph admission and Compact Render ownership are specified in
[[file:10.06-agent-search-projection/10.06.11-selector-seed-typed-topology.org][10.06.11 Selector-seed typed topology]].

An owner-item route records language/path admission before graph construction.
=owner-language-mismatch= is terminal evidence, not a low-confidence
candidate: its compact packet gives the requested language, canonical path
class, and the next valid language route. GraphRoute must not turn it into a
provider retry, broad lexical fallback, or cold-index request. The ASP facade
performs canonical-path, registered-extension, and bounded query-set validation
before allocating owner-item evidence; it does not activate the harness parser
for an admission check.
The packet uses the =semantic-owner-item-evidence.v2= =admission= node. It
contains only route-relevant facts: status, requested language, owner extension,
declared provider extensions, and an optional suggested language. It does not
contain source text, candidate lists, confidence values, or a retry transcript.
* Skeleton-first action frontier
Compact graph action facts must distinguish non-code structural projections from
exact code transport.  Owner-local item hits should project an =item-skeleton=
action with =projection=skeleton= before =syntax-outline= and =query-code=.
The graph/action schema may carry =displayLineRange= and =sourceLocatorHint= as
display or transport hints, but the executable target is the structural selector
until the agent deliberately asks for exact code.  Direct source read fallback
belongs outside the normal graph frontier and requires an explicit fallback
reason when represented in read packets.
* Compact search action row contract
This section supersedes older examples that treated =actionRank= or =[route-graph]= rows as part of default agent-facing seed output. Default search stdout exposes one compact action surface. When =actionFrontier= is rendered in =--view seeds= or facade stdout, the same output must not also render =[route-graph]=, =actionRank=, or full action detail rows such as =A1=fd-query(...)!finder-owner=. Those details belong to typed graph-turbo packets, explicit debug/advisory views, or tests that validate packet materialization. Seeds stdout keeps only =actionFrontier=A1.kind,A2.kind=, =recommendedNext=A1.kind=, and an optional materialized =nextCommand= display line derived from typed actions.
* Rust schema and crate ownership
RFC 10.21 owns the Rust engineering boundary for compact graph schema and render modularization. This RFC defines the agent-facing compact graph semantics; RFC 10.21 defines how those semantics become schema-owned Rust contracts, render IR, render crates, search-core crates, and DB receipts instead of CLI-local formatting code.

Any new compact graph field that changes aliases, relation groups, selector groups, frontier actions, omission/avoid rows, or expansion handles must update the shared schema and Rust contract boundary before adding CLI render behavior.
* Agent-facing render layers
The compact graph render is the normal prompt surface for search. It is not a JSON dump, a debug graph, or a full analyzer receipt. JSON packets remain the machine contract for validators, DB storage, replay, Python graph ranking, and Julia research, but normal stdout should expose only the smallest evidence slice that lets the agent choose the next correct action.

The render has three layers:
#+begin_src text
L0 answer/frontier  -> best selector, bounded evidence, next action, and why
L1 compact graph    -> aliases, typed edges, rank, omissions, avoid rules
L2 machine receipt  -> full packet JSON, DB rows, replay artifacts, metrics
#+end_src
Only =L0= and a bounded =L1= are prompt-facing by default. =L2= is reachable by explicit receipt/debug expansion and by analyzer pipelines; it must not be pasted into the prompt path just because the data exists.

The useful product lesson from graph-rich search systems is action clarity: search returns a candidate, path tracing explains a relation, and snippet retrieval materializes bounded source. ASP should keep that clarity, but render it as one compact evidence packet whenever possible:
#+begin_src text
search/combinator -> compact evidence graph -> exact frontier action
#+end_src
The agent should not need to read a broad JSON object to know whether to inspect an owner, expand a relation path, retrieve a snippet, or stop searching. The prompt-facing row must already separate evidence from next action.

The default graph slice should fit the current decision, not the repository:
- show the top 1-3 evidence nodes unless confidence requires more
- show only typed edges that explain the selected frontier
- preserve parser-owned selectors and source fingerprints
- keep line ranges as display/source transport hints, never action identity
- name omitted facts and unsafe next actions explicitly
- provide expansion handles for owner, path, snippet, and receipt

If the agent needs more context, it should expand progressively:
#+begin_src text
expand owner   -> owner-local items, tests, dependencies, imports
expand path    -> bounded relation path or trace explanation
expand snippet -> parser-owned source projection for one selector
expand receipt -> machine JSON / DB replay only on explicit request
#+end_src
This makes =frontier=, =routeGraph=, =G*= relation groups, and =S*= selector groups a compression language for attention. They are useful only while they reduce the next decision. When they become topology telemetry, ablation metadata, or route-state exhaust, they belong in the receipt layer.

* Workspace and language provenance before graph rank
Every graph candidate carries =workspaceId=, package identity, canonical path,
=languageId=, and provider identity before it is admitted as a node.  The
language harness derives =workspaceId= and the admitted package-root set from
package-manager anchors.  The invocation directory is only a discovery seed;
it is not itself the semantic workspace boundary.

Candidates that join to none of the admitted package roots or whose file kind
is not accepted by the selected provider are terminal admission failures.  A
workspace may legitimately include members outside the invocation directory,
so admission uses provider-resolved membership rather than one path-prefix
check.  Rejected candidates are not low-score nodes and MUST NOT enter Python
graph diffusion, graph owner rank, topology projection, or compact rendering.

This ordering is normative:
#+begin_src text
package-anchor discovery -> workspace membership -> provider admission -> evidence node -> topology -> rank
#+end_src
Ranking a cross-workspace or cross-language candidate and filtering it later is
invalid because its edges already distort graph topology and frontier choice.

* Callable skeleton projection and structural descent

The wire identity is =agent.semantic-protocols.callable-skeleton-projection= with
=schemaVersion: "1"=.  File-name or Rust-type suffixes may carry =v1= for
artifact discovery, but version suffixes MUST NOT leak into the schema value.

The public projection kind =callable-skeleton= and the exact-selector cache mode
=skeleton= are distinct identifiers.  The former names the shared response
contract; the latter is the compact discriminator inside an authenticated exact
projection lookup key.  Implementations MUST expose separate accessors and MUST
NOT compare either identifier against the other.

An admitted base generation MAY contain only exact selector identity and source.
It MUST NOT eagerly compute every callable skeleton merely to admit the
generation.  Whenever a generation or its immutable overlay claims to contain a
derived projection, it records that projection beside the exact selector that
owns it: the public projection kind, the validated shared-schema payload, and the
same generation identity used by the selector proof.  A runtime read admits the
payload only when all three identities agree:

1. the exact selector exists in the active generation;
2. the derived projection kind equals the explicitly requested kind; and
3. the projection proof belongs to that same generation and validates against
   the shared schema.

Projection absence, schema failure, or generation-identity drift is not a source
fallback.  The runtime returns a typed projection miss and MAY request
parser-owned repair only when the requested exact selector already belongs to
the active base generation.  A selector absent from that generation is stale;
lazy projection repair MUST NOT recreate it from an older generation, overlay,
owner cache, or provider result.
A repair candidate is published atomically only after rechecking the active
generation identity; a candidate computed for an older generation is discarded.
Readers therefore observe either the previous complete generation or the next
complete generation, never a selector whose derived projection was attached
across generations.

A mutation-triggered admission is a rebuild, not a generic restore-or-build
request.  Once the runtime admits a mutation receipt, that admission MUST NOT
restore a durable generation produced before the mutation.  Concurrent
mutation work is single-flight only for the same authenticated mutation
identity; distinct mutation identities MUST wait and retry or create distinct
successor work, never alias one in-flight result.

Canonical generation publication and no-op reuse bind both source content and
structural identity.  The publication identity includes the workspace root
digest and selector-set digest, and an existing generation is reusable only
when both its generation digest and selector-set digest equal the candidate.
Equal source bytes with a renamed owner are therefore not a no-op: the old
selector must disappear and the replacement selector must be published.

An exact projection result exposes the selector it actually resolved.  The
active generation Merkle root and selector-set digest authenticate the segment,
but a public exact hit additionally requires membership of the requested
selector and equality between requested and resolved selector identities.
Canonical-item relocation MAY be retained as typed discovery evidence; it MUST
NOT turn an absent old selector into executable source or derived-projection
bytes.

The provider-native exact repair response carries validated derived-projection
packets.  A source-index/import ABI MAY preseed the same packets, but omission is
valid and triggers lazy parser-owned repair on explicit request.  Neither path
teaches the DB core Rust, Python, Gerbil Scheme, or any future language syntax.
Language providers own language facts and skeleton extraction.  Shared schema,
identity admission, atomic publication, compact rendering, and typed misses stay
in the language-neutral projection/core and resident-generation layers.  The CLI
only selects and dispatches the explicit projection.

The provider-native route is an internal structured transport.  A route that
accepts the v1 stdin JSON request MUST also force the v1 JSON response wrapper;
it MUST NOT inherit a public CLI renderer default that emits a bare source or
callable-skeleton payload.  The registered argv therefore carries both the
provider-native stdin binding and its JSON response mode, and registry tests
admit those arguments as one contract.

A provider owner-search signature is discovery metadata, not a derived
projection payload.  The resident layer MUST deserialize and validate the full
=agent.semantic-protocols.callable-skeleton-projection= object before attaching
bytes under =projectionKind: "callable-skeleton"=; non-empty signature text alone
MUST be rejected.

The contract family is v1, while every JSON wire object uses
=schemaVersion: "1"=.  Queryable callable children append the parser-owned
=/segment/<kind>/ordinal-N= identity to the canonical root item selector.
The ordinal is assigned by the provider AST traversal for the bound generation;
it is not a line or byte-offset selector.  Querying that returned selector MUST
materialize the parser span for the same child under the same generation,
parser, and query-pack digests.

The existing =projection=skeleton= action is an item-level frontier choice. It
does not yet define the semantic payload for a large callable, and it does not
make branches, arms, loops, closures, or other callable descendants executable
exact-query targets. This RFC adds a language-neutral callable projection rather
than a Rust-only function outline.

The public projection kind is =callable-skeleton=. A provider receives one exact
callable selector and returns
=agent.semantic-protocols.callable-skeleton-projection= version =v1=. The root
may be a function, method, constructor, closure, lambda, or another
provider-owned callable kind. The shared contract owns node identity,
queryability, relations, omission, and cost semantics. Provider-owned
=languageFacts= carry syntax-specific facts and MUST NOT redefine those shared
semantics.

The projection is explicit. A client asks for =callable-skeleton= or for source;
ASP MUST NOT silently choose between them from a hidden function-size heuristic.
The existing =code= and =skeleton= strings in
=exact-selector-projection-packet.v1= are historical packet vocabulary, not a
requirement to preserve an old CLI. A new public query surface may replace old
flags as a coordinated breaking change.

** Shared callable node model

A callable skeleton is a compact semantic graph. Its common node kinds are
=callable=, =branch=, =arm=, =loop=, =exception=, =resource-scope=,
=invocation=, =binding=, =exit=, =suspension=, =nested-declaration=, and
=language-extension=. Relations retain parser order and semantic edges such as
=contains=, =guards=, =calls=, =returns=, =throws=, =yields=, and =suspends=.
The projection carries source bytes, projected bytes, and omitted bytes.
Provider token estimates are optional and MUST name their estimator when
present.

Rust may map =match= arms, closures, =?=, =await=, and macro invocations into
this graph. TypeScript maps functions, methods, arrows, switch arms, async
boundaries, and provider-owned Effect facts through the =typescript= facade.
Python maps =def=, =async def=, lambdas, context managers, exception handlers,
and yields. Julia maps long and short function forms, =do= blocks, dispatch
facts, and macros. Gerbil Scheme maps definitions, lambdas, =cond=, match,
binding forms, continuations, and macro facts. C-family providers map functions,
methods, lambdas, switch arms, templates, RAII scopes, and preprocessor
boundaries. These mappings need not expose identical node sets.

** Queryable child identity

A skeleton node declares =queryable=true= only when the provider can mint an
exact structural selector for that node. The selector is carried as
=asp.exact-structural-selector.v1=. Version =v1= preserves the root canonical
item selector, binds the active generation, parser identity, and query-pack
digests, and adds opaque, parser-owned semantic descent segments. The packet
=rootSelector= owns that shared identity once. A queryable node carries only
its executable structural =selector= string; the node selector is scoped by
the packet =rootSelector=. Node-level =exactSelector= envelopes are not part of
the v1 callable-skeleton contract because they duplicate generation, parser,
query-pack, and root-item identity. Segment identity MUST NOT be a line number,
display range, or byte offset.

=sourceLocatorHint= remains display-only. Clients MUST execute the returned
exact selector instead of reconstructing one from a hint. A non-queryable node
MUST omit =selector=. A selector whose bound generation or parser identity
is stale fails closed with an actionable stale-selector receipt; it MUST NOT
relocate to a nearby sibling or fall back to source slicing.

Exact query remains exact. It consumes a selector returned by the provider and
does not search for a child. Discovery happens in the skeleton projection; the
subsequent query only materializes the selected descendant.

Projection cost covers the complete serialized packet, including selectors,
relations, language facts, and the cost envelope itself. It MUST NOT clamp
=projectedBytes= to =sourceBytes= or report only the node fragment. When the
packet is larger than the source, =omittedBytes= is zero and the larger
=projectedBytes= remains visible.

** Breaking-change and provider admission

This design does not require old CLI compatibility. It requires an explicit
version boundary and coordinated migration of schemas, provider descriptors,
fixtures, sandtable scenarios, and installed artifacts. A provider declares
callable-skeleton support only after it can satisfy the shared schema and
round-trip every emitted queryable child through exact query. Declared support
fails closed; it MUST NOT silently return the complete callable body or a
line-based approximation.

Rust is the first reference implementation, not the owner of the shared
contract. Before Rust implementation admission, the repository MUST contain:

- the versioned shared skeleton and structural-selector schemas;
- shared valid and invalid fixtures;
- provider mapping notes for every registered language, including explicit
  unsupported node kinds;
- round-trip, whitespace/comment stability, sibling insertion, stale-selector,
  and token/byte reduction acceptance cases.

The implementation order is RFC, shared schemas, cross-language mapping and
fixtures, Rust reference implementation, other provider alignment, sandtable
validation, and real-project token/latency evidence. Source edits, schema syntax
checks, or a Rust-only passing suite do not close this work.

* Frontier action identity and cycle rejection
Typed frontier actions include workspace, language, kind, and normalized query
identity.  GraphRouter rejects an action already present in route history.  It
also rejects inverse generic fallback pairs such as =fd -> rg -> fd= when the
intermediate result added no new owner, path, symbol, selector, or typed failure
node.  An exhausted frontier renders one terminal failure action rather than a
repeated search recommendation.

Python graph ranking consumes only admitted nodes and returns rank/explanation;
it does not own workspace recovery, language correction, or replay suppression.
Those are deterministic admission and router responsibilities shared across
providers.
