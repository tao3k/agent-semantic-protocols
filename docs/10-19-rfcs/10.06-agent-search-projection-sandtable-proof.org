#+TITLE: Search Loop Sandtable Proof Dossier
#+STATUS: DRAFT

* Decision

The proposed =GraphRouter / SearchReasoningRouter / SearchRouter= split is a
promising safety boundary, but the current design is *not ready for Rust
implementation*.

This dossier records a pre-implementation sandtable over the current Rust
workspace.  It does not treat RFC prose, a model judgment, a search hit, or a
partial receipt as implementation proof.

The current decision is:

#+begin_src text
Rust implementation gate: NO-GO
Safety direction: conditionally supported
End-to-end search-loop closure: not demonstrated
Search quality: insufficient
Control-plane liveness: failed
Parallel fan-in proof: failed
Public search-only boundary: unresolved
Performance proof: not established
#+end_src

* Scope and epistemic boundary

This sandtable tests the proposed search loop against real Rust tasks in the
current =agent-semantic-protocols= workspace.

The current =asp rust search= implementation is used only as the provider
observation surface for =SearchRouter=.  The test subject is the complete loop:

#+begin_src text
typed intent and obligations
  -> GraphRouter evaluation
  -> optional SearchReasoningRouter RouteProposal
  -> GraphRouter admission
  -> SearchRouter provider action
  -> canonical packet admission
  -> obligation delta
  -> continue, checkpoint, block, partial, or close
#+end_src

The following are deliberately separated:

- /Provider behavior/: what the current =asp rust search= command returned.
- /Agent behavior/: what a fresh or stateful subagent selected and concluded.
- /Router behavior/: what the proposed authoritative reducer should admit,
  reject, or keep open.
- /Implementation proof/: a future executable reducer and Rust runtime passing
  the same golden traces.

No result in this document proves the future Rust implementation.  At most it
can prove that a proposed transition rule is coherent for the observed trace.

* Architecture under test

** Authority split

- =GraphRouter= owns normalized state, admissibility, evidence admission,
  obligation delta, join evaluation, and terminal closure.
- =SearchReasoningRouter= may produce a finite =RouteProposal=.  It cannot
  execute a provider action, mutate the graph, or declare an obligation closed.
- =SearchRouter= may execute only an admitted typed action under a current
  grant.  Its result is an observation until =GraphRouter= admits it.

** Evidence classes

The reducer must distinguish at least:

- =candidate=: lexical or reasoner-proposed evidence that may guide another
  action;
- =identity-proof=: parser-owned canonical identity under a current snapshot;
- =flow-proof=: typed caller, dependency, or projection edges;
- =test-proof=: concrete test identity plus a relevant assertion or reachable
  test edge;
- =absence-candidate=: no-hit evidence that is not yet a complete negative
  proof;
- =absence-proof=: complete, fresh, untruncated scope proof;
- =control-proof=: lifecycle, capability, budget, or policy evidence;
- =terminal-proof=: recomputable closure proof over every mandatory
  obligation.

A filename hit, an item name, a tests module, a manifest dependency, or a
=warm-miss= cannot be silently promoted to a stronger evidence class.

* Method

** Real-project tasks

Four concrete Rust tasks were used:

| ID | Real task | Primary risk |
|----+-----------+--------------|
| T1 | Locate the exact tree-sitter selector path that bypasses lexical =--term= validation and identify proving tests. | False owner and premature stop |
| M1 | Discover every Rust layer affected by adding a typed proof field to source-index candidate lookup. | Multi-obligation routing and lifecycle liveness |
| S1 | Verify a remembered owner that is deleted and find its current replacement and tests. | Stale memory and false absence |
| M2 | Re-run the source-index task after exact live owners are already known. | Stateful bypass, fan-out, and fan-in |

** Subagent lanes

- A fresh =asp_explorer= lane using the configured lightweight model executed
  T1 without source reads or exact =query=.
- A separate explorer lane attempted M1.
- A reasoning lane emitted advisory =RouteProposal= DAGs.
- A reducer lane evaluated observed packets as simulated =GraphRouter= input.
- An execution lane ran only specifically admitted search actions.

The reducer and reasoning lanes are still models.  Their agreement is not
authority.  Disagreement is evidence that =GraphRouter= must be executable code
and not another prompt role.

** Observation rules

The following rules were applied:

1. A command denied before provider execution produces no provider packet.
2. =quality=low=, =warm-miss=, =needs-cold-scan=, missing owner, and missing
   path terms remain unknown evidence.
3. A =recommendedNext= is a candidate action, not an admitted action.
4. Packet freshness must be proven by the exact root/digest, not by the words
   =live= or =present=.
5. An exact owner path suppresses broad discovery unless a separate open
   obligation proves that owner-local evidence is insufficient.
6. A provider action surface must be validated against the provider capability
   descriptor before admission.
7. Public =search= may use exact =query= internally, but the agent-facing loop
   must not be forced to switch public protocols.

** Baseline agent trace

The fresh lane began with a broad search over the observed error text.

#+begin_src shell
asp rust search pipe 'query requires at least one --term' --workspace . --view seeds
#+end_src

It selected
=build-support/asp-rust-project-harness-policy/src/build_gate.rs= as the best
owner.  A subsequent owner-local search returned an unrelated policy function.
A second broad search again favored =build_gate.rs=.

This was a false-owner route for the implementation question.

The lane stopped with a partial receipt and did not identify concrete proving
tests.  Stopping partial avoided false terminal closure, but the owner route and
the proposed next action were still wrong.

The receipt also reported =commandCount=4= while listing only three commands
and three latency samples.  Therefore free-form subagent metrics cannot be used
as the canonical accounting source.

** Independent owner evidence

Owner-local search against current candidate owners established:

- =provider_selector.rs= exposes selector-classification items;
- =workspace_tree_sitter_query.rs= exposes =has_exact_selector= and =parse=;
- a general owner query observed a tests module but no concrete proving test;
- =tree_sitter_query_diagnostics.rs= returned =no-owner-item-match= under the
  attempted terms.

This evidence rejects =build_gate.rs= as the canonical implementation owner,
but it does not close T1.O2, T1.O3, or T1.O4.

** Simulated reasoning proposal

The reasoning lane proposed five broad =search pipe= nodes, including a node
that searched source text for snapshot vocabulary.

The proposal was unsafe to admit unchanged:

- exact owner paths were already known;
- classifier and =has_exact_selector= existence had already been observed;
- packet freshness is metadata validation, not a semantic source search;
- five broad nodes repeated established axes and increased false-owner risk.

This shows why a reasoner proposal requires deterministic admission and
minimality checks.

** Admitted-action grammar failure

The simulated reducer selected an owner-local test action:

#+begin_src shell
asp rust search owner crates/agent-semantic-client/src/command/workspace_tree_sitter_query.rs tests --query 'exact selector term' --workspace . --view seeds
#+end_src

The provider returned exit =2= and recommended the =items= surface instead.

The action was semantically reasonable but grammatically unsupported.  A
=RouteProgram= containing raw command text cannot be considered safe merely
because its prose intent looks correct.

The admission layer therefore needs a typed provider capability descriptor.
Invalid action surfaces must be rejected before =ExecutionGrantIssued=.

** Search-only to exact-query boundary

After grammar repair, owner-local item search returned =parse= and
=has_exact_selector= but no test identities.  A refined search emitted:

#+begin_src text
rust://crates/agent-semantic-client/src/command/workspace_tree_sitter_query.rs#item/function/has_exact_selector
#+end_src

Its =recommendedNext= was an exact =asp rust query --selector ...= action.

An internal exact materialization confirmed that =has_exact_selector= detects
the two =--selector= forms.  That identity alone does not prove the downstream
term-validation bypass or concrete tests.

This trace demonstrates a hard protocol boundary:

- if only public =search= is exposed, =SearchRouter= must own internal exact
  materialization;
- a provider may return a typed =QueryHandoff= to =SearchRouter=;
- it must not return a prompt-facing raw =query= command as the only way to
  continue;
- =GraphRouter= must evaluate the materialized fact before another stage.

** Observed lifecycle failure

Two distinct =asp rust search pipe= commands were denied before provider
execution.  Both required a root-owned resident bootstrap.

The child could not perform the required bootstrap.  Root bootstrap could reach
=Ready= after a native acknowledgement, but another child remained denied, and
the live binding later returned to an unverified state.

The correct reducer result is:

#+begin_src text
GraphRouteEvaluation = Blocked
providerExecutionCount = 0
packetCount = 0
obligationDelta = {}
reasonerInvocation = forbidden for source semantics
nextActionClass = lifecycle recovery
#+end_src

The second search attempt did not add information.  A production loop must
deduplicate the blocking condition and wait for a control-epoch change rather
than spending search budget on alternate queries.

** M1 verdict

This is an end-to-end liveness failure.  A safe search contract cannot repair
an unreachable execution lane, and a reasoner must not fabricate source
evidence while the lane is blocked.

* M2: Stateful exact-owner fan-out

** Reasoning proposal

After exact owners were supplied as current state, the reasoning lane produced
a materially better finite DAG:

- three independent first-stage axes:
  - candidate type;
  - DB lookup facade;
  - ASP Server DB API;
- three dependent propagation nodes;
- three conditional test-discovery nodes;
- =maxFanout=3=;
- packet freshness evaluated from metadata rather than a search node.

This supports the stateful design claim: when exact owner identities are
already known, the loop should not re-enter generic discovery.

** Executed first-stage fan-out

Three exact-owner searches executed as one reported parallel batch:

| Axis | Owner | Selected identities |
|------+-------+---------------------|
| type | =source_index/types.rs= | =ClientDbSourceIndexCandidate=, =ClientDbSourceIndexSelectorPayloadProof=, lookup result/selectors, related types |

| ASP Server DB API | =server_source_index/api.rs= | =CurrentSourceIndexSnapshot=, =refresh_generation= |

All three reported exit =0= and zero-millisecond rounded latency.

The execution receipt reported only:

It did not carry the exact snapshot root/digest for each packet.  Therefore a
strict =GraphRouter= cannot prove that all three observations belong to the

The model summary is not an authoritative substitute for the provider packet.
The canonical executor receipt must carry exact binding values, and
=GraphRouter= must consume those values directly.

* Argument by architecture component

** GraphRouter

The single-authority direction is supported by the traces:

- it can prevent a false lexical owner from becoming closure;
- it can distinguish provider denial from an empty search result;
- it can keep warm-miss evidence below absence proof;
- it can reject manifest topology as implementation ownership;
- it can prevent fan-in without exact root equality.

However, model simulations disagreed on whether T1 should enter reasoning or
continue directly.  Therefore =GraphRouter= cannot be implemented as an LLM
persona.  It needs an executable reducer with a closed input algebra, failure
precedence, and deterministic transition table.

** SearchReasoningRouter

The reasoner behaved differently depending on state quality:

- with only broad candidates, it overproduced five search nodes and repeated
  already known axes;
- with exact live owners, it produced a coherent bounded three-axis DAG.

This supports reasoning-on-demand and state reuse, but it also proves that
=RouteProposal= admission needs:

- exact-owner preference;
- command capability validation;
- duplicate-axis detection;
- obligation coverage;
- evidence and freshness predicates;
- fanout and command budget limits;
- rejection of metadata-as-search-term nodes.

** SearchRouter

The executor can run bounded exact-owner actions and a parallel first stage.
It still lacks sufficient proof for:

- provider capability validation before execution;
- exact packet binding propagation;
- public-search/internal-query handoff;
- concrete test/caller/dependency materialization through the search surface;
- crash and retry attempt identity.

** Memory

The experiments support advisory memory only:

- an exact current owner can bypass broad reasoning;
- a deleted remembered owner must be revalidated;
- a warm miss cannot turn remembered state into a proven absence.

Memory may select a candidate command shape, but it cannot close an obligation
or prove freshness.

** Closure and stopping

No real scenario in this dossier reached full =ClosureFinalized=.

That is an important negative result.  The current search packets can identify
owners and items, but the loop still lacks an executable mapping from those
facts to claim-specific obligation deltas and test/flow/absence closure.

A =partial= stop is safe only when it explicitly preserves open obligations.
It is not a successful search-loop closure.

** Performance

Observed values are not yet a valid benchmark:

- exact owner searches reported rounded =0 ms=;
- one cold/warm-miss recovery reported about =1561 ms=;
- the fresh lane's command count and latency sample count disagreed;
- the parallel batch reported =0 ms= wall time without a canonical timing
  receipt;
- packet byte size and exact index/materialization state were not consistently
  reported.

The design hypothesis that exact stateful routing is faster is plausible, but
not yet proven.

* Independent adversarial review

An independent review was given only the observed T1, M1, S1, and M2 facts and
was asked to challenge the desired conclusion.

It agreed with the =NO-GO= decision and narrowed the supported claims:

- T1 proves false or premature broad ownership and narrower exact item
  candidates; it does not prove test coverage or the complete bypass flow.
- M1 proves an inaccessible execution lane and zero provider packets; it says
  nothing about source ownership.
- S1 proves only that the current warm evidence is insufficient; it does not
  prove source absence or a replacement owner.
- M2 proves owner-item acquisition and a reported parallel schedule; it does
  not prove complete propagation or same-snapshot synthesis.

The review identified plausible alternative explanations that the loop must
control:

- broad ownership may be a lexical/rank projection rather than parser-owned
  identity;
- tests may live in sibling modules or integration-test owners;
- lifecycle binding or installed-wrapper drift may explain M1 independently
  of provider source behavior;
- a warm index miss may reflect incompleteness rather than deletion;
- different packets may all say =snapshot=present= while carrying different
  roots.

Required positive and negative controls include:

| Scenario | Positive control | Negative control |
|----------+------------------+------------------|
| T1 | Recover a known concrete test and assertion with supported grammar. | A nonexistent selector must not fall back to broad ownership. |
| M1 | Produce one known-good packet through the same verified resident binding. | Contrast an intentionally expired binding with the verified binding. |
| S1 | Prove that the same cold snapshot finds a known-existing owner. | A deliberately nonexistent symbol must produce classified negative evidence on that same root. |
| M2 | Compare exact snapshot/provider/parser/schema digests across every packet. | Inject a mismatched root and require fan-in rejection. |

These controls are not yet executed and therefore remain entry gates.

* P0 design gaps

** Typed provider action capability

=RouteProgram= nodes must not contain executable raw CLI strings as their
authority.  They need a provider-neutral typed action plus a provider
capability proof:

#+begin_src text
ProviderAction
  languageId
  capabilityId
  owner?
  selector?
  surface
  normalizedTerms[]
  view
  expectedPacketSchema
  expectedEvidenceClass
#+end_src

The provider registry must declare which surfaces and fields are valid.

** Canonical provider observation

Every observation admitted by =GraphRouter= needs exact values:

#+begin_src text
SearchObservation
  actionKey
  attemptId
  providerAction
  packetSchema
  sourceSnapshotRoot
  providerDigest
  parserDigest
  schemaDigest
  policyDigest
  quality
  completeness
  truncated
  evidenceClass
  structuralSelectors[]
  recommendedAction?
#+end_src

Model summaries such as =snapshot=present= are non-authoritative projections.

** Obligation reducer

Each obligation class needs a closed reducer:

#+begin_src text
(ObligationState, SearchObservation, EvidenceGraphState)
  -> ObligationDelta | RejectedEvidence
#+end_src

The reducer must encode identity, flow, test reachability, enumeration,
absence, handoff, and partial evidence separately.

** Internal QueryHandoff

The public contract may remain =asp <language> search= only, but exact
materialization must be a typed internal action:

#+begin_src text
SearchRouter
  receives QueryHandoff
  validates exact selector and packet bindings
  invokes provider query internally
  returns canonical SearchObservation
#+end_src

No prompt-facing raw =query= command is required.

** Lifecycle block and recovery

Lifecycle failure is a control-plane state, not semantic uncertainty.

- a repeated denied search must not invoke the reasoner;
- all attempts with the same blocker collapse into one blocked state;
- recovery requires an observable control-epoch or binding-state change;
- a child must have a valid route to request or observe root-owned recovery;
- =Ready= must remain valid long enough for the admitted action or expose an
  explicit expiry/fence.

** Parallel join

Fan-in requires exact equality of authoritative bindings.  It cannot join on
=live=, =present=, equal leaf count, or model confidence.

** Action identity

=actionKey= identifies the logical action.  A separate =attemptId= is required
for physical provider invocations.  The contract must state:

- key derivation and collision domain;
- retry retention window;
- grant consumption and revocation;
- graph-admission deduplication;
- budget reservation/consumption/release;
- late result and cancellation handling.

* Rust entry gates

Rust implementation must not begin until the following design gates are
closed:

| Gate | Required evidence |
|------+-------------------|
| G1 executable reducer | A machine-readable transition table returns one deterministic outcome for every golden state. |
| G2 action capability | Every proposed action validates against a provider capability descriptor before grant. |
| G3 search-only boundary | Exact query materialization is internal and tested without exposing public =query=. |
| G4 observation bindings | Canonical packets carry exact roots/digests and survive subagent projection without loss. |
| G5 obligation reducer | Identity, flow, test, enumeration, absence, and handoff deltas are independently testable. |
| G6 lifecycle liveness | Fresh, stateful, and parallel children can execute admitted search actions without an owner-only bootstrap dead end. |
| G7 fan-out/fan-in | Parallel results join only under exact common bindings; mixed-root traces fail closed. |
| G8 retry semantics | Duplicate, crash, cancellation, and late-result golden traces preserve one graph admission and budget charge. |
| G9 stop correctness | No partial or low-quality trace emits terminal closure; all open obligations remain explicit. |
| G10 quality benchmark | Real-project golden tasks meet owner, flow, test, and stop-quality targets without false-owner routes. |
| G11 performance benchmark | Direct, PlanOnce, and Checkpointed profiles report canonical command count, reasoner count, latency, packet bytes, and storage work. |
| G12 cross-language replay | Equivalent Rust, TypeScript, Python, Julia, Gerbil, Org, and Markdown packets yield the same language-neutral reducer result. |

* Context reconciliation benchmark matrix

This section is the executable companion to
[[file:10.06-agent-search-projection.org::*Proof-carrying context reconciliation][Proof-carrying context reconciliation]].
The main RFC owns the normative algorithm and admission contract.  This section
owns fixtures, independent oracles, deterministic schedules, fault injection,
measurements, and receipts.  A green sandtable result is evidence for the
enumerated transition space only; it is not a new closure authority and is not
a proof over all possible repository states.

** Current verdict

The benchmark is currently =NO-GO=.  The already observed Rust parse failure,
absolute-selector =owner-outside-workspace= rejection, Python sibling-name
projection without executable selectors, repeated =recommendedNext= action,
and resident bootstrap/live-binding mismatch are retained as negative controls.
None of them counts as evidence that =ContextReconciler= is implemented, absent,
correct, or fast.

The benchmark MAY begin scoring reconciler behavior only after all entry gates
below pass.  Until then, the failures establish routing and lifecycle
confounders rather than reconciler quality.

** Reproducibility manifest

Every case MUST bind one immutable manifest containing:

- =caseId= and deterministic seed;
- canonical fixture root, fixture revision, language, and provider;
- source-tree digest plus dirty, staged, untracked, renamed, and deleted overlay
  digest;
- base revision and rebase target revision where applicable;
- resolved provider path, version, and executable digest;
- parser, registry, shared schema, query-pack, policy, and index digests;
- index quality and freshness state;
- initial cache-image digest and cache state;
- root session, resident target, live-binding receipt, and lifecycle state;
- exact selector or search intent and expected scope classification;
- mutation descriptor, dependency topology, expected impacted obligations, and
  expected residual obligations;
- cold-oracle frame digest, residual-obligation digest, and closure result;
- fault-injection point, retry policy, and deterministic concurrency schedule;
- all emitted event, join, grant, closure, and terminal receipts.

A result missing any identity needed to reproduce its evidence graph is
=unknown=, never =pass=.

** Independent oracles and baselines

The reconciler and its oracle MUST NOT share cache-key, dependency-invalidation,
claim-implication, or proof-rebase implementation code.

- =B0 independent fixture oracle=: hand-authored expected impacted obligations,
  reuse admissibility, scope, and failure class.
- =B1 isolated cold full recompute=: fresh process, cache, index view, and
  resident binding on the exact manifest; supplies canonical frame,
  residual-obligation, and closure digests.
- =B2 cache-disabled current runtime=: separates provider, parser, and lifecycle
  behavior from reconciliation behavior and supplies the latency baseline.
- =B3 naive snapshot-only reuse=: intentional negative baseline that must fail
  dependency, obligation, overlay, and proof-binding mutations that a coarse
  cache would miss.

=B0= and =B1= MUST agree before a case is scoreable.  Their disagreement is an
oracle defect and stops that cell.

** Entry gates

*** G0 Manifest identity

Every packet contributing to a case carries the same canonical workspace,
source-tree, overlay, provider, parser, registry, schema, query-pack, policy,
index, and graph-revision bindings.  Snapshot presence without exact digests is
insufficient.

*** G1 Rust owner control

A known Rust implementation symbol produces a valid in-workspace owner/items
result.  The existing parser failure remains a separate negative control.

*** G2 Rust exact-selector control

At least one Rust selector emitted for the test fixture materializes and
executes inside the benchmark workspace.  The current absolute-selector
=owner-outside-workspace= result remains a negative control.

*** G3 Python exact-selector control

The isomorphic Python fixture emits concrete executable selectors and a bounded
next-action sequence.  Sibling names and a repeated owner-search recommendation
do not satisfy this gate.

*** G4 Resident lifecycle control

The root-to-resident binding is verified against the recorded provider digest.
An intentional stale or mismatched binding is retained as a negative control.

*** G5 Independent oracle control

=B0= and =B1= agree on all positive and negative controls before the reconciler
under test is enabled.

property generator version, seeds, fixture digests, and final per-cohort
denominators.  Changing any of those inputs creates a new manifest and new
counts; it does not silently mutate an old benchmark claim.

The coverage layers are:

- =T0=: hand-authored minimal counterexamples;
- =T1=: exhaustive safety-critical partitions;
- =T2=: risk-based t-way covering arrays;
- =T3=: model-based lifecycle, cache, replay, admission, and grant traces;
- =T4=: property and adversarial mutations;
- =T5=: fixed real-project replay.

The products below instantiate =T1= through =T4= for the current proposal.
They do not prove universal completeness.

** Correctness acceptance

*** Zero false reuse

- =B0= and =B1= agree before scoring.
- No deterministic cell admits a reused proof that differs from =B1= in frame
  digest or residual-obligation digest.
- Unknown, parser failure, lifecycle denial, snapshot mismatch, and repeated
  next action never count as safe reuse.
- A provider, parser, schema, query-pack, policy, or obligation-set digest
  change invalidates reuse unless an explicit admissible proof binding covers
  it.
- The claim is worded as zero false reuse over the enumerated benchmark
  transition space, never as a universal proof.

*** Same-snapshot closure

- Every contributing receipt has exact digest equality with the case manifest.
- Final frame equals =B1=.
- =SearchClosureReceipt= is emitted only for the canonical empty residual
  obligation set.
- No mixed-snapshot closure event is accepted.

*** Rebase correctness

- Safe versus unsafe classification agrees with =B0= in every deterministic
  case.
- Post-rebase frame and residual obligations equal =B1=.
- Relevant source, dependency, parser, query-pack, policy, or obligation change
  prevents reuse of the old admission receipt.
- Tree-identical history transport regenerates current receipt identity rather
  than replaying an old terminal receipt.

*** Partial-refresh correctness

- Impacted-obligation recall is exactly =1.0=.
- The refreshed set is a superset of the oracle-impacted set.
- Final frame and residual-obligation digests equal =B1= in every case.
- Precision is reported separately and may improve performance, but it may
  never trade away recall or proof soundness.

*** Branch and join correctness

- The complete residual obligation DAG is the correctness oracle and canonical
  reconciliation state.
- Any frontier or antichain is an optional deterministic planner projection
  over that DAG; it is allowed to be lossy and MUST NOT authorize closure.
- A reused branch carries valid dependency bindings through its join.
- =JoinEvaluated= binds the input proof digests, join policy, obligation set,
  snapshot identity, and graph revision.
- Changing one branch, a mandatory predecessor, or =AND=/=OR=/=quorum= policy
  reopens the affected join and downstream obligations.

*** Failure recovery

- No uncommitted or partially written cache entry is reused.
- After fault removal, frame and residual obligations equal an isolated =B1=
  run.
- Dispatch identities and terminal receipts remain exactly once.
- Repeated-next terminates as bounded unknown or failure, never success.
- Provider lifecycle failure remains separate from semantic absence and
  reconciler failure.

** Performance method and acceptance

Correctness gates run before timing.  Performance runs pin CPU allocation,
concurrency schedule, fixture digest, provider binary, parser, index image,
cache image, and resident state.  Report cold setup separately from steady
state and publish median, =p95=, =p99=, bytes read, parser work, provider
invocations, refreshed obligations, cache reads/writes, and receipt bytes.

Compare against =B1= and =B2= on the identical manifest.  Do not compare a warm
indexed reconciler with a cold baseline that includes index construction.

For cells where the oracle impact is at most ten percent of the obligation
graph:

- refreshed work is lower than full recomputation at the median;
- =p95= wall time is no worse than =B2=;
- final frame and residual-obligation digests remain identical to =B1=;
- no latency or work-saving result is reported for a cell that fails a
  correctness gate.

The first implementation milestone MUST publish distributions and raw receipts;
it MUST NOT set a speculative absolute latency SLO before the fixed-fixture
baseline exists.

** Required receipt set

Each scored cell emits:

- manifest and source/overlay identity receipt;
- owner or selector routing receipt;
- per-obligation reuse, rebase, refresh, or open derivation;
- invalidation propagation and canonical residual-DAG digest;
- optional planner-projection receipt when a frontier or antichain is emitted;
- =QualityGateEvaluated= events;
- =JoinEvaluated= events where branches converge;
- =ActionAdmitted= and =ExecutionGrantIssued= only when their existing
  authority conditions are met;
- =ClosureProof= and =SearchClosureReceipt= only when residual obligations are
  canonically empty;
- fault, retry, dispatch, and terminal receipts;
- normalized Rust/Python parity receipt for =C5=.

The sandtable records these existing events and receipts.  It MUST NOT introduce
=ClosureDisposition=, =ExecutionAuthority=, =ProofSupportCut=, or a
=BranchJoinCertificate= as competing authority types.

** Stop conditions

The run stops immediately on:

- one unsafe reuse;
- one mixed-snapshot closure;
- one missing or duplicated terminal receipt;
- one oracle disagreement;
- one unclassified parser, selector, lifecycle, or repeated-next failure;
- one parity case silently omitted from the denominator.

After a stop, the failed manifest and append-only event trace become a permanent
regression fixture.  Performance measurement resumes only after the
correctness cohort is green again.
