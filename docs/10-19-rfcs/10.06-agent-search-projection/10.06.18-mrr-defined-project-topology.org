** Decision

Project Topology is an admitted MRR program and its materialized relation
closure. It does not sit beside MRR and it does not define an ASP-specific
extension framework over MRR.

The following six profiles form the standard MRR topology prelude:

1. =mrr.topology.workspace.v1=
2. =mrr.topology.engineering.v1=
3. =mrr.topology.domain.v1=
4. =mrr.topology.file.v1=
5. =mrr.topology.structure.v1=
6. =mrr.topology.reference.v1=

They are reusable MRR relation and rule modules, not a closed Rust enum and not
six monolithic project databases. A project uses Scheme/POO declarations to
compose, refine, or replace project-owned domain modules. Deployment, security,
data-flow, runtime authority, and organization-specific concepts are ordinary
MRR programs rather than extension records in another catalog.

The upstream stable Rust facade is =meta-relational-reasoning=. Inside the ASP
workspace, the independent =agent-semantic-mrr= package is the sole maintenance
window for that facade, its Ascent-backed closure engine, =gql-catalog=,
=gql-compiler=, =gql-ir=, and the Scheme/POO ahead-of-time compilation tuple.
Other ASP packages MUST NOT acquire those implementation dependencies directly.
Cargo versions and source revisions remain centrally pinned in
=[workspace.dependencies]=; the package consumes those entries with
=workspace = true= rather than moving dependency resolution into a member.
MRR owns typed identity, relations, query, deduction, explanation, impact
analysis, lineage, transition, admission, and atomic closure materialization.
=gql-core= and =gql= are frontend and projection adapters. GQL is not the
identity or authority of Project Topology.

The dependency direction is one way:

#+begin_example
upstream MRR / Ascent / GQL
  -> agent-semantic-mrr
  -> agent-semantic-topology and agent-semantic-search
  -> agent-semantic-runtime-server and agent-semantic-search-projection
#+end_example

=agent-semantic-mrr= owns generic compiler-derived relation patterns and exact
Scheme source / compiled ABI / MRR bundle receipt admission.
=agent-semantic-topology= still owns project-workspace equality, topology
vocabulary, source-fact attachment, generation transition, and topology
terminal semantics. Runtime owns neither compiler IR nor MRR kernel types; it
submits native query argv to the maintenance facade and consumes the admitted
relation pattern through Search.

** One Authority Pipeline

#+begin_example
native parser facts and source-owned declarations
  -> standard MRR topology prelude
  -> project Scheme/POO MRR program
  -> build.ss ahead-of-time compilation
  -> typed MRR bundle
  -> bounded mrr-ascent candidate closure
  -> MRR lineage, transition, and completeness admission
  -> immutable Project Topology generation
  -> GQL Search Playbook projection
  -> Agent-selected exact Query Playbook selectors
#+end_example

There is no extension catalog between the project program and MRR. There is no
second admission path. There is no Runtime-loaded Scheme interpreter.

Ascent proposes a bounded closure candidate. It cannot admit, publish, relabel,
or overwrite facts. MRR validates program identity, source bindings,
provenance, lineage, removals, transition, budget, fixed-point status, and the
terminal before materialization. GQL renders or queries the admitted result; it
cannot convert display equivalence into semantic authority.

** MRR Program Composition

The topology kernel contains only universal contracts:

- qualified profile, relation, rule-pack, projection, and node identities;
- canonical provider selector identity;
- direct, declared, derived, proposed, contested, and accepted modalities;
- source, declaration, derivation, and semantic-admission witnesses;
- snapshot, provider, grammar, program, bundle, and topology bindings;
- proof dependency, coverage, transition, fixed-point, and terminal receipts.

The kernel does not enumerate Rust methods, Org headings, JSON pointers, Nix
attributes, deployment units, or project domains. Native providers and MRR
programs supply qualified relation vocabulary.

MRR program composition supports three explicit operations:

1. =import= reuses an admitted prelude or project module unchanged.
2. =refine= adds stricter rules or project-owned derived relations while
   preserving imported fact meanings.
3. =replace= supersedes only a project-owned module under the same ownership
   namespace and publishes a new program and bundle identity.

Neither =refine= nor =replace= may reinterpret canonical selectors,
parser-produced facts, source identity, modality, witness provenance,
workspace containment, MRR admission, or terminal semantics. A project can
override its domain policy without overriding the truth kernel.

Gerbil Scheme and POO own the declarative MRR program, outer scheduling,
resource ordering, retry budgets, and termination policy. =build.ss= compiles
the declaration ahead of time into a typed native boundary. Scheme does not run
inside the Rust/Ascent Search or Query hot path.

*** Relation, Proof, And Frontier Algebra

The synchronized model has three disjoint outputs:

1. extensional edges supplied by a parser or admitted source contract;
2. intensional edges derived by the admitted MRR/Ascent program;
3. frontier obligations classified from expected relations and coverage.

Every extensional edge is a tuple
=direct(relation, from, to, modality, witness, binding)=. The relation name is
part of the fact and MUST NOT be erased into an untyped =direct(from,to)=
relation before inference. A generic path rule may derive
=TOPOLOGY_REACHABLE=, but it never relabels that conclusion as =CALLS=,
=COVERS=, =READS_CONFIG=, or another source-owned relation.

Every intensional edge is a tuple
=derived(relation, from, to, rule, proof, premises, binding)=. Its complete
premise edge set is preserved in the proof DAG. Project rules may compose
different extensional relations, but the head relation must be a separately
declared derived relation. For example, =CALLS(x,y)= and =READS_CONFIG(y,c)=
may derive =DEPENDS_ON_CONFIG(x,c)=; they may not fabricate
=READS_CONFIG(x,c)= unless that transitivity is explicitly part of the
source-owned relation contract.

An expected relation is an obligation, not a positive edge. For one bound
=expected(anchor, relation, targetKind, scope)=:

#+begin_example
positive witness exists                 -> no FRONTIER
no positive witness + complete coverage -> certified-missing FRONTIER
no positive witness + partial/no coverage -> unknown FRONTIER
#+end_example

Absence from an Ascent candidate set is never complete coverage. A proposed
model annotation may open an expected obligation but cannot close it, certify
absence, or become a factual premise. Frontier classification is recomputed
after every source or program transition and is admitted under the same
topology-generation binding as its positive and coverage inputs.

The public GQL is an information-preserving view of these outputs. Direct and
derived edges retain modality and witness/proof fields; =FRONTIER= retains the
expected relation, target kind, depth, state, reason, and optional coverage
reference. Ascent relation declarations and intermediate tuples remain
internal, but no admitted conclusion used for Agent reasoning may disappear
from the GQL projection.

** Git-Tracked Structured Mapping

The standard native topology program is a distributable ASP Org resource. Its
contract and audited template live in the =org= resource tree:

#+begin_example
org/
  contracts/asp/topology/program.v1.org
  templates/asp/topology/program.v1.org

.agents/asp/topology/
  manifest.org
#+end_example

=orgize= parses the audited template into typed program and rule fields through
its element graph and exact indexed =node-property= queries. The loader accepts
only the document-level contract property, the unique top-level program
headline, and rule or expectation drawers in that program subtree. Similar
property names elsewhere, nested program lookalikes, and inherited values are
not declarations. Org Contract trace validates the governing
=asp.topology.program.v1= contract. Runtime binds the exact Org source digest
into the topology resolver identity before constructing the MRR/Ascent program,
so editing or replacing the native resource creates a different generation
boundary.

This query and contract path is read-only. It constrains which reviewed values
may become typed MRR program metadata; it does not grant an Agent or LLM write
authority over the resource, parser-owned EDB facts, or candidate promotion.
Source relations change only with their native source/provider evidence and a
new admitted generation. Ascent consumes those relation-bearing facts to offer
bounded, witness-preserving recommendation candidates; MRR remains the
acceptance boundary.

=.agents/asp/topology/manifest.org= remains only the stable project/workspace
identity surface. It maps every logical workspace key to one normalized
repository-relative =workspaceRootPath=. The root path is a containment and
selector-resolution boundary, not a host path or independent identity. It does
not own, copy, or override the standard inference program. Native rules needed
by every ASP user MUST NOT live under =.agents=.

Project-specific semantic input, when a later version admits it, must have its
own versioned Org contract and typed admission path. It cannot be smuggled into
the workspace manifest or interpreted as an untyped extension registry.

** Worktree Resolution And Placement

Project identity, worktree selection, and checkout placement are different
layers. The architecture adopts the useful separation demonstrated by
worktree-oriented Git tooling without making that tooling or its branch-based
addressing part of the protocol:

1. =projectWorkspaceIdentity= identifies the durable logical workspace.
2. A branch, pull-request ref, or task label is an ergonomic
   =worktreeHandle=. It helps a Host locate or create a checkout but is not
   content identity and is never Query admission authority.
3. =workspaceRootPath= is the Git-tracked, repository-relative source boundary
   for that logical workspace.
4. =checkoutRootPath= is a Host-local physical path selected by user policy or
   a deterministic path template. Moving it does not change project or source
   identity.
5. =sourceSnapshotDigest= establishes the exact committed tree and admitted
   overlay observed in that checkout.

User-local placement policy MUST remain outside the repository topology. It may
choose sibling, nested, centralized, or branch-derived checkout paths. The
Git-tracked manifest owns only shared semantic configuration: canonical project
locator and aliases, logical workspace keys, repository-relative roots, MRR
program composition, and provider requirements.

Runtime MUST resolve Git common and worktree-private paths through Git's
worktree-aware interfaces. It MUST NOT assume that =.git= is a directory, that
the main checkout contains the current worktree's private state, or that a
worktree-private identifier is portable to another host.

Repository-level CAS objects MAY be shared between worktrees when their complete
content identities match. Mutable active-generation pointers, dirty overlays,
leases, sessions, and in-flight Search or Query state are worktree-scoped. A
branch name, checkout path, shared Git ref, or equal activation generation can
never substitute for an equal source-snapshot binding.

Runtime databases, Tantivy indexes, rank state, locators, temporary
transactions, and Hook journals remain outside the Git-tracked topology.

** Identity And Admission

The stable Project Workspace manifest binds only the first component below.
The Runtime-owned Project Topology publication joins that exact parser-owned
workspace binding with the mutable generation identities:

#+begin_example
(projectWorkspaceIdentity,
 sourceSnapshotDigest,
 providerCatalogDigest,
 parserCatalogDigest,
 mrrPreludeDigest,
 projectProgramDigest,
 schemeProgramDigest,
 compiledProgramAbiDigest,
 mrrBundleIdentity,
 ascentProgramDigest,
 topologyRootDigest)
#+end_example

The first component has canonical wire form
=<canonical-git-locator>#workspace/<logical-key>=, for example
=git+https://github.com/tao3k/agent-semantic-protocols.git#workspace/root=.
The Project Workspace manifest owns both the canonical locator and logical key. It may admit
explicit repository aliases for a reviewed rename or mirror migration, but it
never derives identity from the current clone path, remote name, Host session,
or Runtime-generated workspace identifier. Local-only =git+file://= identities
are valid for local projects but are not cross-machine identities.

The program binding embeds the complete shared =projectWorkspace= object:
=projectWorkspaceIdentity=, =workspaceRootPath=, =portability=, and reviewed
=repositoryAliases=. A generic Runtime =workspaceId= or arbitrary nonempty
=workspaceIdentity= is not a substitute. Changing only =workspaceRootPath=
preserves the durable project identity but changes the topology program binding
and its selector-containment boundary.

The Git-tracked Project Workspace manifest MUST NOT copy
=sourceSnapshotDigest=, provider/parser catalog digests, MRR/ABI identities, or
=topologyRootDigest=. Runtime receipts own those mutable values. Keeping them
out of the stable declaration avoids a self-referential source digest and
prevents an old manifest projection from authorizing a current generation.

This project identity does not identify source state. =sourceSnapshotDigest=
binds the exact committed tree and admitted overlay; Runtime instance identity
is an orthogonal operational binding and is excluded from the reusable topology
identity. A physical Git worktree is likewise host-local. Cross-machine
equivalence of two checkouts is established by equal project-workspace and
source-snapshot bindings, not by equal worktree paths or private Git dirs.

There is no =extensionCatalogDigest=. Domain customization is already contained
in =projectProgramDigest=, its compiled ABI, and =mrrBundleIdentity=.

=mrrBundleIdentity= uses the MRR facade's domain-separated wire form
=mrr:reasoning-bundle:v1:<sha256>=. A generic content digest cannot impersonate
this identity, even when the underlying hexadecimal payload happens to match.

No =current= pointer is required. Git exposes the reviewable working state;
content-addressed objects and the manifest identify the admitted generation.
Activation or publication generation remains a transaction fence and an
observability value, never topology freshness identity.

Search imports only an already compiled and admitted MRR bundle. Missing,
stale, uncompiled, ABI-incompatible, namespace-conflicting, or partially
composed programs fail before Ascent evaluation.

The ASP-side binding is
[[file:../../../schemas/project-topology-program-binding.v1.schema.json][project-topology-program-binding.v1]].
It references the admitted MRR identities and AOT receipt without reproducing
MRR relation, query, lineage, transition, or bundle semantics.

The Project Topology Library owns shared topology definitions such as coverage
certificates, semantic annotations, and exactly-one terminal shape. Search
settlement schemas MUST reference those definitions instead of copying them.
Validators MUST receive an explicit offline schema registry containing the
exact topology-library schema identity; remote schema retrieval and silent
single-file fallback are forbidden admission paths.

The Rust maintenance boundary is the independent =agent-semantic-mrr= package.
It owns external MRR/Ascent/GQL dependency acquisition, compiler adapters, and
generic Scheme AOT tuple admission. The independent
=agent-semantic-topology= package owns project-specific topology admission,
attaches the admitted MRR program binding to the parser-owned Project Workspace,
and owns incremental generation contracts. Search projection depends on the
topology package and owns only Search settlement, GQL rendering, and Query
handoff. Rust domain type names do not carry wire versions; schema identifiers
and schema-version constants own protocol evolution.

An admitted terminal is success-only evidence: its =reasonKind= MUST be null.
A failed or blocked attempt is a distinct typed terminal and MUST NOT be
serialized as an admitted binding carrying a failure reason. The compilation
receipt MUST be independently admitted and MUST bind the exact Scheme program,
compiled ABI, and MRR bundle identities from the product tuple.

** Incremental Construction

Native parser output is the factual substrate. A changed owner produces an
exact predecessor-bound relation delta:

#+begin_example
successor = (predecessor - removed) union added
#+end_example

Declaration skeleton identity is separate from body-derived relation identity.
A body edit may preserve membership while invalidating CALLS, EMITS, RETURNS,
REFERENCES, or another content-bound relation.

Removing a premise retracts every transitively dependent derived relation. An
incremental successor is admitted only when it is observationally equivalent
to a separately verified from-scratch MRR evaluation under the same program and
source identity. Append-only union is not an incremental topology algorithm.

Neither a nonzero receipt identifier nor an embedded receipt is evidence of an
independent rebuild. The complete rebuild receipt MUST equal a record in the
admitted receipt set; ID membership alone is insufficient. That record MUST
bind the exact source snapshot, MRR program, topology generation, and recomputed
library identity. A fixed-point receipt has the same replay boundary: its
complete record MUST be independently admitted and bind the exact source and
program identities in addition to proving =candidate = next=. A stable closure
from another generation or program is not reusable evidence, and an admitted
ID collision cannot authorize forged receipt fields.

The following paths are excluded from topology input:

- =.agents/asp/topology/**=
- =.cache/**=
- =.git/**=
- Runtime transaction journals and staging directories.

This prevents self-indexing and generation feedback loops.
The manifest authority reads =.agents/asp/topology/manifest.org= only for the
workspace identity binding described above; that does not make the directory a
source-fact or inference-program input.

** Model-Assisted Semantics

An Agent or model may propose summaries, domain groupings, architectural roles,
and cross-domain relations. Every proposal binds the selected topology slice,
model and prompt identity, premises, output digest, and uncertainty state.

Proposed semantics can affect ranking or open a frontier, but cannot become a
factual MRR premise. Promotion requires an independent source-owned or
human-authorized admission receipt and therefore creates a new Semantic
Topology identity. Natural language explains a proof-connected subgraph; it
does not replace the subgraph.

** Search And Query Projection

Search Playbook automatically imports the admitted MRR topology bundle. It does
not expose program loading, Scheme, or Ascent as public flags. The default
response is one compact Org container with one GQL settlement graph containing:

- native and document nodes with exact selectors;
- direct and derived relations with preserved modality;
- request-local fd, rg, Tantivy, native-syntax, and jq projections;
- topology depth and proof-connected paths;
- admitted or proposed natural-language annotations;
- coverage-aware known, missing, and unknown boundaries.

Canonical selectors remain on their GQL nodes. The Agent reads the graph and
passes only the selectors it chooses to Query Playbook; Search does not flatten
them into a second materialization or handoff set.

Project-owned relations and rules MUST have one synchronized semantic model
across the Org declaration, compiled MRR/Ascent bundle, Rust topology
projection, and Lean model. Lean formalization begins from the intended
relation and frontier semantics, constructs finite counterexamples for missing
witness, unsound closure, incomplete retraction, and false absence, and feeds
every discovered missing premise back into this RFC before implementation is
accepted. A compiling Ascent program or Lean file alone is not cross-layer
semantic closure.

The typed receipt carries complete MRR program, bundle, closure, proof-DAG,
ranking, topology, and terminal identity. GQL is a compact Agent reasoning
projection, not an admission receipt.

** Migration And Deletion

The current ASP workspace may temporarily consume legacy =gql-catalog=,
=gql-compiler=, or =gql-ir= dependencies and schemas. This compatibility is a
migration input only. It MUST NOT become a permanent bridge or alternate
authority.

A local checkout directory may retain a historical name such as =gql-rust=,
and a developer's local Git remote may lag the published repository rename.
Neither value is semantic Project Topology identity. Package metadata, pinned
source revision, admitted MRR bundle identity, and the canonical repository
identity are authoritative. Renaming a local directory is not a prerequisite
for MRR adoption, while production dependency URLs and repository metadata
must converge during migration.

Migration proceeds as follows:

1. bind existing GQL facts to the new MRR program and bundle identities;
2. make MRR the only closure and admission authority;
3. route GQL rendering through the admitted MRR result;
4. migrate callers to the =meta-relational-reasoning= facade;
5. delete legacy catalog/compiler authority and compatibility fields;
6. reject artifacts that still require the removed authority.

The migration is complete only when the old repository identity, old Cargo
dependencies, old catalog authority, and compatibility path have no production
callers. A deprecated field with a permanent reader is not deletion.

** Formal Obligations And Counterexamples

The formal model MUST prove:

- open profiles do not require a new kernel variant;
- project program refinement preserves imported core facts;
- project-owned replacement cannot shadow a core relation signature;
- equal GQL shape does not imply equal modality or authority;
- an Ascent candidate is not an admitted MRR closure;
- program or compiled-ABI drift invalidates reuse;
- deletion-complete replacement retracts transitive descendants;
- budget exhaustion is distinct from fixed point;
- proposed model semantics cannot become factual premises;
- topology output cannot become its own parser input.
- successful admission requires an independently admitted AOT receipt;
- an admitted terminal cannot carry a failure reason;
- equal serialized digest shapes cannot substitute across identity domains.
- relation erasure cannot turn heterogeneous direct edges into an invented
  semantic relation;
- every derived edge has a complete, nonempty premise set under the same
  source/program binding;
- removing any premise retracts every dependent derived edge;
- a positive witness suppresses the corresponding frontier;
- certified missing requires complete relation coverage;
- partial or absent coverage yields unknown rather than false absence;
- proposed semantics cannot close either a positive relation or a frontier.

The model MUST retain executable counterexamples for closed profile enums,
parallel extension admission, core-signature shadowing, GQL authority erasure,
append-only deletion, activation-generation freshness, uncompiled hot-path
programs, proposed prose as facts, fuel exhaustion as fixed point, relation-kind
erasure, witness-free derivation, stale derived descendants, false absence from
partial coverage, and simultaneous positive-edge/frontier publication.

The formal model is
[[file:../../../packages/proofs/ASPProof/ProjectTopologyProgram.lean][ProjectTopologyProgram]].
Its adversarial countermodels are
[[file:../../../packages/proofs/ASPProof/Audit/ProjectTopologyProgram.lean][ProjectTopologyProgram Audit]].
The schema-facing, domain-separated refinement boundary is
[[file:../../../packages/proofs/ASPProof/ProjectTopologyIdentityRefinement.lean][ProjectTopologyIdentityRefinement]],
with adversarial checks in
[[file:../../../packages/proofs/ASPProof/Audit/ProjectTopologyIdentityRefinement.lean][ProjectTopologyIdentityRefinement Audit]].

** Implementation Order

#+begin_example
RFC and Lean countermodels
  -> shared MRR topology manifest and bundle schemas
  -> Org contract and deterministic fixtures
  -> agent-semantic-mrr maintenance facade
  -> direct MRR / Ascent / GQL dependency deletion from consumers
  -> provider topology adapters
  -> incremental Runtime builder and MRR admission
  -> Search GQL projection and independently Runtime-bound Query request
  -> deletion of legacy catalog authority
  -> sandtable and representative-project evidence
#+end_example

No Rust implementation precedes acceptance of the RFC, formal model, and shared
schemas. Transitional compatibility has an explicit deletion stage and cannot
publish a second semantic authority.
