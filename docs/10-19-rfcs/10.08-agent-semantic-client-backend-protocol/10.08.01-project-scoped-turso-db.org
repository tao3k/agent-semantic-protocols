#+TITLE: RFC 10.08.01 - Project-scoped Turso DB
#+STATUS: accepted

* Decision

ASP owns one physical Turso facts database per stable Project ID:

#+begin_example
STATE_ROOT/projects/by-id/PROJECT_ID/live/client/facts.turso
#+end_example

ASP does not create a persistent database per resident agent, per Explore
worker, or per workspace.  Concurrent workers consume project-owned read
snapshots.  A project-owned broker serializes mutable publication.

Workspace state remains a logical partition of the project database.  Every
mutable or replaceable fact must carry:

- =project_id=
- =workspace_id=
- =scope_id=
- its content or publication =generation=

An immutable content-addressed row may be shared only when its identity includes
the complete parser, query-pack, source, and Merkle proof identity.

* Physical and logical layout

The project database and project DB manifest live below the Project ID:

#+begin_example
projects/by-id/PROJECT_ID/live/client/facts.turso
projects/by-id/PROJECT_ID/live/client/manifest.json
#+end_example

Workspace-local activation, cache manifests, hooks, and artifacts remain below:

#+begin_example
projects/by-id/PROJECT_ID/workspaces/WORKSPACE_ID/...
#+end_example

The workspace manifest references the project database plus its
=workspace_id/scope_id= namespace.  It must not imply ownership of a separate
physical database.

* Concurrency ownership

The project DB has one mutable owner:

1. one broker owns schema migration and write transactions;
2. publication is serialized per project and generation;
3. readers use read-only MVCC snapshots and never enable or migrate schema;
4. resident agents never receive direct write permission to the Project state
   root;
5. an ephemeral search overlay belongs in memory or a disposable session
   directory, not in a resident-specific Turso database.

High concurrency is therefore a connection and snapshot property, not a reason
to duplicate durable facts by agent role.

* Schema version 1 partition audit

The active schema is not uniformly workspace-safe:

- =asp_cache_generation= uses =generation_id= as its only primary key.
- =asp_syntax_query_replay= uses =generation_id= as its only primary key.
- source-index scope, owner, layout, and token tables include
  =project_root= in their keys, but do not carry the stable Project,
  workspace, and scope identities.
- provider-command selection and artifact events include =project_root= or an
  artifact path in their keys, but do not carry the complete logical
  partition.
- =asp_artifact_root= already carries
  =repo_id/workspace_id/scope_id/generation=.
- artifact edges, repair frames, and proof receipts are shareable only when
  their content-addressed identity is complete and verified.
- search-projection tables use a caller-owned =namespace= and therefore require
  a contract-visible namespace derivation before project-wide sharing.

Schema version 2 must make the logical partition explicit for every mutable
table. Existing path, namespace, or generation strings may remain lookup
attributes, but they are not substitutes for the stable composite partition
key.

** Version 1 amendment

This repository has not published a second client DB schema version.  The
project-scoped partition contract therefore amends schema version 1 in place;
implementations MUST NOT create a parallel =v2= schema, file, or compatibility
branch.

The amended version 1 tables use composite identities instead of a globally
unique generation identifier.  Cache rows are keyed by project, workspace,
scope, and generation.  Every lookup, prune, clear, and invalidation statement
must carry the same partition predicate.

The physical database boundary is Turso 0.7 native format.  An earlier SQLite
or SQLite-compatible file MUST NOT be opened and amended in place with
=PRAGMA=, =ALTER TABLE=, or compatibility DDL.  Migration treats the earlier
database only as an input identity: canonical v1 manifests and durable
artifacts are replayed into a newly created Turso 0.7 sibling file, the new
file is validated, and only then is it atomically promoted to =facts.turso=.
The earlier file remains a rollback artifact until the promotion receipt is
durable.

The active Turso 0.7 file records both logical schema version =1= and a
physical-format migration identity.  Absence of that identity is a cutover
condition, not permission to retain a SQLite compatibility path.

This in-place amendment is allowed only because project-scoped
=facts.turso= has not passed the cutover gate.  Once a released client DB
schema has external compatibility commitments, future incompatible changes
must use an explicit migration/version boundary.

* MVCC partition performance gates

The generic =TursoMvccStore= owns SQL, =BEGIN CONCURRENT= retry policy, and
partition compare-and-append.  Context-product and loop adapters MUST use the
typed store API and MUST contain no SQL.

Correctness gates run on every normal test pass:

- two commits against the same partition head produce exactly one commit and
  one conflict;
- stale-head replay appends no second record;
- commits against distinct run/partition keys both commit and retain isolated
  record streams.

The explicit release-host benchmark
=partitioned_mvcc_write_and_read_latency_receipt= measures one append and one
read for each of 64 initialized partitions by default.  It emits partition
count plus write/read p95 latency.  Defaults are =100000us= write p95 and
=50000us= read p95; release environments MAY tighten them through
=ASP_TURSO_MVCC_BENCH_MAX_WRITE_P95_US= and
=ASP_TURSO_MVCC_BENCH_MAX_READ_P95_US=.  The sample count is controlled by
=ASP_TURSO_MVCC_BENCH_PARTITIONS=.

These gates prove in-process MVCC partition behavior only.  They MUST NOT be
presented as multi-process local-replica safety: a single resident/broker owns
the mutable project database, while other processes use that owner or immutable
snapshots.

* Migration gate

The current workspace-local database is an implicit isolation boundary.  In
schema version 1, cache-generation and syntax-replay primary keys do not carry
workspace or scope identity, and search-projection namespaces are caller-owned.
The active path must not switch to the project DB until schema version 2
provides explicit partitioning.

Migration is fail-closed:

1. enumerate legacy workspace databases for one Project ID;
2. open each legacy database read-only;
3. import rows with explicit project/workspace/scope identity;
4. reject collisions rather than overwrite another workspace;
5. compare per-table counts and generation/content digests;
6. atomically publish the project DB manifest;
7. retain legacy databases until the project DB receipt is verified and
   rollback is possible.

The migration receipt records source workspace IDs, source DB digests,
destination DB digest, per-table row counts, collision count, and active
manifest generation.

** Version 1 exact cache lookup pointer

An exact request-fingerprint lookup MUST NOT scan or sort historical cache
generations.  Version 1 owns a single active-generation pointer keyed by:

- project root
- language id
- provider id
- export method
- request fingerprint

Import updates the immutable generation row and a materialized active row in
the same write transaction.  The active row uses one collision-free,
length-prefixed canonical lookup key derived from the five identity fields and
contains the complete version 1 cache-hit payload.  Exact lookup is therefore
one primary-key read: it does not join the historical generation table, has no
=ORDER BY updated_at_ms=, and does not require an optimizer-specific
=INDEXED BY= hint.  Prune, clear, and project invalidation update generation
rows and active rows as one consistency boundary.

The reverse mapping uses a second single-column, length-prefixed canonical
generation key.  Replacing an active row therefore resolves both uniqueness
constraints with single-key indexes; it MUST NOT require a composite-index
scan for each imported generation.

Historical recency lookup without a request fingerprint remains a separate
ordered query.  Its performance does not define the exact reasoning-cache hit
path.

** Version 1 cache write batching

S2 MUST measure cache-generation import and exact-fingerprint lookup as separate
phases.  A lookup latency receipt without the write phase is incomplete.

The version 1 Turso write path MUST:

- validate and serialize the complete manifest before opening the transaction;
- write cache generations and active-generation pointers in one transaction;
- bind multiple rows per SQL statement with a bounded parameter count instead
  of awaiting one statement per generation;
- preserve manifest order so the final row for a lookup key remains the active
  generation; and
- report =writeWallMs=, =writeOperationsPerSecond=, =lookup p50/p95/p99=, and
  the configured write and lookup gates in the same S2 receipt.

The default 10,000-generation S2 gate is 5,000 milliseconds for the complete
write phase.  Performance closure MUST use an optimized production profile.
An unoptimized test build remains useful for correctness, but its wall time is
not a production performance receipt.

** Turso 0.7 full cutover algorithm

*** Version 1 migration receipt

The cutover MUST treat =facts.turso= and =search-projection.turso= as one
project-client migration unit.  A legacy SQLite or SQLite-compatible file MAY
be opened only by the bounded migration reader; it MUST NOT become the active
runtime database and MUST NOT be amended in place.

Before promotion, every durable version 1 family MUST produce a receipt with:

- source record count and deterministic source digest
- target record count and deterministic target digest
- a verified state requiring equal counts and equal digests

The required families are cache manifest, syntax query replay, source index,
structural/search projection, provider command selection, artifact event, and
artifact pointer/graph.  An empty family is complete only when its replayer
records an enumerated zero count and the canonical empty digest.  A boolean
"covered" flag without count and digest evidence is not sufficient.

Promotion is permitted only after all family receipts verify, both Turso 0.7
physical-format receipts exist, all writer/read handles are closed, and both
database pools are evicted.  The staging directory is then renamed into the
project-id client directory as one atomic filesystem operation.  The legacy
source remains a rollback artifact and is never reopened by the normal client
DB path.

The migration owner must replay every durable v1 input into one staging
Turso 0.7 database.  Cache manifests, syntax-query packets, source and
structural index artifacts, provider-command selections, artifact events, and
artifact-pointer authority are one migration unit; a cache-only import is not
a complete database migration.

The cutover sequence is:

1. freeze the project writer broker and enumerate all workspace-owned v1
   manifests and durable artifacts;
2. create a sibling staging directory and let Turso 0.7 create a new
   =facts.turso= with experimental indexes and the v1 physical-format marker;
3. replay each authoritative input through its normal Turso 0.7 writer API,
   never by attaching or querying the SQLite file;
4. validate per-workspace/per-scope row counts, artifact identities, Merkle
   roots, and representative lookups;
5. close and evict all staging connections, make the migration receipt
   durable, then atomically promote the staging directory;
6. retain the earlier database as a read-disabled rollback artifact until the
   promoted database passes S0 through S6.

Any missing replayer, count mismatch, lock timeout, SQLite header at the
promotion target, or absent physical-format marker fails closed before
promotion.

* Scenario-based performance validation

Project-scoped Turso performance is validated as a system scenario, not as one
isolated SQL micro-benchmark. Every receipt records the code revision, schema
version, Turso version, operating system, filesystem, CPU count, reader count,
writer count, row count, sample count, and resolved DB path.

The required scenario matrix is:

| ID | Scenario | Workload | Required evidence |
|----+----------+----------+-------------------|
| S0 | Partition correctness | two workspaces under one Project ID publish the same generation IDs | both workspaces remain queryable; zero cross-partition hits |
| S1 | Cold bootstrap | empty project state, schema bootstrap, first manifest import | p50/p95 wall time, files created, bytes written |
| S2 | Warm lookup | 1,000 generations, 10,000 cache and exact-selector lookups | p50/p95/p99 latency, operations per second, hit/miss correctness |
| S3 | Single writer and many readers | one writer publishes 32 generations while 8 and 16 readers hold pinned read sessions | read/write throughput, p95 latency, busy/locked/retry counts, final generation |
| S4 | Multi-workspace sharing | four workspaces share one physical project DB and use colliding local generation names | per-workspace counts and digests, total DB bytes, zero overwrite |
| S5 | Legacy migration scale | 1, 4, and 16 workspace databases with 100, 1,000, and 10,000 rows per workspace | rows per second, p95 workspace import time, collision count, source/destination digest equality |
| S6 | Sandboxed broker read | direct state-root DB open is denied while the project broker serves the same read | broker p95 overhead, permission-denied classification, result digest equality |

Correctness gates are absolute:

- zero cross-workspace or cross-scope hits;
- zero lost committed generations;
- zero unclassified =busy=, =locked=, or permission errors;
- readers observe one complete generation, never a partially published one;
- migration row counts and content digests match before activation;
- no resident-agent-specific persistent database is created.

Performance gates are comparative so that hardware speed is not mistaken for a
protocol property:

- S2 warm lookup p95 must not regress beyond 1.50 times the workspace-local
  baseline on the same machine and revision;
- S3 throughput with eight readers must remain at least 70 percent of the
  single-reader baseline, with zero lock failures;
- S4 total durable bytes must remain below the sum of four workspace-local
  databases after equivalent facts are imported;
- S5 normalized time per row at 16 workspaces must remain within 2.00 times the
  one-workspace result;
- S6 broker read p95 must remain within 2.00 times an allowed direct read while
  returning the same result digest.

S0 is a prerequisite for S1 through S6. A fast run that overwrites another
workspace is a failed run. The project DB path must not become active while any
required correctness gate is red.

* Observed clean-HEAD baseline

The first scenario run was executed on 2026-07-24 against client DB engine
commit =a5cd96159d6ec02f9497edb4c9d3d83735ed046e=.  The scenario harness was
injected into a clean checkout so unrelated worktree changes could not affect
the engine under test.

| Scenario | Result | Receipt |
|----------+--------+---------|
| S0 partition correctness | FAIL | Reusing =shared-generation= in workspace B replaced workspace A's row.  Workspace A missed while workspace B hit. |
| S1 cold bootstrap | PASS | 16 samples: p50 22,751 us; p95 and p99 45,302 us. |
| S2 warm lookup | FAIL for cutover | 1,000 generations and 1,000 lookups: 13 operations/s; p50 61,315 us; p95 158,125 us; p99 302,487 us. |
| S3 one writer, many readers | FAIL | 8 readers x 64 reads plus 32 publications: 131/512 read errors and 1 writer error; every reported error was =database is locked= and the final generation was not visible. |

S0 is a schema isolation failure, not a tuning issue.  S2 and S3 also expose
an ownership problem in the current engine: a read or write session stores only
the database path, then each operation reconnects and attempts schema bootstrap.
Concurrent reads therefore contend with DDL/bootstrap work, and a warm lookup
pays connection and bootstrap costs that should be amortized by a project
broker.

These receipts prohibit switching =ClientDbEngine= to the project-scoped
physical database.  The next implementation must first provide:

1. amended schema v1 composite partition keys that include project, workspace, scope,
   and generation identity where applicable;
2. one project writer broker that owns connection establishment, schema
   bootstrap, migration, and publication;
3. long-lived read-only snapshot connections that never run bootstrap or DDL
   on the lookup path; and
4. a green rerun of S0, S2, and S3 before S4 through S6 can authorize cutover.

* Required validation

- Two workspaces under one Project ID resolve the same physical DB path.
- Their workspace manifests, hooks, caches, and artifacts remain distinct.
- Identical generation IDs in different workspaces do not collide.
- Replacement and invalidation affect only the selected
  =workspace_id/scope_id=.
- Many concurrent readers observe a pinned generation while one writer
  publishes the next generation.
- A sandboxed Explore can search through the broker without write access to the
  project DB directory.
- Cache status reports =unavailable(permission-denied)= rather than
  =unimported= when a direct DB open is denied.
