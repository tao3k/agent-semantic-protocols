#+TITLE: RFC 10.20 Research - tgrep Performance Architecture
#+DATE: 2026-09-12
#+STATUS: Research

* One-sentence summary

The fundamental lesson from =tgrep= is not to remove GREP from SearchLoop or add
another search daemon.  V1 GREP is the fast lexical-anchor stage before parser
and Relation/Query reasoning.  The high-leverage change is to implement that
existing =rg= axis as a generation-bound trigram candidate index followed by
an in-process resident GREP exact matcher, then fuse it with Tantivy before
native syntax and graph reasoning, all under ASP Runtime Server authority.

* Scope and authority boundary

This note studies performance architecture only.  It does not change the public
Search/Query contract and does not authorize:

- a =tgrep= subprocess or TCP daemon on the ASP request path;
- a second workspace crawler, watcher, lifecycle owner, or index directory;
- client-local search fallback;
- weakening =ProjectId=/=WorkspaceId=/content-generation identity;
- replacing Tantivy lexical retrieval or provider-native structural facts;
- changing V1 Scheme source, request/result schema, or the public =rg= axis;
- treating benchmark wall time without work-count and identity receipts as
  acceptance.

ASP Runtime Server remains the sole owner of inventory, source bytes,
generation admission, derived attachments, query execution, cancellation, and
publication.  The byte-coverage attachment discussed here is an internal
generation artifact, not a new public backend.

** Differential correctness counterexample

The upstream fuzz target for =tgrep-core::query= checks that arbitrary patterns
do not panic; it does not prove the required candidate-superset property.  A
direct indexed differential found a false absence for Unicode case folding:

#+begin_src text
fixture owner A: contains both "ÜBER" and "über"
fixture owner B: contains only "ÜBER"
query: -i 'über'

tgrep indexed plan: AND(3 trigrams), candidates 1/2
tgrep owners: A
rg owners: A, B
#+end_src

The tgrep builder materializes original bytes plus ASCII-lowercased trigrams,
while its case-insensitive query plan lowercases a UTF-8 string with Unicode
case conversion.  The exact matcher can match owner B, but the candidate index
removes it first.  This is a concrete false negative, so tgrep's current query
planner and case-folded index cannot be imported as V1 correctness authority.
The packed key, mmap, external-sort, and posting-intersection techniques remain
useful only after ASP-specific candidate-superset differential proof.

* What tgrep changes fundamentally

** Query cost becomes candidate-dependent

A scanning grep pays approximately =O(total admitted bytes)= per query.  tgrep
extracts mandatory literals from regex HIR, turns their overlapping trigrams
into posting lists, starts with the shortest posting, and verifies the original
matcher only against the surviving files.  The steady-state cost is closer to:

#+begin_src text
posting lookup + posting intersection + bytes of candidate files + output
#+end_src

This is the architectural gain.  SIMD tuning of a full-corpus scan cannot
remove its dependence on total corpus bytes.

** Read and write representations are deliberately different

The build path uses mutable maps, bounded arenas, spill files, sorting, and
merge.  The read path uses immutable sorted tables and mmap slices.  tgrep does
not keep the convenient build representation alive merely because it was easy
to construct.

That separation yields:

- bounded heap independent of repository posting volume;
- compact sequential posting reads;
- OS-managed page residency;
- cheap process/server reopen;
- a publication artifact that can be validated before it becomes current.

** Memory is budgeted by actual liability

tgrep bounds a batch simultaneously by file count, owned heap bytes, and mapped
bytes.  Large mapped inputs receive a small heap charge plus a separate mapped
residency budget.  This avoids both failure modes: reading several large files
onto the heap at once, and serializing mmap work because mapped bytes were
charged as heap.

The external posting sorter applies the same principle to index construction:
the arena budget controls peak heap, sorted spill segments absorb excess work,
and a k-way merge streams the final index.

** Publication is snapshot-based

The server queries one =Arc<IndexReader>= snapshot for the complete request.
Flush builds a replacement generation outside the query lock and swaps the
reader briefly.  In-flight requests retain the old mmap until their =Arc=
drops.  This avoids mixed file-id generations and long stop-the-world flushes.

The live overlay is useful as a latency pattern, but ASP must not copy its
weaker identity semantics directly.  In ASP, any delta visible to a query must
be bound to an explicit content generation and publication receipt.

** False positives are made cheap before exact verification

tgrep stores per-file positional masks and an 8-bit next-byte Bloom mask beside
each trigram posting.  They cannot establish a match, but they can reject more
files before opening/scanning contents.  Exact matching remains authoritative.

* GREP's position in the complete ASP SearchLoop

GREP is not the final code-understanding engine.  Its V1 responsibility is to
turn native rg keyword/regex combinations into fast owner and byte anchors.
Those anchors bound the expensive work that follows:

#+begin_src text
one admitted Scheme composition
  -> V1 rg lexical anchors (trigram candidates, then exact resident match)
  -> V1 Tantivy ranked lexical owner set
  -> fused immutable owner context
  -> provider-native syntax selectors
  -> Relation / graph Query computation
  -> compact generation-bound evidence
#+end_src

The stages are deliberately complementary.  Tantivy is good at tokenized,
ranked lexical retrieval but does not preserve arbitrary byte substring,
punctuation, or native rg regex semantics.  A parser gives structural precision
but should not pay to parse or traverse the whole workspace for every lexical
question.  The GREP stage therefore remains architecturally necessary even
when no =rg= process remains on the request path.

ASP already implements the correct high-level topology:

  -> generation-bound result receipt

The first resident GREP implementation closes the query-time representation
gap.  Remaining gaps are primarily build-time and exact-semantics breadth:

| concern | resident GREP implementation | remaining lesson |
|-
| trigram key | packed 24-bit =u32= in a sorted directory | benchmark lookup layout and optional perfect hashing |
| per-owner extraction | build-time unique gram set | allocation-aware extraction and bounded external construction |
| postings | delta-varint postings in the V1 generation mmap | optional positional and next-byte masks |
| build memory | still proportional to the complete temporary postings map | fixed arena plus external spill/merge |
| query intersection | retain smallest posting vector; stream later AND postings in place; stop at zero or one candidate because exact verification is authoritative | bound OR-union allocation and measured decoded work |
| false-positive filter | trigram membership only | optional positional and next-byte masks |
| reopen | validates and borrows published mmap; no workspace postings rebuild | preserve this invariant under delta generations |
| delta | build a new immutable attachment | reuse unchanged immutable segments; publish one new generation |
| regex planning | HIR-derived conservative AND/OR plan shared with literal evaluation | generated candidate-superset differential coverage |
| correctness evidence | focused candidate-superset differential cases | generated/property differential corpus against rg |
| case folding | unsafe trigram plans use the bounded Tantivy fused scope, never claim global absence | proved Unicode folding strategy or qualified matcher extractor |

ASP is already stricter where it matters: content/Merkle identity, authority,
typed budgets, exact-byte verification, selector projection, and atomic Runtime
publication.  Those properties must constrain the optimization rather than be
traded away for tgrep compatibility.

* Recommended architecture

** P0: instrument the real request path before replacement

Add one generation-bound receipt covering:

- query-plan construction nanoseconds;
- grams requested and distinct grams;
- posting lengths and chosen first posting;
- raw candidate count and verified owner count;
- bytes verified;
- index lookup, owner resolution, exact match, projection, graph, serialization,
  ClientFrame transport, and total nanoseconds;
- allocation/retained-byte estimate for byte coverage;
- explicit workspace filesystem calls, provider calls, native finder processes,
  and child processes. Mapped page faults are not zero physical I/O.

Without this split, a sub-millisecond index can be hidden behind owner-string
cloning, projection, transport, or rendering.

Generation owner cardinality and membership are direct reads of the authoritative
resident owner directory. Retrieval must not clone the entire path directory
into a per-request set merely to validate Tantivy hit ownership. Language-route
filtering remains mandatory and unchanged by this representation optimization.

** P1: preserve V1 and introduce a private trigram candidate seam

Keep =ResidentByteCoverageIndex= behavior but move the physical representation
behind a private generation-local interface:

#+begin_src rust
trait GrepCandidateAttachment {
    fn candidate_owner_ids(
        &self,
        plan: &GrepCandidatePlan,
        authority: Option<&ResidentSearchAuthority>,
        budget: CandidateBudget,
    ) -> Result<CandidateOwnerIds, ByteCoverageError>;
}
#+end_src

The public input remains the V1 =(rg ...)= native argv leaf.  Runtime compiles
it into an internal =GrepCandidatePlan=; no plan object crosses the wire and no
schema version changes.  The interface returns generation-local owner IDs, not cloned paths.  Path and
content resolution happen against the same leased generation after candidate
selection.  The exact matcher and rg differential corpus are the correctness
references; no heap-map fallback is selected silently in production.

** P1.5: Tokio owns scheduling, not the search algorithm

Resident GREP remains a synchronous CPU/mmap kernel.  Making posting decode or
regex matching syntactically =async= would not accelerate it and would obscure
benchmarks.  The async Runtime route instead acquires a bounded global Tokio
semaphore and moves the deterministic GREP plus Tantivy retrieval phase to
=spawn_blocking=.  This prevents CPU scans and mmap page faults from occupying
the RPC reactor while preserving one ordered fan-in.  Do not spawn one task per
file: batching, cancellation checkpoints, and one request-level concurrency
budget are required before introducing owner-shard parallelism.

** Lean/Rust cost refinement loop

=ASPProof.ResidentGrepCost= models the Rust receipt fields and proves:

- exact hits are a subset of candidates under =SoundMandatoryGrams=;
- adding mandatory grams cannot widen the candidate set;
- only a sound selective plan or exactly verified fused scope may publish absence;
- pushing a complete Tantivy scope into sound candidates preserves exact hits;
- streaming decode has a conditional prefix-work bound;
- fixed request costs impose an Amdahl-style limit on end-to-end acceleration.

The zero-process, mapped-heap and reactor-placement statements are conditional
model properties, not proofs that the Rust implementation satisfies their
premises. Neither those statements nor arithmetic witnesses establish a 10x,
20x or 100x measured speedup. Rust differential tests and attributable request
receipts must independently discharge the implementation obligations.

The model exposed one implementation bug during this work: the earlier Rust
path sorted postings by length only after decoding all of them.  The format API
now reads =posting_count= from the directory first and decodes the rarest
posting.  Intersection stops at zero candidates, or at one candidate because
the exact matcher must inspect that owner anyway and remains the result
authority.  Decoding every remaining common posting cannot improve the work
bound in that state.  Rust receipts report =decodedPostingCount= so the
theorem-side cost model can be calibrated against actual executions.

For regexes with no sound mandatory trigram, V1's required =rg ∩ Tantivy=
composition provides the bounded fallback: Tantivy is evaluated first and the
resident exact matcher scans only that owner scope.  A standalone
=notMaterialized= plan still cannot publish absence.

** P2: build a compact mmap byte-coverage artifact

Recommended V1 physical layout:

#+begin_src text
header:
  schema/version, gram width, generation digest, owner-table digest,
  artifact digest, complete coverage count

lookup table, sorted by packed 24-bit gram:
  gram, posting byte offset, posting count

posting stream:
  delta-varint owner id, optional loc mask, optional next-byte mask

owner table:
  generation-local owner id -> owner record index/content digest authority
#+end_src

Open validates bounds, ordering, coverage identity, and artifact digest before
publication.  Queries binary-search the fixed lookup table and decode only the
selected postings.  No request rebuilds or mutates the artifact.

** P3: make construction externally sorted and resource-owned

Use the already-admitted inventory and owner bytes exactly once.  Extraction
workers emit =(gram, owner-id, masks)= records into a bounded arena.  Full
arenas sort and spill; final construction k-way merges directly into the mmap
artifact.  Resource selection comes from Runtime Server's existing CPU and
memory supervisor and is included in the build receipt.

The batch contract must bound:

- file count;
- owned input bytes;
- mapped input bytes;
- extracted posting arena bytes;
- spill count and merge fan-in;
- deadline/cancellation checks.

No product constant such as 64 MiB is accepted solely because tgrep uses it;
ASP calibrates within Host-authorized bounds and binds the decision to engine,
capacity, and workload identity.

** P4: reuse immutable shards, not a query-visible uncommitted overlay

RFC 10.05 already requires content-addressed shard reuse.  Implement the byte
attachment in the same model:

#+begin_src text
previous generation immutable byte shards
  + added/changed owner posting shards
  - retired owners
  -> validated candidate artifact
  -> equivalence checks
  -> atomic attachment publication for exact contentGenerationDigest
#+end_src

An in-memory delta may be used while constructing the candidate generation, but
it is not query-visible until generation identity and complete coverage are
committed.  This preserves ASP's stronger absence and provenance guarantees.

** P5: add safe pre-verification masks only after equivalence

Positional and next-byte masks are worthwhile when candidate verification bytes
remain material after P2/P3.  They are optional pruning evidence, never match
evidence.  Differential tests must prove that every exact matcher hit remains
inside the candidate set across fixed strings, HIR concatenation/alternation/
repetition/classes, repeated grams, ASCII and Unicode case modes, word/line
anchors, and every admitted V1 native rg option.  Candidate false positives are
allowed; candidate false negatives are not.

** P6: remove fixed client overhead from the dominant path

tgrep's local run showed server work below 1ms for selective warm queries while
fresh client wall time averaged about 10ms.  ASP should measure and then reduce:

- CLI startup and configuration resolution;
- Runtime endpoint discovery/admission checks already proven by a live lease;
- repeated ClientFrame encoding/decoding;
- owner-path/string cloning before result limits are applied;
- rendering work for fields the requested view does not consume.

The solution remains the existing Runtime service and typed ClientFrame, not a
benchmark-only socket or persistent CLI process.

* What not to copy

- Do not copy tgrep's TCP JSON-RPC protocol; ASP already has a typed Runtime
  transport and stronger request identity.
- Do not let a file watcher define freshness.  Watch events may propose a new
  generation, but Merkle/content admission proves it.
- Do not serve an on-disk index whose age is merely documented.  ASP requests
  bind the exact generation or fail typed.
- Do not scan the filesystem when the byte attachment is absent or a query is
  unsupported.  Preserve =query-not-ready= and the declared next action.
- Do not replace either GREP or Tantivy with the other.  GREP owns byte/regex
  lexical anchors; Tantivy owns tokenized ranked lexical recall; V1 fuses them.
- Do not broaden the public grammar to tgrep/ripgrep compatibility while doing
  storage work.  Query semantics and physical representation are separate
  changes.
- Do not depend on =tgrep-core= as an authority: its matcher is private to the
  CLI, its walker/index publication duplicates ASP ownership, and the Unicode
  counterexample disproves full rg parity.
- Do not fork the full rg CLI.  If exact matching needs ripgrep code, consume a
  toolchain-compatible published library boundary after differential admission;
  directory walking, ignore discovery, printing, and process dispatch remain
  outside the resident V1 executor.

* Acceptance matrix

** Resident Search V1 MVP: one product boundary

The deliverable is a usable vertical SearchLoop, not a collection of decoder,
proof, or matcher milestones. One admitted immutable CompleteGeneration must
support Scheme Search composition, in-process lexical acquisition, native
structural grounding, optional Relation evaluation, and exact Query projection.
The same generation identity must survive durable reopen. No runtime rg binary,
second workspace walker, client-owned index, or public version upgrade is
introduced. Unsupported rg semantics fail explicitly rather than silently
changing the matched set.

The MVP has one acceptance decision and the following mandatory gates:

| Gate | Required product evidence | Insufficient evidence |
| Source identity | Tested source/build and active Runtime artifact are attributable | Installed older binary happens to answer |
| Correctness | Admitted regex/flags agree with reference; no false-negative candidate plan; filter/limit ordering and Unicode covered | Empty results or hand-authored receipts |
| Lifecycle | Real generation publication and durable reopen preserve owners, selectors and relations | Server health alone |
| Vertical route | Public Scheme search yields parser-owned selectors, exact Query consumes them, optional graph stays structurally scoped | Calling only the GREP kernel |
| Resource safety | Bounded CPU admission, decoded work, bytes read, memory ownership and incomplete coverage are explicit | Tokio use or mmap use alone |
| Performance | Same-corpus cold and warm p50/p95/p99, build/reopen cost and concurrent behavior, with work counters | A selective microbenchmark or a Lean arithmetic example |

Full Search, Runtime Server, Client DB and Lean suites are supporting gates.
A zero-test filtered invocation is NOT_EVALUATED. A failed broad suite remains
failed until fixed or independently demonstrated to be outside this change;
focused passes cannot replace it. Missing real-route publication, identity,
projection, parity, or performance evidence means MVP NOT_COMPLETE.

The first MVP does not require external-sort construction, incremental shards,
positional masks, a tgrep-core dependency, or a new protocol. Those mechanisms
are subsequent optimizations unless measured MVP resource admission requires
them. Public native Scheme and Tree-sitter Query remain the source language;
the acceptance tooling is not a second query API.

Implementation and verification proceed as one continuous delivery:
contract reconciliation -> lexical semantics and unified candidate execution ->
generation publication/reopen -> real Search/Query route -> resource and
performance qualification -> single acceptance report. Intermediate test
counts are progress only, not separate MVP deliveries.

** Correctness

- byte-for-byte differential equivalence with the current reference backend;
- no false absence under posting/mask false positives;
- corrupt/truncated/identity-mismatched artifacts fail before publication;
- one request resolves candidates, owner identities, and bytes from one leased
  generation;
- dirty changes cannot appear until a new generation is admitted;
- concurrent publication cannot mix owner IDs across generations.

** Performance

Use at least 4,096 admitted owners, 32 cold build samples, 512 warm query
samples, and a 32-query burst, separated into selective, medium, high-hit,
repeated-gram, and no-hit cohorts.  Report p50/p95/p99/max plus:

- owners, source bytes, unique grams, posting entries, and artifact bytes;
- build throughput and peak private/anonymous bytes;
- spill segments and merge fan-in;
- raw candidates, verified owners, and verified bytes per query;
- transport and render time separate from server execution;
- zero query-time filesystem/provider/process work.

Initial hypotheses to test, not acceptance claims:

- warm selective byte-candidate lookup p99 below 1ms at 4,096 owners;
- byte-coverage retained heap at least 70% below the former heap map on a
  large generation;
- build peak private bytes bounded by the admitted arena plus owner metadata,
  rather than total posting count;
- delta build work proportional to changed/retired owners and affected shards;
- no more than 5% regression for high-hit queries where exact verification and
  output dominate.

** Product outcome

*** Org / Lean / Rust refinement boundary

Verified source-build recovery reuses existing durable canonical and Source
Index records only after a fresh complete snapshot agrees in source root,
provider/scope digest, owner membership and ProjectResolution.  The stored
execution binding must also match the current Runtime bundle, schema bundle
and provider closure.  Reconstructed import bytes are the current same-pass
bytes and must validate against the persisted canonical import digest.  Missing
or stale products cause ordinary construction; corrupt or cross-generation
durable records fail closed.  No V1 public field or schema version is added.
This recovery eliminates provider re-projection for unchanged workspaces, not
snapshot I/O, durable record decoding or publication validation.

= Canonical assembly work model
For owner bytes $b$ and selector count $s$, count only bytes hashed:
$ H_("old") = b (s + 1), quad H_("new") = b $
$ H_("old") = H_("new") + b s $
These equations exclude parsing, allocation, transport, validation and storage.
They imply no numerical wall-clock speedup.
Verified recovery still pays snapshot, durable decoding and validation costs:
$ T_("restore") = T_("snapshot") + T_("decode") + T_("validate") + T_("publish") $
It removes provider projection only when all required identities match.
Reuse requires the cached digest to be computed from the same immutable bytes.
Durable reuse additionally requires current content, execution and scope
identity; request-coalescing identity alone is insufficient.
First-computation observation and ready resident read have distinct budgets:
$ B_("ready") = 1 "ms", quad T_("first") = T_("generation wait") + T_("compute wait") + T_("return") $
The temporary 60-second observation deadline bounds diagnosis, not acceptance.
It is absolute from request admission, never renewed by a notification.
For an empty-cache workspace, exact source acquisition has a byte-work lower
bound: $ W_("snapshot") >= B_("source") $.  Therefore no wall-clock bound below
one millisecond is valid for arbitrary repository size.  The architecture
instead removes unrelated work from the first-Search critical path:
$ W_("first Search") = W_("snapshot") + W_("Search Core") + W_("exact verify") + W_("candidate parser") + W_("requested refine") $
$ W_("full parser") + W_("durability") + W_("global graph") in.not W_("first Search") $
For a candidate parser artifact of size $c$ in a workspace of size $w$:
$ W_("resident semantic publish") = c $
$ W_("canonical rewrite") = c + w $
The first form is required on the Search path; the second is forbidden there.
This also forbids a subtler implementation error: cloning every canonical
owner into an in-memory object called an overlay.  Let $b$ be copied immutable
base-owner bytes and $d$ be the new semantic delta bytes:
$ W_("resident overlay publish") = b + d, quad b = 0 $
The Runtime lease owns the immutable base.  The overlay stores only changed
owners, tombstones, Relation deltas and selector deltas; base owners and base
relations are read through the lease.  The workspace snapshot is shared by
reference until a path delta derives a new snapshot.  Thus no canonical file
rewrite and no in-memory full-base copy may hide inside candidate publication.
The same boundary applies to the Search data plane.  Let $p$ be its
workspace-proportional construction work, $a$ one immutable-reference retain,
and $h$ the number of resident read handles:
$ W_("plane admission") = p, quad W_("handle open") = h a $
$ W_("request workspace rebuild") = 0 $
The forbidden design pays $h p$ by validating the generation and rebuilding
Merkle, manifest, corpus and indexes for each handle.  Admission binds and
constructs the plane once on a bounded blocking lane; every resident handle
then shares that exact generation-bound plane by reference.  These are logical
work terms; Rust tests establish shared identity and live timings.
Internally encoded byte coverage carries its already constructed directory
layout into the admitted plane.  It does not hash and decode every posting a
second time as though its own private encoder were an untrusted wire source.
Externally supplied bytes and mmap restore still cross one complete digest,
directory and posting validation boundary:
$ V_("internal encoded") = 0, quad V_("external restore") = 1 $
Let $r_s$ and $r_a$ be generation-resident source and auxiliary reads, while
$f_s$ and $f_a$ are request-time filesystem reads. Candidate projection keeps
the admitted bytes distinct from searchable ownership:
$ W_("projection input") = r_s + r_a, quad f_s = 0, quad f_a = 0 $
$ N_("search owners") = N_("searchable source"), quad N_("auxiliary") in.not N_("search owners") $
Packed integer grams use a fixed-key integer hasher during construction and are
sorted before encoding, so construction speed cannot change V1 deterministic
artifact bytes.  Query decoding continues to consume the sorted V1 format.
For $n$ candidate owners in $g$ provider groups, fixed RPC/lifecycle setup $s$
and per-owner payload work $p$:
$ W_("serial owner RPC") = n s + n p $
$ W_("provider-group batch") = g s + n p, quad g <= n $
The grouping removes repeated setup; it does not claim that parser payload work
is constant or that byte-budget frame splitting is free.
Process-cold recovery targets a small verified manifest; resident lookup keeps
the 1ms budget.  These equations count logical work, not elapsed time.

The user approved measuring first computation separately before setting its
production latency limit. Runtime starts each resident request with the strict
1ms budget. Only a generation miss or uncached Search/Query computation marks
that request as first-computation, including joiners of existing work. A cache
hit never makes that transition. For diagnosis the first-computation absolute
deadline is 60 seconds from dispatch admission, not 60 seconds per stage.
Timeout is failure, not a usable result. Ready generation failures are terminal;
the request does not silently resubmit a failed build. ClientFrame dispatch
timings exclude client startup and network transport; report these separately.
No V1 wire fields or schema versions change for this internal budget policy.

Cold acceptance distinguishes an empty-artifact full build, a process-cold
reopen of admitted durable artifacts, and a changed-owner generation.  A
reopen must not be reported as an empty-artifact build.  Sub-millisecond
lookup is a hypothesis for bounded resident work, not a promise to read,
parse and durably publish an unbounded repository in that time.

The existing =snapshotMerkleMaterializationMicros= interval includes source
snapshot collection, provider projection, and canonical assembly.  Diagnosis
must split these stages before attributing that interval to hashing.  Provider
readiness belongs once per participating provider per build, not once per
projection batch.  Per-stage internal timing does not change the V1 public
schema or weaken generation admission.  A =materializing= response is not a
usable result and must not count as successful first-result latency.

The pointer-only =restored_generation_covers_demand= still rejects restored
coverage without source verification. The source builder now owns verified
reuse after current snapshot acquisition. The =blake3-runtime-admission-v1= candidate digest
identifies a coalescing lane, not source bytes. Ordinary RestoreOrBuild skips the
pointer-only restore attempt; it would otherwise load an unverified generation
that is always discarded. A lightweight durable source-identity probe rejects
changed content before decoding the full canonical materialization. The digest
identifies a coalescing lane, not source bytes; persisting and comparing it
cannot establish freshness.  Recovery optimization must bind the durable
generation to content identity, provider execution identity and scope, and
validate current-worktree changes before admission.  A lost watcher interval,
changed provider, changed source, deletion or corrupt artifact must not be
treated as unchanged.  Without continuity evidence, source revalidation may
still be required, but unchanged content must not require repeating parser
projection merely because the process restarted. The new path still performs
snapshot I/O and durable validation. Zero-I/O verified reopen and changed-owner
parser reuse remain separate requirements.

Canonical import must hash each immutable owner once, then compare every
selector's source digest with that computed owner digest.  Rehashing the whole
owner for each selector costs =sum(ownerBytes * selectorCount)= instead of
=sum(ownerBytes) + totalSelectorCount=.  Reuse is valid only within this
same-byte assembly; it must not trust an externally supplied digest or skip
per-selector range and payload checks.

Canonical assembly is synchronous CPU work and must execute on a blocking
worker, not inside a Tokio async worker poll.  Moving it does not reduce its
work count or prove faster cold completion; it isolates unrelated request
latency.  The worker owns the same captured bytes and candidate identity.

The replacement invariant is =SearchCoreReady before DurableReady=.  Segment
and Turso failures remain terminal for restart durability, but they do not turn
an admitted process-resident generation back into =query-not-ready=.  The
durable format must become a small manifest over content-addressed components;
rewriting three complete copies per generation is forbidden.  Unchanged owner
bytes reuse their source and parser artifacts, while a new generation writes
only its proof/manifest and changed components.

The parser lookup order is part of that invariant: artifact validation precedes
provider readiness.  Starting a language process and then discovering a cache
hit is an architectural miss because it destroys process-cold recovery.  On a
typed miss the provider is started once and the same owner request is completed;
there is no polling loop or second public Search invocation.

The parsed owner is published only into the resident semantic overlay.  Calling
the complete-generation publisher from this path is forbidden: it would turn a
candidate-sized update back into a full-workspace encode, fsync and reopen
barrier.  The durable parser artifact is the restart authority, so a later
process revalidates and reattaches it without provider startup.

Candidate projection must consume the immutable source and auxiliary bytes
already admitted by the resident generation.  Sending only owner paths and
then reopening source files or ancestor configuration files on the request
path is forbidden: it races the admitted content identity, repeats acquisition
work, and makes parser latency depend on filesystem state after admission.
Auxiliary inputs are a distinct resident content class: they are bound by the
same workspace snapshot and persisted generation, but are not searchable source
owners and do not acquire a language-provider authority merely because they
influence parser identity.  Runtime projection selects the applicable
generation-bound auxiliary owners by canonical ancestor path and registered
=configFiles=, constructs the candidate Merkle tree from those resident bytes,
and reports zero query-time source and auxiliary filesystem reads.  A missing,
changed, or corrupt resident auxiliary input is an identity failure; Runtime
must not fall back to the live filesystem.

A focused 2026-09-12 resident-input counterexample removed both the source file
and its =Cargo.toml= from the worktree before projection.  The request reached
the typed parser-artifact miss from the admitted bytes, reporting
=sourceFilesystemReadCount=0=, =auxiliaryFilesystemReadCount=0=, 21 resident
source bytes, 28 resident auxiliary bytes, and 485us input preparation.  A
second case rejected corrupt auxiliary bytes before cache/provider execution.
This proves the data-plane boundary and a sub-millisecond one-owner preparation
sample; it is not yet a distribution for provider parsing or complete first
Search latency.

Project Topology is not a generation-Ready attachment in the minimal-core
architecture.  Search builds a request-local topology from materialized fused
candidates and, when graph semantics require it, a bounded one-hop Relation
neighbourhood.  This prevents both full-repository parser work and a stale
first-query topology from becoming permanent generation state.

The generation builder owns only the lexical attachment.  A Tantivy clause
waits for that lexical terminal and never for Graph.  Graph cardinality, budget
and construction are derived from the request-local semantic owner cut after
retrieval, so a global Graph build can neither contend with nor delay first
Search.

Performance work is complete only if the real =search playbook= route reduces
end-to-end p95/p99 or expands the safely admitted corpus under the same Host
budget.  A faster microbenchmark with unchanged or slower ClientFrame-to-result
latency is diagnostic evidence, not closure.

* Dependency verdict

** Decoder audit constraint (V1 unchanged)

Reopening validates delta postings with constant auxiliary decoder state, not
one allocated owner vector per posting. Declared counts must be bounded by
both encoded bytes and owner cardinality before allocation. Query intersections
retain only the smallest candidate vector and stream subsequent postings;
decoding may stop once all candidates have been decided. Sequential delta
encoding does not support constant-time membership probes: worst-case decoded
work remains the sum of traversed posting lengths. Logical work reductions
are not wall-clock speedup claims; fixed request costs must remain in the model.
The directory stores each three-byte gram in a four-byte field and occupies
32 bytes per entry. No eightfold key-memory or 100-fold performance theorem
is justified by those field sizes alone.

A Tantivy result truncated before lexical intersection is not a complete
candidate authority. The current Tantivy-first execution must reject that
scope as =query-not-ready= before exact GREP or absence publication. This
conservative admission can reject queries previously answerable by filtering
before top-k; recovering that capacity requires scoped retrieval or pagination,
not silently treating truncated recall as a complete intersection.

The two proposed choices are not equivalent responsibilities:

1. =tgrep-core= supplies indexed candidate selection but not the full CLI's
   exact matcher.  Direct dependency would also import a second index format,
   filesystem builder, walker, and publication model.  Verdict: do not import
   it wholesale; reproduce only the admitted physical techniques.
2. ripgrep's published library crates supply exact regex/search semantics, but
   the full rg binary is not a library backend and its index is explicitly
   unstable.  The current upstream repository also requires Rust 1.96 while
   ASP is fixed at 1.95.  Verdict: do not fork or raise MSRV.  First preserve
   the current resident exact matcher; separately qualify the newest compatible
   =grep-regex=/=grep-searcher= release before adding a dependency.

The selected architecture is therefore an ASP-owned trigram candidate artifact
plus an independently qualified in-process exact matcher.  This retains the
role of GREP while eliminating query-time rg processes and duplicate lifecycle
authority.

* Verdict

ASP does not need tgrep's product architecture, but it does need GREP's role.
The V1 =rg= axis remains the coarse lexical-anchor stage that makes parser and
Relation/Query work selective.  What may disappear is the external rg process,
not the rg semantics or its position in the SearchLoop.

ASP does need tgrep's physical-index discipline.  The resident implementation
now publishes a compact mmap artifact, reopens postings and source bytes without
workspace-sized heap reconstruction, evaluates regex-HIR AND/OR plans rarest
first, and runs the lexical phase on a bounded Tokio CPU lane.  External posting
construction, bounded OR unions, broader rg differential semantics, and
independently measured end-to-end request cost remain the next performance
closure points.
